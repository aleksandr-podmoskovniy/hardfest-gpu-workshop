# Почему LLM отвечает медленно?

Памятка по мастер-классу. Это объяснение механизмов, не показания живого стенда.

## Долго нет первых слов

Запрос может ждать очереди. После этого начинается обработка входа — **prefill**.
Сначала сопоставляем Waiting, время до первого токена (**TTFT**) и длину входа.
Одного графика загрузки GPU для диагноза мало.

Вопрос: «Десять человек отправили разные длинные документы. Почему
одновременно работать могут только два запроса, хотя лимит сессий равен десяти?»

## Память заполнена — нужно покупать карту?

На GPU находятся веса, рабочие буферы и **KV-кеш** — сохранённые ключи и значения
для уже обработанных токенов. Веса у запросов к одному экземпляру общие,
а независимые истории требуют отдельного состояния.

Для одинаковых слоёв с полным attention размер K/V-данных в байтах:

```text
KV = 2 × b × L × Hkv × D × S × N
```

`b` — байт на элемент; `L` — слоёв с собственными K/V; `Hkv` — KV-голов; `D` — размер головы;
`S` — токенов в истории, включая уже созданный ответ; `N` — независимых историй.
Двойка учитывает и K, и V. Для разных типов слоёв их вклады считают отдельно.
Веса, буферы и накладные расходы сюда не входят.

Вопрос: «Оцени KV для десяти окон 256K. Сначала перечисли недостающие параметры
модели; не подставляй параметры Gemma в Qwen».
Полный расчёт — в [бюджете памяти](../docs/MEMORY_BUDGET.md).

## Повтор документа начался быстрее

**Prefix caching** повторно использует KV совпадающего начала. Это не кеш
готовых ответов: вопрос в конце может быть другим. Он сокращает повторную
обработку входа, но не устраняет генерацию нового ответа.
См. [объяснение vLLM](https://docs.vllm.ai/en/v0.31.0/features/automatic_prefix_caching/).

**RAM-offload** сохраняет блоки вне GPU для последующего возврата.
Быстрый повтор ещё не доказывает offload: блоки могли остаться на GPU.
Нужны данные о чтении из RAM и возврате вытесненного префикса.

**FP8 KV** уменьшает размер элемента кеша: вместо двух байт BF16 — один байт.
Это не RAM-offload: кеш может оставаться на GPU, а веса модели не меняются.
Движок может заранее занять отведённую память под пул блоков. Поэтому после
FP8 график занятой VRAM может остаться почти прежним, но в пул поместится больше
токенов. Проверяются ёмкость пула, доля занятых блоков, очередь и вытеснения
при одинаковых длинах и числе запросов. Перенос в RAM для FP8 не обязателен.

Вопрос: «После включения FP8 KV занятость VRAM почти не изменилась.
Почему это не доказывает, что настройка бесполезна?»

## Первые слова появились, но продолжение идёт медленно

Это уже **decode**, создание новых токенов. Здесь важны время следующего
токена и завершённость ответа, а не только TTFT.
**Speculative decoding** предлагает продолжение вспомогательным механизмом,
а основная модель его проверяет. Процент принятых токенов сам по себе
не доказывает ускорение: предложение и проверка тоже стоят времени.

Вопрос: «Какие измерения нужны, чтобы понять, окупается ли speculative decoding?
Почему одного acceptance rate недостаточно?»
