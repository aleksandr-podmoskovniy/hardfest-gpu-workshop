# Инференс без простоя GPU: чиним LLM-сервис руками и делим карту на живом кластере

Александр Подмосковный, Флант / Deckhouse Platform

**Почему LLM отвечает медленно — и что именно стоит менять?** Проверим это
на работающей Gemma: сначала память, затем обработку запросов. После ручной
настройки передадим запуск AI Inference, разместим три сервиса на одной A30
и завершим моделью Qwen, которой нужны две H100.

> [!TIP]
> Откройте **[ai.ap4y.ru](https://ai.ap4y.ru)**, зарегистрируйтесь и дождитесь
> одобрения. Стенд подготовлен, **`Gemma A — Base` уже запущена**.
> Личный ключ, доступные модели и лимиты выдаются автоматически.
> Пока появляется доступ, посмотрите схему ниже.

| По ходу работы | Что проверяем |
| --- | --- |
| **Gemma A → B Cache → B Tune** | Где уходит время; что дают кеширование и оптимизация вычислений |
| **Ручной запуск → AI Inference** | Как воспроизвести ту же конфигурацию автоматически |
| **Одна A30 → три сервиса** | Как разделить GPU между поиском по документам и распознаванием речи |
| **Две H100 → Qwen TP2** | Как запустить модель, не помещающуюся на одну карту |

**Вопросы можно задавать на любом этапе.** Перед опытом сначала выберите свой
прогноз, затем проверьте его по ответу и графикам. Разбор можно раскрыть после
проверки. Аккаунт, чат и базы знаний сохранятся при переходах между моделями.

Для двух RTX 5060 Ti есть [самостоятельный сценарий RTX](RTX5060.md).
У него те же исследуемые механизмы, но свои модели, расчёты памяти и параметры.

## Стенд и подключение

![Два кластера: Open WebUI и A30, ai-mcp-gateway и две H100](assets/01-topology.svg)

| Место | Что здесь работает |
| --- | --- |
| Управляющий кластер | Argo CD читает частный GitLab k8s-config |
| Кластер с A30 | Open WebUI, эмбеддер и реранкер в одной MIG-партиции через MPS; Whisper во второй |
| Кластер с двумя H100 | Ручные Gemma, затем сервисы AI Inference; ai-mcp-gateway на базе Bifrost |

**ai-mcp-gateway — единая точка входа к моделям**, здесь на базе Bifrost.
Он проверяет личный ключ, выбирает маршрут и учитывает запрос; ответ генерирует
vLLM на GPU. Argo CD в обработке сообщения не участвует: он доставляет
конфигурацию сервисов из Git.

<details>
<summary>MIG, MPS, управляющий кластер — что на схеме</summary>

**MIG** — аппаратные разделы поддерживаемой GPU; **MPS** — совместное выполнение
нескольких процессов внутри GPU или MIG-раздела. На A30 применим оба механизма,
когда дойдём до небольших моделей.

**Управляющий кластер** запускает Argo CD; он может совпадать с кластером A30.
Маршрутизация и TLS между чатом, шлюзом и API моделей подготовлены заранее.
Доступ к модели не даёт доступа к Kubernetes MCP — инструментам управления
кластером, у которых отдельная авторизация.

</details>

<a id="chat"></a>
### Один чат на всех этапах

| Название в Open WebUI | Назначение |
| --- | --- |
| `Gemma A — Base` | Ручной запуск без исследуемых оптимизаций |
| `Gemma B — Tune` | Ручная B: сначала Cache, затем полный Tune |
| `Gemma A — DP` | Gemma, созданная через AI Inference |
| `Qwen — TP2` | Финальный сервис на двух H100 |

`DP` здесь — метка платформенного запуска, **не Data Parallel**.
Каждая модель подключается отдельным маршрутом Bifrost: без балансировки A↔B,
fallback между ними и кэша готовых ответов.

**Virtual Key (VK)** — персональный ключ шлюза: разрешённые модели, лимиты
и привязка запросов к участнику. Он появляется после одобрения аккаунта;
копировать общий ключ в браузер не нужно.

<details>
<summary>Демонстрационный бюджет и границы доступа</summary>

Бюджет — $500 на 24 часа; тариф чата — $10 за миллион входных и $20 за миллион

Администратор входит по OIDC и использует отдельное MCP-подключение.

Проверка выдачи, запретов, расхода и отзыва описана в
[подключении чата](docs/CHAT_AND_ACCESS.md). Участникам доступны базы знаний
и голос, но не Kubernetes MCP. Фоновая индексация и голосовой API требуют
отдельного учёта: личный VK чата не персонализирует их автоматически.

</details>

## 1. Пробуем уже работающую Gemma A

После одобрения аккаунта откройте в чате `Gemma A — Base` и задайте вопрос:
«Почему длинная история чата занимает память GPU, если веса модели не меняются?»
Затем попробуйте свой вопрос или попросите развёрнутый ответ. Обратите внимание
на **две разные задержки: ожидание начала и темп появления текста**.

### Как Base уже попала в чат

Пока идут ответы, откроем Application `hardfest-gemma-a` в Argo CD.
Он уже синхронизирован: посмотрим применённый commit, [профиль A](values/gemma-a.yaml),
Deployment и GPU claim. Это ручная конфигурация vLLM через Helm, **ещё не
InferenceService**. Повторно запускать или перезапускать A сейчас не нужно.

![GitLab хранит Helm values, Argo CD применяет выбранный коммит в целевой кластер](assets/12-gitops.svg)

Путь от исходника до ответа: Git хранит параметры, Argo применяет Helm chart,
**DRA (Dynamic Resource Allocation)** выделяет одну H100 через заявку
**ResourceClaim**, vLLM читает доставленные ai-models веса.
В консоли отдельно видна модель в каталоге, а в WebUI — её чат-маршрут.
Запись в каталоге, запущенный процесс и доступ пользователя — три разных звена.

![Честное сравнение: одинаковые веса и запросы, по одной H100 и общий предел 16K](assets/04-ab.svg)

**Base — исходная точка сравнения.** У неё явно выключены prefix cache,
chunked prefill, CUDA graphs, KV-offload и speculative decoding: каждый
механизм разберём ниже. Это одна версия vLLM 0.31, не сравнение разных движков.
Окно A — **16 384 токена**: без chunked prefill нужен большой рабочий буфер.

### От ответа в чате к графикам

Перейдём в **AI Inference / Service performance**, выберем namespace
`hardfest-demo` и Service `hf-gemma-a`. На интервале наших вопросов видны
новые запросы и выходные токены. Название дашборда не ограничивает его

| Что заметили в чате | На что смотрим |
| --- | --- |
| Ответ ещё не начался | Очередь, активные запросы и **TTFT** — время до первого токена |
| Текст идёт медленно | **ITL** — интервалы между токенами; **TPOT** — среднее время на токен после первого |
| Несколько людей ждут одновременно | Running / waiting, ошибки и throughput |
| GPU занята, но ответы не ускоряются | Вычислительная загрузка, видеопамять и KV-пул |

### Опыт 1. Медленный старт или медленный ответ?

1. **Предскажите:** что сильнее изменит длинная история — TTFT или темп следующих токенов?
2. **Попробуйте:** сравните короткий вопрос с длинным входом в контрольной серии ниже.
3. **Проверьте:** **TTFT, очередь и TPOT** на одном интервале. По суммарным tokens/s
   нельзя судить о скорости одного ответа.

<details>
<summary>Разбор: три причины ощущения «тормозит»</summary>

Запрос может ждать очереди, долго обрабатывать вход или медленно генерировать
продолжение. Длинный вход увеличивает работу prefill, но под нагрузкой добавляется
очередь. Какой этап преобладает сейчас, определяем по измерению.

</details>

Теперь ненадолго отделим свободные вопросы от контрольного замера:
8192 входных и 2048 выходных токенов, 8 запросов, concurrency 4.
Пока выполняется серия, пользовательские запросы к A приостановлены.
Запишем фактические длины, длительность и ошибки.
Позже ровно эту нагрузку повторим на B. Короткий чат показывает ощущение
пользователя, фиксированная серия позволяет сравнить конфигурации.

<details>
<summary>Команда одинаковой нагрузки для A и обеих B</summary>

Терминал открыт в частном `k8s-config`; контексты заданы при подготовке.
Выберите сервис и новое имя серии, чтобы не затереть предыдущий результат:

```bash
export SLOT=a SERIES=a-base-1
# B1: export SLOT=b SERIES=b-cache-1
# B2: export SLOT=b SERIES=b-spec-1
export TOKENIZER_PATH=/data/modelcache/models/gemma-4-31b
mkdir -p "results/hardfest/$SERIES"
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec "deployment/hf-gemma-$SLOT" -- \
  vllm bench serve --backend vllm \
    --base-url "http://hf-gemma-$SLOT.hardfest-demo.svc.cluster.local:8000" \
    --endpoint /v1/completions --model gemma-4-31b --tokenizer "$TOKENIZER_PATH" \
    --dataset-name random --seed 42 \
    --random-input-len 8192 --random-output-len 2048 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 4 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/hardfest/$SERIES/bench.txt"
```

В JSON проверяем все четыре поля, не только код завершения CLI:

| Поле | Значение |
| --- | --- |
| `failed` | `0` |
| `completed` | `8` |
| `total_input_tokens` | `65536` |
| `total_output_tokens` | `16384` |

Повтор seed прогревает серверный prefix cache. Первый проход и повтор
сохраняйте отдельно; не называйте их одинаково холодными.
Клиент внутри Pod тоже потребляет CPU: это короткая демонстрационная проверка.
Для итоговых цифр нужен один отдельный CPU-клиент и несколько повторов.

</details>

Если график пуст, проверьте выбранный сервис и интервал, а не считайте это нулём.
Теперь разберём, из каких частей состоит увиденное ожидание.

<a id="latency"></a>
## 2. Разбираем время ответа

![Путь запроса: очередь, prefill и последовательная генерация токенов](assets/02-latency.svg)

**У каждого этапа своя причина задержки и свой способ оптимизации.**

| Этап | Простое объяснение | Что разберём |
| --- | --- | --- |
| **Queue** | Запрос ждёт, пока движок возьмёт его в работу | Вместимость и управление нагрузкой |
| **Prefill** | Модель обрабатывает весь вход и подготавливает состояние истории | Prefix caching и chunked prefill |
| **Decode** | Модель генерирует следующие токены шаг за шагом | Speculative decoding |

**Токен** — часть текста, не обязательно слово. Если модель рассуждает,
reasoning-токены тоже генерируются на decode и занимают место в контексте.
Это не отдельный универсальный этап GPU: сначала могут появляться токены
рассуждения, а уже потом видимый финальный ответ.

`Tответа ≈ Tочереди + Tprefill + Tdecode + Tпрочее`.
В последнее слагаемое входят сеть, шлюз, токенизация и передача потока.
**TTFT** измеряет время до первого токена на выбранной границе измерения;
первые слова финального ответа в WebUI могут появиться позже.
**Output tokens/s** всего сервиса — суммарная производительность всех его
запросов, не темп одного ответа. **p95** — порог, ниже которого находятся 95%
измерений; несколько ручных вопросов не дают устойчивой оценки этой величины.

На одном временном интервале сравним три ситуации:

| Что отправляем | Что ищем на графиках |
| --- | --- |
| Короткий вопрос без очереди | Базовую задержку и темп выдачи текста |
| Новый длинный документ, короткий ответ | Время prefill и TTFT |
| Несколько длинных ответов одновременно | Running / waiting, ITL, throughput и ошибки |

### GPU занята — но чем?

**Память и вычисления — разные ограничения.**
Prefill часто хорошо загружает вычислительные блоки; decode при малом batch
может упираться в чтение весов из памяти. Заполненная видеопамять тоже не
доказывает нехватку: движок заранее резервирует KV-пул.
Поэтому рядом смотрим вычисления, память, очередь и время ответа.
[Как измерять и не ошибиться с p95](docs/MEASUREMENTS.md).

Раз начальный длинный запрос дорог, выясним, какое состояние он оставляет
в памяти и можно ли не вычислять его заново.

<a id="memory"></a>
## 3. Считаем память от одного токена до восьми историй

| Память GPU занята | От чего зависит объём |
| --- | --- |
| **Весами модели** | Модель и точность хранения; веса общие для запросов и не растут от длины разговора |
| **Рабочими буферами** | Prefill, активации и настройки выполнения, в том числе CUDA graphs |
| **KV cache** | Архитектура, длины и число живых историй, точность KV |

**KV-кеш — сохранённое состояние истории, не готовый ответ.** Разберём,
из чего он состоит, и посчитаем объём от одного токена до нескольких сессий.

![Attention сохраняет ключи и значения предыдущих токенов для продолжения генерации](assets/13-attention.svg)

### Откуда берётся формула

Модель обработала `t1, t2, t3` и сгенерировала `t4`. Следующий шаг уже продолжает
`t1, t2, t3, t4`. На каждом attention-слое текущий **query Q** сравнивается
с **keys K**, а полученные коэффициенты задают взвешенную сумму **values V**.
Q нужен для текущего вычисления; K/V сохраняем для следующих токенов.
Без этого повторно рассчитывали бы состояние уже известного текста.

<details>
<summary>Query, Key и Value — простое пояснение</summary>

**Query** — вектор текущего токена: что ищем в истории. Его сопоставляют
с векторами **Key** предыдущих токенов, затем смешивают их **Value**
с полученными весами. **Attention** — этот механизм выбора и смешивания.
Это операции с числами, а не буквальная база вопросов и ответов.

</details>

Число query-голов не обязательно равно числу KV-голов. В **Grouped-Query
Attention (GQA)** несколько голов Q используют общий набор K/V. Поэтому для
объёма кеша берём `num_key_value_heads`, а не `num_attention_heads`.
Это архитектура модели, не переиспользование префикса между людьми.

![Вывод формулы: от K и V одного токена в одном слое до N независимых историй](assets/25-kv-derivation.svg)

У одного токена в одном слое два набора векторов: `2 × Hkv × D` элементов.
Умножаем на размер элемента `b`, число токенов `S`, число одинаковых слоёв `L`
и число независимых историй `N`. Получаем байты, не гигабайты.

```text
KV_bytes = 2 × L × Hkv × D × b × (S₁ + S₂ + … + Sₙ)
При одинаковой длине: KV_bytes = 2 × N × L × Hkv × D × S × b
```

| Обозначение | Что подставлять |
| --- | --- |
| `Hkv` | Количество **KV-голов**, не query-голов `num_attention_heads` |
| `D` | Размерность одной KV-головы; не угадываем её по размеру hidden state |
| `b` | Байты на элемент KV: BF16/FP16 — 2, FP8 — 1; точность весов задаётся отдельно |
| `S` | Токены входа **плюс** уже сгенерированные токены; для верхней оценки — их суммарный предел |
| `L` | Слои, хранящие собственные K/V |
| `N` | Число одновременно живущих независимых историй; при разных длинах складываем их расходы |

Эта первая формула предполагает full attention и одинаковые слои. У Gemma
архитектура сложнее: full-слои видят всю историю, sliding-слои — только своё окно.
Поэтому считаем два слагаемых. Общий префикс пока не разделяем между запросами —
его переиспользование проверим отдельным опытом.

### Подставляем Gemma 4 31B

В [закреплённом config.json](https://huggingface.co/google/gemma-4-31B-it/blob/842da3794eaa0b77d5f08bae87a17459d91ff475/config.json)
открываем `text_config`, а не конфигурацию vision-энкодера:

| Слои | Число | KV-голов | Размерность | Сколько токенов сохраняем |
| --- | ---: | ---: | ---: | --- |
| Full attention | 10 | 4 | 512 | `S` |
| Sliding attention | 50 | 16 | 256 | `min(S, 1024)` |

![Формула KV для Gemma учитывает global attention и ограниченное sliding window](assets/11-gemma-kv.svg)

Один токен одного **full-слоя** в BF16 занимает
`2 × 4 × 512 × 2 = 8192 байта = 8 KiB`.
Десять таких слоёв дают **80 KiB на токен истории**.
У одного sliding-слоя другая размерность и число голов:
`2 × 16 × 256 × 2 = 16 KiB`; 50 слоёв — **800 KiB на токен локального окна**.
Но это окно ограничено 1024 токенами: старая часть истории здесь не растёт.

Для одной истории:

```text
KV(S) = 2 × b × [10 × 4 × 512 × S + 50 × 16 × 256 × min(S, 1024)] байт
```

Считаем **одну историю 16K в BF16**, соответствующую пределу начального A/B:

1. Full: `2 × 2 × 10 × 4 × 512 × 16384` = **1,25 GiB**.
2. Sliding: `2 × 2 × 50 × 16 × 256 × 1024` = **0,78125 GiB**.
3. Всего: **2,03125 GiB**. Для четырёх независимых историй такой длины — **8,125 GiB**.

Проверка обычным `awk`; меняем `S`, `N` и `b`, не параметры архитектуры:

```bash
awk -v S=16384 -v N=4 -v b=2 'BEGIN {
  W = S < 1024 ? S : 1024
  full = 2*b*10*4*512*S / 1073741824
  local = 2*b*50*16*256*W / 1073741824
  printf "Full %.5f + sliding %.5f = %.5f GiB/history; %d histories = %.5f GiB\n", full, local, full+local, N, N*(full+local)
}'
```

### Опыт 2. Удвоили контекст — удвоили память?

1. **Предскажите:** KV у Gemma вырастет ровно вдвое или меньше? Изменит ли FP8 KV веса?
2. **Посчитайте:** замените `S=16384` на `S=32768`. Отдельно попробуйте `b=1`.
3. **Проверьте:** расчёт и **занятость KV-пула**, а не только общую память в `nvidia-smi`.

<details>
<summary>Разбор расчёта и точности KV</summary>

При 32K в BF16 получаем **2,5 + 0,78125 = 3,28125 GiB на историю**.
После 1024 токенов растёт только full-слагаемое, а не вся сумма.
При `b=1` полезный FP8 KV вдвое меньше; веса остаются прежними.

Флаг `attention_k_eq_v` не убирает множитель 2: выбранный vLLM хранит K и V
отдельно — после нормализации и RoPE это не одна копия.
[Реализация Gemma в vLLM 0.31](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/gemma4.py).

</details>

![Сравнение теоретического KV одной истории при 64K, 128K и 256K](assets/03-memory.svg)

### Длинный контекст — это вход вместе с генерацией

Возьмём окно 128K: `122 880 входных + 8192 сгенерированных = 131 072 токена`.
Во вход входят системный промпт, шаблон чата, документы и история.
В генерацию — и reasoning, и финальный текст. Если занять всё окно документом,
ответу не останется места, даже если в WebUI выставлен большой output limit.

Для Gemma 31B одна история 128K даёт:
`80 KiB × 131072 + 800 KiB × 1024 = 10,78125 GiB` в BF16.
Теперь сложим независимые истории, пока не учитывая общий префикс:

| Истории по 128K | KV в BF16 | KV в FP8 |
| --- | ---: | ---: |
| 1 | 10,78125 GiB | 5,390625 GiB |
| 4 | 43,125 GiB | 21,5625 GiB |
| 8 | 86,25 GiB | 43,125 GiB |

Ни одно число не включает веса, буферы или assistant.
Восемь подключённых пользователей не обязательно держат восемь полных окон
одновременно; но обещать восемь полных окон без такого расчёта тоже нельзя.

### Сколько места остаётся после весов

Оценка бюджета: `Kpool ≈ G × u − W − R`, где `G` — доступная память GPU,
`u` — доля памяти движка, `W` — фактическая память весов, `R` — прочие резервы.
Размер checkpoint на диске не подставляем вместо `W` без проверки загрузки.

Учебный пример, не характеристика наших H100: `G=96 GiB`, `u=0,90`,
`W=64 GiB`, `R=6 GiB`. Остаётся `96 × 0,90 − 64 − 6 = 16,4 GiB`.
Для посчитанной Gemma это теоретически `floor(16,4 / 10,78125) = 1` история
128K в BF16 или `floor(16,4 / 5,390625) = 3` в FP8.
Это верхняя оценка полезного KV: реальные блоки и резервы могут уменьшить её.
На своём запуске заменим учебные числа данными движка.

### Сверяем расчёт с движком

Почему формулы недостаточно? Движок хранит KV блоками, а история ссылается
на них через таблицу соответствий. Условно при блоке на 16 токенов история
из 35 токенов потребует три блока, последний заполнен частично.
Физически они не обязаны лежать рядом. Если два запроса имеют одинаковые первые
32 токена, prefix cache может переиспользовать два полных блока вместо их
повторного вычисления. Завершение запроса освобождает его активные ссылки;
блоки могут оставаться кешированными до вытеснения.

16 здесь — учебный размер, не настройка наших профилей. У гибридной модели
есть разные группы full/sliding attention, размер блока и правила выравнивания
нужно брать из конкретного runtime. Это связывает расчёт полезных байтов
со следующим опытом: возвращать из RAM будем блоки, а не готовые ответы.

Посчитали **полезные KV**, но vLLM выделяет пул блоков заранее. В нём есть свободные
блоки, округление и накладные расходы размещения разных типов attention. Prefill
требует рабочих буферов; длинный вход без chunking способен не поместиться, даже
если KV по формуле мал. Для assistant нужен ещё собственный бюджет.

После запуска A выпишите из логов размер GPU KV-пула и объявленную вместимость
в токенах. Затем отправьте один запрос, длинный запрос и четыре параллельных;
на дашборде сопоставьте занятость KV-пула, очередь и preemption. `nvidia-smi`
показывает всю занятую память, а не только KV этих четырёх историй.
[Команды проверки и разбор расхождения](docs/MEMORY_BUDGET.md#verify-kv).

**FP8 уменьшает байты, длина увеличивает full-KV, общий префикс убирает повторную
работу.** Теперь проверим последний механизм и добавим хранение блоков в RAM.

<a id="ram"></a>
## 4. Первая итерация: prefix cache и KV в RAM

**Не вычислять повторно и не потерять вычисленное — две разные задачи.**

| Механизм | Что делает |
| --- | --- |
| **Prefix caching** | Переиспользует KV одинакового начала запроса, а не готовый ответ |
| **KV RAM offload** | Сохраняет KV-блоки в RAM и возвращает их на GPU, когда они снова нужны |

![Повтор общего префикса позволяет переиспользовать уже рассчитанный KV](assets/14-prefix.svg)

Вернёмся к документу, по которому несколько человек задают разные вопросы.
Если документ и всё до него совпадают **в токенах**, их K/V можно вычислить один
раз. Это **Automatic Prefix Caching**: экономим повторный prefill, а не генерацию
нового ответа. Изменение системного промпта или начала документа нарушает совпадение.
[Как работает prefix caching](https://docs.vllm.ai/en/v0.31.0/features/automatic_prefix_caching/).

Но GPU-пул конечен. Пришли другие документы, блоки старого вытеснились —
повторный вопрос снова требует prefill. Сохраним копию KV в RAM, чтобы было
откуда восстановить эти блоки. Веса и активные вычисления остаются на GPU.

### Включаем B Cache

В первом профиле B, `values/gemma-b.yaml`, окно остаётся 16K,
chunked prefill и CUDA graphs выключены. Отличия от A — prefix cache,
FP8 для KV, Triton attention и CPU-пул 32 GiB. Сравниваем **набор настроек**,
а не приписываем всю разницу одному offload.

**Перед запуском проверьте RAM:** на VM с 128 GiB профили с offload выполняются
последовательно — сначала остановите A через Git/Argo. Не называйте такой
замер одновременным A/B. [Бюджет RAM](docs/MEMORY_BUDGET.md#ram-выбрать-порядок-запуска).

```yaml
kv-transfer-config:
  kv_connector: OffloadingConnector
  kv_role: kv_both
  kv_connector_extra_config:
    cpu_bytes_to_use: 34359738368
```

![CPU KV хранит вытесненные блоки и возвращает их при повторном обращении](assets/05-kv-ram.svg)

Оценим цену: `Tпереноса ≈ объём / эффективная полоса`.
Например, `5,390625 GiB / 25 GiB/с ≈ 0,216 с` для полезного FP8 KV истории
128K. Это иллюстрация, не замер PCIe: реальные переносы зависят от блоков,
backend, синхронизации и конкуренции за RAM. Сравниваем эту цену со временем
повторного prefill. [Устройство CPU offload](https://docs.vllm.ai/en/v0.31.0/features/kv_offloading_usage/).

Теперь включим первую B на второй H100: в частном Git меняем только этот
профиль, проверяем render, отправляем commit и применяем его в Argo.
В diff видны именно разобранные настройки. Ждём готовности Pod и ответа API,
затем открываем `Gemma B — Tune` в WebUI — пока это первая, кеширующая итерация B.
Ручная A остаётся на первой карте, если проверенный бюджет RAM позволяет
одновременное сравнение.

## 5. Вторая итерация: chunked prefill и speculative decoding

**Быстрее начать ответ и быстрее продолжать его — разные задачи.**
Сначала поделим длинный prefill на порции, затем проверим цену decode.

### Chunked prefill: дать место уже начатым ответам

![Chunked prefill делит большой ввод на порции и чередует его с decode](assets/06-scheduler.svg)

Мы сократили повторную работу. Но что происходит, когда новый длинный документ
приходит, пока модель уже пишет другим пользователям? Prefill читает много
токенов сразу; decode продвигает активные ответы небольшими шагами.
**Chunked prefill** ограничивает порцию входа, чтобы планировщик мог чередовать
её с decode. Меньше порция — чаще возможность продолжить ответы, но больше
шагов на новый документ. Это компромисс TTFT и ITL, не бесплатное ускорение.

Не перепутаем три независимых ограничения:

| Настройка | Что ограничивает |
| --- | --- |
| `max-model-len` | Длину одной истории: вход и генерацию |
| `max-num-seqs` | Число одновременно обрабатываемых последовательностей |
| `max-num-batched-tokens` | Бюджет токенов текущего шага планировщика |

Вторая конфигурация, `values/gemma-b-spec.yaml`, сохраняет prefix cache,
FP8 KV и 32 GiB CPU KV. К ним добавляются prefill по 2048 токенов,
CUDA graphs и отдельная Gemma assistant. Прежде чем менять процесс,
разберём, какую работу выполняет assistant.

**CUDA graphs** — повторное использование подготовленной последовательности
GPU-операций, чтобы тратить меньше времени на их запуск. Оно тоже требует памяти.

### Speculative decoding: предложить и проверить

![Assistant предлагает токен, основная модель проверяет предложение](assets/07-speculation.svg)

**Speculative decoding** меняет цикл генерации: **draft** — вспомогательный
предсказатель — предлагает продолжение; **target**, основная модель, проверяет его.
При первом отклонении хвост предложения
не становится ответом. Средняя цена выданного токена приблизительно равна
`(время draft + время verification) / число выданных токенов за цикл`.
Нужны и acceptance, и фактическая задержка: высокая доля принятия не гарантирует
ускорение, если черновик дорог.

У нашей Gemma отдельный совместимый **assistant** используется методом `mtp`
в vLLM. **MTP (Multi-Token Prediction)** — предложение последующих токенов
для проверки основной моделью. Это не произвольная модель 2B и не EAGLE3 от другой архитектуры.
У Qwen позже увидим MTP в основном checkpoint.
[Поддержка MTP и Gemma assistant](https://docs.vllm.ai/en/v0.31.0/features/speculative_decoding/mtp/).

<details>
<summary>Что ещё существует: cache-aware routing и prefill/decode disaggregation</summary>

Для нескольких реплик существует **cache-aware routing**: запрос направляют
туда, где вероятнее найти нужный префикс. **Prefill/decode disaggregation**
разносит обработку входа и генерацию по разным исполнителям с передачей KV.
Эти два механизма сегодня не разворачиваем; их место в архитектуре и ссылки —
в [словаре и источниках](docs/SOURCES.md).

</details>

### Переключаем B Cache → B Tune

Сначала скроем маршрут B в WebUI и дождёмся завершения её запросов.
Теперь вернёмся в Argo. Через GitOps остановим первую конфигурацию B,
заменим её рабочий values полным профилем из `values/gemma-b-spec.yaml`,

A не меняем. В Pod проверим две модели

В рабочем `gemma-b.yaml` сначала поставьте `replicaCount: 0` и примените остановку.
Затем замените профиль целиком:

## 6. Gemma через AI Inference

![Model, класс и стратегия превращаются в план и управляемый сервис](assets/09-platform.svg)

**Задача автоматизации — воспроизвести согласованный запуск, а не ускорить
одинаковый vLLM.** Веса, окно, точность KV, offload, assistant, RAM и GPU
должны совпасть с ручной конфигурацией.

Центр AI Inference — планировщик запуска: он сопоставляет метаданные Model,
запрошенную стратегию, допустимые DeviceClass и рецепты. Результат — расчёт
ресурсов и параметры runtime. Это не замена Kubernetes scheduler:
Kubernetes и DRA затем выделяют конкретные устройства для workload.

### Сначала рецепт, потом освобождение GPU

Откроем подготовленный `platform/gemma.yaml`: в нём Model, класс и стратегия,
а не скопированная командная строка vLLM. Для этого опыта заранее проверяется
рецепт, совпадающий с B по окну, CPU KV, assistant, chunked prefill и остальным
параметрам. Название Throughput само по себе такого совпадения не гарантирует.
Справочный Gemma 64K без CPU KV и assistant — другая конфигурация;
[проверка нужной поставки](docs/SETUP.md#inference-readiness) относится к подготовке.

Теперь скрываем Base в WebUI, дожидаемся завершения её запросов,
останавливаем ручную A на первой H100, дожидаемся освобождения её claim
и включаем заказ через `charts/inference-service`. Ручная B остаётся на второй
карте; RAM для двух настроенных моделей зарезервирована при подготовке стенда.
В Argo смотрим применение заказа, в консоли — InferenceService, рассчитанный
план, claim и дочерний Pod. Здесь впервые вместо ручного описания процесса
показываем полный результат работы планировщика AI Inference.

| Сопоставляем | Что проверяем |
| --- | --- |
| Наш расчёт `W + KV(N,S) + R` | Предположения о весах, истории и резервах |
| План AI Inference | Количество GPU, рецепт, окно и бюджеты |
| Запущенный контейнер | Фактические параметры, offload и assistant |

Если параметры или нагрузка различаются, это сравнение разных режимов,
а не качества автоматизации. После ответа API включим маршрут **`Gemma A — DP`**
для `hf-platform-gemma`. На дашборде меняется Service, не набор показателей.

В подготовленном `platform/gemma.yaml` включите `order.enabled: true`.
Это Helm values, не сырой Kubernetes-манифест:

```bash
set -o pipefail
helm template hf-platform-gemma "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После проверки — commit/push этого файла и Sync `hardfest-gemma-platform`.
В консоли открываем `hf-platform-gemma`: Model → план → claim → Pod.
В плане и контейнере должны совпасть окно, кеши и assistant последней ручной B.

<details>
<summary>Проверить API платформенной Gemma; затем тем же способом Qwen</summary>

В консоли найдите Service созданного заказа и его порт.
В отдельном терминале откройте port-forward на локальный 18005:

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get service hf-platform-gemma
kubectl --context "$GPU_CONTEXT" -n hardfest-demo port-forward svc/hf-platform-gemma 18005:80
```

Если Service публикует другой порт, замените 80 фактическим.
В основном терминале введите ключ этого сервиса из менеджера секретов:

```bash
set +x
IFS= read -r -s MODEL_API_KEY
curl --fail --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  http://127.0.0.1:18005/v1/models
```

Скопируйте ID из ответа в поле `model`, затем отправьте вопрос:

```bash
curl --fail-with-body --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  -H 'Content-Type: application/json' http://127.0.0.1:18005/v1/chat/completions \
  -d '{"model":"REPLACE_SERVED_MODEL_ID","max_tokens":512,"temperature":0,"messages":[{"role":"user","content":"Зачем нужен KV-кеш?"}]}'
unset MODEL_API_KEY
```

Нужен законченный текст без ошибки. После проверки закройте port-forward.
Для Qwen повторите с `hf-qwen-platform`, его портом, ID и ключом.
Секрет не попадает в аргументы curl или Git.

</details>

Это функциональное сравнение с наблюдением задержек. Для числового сравнения
производительности нужен общий CPU-клиент с авторизацией; команда ручного A/B
выше не применяется к платформенному StatefulSet без адаптации.

2. **Попробуйте:** пройдите цепочку **Model → план → claim → Pod → API → чат**.
   Задайте одинаковые вопросы ручной B и `Gemma A — DP`.
3. **Проверьте:** законченные ответы и отдельные ряды **TTFT / ITL / ошибки**

<summary>Разбор: что доказывает каждый шаг запуска</summary>

Argo подтверждает применение конфигурации, план — расчёт, claim — выделение
устройств. Успешный API-ответ проверяет инференс; ответ в чате дополнительно
проверяет маршрут и личный доступ. Совпадающие параметры позволяют сравнивать

<a id="placement"></a>
## 7. Три сервиса на A30

До сих пор одна модель занимала целую карту. Теперь другая задача:
эмбеддеру и реранкеру не нужна отдельная большая GPU каждому, а голосовой
сервис должен работать рядом. Сменим кластер в консоли и datasource графиков:
эти модели живут на A30, не на освобождаемых H100.

### Kubernetes выдаёт устройство; MIG и MPS делят его ресурсы

Сначала разделим два уровня. Kubernetes **device plugin** обычно публикует
целочисленный extended resource, например количество GPU. **Dynamic Resource
Allocation (DRA)** использует классы и ResourceClaim для выбора устройств
по свойствам и их подготовки драйвером. Ни один из этих API сам по себе
не задаёт физическую изоляцию: её обеспечивает выбранный механизм GPU.
[Device plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/),
[DRA](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/).

| Механизм | Что делится | Что важно для соседей |
| --- | --- | --- |
| **MIG — Multi-Instance GPU** | Аппаратные вычислительные ресурсы и память GPU | Фиксированные допустимые профили, отдельные экземпляры |
| **MPS — Multi-Process Service** | Совместное выполнение процессов на GPU или внутри MIG | Не добавляет память и не заменяет аппаратную изоляцию MIG |
| Time-slicing | Доступ контекстов к общему устройству во времени | Само по себе не делит память на изолированные аппаратные части |

В этой работе DRA связывает заказ с MIG/MPS нашего GPU-драйвера.
HAMi — другой стек управления совместным использованием устройств,
Volcano — планировщик workloads; это не названия режимов NVIDIA и не
взаимозаменяемые варианты MIG. Vulkan — графический/compute API, а не
Kubernetes scheduler. Выбор и ссылки разобраны в [источниках](docs/SOURCES.md).

### Что делает каждый сервис

![Одна A30: эмбеддер и реранкер делят 2g.12gb через MPS, Whisper занимает вторую 2g.12gb](assets/08-mig-mps.svg)

| Сервис | Простое объяснение | Модель и размещение |
| --- | --- | --- |
| **Эмбеддер** | Превращает текст в вектор, чтобы находить близкие по смыслу фрагменты | Qwen3 Embedding 4B, W4A16; первая `2g.12gb`, MPS |
| **Реранкер** | Повторно оценивает найденные фрагменты относительно вопроса и меняет их порядок | Qwen3 Reranker 4B, W4A16, sequence classification; та же партиция, MPS |
| **Whisper** | Преобразует речь в текст; это распознавание, не синтез речи | Whisper large-v3; вторая `2g.12gb`, отдельно |

Это три **InferenceService в кластере A30**, а не три ручных Deployment
и не объекты в консоли H100-кластера. MIG разделяет ресурсы аппаратно;
MPS делит вычисления внутри партиции, но не превращает процессы в отдельные GPU.

**W4A16** — 4-битные веса и 16-битные активации. Профиль `2g.12gb` —
конкретный размер MIG-раздела A30, не универсальный профиль любой карты.

### Проверяем размещение до и после заказа

До заказа снимем `nvidia-smi -L` и список GPU instances. Затем создадим заказы
через Argo, проследим ResourceClaim и повторим снимок на той же A30.
Для опыта динамического создания исходно нужна свободная поддерживаемая
геометрия и включённый MIG mode. Если нужные MIG уже существовали, мы показали
их выделение, а не создание. Работающие чужие партиции не переразмечаем.
В уже открытом терминале ноды A30 до и после запуска:

```bash
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

![Индексация документов, поиск и reranking подготавливают контекст для выбранной LLM](assets/16-rag.svg)

**RAG (Retrieval-Augmented Generation)** — ответ с найденными фрагментами
документов в контексте. Эмбеддер ищет, реранкер уточняет выбор, LLM формулирует
ответ. Документы не становятся от этого новыми весами модели.

Для этого этапа модели подготовлены через `catalog/a30.yaml`, заказы — через
`platform/embedding.yaml`, `platform/reranker.yaml`, `platform/whisper.yaml`.
В трёх подготовленных values включите `order.enabled: true`, проверьте
Helm render и отправьте commit. В Argo последовательно синхронизируйте
`hardfest-embedding-platform`, `hardfest-reranker-platform`,
`hardfest-whisper-platform`. Их destination — кластер A30.
В его консоли дождитесь готовности всех трёх InferenceService.

Это **три разных API**, не три chat completion. Проверьте каждый отдельно,
затем эмбеддер и реранкер одновременно: время, ошибки, пик памяти и общий
MIG UUID. Источник метрик на дашборде — **кластер A30**.

### Опыт 7. Вопрос по документу, затем голосом

1. **Предскажите:** нужен ли новый индекс при смене Gemma на Qwen? А при смене эмбеддера?
2. **Попробуйте:** загрузите документ в базу знаний, задайте вопрос и проверьте
   источник ответа. Затем продиктуйте фразу и сверьте распознанный текст.
3. **Проверьте:** **запросы, задержки и ошибки embedding / rerank / transcription**.
   Отсутствие выходных токенов у этих сервисов не означает отказ.

<summary>Разбор: когда индекс нужно перестраивать</summary>

При переходе Gemma → Qwen индекс сохраняется. При смене эмбеддера векторы

</details>

## 8. Qwen через AI Inference на двух H100

**Теперь обе карты работают над одной моделью, а не обслуживают две её копии.**

![После проверки модели и плана обе Gemma останавливаются, две H100 получает Qwen](assets/17-qwen-transition.svg)

Qwen — обязательный финальный этап. Сначала проверьте готовность его артефакта,
runtime, рецепта и класса. Скройте обе Gemma в WebUI и дождитесь завершения
текущих запросов; затем освободите обе H100 через GitOps.
Уже работающие сервисы A30 и чат остаются включёнными.

Вернёмся в основной GPU-кластер. Вместо двух независимых копий модели теперь
нужна одна модель, разделённая между двумя устройствами. **Tensor Parallelism
(TP2)** делит тензорные вычисления по GPU и добавляет обмен промежуточными
результатами. Это не Data Parallel и не название TensorRT: runtime остаётся vLLM.

Заказ `platform/qwen.yaml` создаёт `hf-qwen-platform`.
В плане должно быть `acceleratorCount=2`, в DRA claim — две разные карты
одной ноды, в конфигурации движка — `tensor-parallel-size: 2`.
Один DeviceClass без требуемого количества карт не подтверждает TP2.

![Tensor Parallel делит вычисления модели между двумя GPU и требует межкарточного обмена](assets/10-tp2.svg)

В подготовленном `$DEMO_DIR/platform/qwen.yaml` меняем только
`order.enabled: true`; Model, класс и стратегия уже заданы. Не заменяем
этот values сырым InferenceService.

```bash
set -o pipefail
helm template hf-qwen-platform "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/qwen.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После успешной проверки — commit/push и Sync `hardfest-qwen-platform`.
В консоли проверяем готовность `hf-qwen-platform`, две разные GPU в claim
и `tensor-parallel-size: 2` в Pod. Затем `/v1/models`, законченный ответ
`/v1/chat/completions` и тот же вопрос через Virtual Key в WebUI.
Наличие NVLink само по себе не доказывает скорость обмена.

![Qwen использует собственные MTP-головы без отдельной модели assistant](assets/18-qwen-mtp.svg)

У Qwen MTP встроен в модель: отдельная Gemma assistant ему не нужна.
Проверяем включённый MTP, статистику принятия предложений и decode.
Для этого рецепта применяется native KV-offload с Simple CPU backend;
не копируйте в него Gemma OffloadingConnector.

![Нагрузка Qwen растёт от одного до восьми клиентов: сравниваем активные запросы, очередь и задержки](assets/19-qwen-capacity.svg)

### Опыт 8. Восемь участников — восемь полных окон?

1. **Предскажите:** если сервис принимает восемь запросов, поместятся ли восемь
   историй предельной длины одновременно на GPU?

<details>
<summary>Разбор: параллельность, очередь и вместимость KV</summary>

Лимит окна ограничивает одну историю. `max-num-seqs` — число последовательностей

После ответа API добавьте Qwen в разрешённые модели действующих VK

сначала чтением, затем изменением одного тестового ресурса с откатом.

## 9. Запрос участника, личный ключ и стоимость

Qwen и сервисы A30 пока остаются включёнными. Отправим последний вопрос
в WebUI и откроем Bifrost рядом с чатом: найдём только что отправленный запрос,
его модель, личный VK, входные и выходные токены и расчётную стоимость.
Сверим два одобренных аккаунта: ключи разные, маршруты разрешены политикой,
остановленные модели не подменяются незаметным fallback. Провайдерский ключ
backend не принимаем за доказательство персонального доступа.

Настройка бюджета и его соблюдение — разные проверки. У используемой HA-схемы
есть ограничение точности общего счётчика расходов; стоимость отдельного запроса
не доказывает правильность суммарного лимита.
[Границы учёта и проверка лимита](docs/CHAT_AND_ACCESS.md#проверить-выдачу-и-отзыв).

Теперь можно ответить на вопрос из начала: нужны ли ещё карты?
Сначала выясняем, сколько историй помещается в память, сколько запросов
завершается с нужной задержкой и какая доля GPU действительно нужна каждому
сервису. Prefix cache уменьшает повторную работу, offload добавляет слой хранения,
chunking меняет обслуживание очереди, speculation — цену decode, MIG/MPS —
плотность размещения. Платформа связывает эти решения с воспроизводимым заказом.
Ни один механизм не заменяет остальные и не отменяет измерений.

| Опыт | Доказательство |
| --- | --- |
| A → B cache → B compute | Конфигурации, одинаковая нагрузка, сырые результаты и ошибки |
| KV в RAM | Сохранение и обратная загрузка блоков, расход RAM и время повторного запроса |
| Большее окно | Законченный длинный ответ, реальная длина и бюджет памяти |
| AI Inference | Готовый заказ, нужный план, GPU claim, API и ответ через чат |
| A30 | Три готовых сервиса и успешные embeddings/rerank/transcription |
| Личный доступ | Разные VK двух аккаунтов, раздельный расход, проверенные запреты |

Для публикуемых цифр выполните не менее трёх независимых прогонов и сохраните
разброс. p95 вычисляется по запросам, а не усредняется между готовыми отчётами.
Шаблон результатов — в [методике](docs/MEASUREMENTS.md).
Проверки файлов и Helm render не являются такими прогонами.

<a id="cleanup"></a>
## Остановка после завершения работы

К остановке переходим после финальных запросов, разбора учёта и сохранения результатов.
Сначала скройте останавливаемые маршруты от участников.
Ручные workloads выключаются `replicaCount: 0` с commit/push/sync.

Для платформенных заказов `order.enabled: false` убирает объект из Helm render,
но **sync без prune не удаляет существующий InferenceService**.
В Argo просмотрите diff и удалите только выбранный заказ с его дочерним workload
по [инструкции остановки](docs/GITOPS.md#остановка). Это отдельное явное действие.

Не удаляйте Namespace, Model, PVC, GPUClass/GPUPool, чаты и базы знаний.
После остановки проверьте отсутствие Pod нагрузки и освобождение claims.

## Подготовка своего стенда

Этот раздел нужен для воспроизведения работы, не для первого действия в чате.
К началу основного маршрута A уже отвечает, модели доставлены, маршруты и графики
проверены. B и платформенные заказы подготовлены, но не занимают H100.

Пройдите [подготовку инфраструктуры и запуск A](docs/SETUP.md),
[GitOps](docs/GITOPS.md), [каталог моделей](catalog/README.md),
[подключение чата](docs/CHAT_AND_ACCESS.md) и [мониторинг](docs/OBSERVABILITY.md).
Контексты и переменные команд определены в подготовке.

адресно из частного Git, не включая всё одновременно.

Для параллельной ручной B и платформенной Gemma нужен проверенный бюджет
не менее 192 GiB RAM. На 128 GiB используется отдельный последовательный вариант,
не одновременное сравнение. [Расчёт RAM](docs/MEMORY_BUDGET.md#ram-выбрать-порядок-запуска).
Веса ai-models должны быть готовы на целевой ноде; OCI-образ vLLM кешируется отдельно.
