## Цель мастер-класса

Разобраться, что ограничивает LLM-сервис: память под контексты, обработка входа, генерация или размещение моделей на GPU. На одинаковых весах и запросах сравнить исходный и настроенный запуск, затем воспроизвести выбранную конфигурацию через Deckhouse Platform.

Практическая часть проходит через четыре задачи:

- Оценить память длинных контекстов и проверить повторное использование KV-кэша, в том числе через RAM.
- Измерить влияние chunked prefill, батчинга, CUDA graphs и черновой модели.
- Разместить эмбеддер и реранкер с динамическим MIG и MPS, проверить выделение и освобождение ресурсов.
- Перенести выбранные настройки в сервис платформы и повторить проверку API.

Результат работы — манифесты, зафиксированные параметры запуска и отчёт по одинаковой нагрузке. Их можно использовать для повторного прогона на своей площадке. Дополнительный раздел — запуск большой модели на двух H100.

## Подготовка окружения

### Что потребуется

- Kubernetes/DKP с DRA, установленными GPU-драйвером и контроллером GPUClass/GPUPool.
- Две сопоставимые H100 для одновременного A/B; отдельная A100 с поддержкой MIG для разделения GPU.
- Доставленные веса моделей на PVC и совместимый runtime из [models.lock.json](models.lock.json).
- Свободная host RAM для эксперимента с KV-offload; стартовый бюджет connector — 64 GiB, его нужно согласовать с лимитами Pod и доступной памятью.
- Python 3.10+, Git, kubectl и kubeconfig с доступом к учебному namespace `hardfest-demo`.
- Для раздела автоматизации — ai-models, ai-inference и Console с совместимыми CRD.

Можно изучать теорию и генерировать манифесты без GPU. Для последовательного A/B достаточно одной совместимой карты, но между вариантами нужен перезапуск. Раздел MIG/MPS требует соответствующих оборудования и драйвера.

### Получить материалы

В терминале на своём компьютере:

```bash

cd hardfest-gpu-workshop
python3 scripts/hf.py init-site
```

**Ожидаемый результат:** создан личный файл `.local/site.json`. Скрипт не выбирает кластер автоматически и не перезаписывает существующий файл; при повторной работе шаг `init-site` пропустите.

Заполните его по [инструкции подготовки](docs/SETUP.md): kubeconfig, context, ожидаемый API, GPU-ноды, сгенерированные DeviceClass, PVC и пути моделей. Не коммитьте `.local`. Namespace, PVC, модели и GPU-классы должны существовать до запуска упражнений.

### Проверить локальные инструменты

```bash
python3 -m unittest discover -s tests -v
python3 scripts/check_public.py
python3 scripts/check_docs.py
python3 scripts/hf.py --site config/site.example.json render a
```

**Ожидаемый результат:** проверки завершаются успешно, `render` выводит манифесты с `replicas: 0`. Эти команды не подключаются к кластеру.

Все дальнейшие команды выполняются из корня этого репозитория. `apply/start/stop --ack` изменяют ресурсы явно выбранного стенда. Не используйте общие production GPU. Перед запуском сверяйте [условия готовности](docs/REHEARSAL.md) и [что уже проверено](docs/STATUS.md); отсутствие подтверждённого прогона не заменяется успешной генерацией YAML.

## 1. Время ответа и первый запрос

1. Выберите учебный документ в подготовленном чате.
2. Задайте вопрос: например, «Какие ограничения здесь есть и какие действия предлагаются?».
3. Отметьте время первого отклика и первых слов итогового ответа.

Используйте только учебные документы. Если UI/RAG ещё не подготовлен, выполняйте запросы через прямой API; этот путь проверяет генерацию, а не поиск по базе знаний.

### Из чего складывается время ответа

| Фаза | Что происходит |
| --- | --- |
| Очередь | Запрос ждёт возможности обработки |
| Prefill | Модель обрабатывает вход |
| Генерация | Модель выдаёт токены рассуждения и ответа |
| Текст в чате | Интерфейс показывает финальный ответ |

**TTFT** — время до первого генерируемого токена, а не обязательно до первого видимого слова финального ответа. Очередь измеряем отдельно: запрос может долго ждать и сравнительно быстро обработаться.

Проверьте, к какому кластеру подключены команды и какие устройства доступны:

```bash
python3 scripts/hf.py preflight
python3 scripts/hf.py get nodes
python3 scripts/hf.py get deviceclasses
```

**Проверка:** выбран ожидаемый API/context, нода Ready, DeviceClass создан контроллером. Имя H100 в inventory ещё не доказывает доступ CUDA. Проверьте его отдельно до нагрузочных тестов.

**Стоп:** NotReady/cordon, чужая нагрузка на выделенных картах или неизвестный владелец DeviceClass. Эти условия сначала разбирает администратор площадки.

## 2. Память: сколько места нужно контекстам?

### Веса, буферы и KV — три разных расхода

Одна копия модели занимает память под веса. Движку нужны рабочие буферы и память CUDA graphs. Оставшееся место используется для KV-кэша запросов. Свободные вычислительные блоки не означают, что туда поместится ещё один длинный контекст.

Авторегрессионная модель дописывает текст по одному шагу. В attention **Q** текущей позиции сравнивается с **K** истории, затем полученные веса применяются к **V**. Старые K/V сохраняем; Q нужен для текущего вычисления. Это состояние вычислений, не сохранённый готовый ответ.

При GQA несколько Q-голов используют общие K/V. У GPT-OSS-120B из учебного примера 64 головы Q и **8 KV-голов**. Считать KV по всем 64 головам нельзя.

### Считаем память длинного запроса

Для BF16, head dimension 64 и восьми KV-голов одна позиция одного слоя занимает:

`2 × 8 × 64 × 2 = 2048 байт = 2 KiB`.

Первая двойка — K и V, последняя — два байта BF16. В GPT-OSS-120B чередуются 18 полных и 18 локальных слоёв с окном 128:

`KV(S) = 2 KiB × [18 × S + 18 × min(S, 128)]`.

При `S = 131072` получаем **4,5044 GiB** полезных KV-данных. Движок выделяет память блоками; округления и рабочие расходы нужно учитывать отдельно. Параметры и подробная выкладка — в [главе о памяти](docs/chapters/01-memory.md).

**Задание:** сколько KV-памяти нужно четырём и восьми независимым полным контекстам 128K?

<details>
<summary>Проверить расчёт</summary>

Четыре — **18,02 GiB**, восемь — **36,04 GiB**, без весов и рабочих буферов.

```bash
python3 scripts/kv_math.py --sessions 4
python3 scripts/kv_math.py --sessions 8
```

</details>

### Почему четвёртый контекст может не поместиться

Учебный бюджет со слайдов: `96 GiB × 0,90 − 64 GiB − 6 GiB = 16,4 GiB`. Делим на 4,5044 GiB — в идеальной модели помещаются три полных независимых истории, а на четвёртую памяти не хватает. **96 GiB — условие задачи, не измеренная ёмкость H100 на стенде.**

Контекст включает весь вход и генерацию: 120K входа + 8K рассуждения и ответа = 128K. Окно `max-model-len` задаёт потолок истории, а не выделяет столько памяти заранее каждому пользователю.

**Вывод:** перед запуском Gemma проверяем её собственный config и фактический KV-пул. Большой объём RAM не заменяет память активного вычисления на GPU.

## 3. Запуск двух конфигураций и сравнение A/B

Подготовьте A/B по [лабораторной](labs/01-ab.md). A использует штатную конфигурацию выбранной vLLM, B — пакет явных настроек. Одинаковые веса, контекст и запросы позволят сравнить результат. Перед измерением прогрейте kernels на других префиксах, не на документах контрольной серии.

```bash
python3 scripts/hf.py render a
python3 scripts/hf.py render b-tuned
# После проверки двух свободных H100:
python3 scripts/hf.py apply a --ack
python3 scripts/hf.py apply b-tuned --ack
python3 scripts/hf.py start a --ack
python3 scripts/hf.py start b-tuned --ack
python3 scripts/hf.py model-info a
python3 scripts/hf.py snapshot a --out .local/runs/ab-a.json
python3 scripts/hf.py snapshot b-tuned --out .local/runs/ab-b.json
```

Заранее генерируем dataset **внутри готового Pod**, с его tokenizer. Файл сохраняется на ноутбуке; путь `/models/gemma` вручную подставлять не нужно. Для повторной генерации выберите новое имя файла: существующее не перезаписывается.

```bash
python3 scripts/hf.py dataset a --input-fraction 0.5 --output-tokens 2048 \
  --documents 32 --out .local/long.jsonl
```

В терминале **T1** (команда остаётся работать):

```bash
python3 scripts/hf.py port-forward a 18001
```

В терминале **T2**:

```bash
python3 scripts/hf.py port-forward b-tuned 18002
```

Простейшая проверка транспорта (НЕ замер длинного контекста):

```bash
python3 scripts/bench.py --url http://127.0.0.1:18001 --dataset examples/smoke.jsonl --concurrency 1 --requests 2
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset examples/smoke.jsonl --concurrency 1 --requests 2
```

Затем выполняем **одинаковый** подготовленный dataset:

```bash
python3 scripts/bench.py --url http://127.0.0.1:18001 --dataset .local/long.jsonl \
  --concurrency 4 --requests 8 --cold --metrics --label a-long --out-dir results/raw/ab
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset .local/long.jsonl \
  --concurrency 4 --requests 8 --cold --metrics --label b-long --out-dir results/raw/ab
python3 scripts/report.py --directory results/raw/ab
```

Восемь запросов — короткая проверочная серия, а не достоверный production p95. Для устойчивого сравнения выполните не менее трёх повторов и более длинную серию из [методики измерений](docs/MEASUREMENTS.md); зафиксируйте состояние кэша перед каждой. Флаг `--cold` только запрещает повтор строк dataset — он не очищает server cache.

**Ожидаемый результат:** оба API возвращают сгенерированный ответ; снимки настроек лежат в `.local/runs/`, результаты запросов — в `results/raw/ab/`. `report.py` выводит отдельную строку для каждого прогона. Ошибка запроса не должна превращаться в нулевую задержку.

**Сравните:** client TTFT, server queue, prefill, output tokens/s и errors. TTFT включает ожидание; среднее prefill не является p95 TTFT. [Правила измерений](docs/MEASUREMENTS.md).

## 4. Возврат KV-кэша из RAM

**Задача:** сравнить повтор документа после вытеснения его KV из GPU — без CPU-tier и с ним. Это не выгрузка весов через `--cpu-offload-gb`: веса остаются на GPU, блоки KV сохраняются в RAM и возвращаются на GPU перед вычислением.

Профиль `b-cache` добавляет к `b-tuned` OffloadingConnector с бюджетом **64 GiB**. В используемом connector этот бюджет общий на workers. До запуска проверьте свободную RAM и лимит памяти Pod. [Конфигурация и ограничения](labs/02-kv-ram.md).

### 4.1. Контрольная серия без CPU-tier

Нужен готовый `.local/long.jsonl` с 32 документами. Чтобы не принять прогретый кэш предыдущего A/B за холодный вход, перезапустите B:

```bash
python3 scripts/hf.py stop b-tuned --ack
python3 scripts/hf.py apply b-tuned --ack
python3 scripts/hf.py start b-tuned --ack
```

В T2 завершите предыдущий port-forward через Ctrl+C и запустите:

```bash
python3 scripts/hf.py port-forward b-tuned 18002
```

В T0 выполните **X → другие документы → X**:

```bash
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset .local/long.jsonl \
  --offset 0 --requests 1 --concurrency 1 --metrics --label x-first --out-dir results/raw/cache-off
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset .local/long.jsonl \
  --offset 1 --requests 31 --concurrency 4 --cold --metrics --label other-docs --out-dir results/raw/cache-off
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset .local/long.jsonl \
  --offset 0 --requests 1 --concurrency 1 --metrics --label x-return --out-dir results/raw/cache-off
python3 scripts/report.py --directory results/raw/cache-off
```

### 4.2. Та же серия с CPU-tier

```bash
python3 scripts/hf.py stop b-tuned --ack
python3 scripts/hf.py apply b-cache --ack
python3 scripts/hf.py start b-cache --ack
python3 scripts/hf.py logs b-cache
```

**Ожидаемый результат:** в логах включён OffloadingConnector с заданным CPU budget, API готов. В T2 завершите старый port-forward и переподключитесь:

```bash
python3 scripts/hf.py port-forward b-cache 18002
```

В T0 повторите те же документы, сохраняя отдельный результат:

```bash
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset .local/long.jsonl \
  --offset 0 --requests 1 --concurrency 1 --metrics --label x-first --out-dir results/raw/cache-on
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset .local/long.jsonl \
  --offset 1 --requests 31 --concurrency 4 --cold --metrics --label other-docs --out-dir results/raw/cache-on
python3 scripts/bench.py --url http://127.0.0.1:18002 --dataset .local/long.jsonl \
  --offset 0 --requests 1 --concurrency 1 --metrics --label x-return --out-dir results/raw/cache-on
python3 scripts/report.py --directory results/raw/cache-on
```

### 4.3. Проверка результата

Сравнивайте `x-return` без CPU-tier и с ним, а не смешивайте все три этапа в один speedup. Начальное состояние engine и способ прогрева должны совпадать; для прогрева используйте другой префикс, не X.

31 документ — нагрузка, **не гарантия вытеснения**. Подтвердите GPU eviction и CPU store/load по доступным counters/trace. Если X остался в GPU, измерен GPU prefix hit, а не эффект RAM. Недоступная instrumentation означает неподтверждённый результат.

Оценка из учебного расчёта: `4,50 GiB / 25 GiB/с ≈ 0,180 с` — только передача при условной скорости, не TTFT и не замер шины. Сравнивайте также очередь, prefill и полный ответ. [Подробности](docs/chapters/02-scheduler.md).

## 5. Chunked prefill, батчинг и CUDA graphs

Вернёмся к сравнению A и B tuned, снятому до включения RAM-tier. Посмотрим, какие параметры отличаются:

```bash
python3 scripts/hf.py diff a b-tuned
```

Prefill обрабатывает вход, decode продолжает ответы. Chunked prefill позволяет делить обработку длинного входа между шагами scheduler.

| Бюджет шага | Три генерируемых ответа | Остаётся для нового входа |
| --- | --- | --- |
| 8192 токена | 3 × 1 токен | 8189 токенов |
| 2048 токенов | 3 × 1 токен | 2045 токенов |

Меньше входа за шаг — больше шагов на документ, но потенциально меньше задержка уже работающих ответов. Это учебная иллюстрация, а не обещание одновременного выигрыша по всем метрикам. В нашем B-профиле исходный кандидат — 4096.

### Три ограничения vLLM

| Параметр | Что ограничивает |
| --- | --- |
| `max-model-len` | Длину одной истории: вход + генерация |
| `max-num-seqs` | Число обрабатываемых scheduler sequences |
| `max-num-batched-tokens` | Число токенов текущего шага |

**FP8 KV** уменьшает полезный размер K/V относительно BF16, но не весь расход памяти процесса. **CUDA graphs** уменьшают накладные расходы повторного запуска подготовленных вычислений, занимая дополнительную память. Проверяем effective config и startup logs, а не только наличие флага.

Штатная vLLM уже может включать часть оптимизаций: исходный A не замедляем искусственно. Пакет настроек даёт суммарный эффект; чтобы приписать его одному флагу, нужна отдельная серия с изменением только этого параметра. [Scheduler и методика сравнения](docs/chapters/02-scheduler.md).

## 6. Генерация с черновой моделью

Черновая модель предлагает продолжение, основная проверяет его. У черновика есть собственные веса, состояние и стоимость вычисления. В практике используем Gemma assistant; GPT-OSS/EAGLE3 из презентации — пример того же принципа, но не взаимозаменяемая конфигурация.

Сравниваем B tuned и B spec **без** одновременного добавления RAM offload. [Лабораторная speculation](labs/03-speculation.md).

```bash
python3 scripts/hf.py stop b-cache --ack
python3 scripts/hf.py apply b-spec --ack
python3 scripts/hf.py start b-spec --ack
```

В терминале T2 переподключите API:

```bash
python3 scripts/hf.py port-forward b-spec 18002
```

**Ожидаемый результат:** в логах B загружен assistant и активирован speculative method. Отсутствие ошибок само по себе этого не подтверждает.

Выполните запрос с длинным ответом, затем несколько параллельных. Измерьте accepted tokens по позициям и output throughput.

В примере со слайдов три токена приняты, четвёртый отвергнут, зависимый от него хвост отброшен. Средняя стоимость выданного токена за цикл:

`(время черновика + время проверки + накладные расходы) / число выданных токенов`.

**Вывод:** высокий acceptance сам по себе не доказывает ускорение. Сравниваем полное время и качество ответа; при проигрыше фиксируем проигрыш. [Подробный разбор цикла](docs/chapters/03-speculation.md).

## 7. Динамический MIG и MPS

Эмбеддер превращает текст в вектор, реранкер оценивает найденные фрагменты. Для них не обязательно резервировать целую карту.

| Механизм | Как делится GPU |
| --- | --- |
| MIG | Аппаратные части с выделенными памятью и вычислительными ресурсами |
| MPS | Несколько процессов совместно используют ресурсы GPU или одного MIG instance |
| Time-slicing | Процессы чередуют выполнение; общая ёмкость памяти не увеличивается |

На отдельной A100 MIG mode включён заранее, но **разделы не преднарезаны**. GPUClass/GPUPool создаёт DeviceClass; scheduler выделяет ресурс по ResourceClaim, а DRA-драйвер подготавливает MIG для контейнера. [Лабораторная MIG/MPS](labs/05-mig-mps.md).

```bash
python3 scripts/hf.py get deviceclasses
python3 scripts/hf.py apply embed-mig --ack
python3 scripts/hf.py start embed-mig --ack
python3 scripts/hf.py get resourceclaims
```

Для проверки embedding API откройте отдельный терминал T3:

```bash
python3 scripts/hf.py port-forward embed-mig 18003
```

В T0:

```bash
curl --fail --max-time 30 http://127.0.0.1:18003/v1/embeddings \
  -H 'Content-Type: application/json' \
  -d '{"model":"embedding","input":["Динамическое разделение GPU","Очередь инференса"]}'
```

**Ожидаемый результат:** ответ содержит вектор для каждого входного текста, без ошибки модели или allocation.

После настройки и проверки `reranker_profile` из [лабораторной](labs/05-mig-mps.md) запустите два MPS-клиента:

```bash
python3 scripts/hf.py apply embed-mps --ack
python3 scripts/hf.py start embed-mps --ack
python3 scripts/hf.py apply rerank-mps --ack
python3 scripts/hf.py start rerank-mps --ack
python3 scripts/hf.py get resourceclaims
```

Без подтверждённого reranker-профиля скрипт остановит его запуск. Allocation должен подтвердить, что оба MPS-клиента используют один MIG instance. Два Pod на одной физической карте ещё не доказывают MPS-sharing.

Измерьте каждое API отдельно и оба вместе: корректность результата, время ответа, ошибки и пик памяти. **25% MPS — не обещание 25% throughput** и не аппаратная изоляция MIG.

Остановите демонстрационные процессы по одному, наблюдая освобождение claims и ёмкости. PVC и модели сохраняются. Если эти API включены в подготовленный RAG, сначала выполните следующий шаг с повторным вопросом, а затем cleanup из лабораторной. [Размещение и путь RAG](docs/chapters/04-placement.md).

## 8. Повтор запуска через Deckhouse Platform

Ручной подбор отвечает на вопрос «что работает?». Платформа должна воспроизвести выбранную конфигурацию и управлять её запуском. [Лабораторная Deckhouse](labs/04-deckhouse.md).

Освободите A, сохранив ручной B:

```bash
python3 scripts/hf.py stop a --ack
```

В мастере Console создайте сервис `hf-platform-gemma`: источник ai-models, та же ревизия модели, согласованные контекст, GPU-профиль и стратегия.

| Уровень | Что проверяем |
| --- | --- |
| AI Models | Модель и ревизию весов |
| InferenceService и план | Выбранные контекст, память, runtime, параметры и DeviceClass |
| Контейнер | Фактические args, image и выделенный GPU |
| API | Живой ответ на тот же запрос |

Перед применением экспортируйте форму CRD из установленной версии и проверьте её server-side dry-run. Если платформа не поддерживает speculation или KV connector, это явное отличие конфигураций, а не скрытая «галочка оптимизации».

### Повторите вопрос в сервисе A

В подготовленном RAG сохраните документ, индекс, эмбеддер и реранкер; переключите только endpoint генерации на новый сервис A. Повторите исходный вопрос. Если RAG ещё не подготовлен, проверяйте прямой API и не называйте это сквозным RAG-тестом.

Сравните **три запуска**: исходный A, вручную настроенный B и новый A через Deckhouse. Одинаковые запросы, sampling, параллелизм и история кэша; отдельно — время ответа, завершённые запросы и ошибки. [Форма отчёта](results/REPORT.template.md).

## 9. Большая модель на двух H100

Перед TP2 удалить созданный в предыдущем шаге **конкретный** сервис Deckhouse через Console, дождаться освобождения его claim. Скрипт не трогает ресурсы Deckhouse за пользователя.

```bash
python3 scripts/hf.py stop b-spec --ack
python3 scripts/hf.py apply tp2 --ack
python3 scripts/hf.py start tp2 --ack
```

**Ожидаемый результат:** Qwen запущена с TP2 и отвечает через API. Затем создайте dataset её tokenizer и измерьте последовательность нагрузок 1 → 2 → 4 → 8 → 16 → 32 → 50. Прекратите рост при ошибках или нарушении выбранных ограничений по времени ответа. Подготовка весов не доказывает, что модель уже работает на этом оборудовании. [Проверки TP2 и поиск допустимой нагрузки](labs/06-tp2.md).

## 10. Остановка и освобождение ресурсов

Остановите только этапы, которые запускали. Для B достаточно одной команды: все его профили используют Deployment `hf-gemma-b`.

```bash
python3 scripts/hf.py stop a --ack
python3 scripts/hf.py stop b-spec --ack
python3 scripts/hf.py stop tp2 --ack
python3 scripts/hf.py stop rerank-mps --ack
python3 scripts/hf.py stop embed-mps --ack
python3 scripts/hf.py stop embed-mig --ack
python3 scripts/hf.py get resourceclaims
```

Не запускавшиеся Deployment могут вернуть `not found`: это не повод удалять namespace. Если создавали `hf-platform-gemma` через Console, удалите только этот InferenceService отдельно.

**Ожидаемый результат:** Pod завершены, их claims освобождены, GPU снова доступны; PVC и модели сохранены. Освобождение claim не всегда означает немедленное удаление MIG instance — проверьте reconcile и retention policy драйвера. Не снимайте finalizers вручную.

## Разбор результатов: нужны ли дополнительные карты?

| Что проверили | Что теперь можем решить |
| --- | --- |
| Память | Сколько длинных контекстов помещается одновременно и что даёт повторное использование KV |
| Вычисления | Сколько запросов завершается вовремя и окупаются ли chunking, graphs и черновик |
| Размещение | Какая часть GPU действительно нужна сервисам поиска |
| Автоматизация | Воспроизводит ли платформа проверенный запуск и показывает ли причины размещения |

Новые карты нужны, когда измеренное ограничение осталось после выбора подходящей конфигурации, а не просто потому, что в чате долго крутится индикатор ожидания.
