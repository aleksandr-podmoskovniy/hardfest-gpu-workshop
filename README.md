# Инференс без простоя GPU: чиним LLM-сервис руками и делим карту на живом кластере

Александр Подмосковный, Флант / Deckhouse Platform

Вариант стенда: **две H100 для Gemma 4 31B и Qwen, A30 для небольших моделей**.

<a id="ab"></a>
## 1. Базовая модель под нагрузкой

Исходное состояние — подготовленный стенд: **Gemma A — Base** на одной H100 отвечает
в [Open WebUI](https://ai.ap4y.ru). После регистрации и одобрения аккаунта
личный доступ выдаётся автоматически.

**LLM (Large Language Model)** — большая языковая модель.
Её запуск для обработки запросов называется **инференсом**.
Здесь модель работает на **GPU (Graphics Processing Unit)** — графическом процессоре.
Текст разбивается на **токены**: части слов, слова и знаки.

<a id="chat"></a>
Начальная проверка — законченный ответ в чате. Затем фиксированная нагрузка
покажет, где возникает ограничение. Дальше у второго экземпляра той же модели
последовательно меняются настройки — и сравниваются ответы и графики.

<a id="monitoring"></a>
### Что фиксируется под нагрузкой

Дашборд **AI Inference / Service performance**: namespace `hardfest-demo`,
Service `hf-gemma-a`, интервал контрольной серии.

| Показатель | Что означает |
| --- | --- |
| Running / Waiting | Выполняемые запросы и очередь |
| Использованная память GPU | Веса, состояние запросов и рабочие буферы |
| GPU utilization | Доля времени выполнения GPU-операций |

Занятая память не равна занятым вычислениям. Очередь тоже не указывает
на единственную причину: запросам может не хватать **памяти**,
вычислительного времени или подходящего **размещения**.
Эти три ограничения разбираются по очереди.

Например, очередь вместе с вытеснениями запросов из KV-пула ведёт к проверке
памяти. Если вытеснений нет, но генерация медленная, важнее время вычислений.
Один график не ставит диагноз: **очередь показывает симптом, остальные метрики
помогают проверить причину**.

### Одинаковая нагрузка для A и B

A сохраняет исходные настройки. У B последовательно меняются кеширование
и вычисления. Контрольное окно — **16K**, серия — **8 запросов по 8192 входных
и 2048 выходных токенов, 4 одновременно**. Длинный контекст проверяется отдельно.

**Во время замера свободные запросы в чат приостановлены.**
Для A/B используются одни веса, запросы и условия.

<details>
<summary>Исходный профиль и команда контрольной серии</summary>

A запускается через Helm: чарт превращает настройки в объекты Kubernetes.
Сервер модели — **vLLM 0.31**. В [профиле A](values/gemma-a.yaml) выключены
prefix cache, KV-offload, chunked prefill, CUDA graphs и speculative decoding.
Без chunked prefill большой рабочий буфер ограничивает окно A: 16 384 токена.

Application `hardfest-gemma-a` уже применён при подготовке.
Команда выполняется из частного `k8s-config`; контексты и пути заданы
в [подготовке](docs/SETUP.md). `SLOT` выбирает сервис, `SERIES` — имя результата.

```bash
export SLOT=a SERIES=a-base-1
# B1: export SLOT=b SERIES=b-cache-1
# B2: export SLOT=b SERIES=b-spec-1
export TOKENIZER_PATH=/data/modelcache/models/gemma-4-31b
mkdir -p "results/hardfest/$SERIES"
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec "deployment/hf-gemma-$SLOT" -- \
  vllm bench serve --backend vllm \
    --base-url "http://hf-gemma-$SLOT.hardfest-demo.svc.cluster.local:8000" \
    --endpoint /v1/completions --model gemma-4-31b --tokenizer "$TOKENIZER_PATH" \
    --dataset-name random --seed 42 \
    --random-input-len 8192 --random-output-len 2048 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 4 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/hardfest/$SERIES/bench.txt"
```

Успешная серия: `failed=0`, `completed=8`,
`total_input_tokens=65536`, `total_output_tokens=16384`.
Первый проход и повтор сохраняются отдельно: одинаковый seed прогревает кеш B.
Для итогового сравнения нужен отдельный клиент:
команда выше делит с моделью **CPU (Central Processing Unit)** — процессор узла.

</details>

<a id="memory"></a>
## 2. Память: веса и KV-кеш

**VRAM (Video Random Access Memory)** — память GPU.
Её занимают три разных компонента:

- **Веса** — выученные параметры, общие для всех запросов экземпляра модели.
- **KV (Key–Value) cache** — ключи и значения уже обработанных токенов.
- **Буферы** — промежуточные данные вычислений.

KV нужен, чтобы следующий токен использовал состояние прошлой истории,
не вычисляя его заново. Это **не кеш готовых ответов**.
Чем длиннее независимые истории, тем больше памяти они требуют.

### Почему нет одной цены токена в памяти

**Attention** — механизм, которым модель связывает текущий токен с контекстом.
У слоя с **full attention** KV растёт со всей историей. У **sliding-window
attention** сохраняется только последнее окно. В одной модели эти слои
могут чередоваться; другие архитектуры ещё и делят KV между слоями.

Поэтому правило «на токен нужно столько-то байт» выводится из конкретной
модели. У Gemma можно отдельно посчитать растущую и ограниченную части.

### Реальный расчёт для Gemma 4 31B

В этой архитектуре 10 слоёв хранят полную историю, 50 — последние 1024 токена.
**1024 — локальное окно части слоёв, а не предел запроса.**

Для одной истории в **BF16 (Brain Floating Point 16)** — два байта на элемент:

**`KV ≈ 80 KiB × S + 0,78125 GiB`**, при `S ≥ 1024`.

`S` включает вход и уже сгенерированный ответ.
В **FP8 (8-bit Floating Point)** элемент занимает один байт: полезный KV вдвое меньше,
но веса модели не меняются.

| Контекст | 1 история, BF16 | N=8, BF16 | N=8, FP8 |
| --- | ---: | ---: | ---: |
| **128K = 131 072** | 10,78125 GiB | **86,25 GiB** | **43,125 GiB** |
| **256K = 262 144** | 20,78125 GiB | **166,25 GiB** | **83,125 GiB** |

`N` — число независимых историй; в таблице их восемь. Общие кешированные блоки префикса
не нужно умножать на восемь. В таблице нет весов и рабочих буферов;
она не обещает восемь полных окон одновременно.

<details>
<summary>Вывод формулы из архитектуры и расчёт командой awk</summary>

Attention-головы — параллельные части этого механизма. В **GQA
(Grouped-Query Attention)** несколько голов используют общие K/V.
Память определяется числом KV-голов `Hkv`, их размерностью `D`,
числом слоёв, длиной истории `S` и байтами элемента `b`.
Множитель 2 учитывает отдельно ключи и значения.

Параметры Gemma взяты из
[закреплённого config.json](https://huggingface.co/google/gemma-4-31B-it/blob/842da3794eaa0b77d5f08bae87a17459d91ff475/config.json):

| Attention | Слоёв | Hkv | D | Сохранённых токенов |
| --- | ---: | ---: | ---: | --- |
| Full | 10 | 4 | 512 | `S` |
| Sliding | 50 | 16 | 256 | `min(S, 1024)` |

```text
KV(S) = 2 × b × [10 × 4 × 512 × S + 50 × 16 × 256 × min(S, 1024)] байт
```

В BF16 полная часть даёт `2 × 2 × 10 × 4 × 512 = 80 KiB` на токен,
скользящая — `2 × 2 × 50 × 16 × 256 × 1024 = 0,78125 GiB`.
При росте 128K → 256K удваивается только полная часть.

```bash
awk -v S=131072 -v N=8 -v b=2 'BEGIN {
  W = S < 1024 ? S : 1024
  full = 2*b*10*4*512*S / 1073741824
  local = 2*b*50*16*256*W / 1073741824
  printf "Full %.5f + sliding %.5f = %.5f GiB/history; %d histories = %.5f GiB\n", full, local, full+local, N, N*(full+local)
}'
```

Для 256K меняется `S=262144`, для FP8 — `b=1`.
Формат хранения: [реализация vLLM 0.31](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/gemma4.py).

Реальная вместимость ограничена пулом:
`Kpool ≈ G × u − W − R`, где `G` — память GPU, `u` — доля для движка,
`W` — веса, `R` — буферы и резервы.
Пул резервируется заранее; его размер и занятые блоки важнее общей цифры
`nvidia-smi`. [Проверка памяти](docs/MEMORY_BUDGET.md#verify-kv).

</details>

<a id="ram"></a>
### B Cache: не пересчитывать одинаковое начало

**Prefix caching** переиспользует KV совпадающих начальных токенов.
Новый вопрос в конце документа сохраняет общий префикс; изменение начала сокращает его.
**RAM (Random Access Memory)** — оперативная память узла.
**KV RAM offload** сохраняет вытесненные блоки там и возвращает их на GPU.
Веса и активные вычисления остаются на карте.

B Cache сохраняет окно 16K и добавляет prefix cache, FP8 KV и **32 GiB RAM**
для KV. Остальные оптимизации пока выключены. После применения профиля
маршрут **Gemma B — Tune** указывает на эту первую конфигурацию B.

**На узле со 128 GiB сначала A останавливается через Git/Argo; профили выполняются
последовательно.** Перед остановкой отключается её маршрут и завершаются запросы.
Одновременный запуск требует достаточного
[бюджета RAM](docs/MEMORY_BUDGET.md#ram-выбрать-порядок-запуска).

<details>
<summary>Запуск B Cache через Git и Argo CD</summary>

Рабочий файл — `$DEMO_DIR/values/gemma-b.yaml`, включение — `replicaCount: 1`.
Профиль используется целиком, поверх него — только привязки площадки.
В нём задан Triton attention и CPU KV-пул:

```yaml
kv-transfer-config:
  kv_connector: OffloadingConnector
  kv_role: kv_both
  kv_connector_extra_config:
    cpu_bytes_to_use: 34359738368
```

Проверка рендера и API-схемы:

```bash
set -o pipefail
helm template hf-gemma-b "$DEMO_DIR/charts/vllm-runtime" -n hardfest-demo \
  -f "$DEMO_DIR/values/gemma-b.yaml" -f "$DEMO_DIR/site/gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После успешной проверки:

```bash
git add -- "$DEMO_DIR/values/gemma-b.yaml"
git diff --cached --check
git diff --cached
git commit -S -s -m "Start Gemma with prefix cache and RAM KV"
git push
git rev-parse HEAD
```

У `hardfest-gemma-b` проверяется diff и выполняется Sync напечатанного коммита
**без общего Prune**. Только после готовности и ответа модели включается маршрут
**Gemma B — Tune**; сейчас он указывает на B Cache.
Дальнейшие изменения проходят тот же путь Git → render → commit/push → Argo.
[GitOps](docs/GITOPS.md).

</details>

### Что должно измениться на графиках

Два новых чата B получают одинаковый текст документа прямо в сообщении,
но разные вопросы в конце. Вложения и база знаний здесь не используются:
поиск фрагментов меняет префикс.

**TTFT (Time To First Token)** — время до первого токена.
Сопоставление TTFT и **prefix-cache hit rate** — доли попаданий —
показывает эффект повторного использования. Для A/B повторяется контрольная серия,
а не произвольные вопросы.

Offload проверяется отдельно: после вытеснения префикса из GPU запрос повторяется.
`GPU→CPU` означает сохранение, `CPU→GPU` вместе с external-prefix hits —
возврат из RAM. Выделенные 32 GiB сами по себе переносов не доказывают.
[Готовый опыт вытеснения и повтора](docs/MEASUREMENTS.md#offload-replay)
задаёт размер тестового GPU-пула, последовательность запросов и возврат настроек.
[Prefix caching](https://docs.vllm.ai/en/v0.31.0/features/automatic_prefix_caching/),
[KV-offload](https://docs.vllm.ai/en/v0.31.0/features/kv_offloading_usage/).

<a id="speculation"></a>
## 3. Вычисления: prefill и decode

Кеш помогает со знакомым текстом. Новый вход всё равно нужно обработать,
а продолжение — сгенерировать. У этих фаз разная стоимость.

<a id="latency"></a>
### Две фазы одного запроса

**Prefill** обрабатывает вход и строит KV; **decode** последовательно выдаёт токены.
Перед ними запрос может ждать в очереди:

`Время ответа ≈ очередь + prefill + decode + прочие задержки`.

![Очередь, обработка входа и генерация образуют время ответа](assets/02-latency.svg)

TTFT отражает ожидание начала. **ITL (Inter-Token Latency)** — интервал между
токенами, **TPOT (Time Per Output Token)** — среднее время выходного токена
после первого. Рассуждения модели (**reasoning**) тоже относятся к decode:
первые слова финального ответа могут появиться позже первого токена движка.

### Chunked prefill: не занимать исполнение всем входом

Длинный prefill может задерживать соседние запросы.
**Chunked prefill** обрабатывает вход порциями; между ними движок продолжает
decode начатых ответов. Меньшая порция даёт больше таких возможностей,
но требует больше шагов обработки входа.

![Порции prefill чередуются с decode](assets/06-scheduler.svg)

Исходная смешанная серия выполняется ещё на B Cache: вход **8192 токена**,
через **50 мс** — вход **128 токенов**, у обоих выход 512. Затем ровно эта пара
повторяется на Tune в том же окне 16K.
[Один клиент с фиксированным расписанием](docs/MEASUREMENTS.md#mixed-prefill)
сохраняет реальные времена: если запросы не перекрылись, опыт не показал конкуренцию.

### Speculative decoding: дешевле предложить и проверить

Небольшой **draft** предлагает токены, основная модель — **target** —
проверяет продолжение. Непринятый хвост не попадает в ответ.

![Draft предлагает продолжение, target проверяет его](assets/07-speculation.svg)

У Gemma используется совместимый assistant с **MTP (Multi-Token Prediction)** —
предсказанием следующих токенов. Произвольная маленькая модель его не заменяет.
Выигрыш зависит от стоимости предложения и проверки, а не только от
**acceptance** — доли принятых токенов.
[Gemma assistant и MTP](https://docs.vllm.ai/en/v0.31.0/features/speculative_decoding/mtp/).

### B Tune: тот же контроль, полный набор настроек

Tune сохраняет prefix cache, FP8 KV и 32 GiB RAM, добавляя chunked prefill
с бюджетом шага **`max-num-batched-tokens: 2048`**, assistant и **CUDA graphs** —
переиспользуемые последовательности GPU-операций.

**Перед заменой маршрут B отключается, запросы завершаются, B останавливается.**
Две B одновременно не запускаются; настройки A не меняются.

<details>
<summary>Замена Cache на Tune и подключение assistant</summary>

1. В рабочем `gemma-b.yaml`: `replicaCount: 0`, commit/push и Sync;
   продолжение только после остановки Pod.
2. Замена профиля целиком:

```bash
cp "$DEMO_DIR/values/gemma-b-spec.yaml" "$DEMO_DIR/values/gemma-b.yaml"
```

3. `replicaCount: 1`; второй `valueFiles` Application B —
   `../../site/gemma-assistant.yaml`. Он подключает модель и assistant из ai-models.
4. Render с этим site-файлом, commit/push обоих изменённых файлов,
   Sync того же Application. При App-of-Apps сначала обновляется родитель.
5. Проверка параметров и загрузки обеих моделей; после успешного ответа
   возвращается маршрут **Gemma B — Tune**.

</details>

На Tune повторяются смешанная серия и контрольный A/B без фоновых запросов.
Сравниваются TTFT короткого запроса, ITL, выходные токены/с и ошибки.
Это эффект всего профиля; отдельный вклад MTP требует изменения только MTP.

При нескольких исполнителях есть ещё два подхода, не включённые в стенд:
[cache-aware routing](https://docs.dynamo.nvidia.com/dynamo/knowledge-base/concepts/system-architecture/kv-aware-routing)
направляет запрос к сохранённому префиксу;
[prefill/decode disaggregation](https://docs.vllm.ai/en/v0.31.0/features/disagg_prefill/)
разносит фазы, передавая между ними KV.

<a id="long-context"></a>
### Расширение окна до 128K

Теперь меняется только окно B; короткий A/B остаётся отдельным измерением.

| Окно | Вход | Выход | Запросов / одновременно |
| --- | ---: | ---: | ---: |
| 64K | 57 344 | 512 | 1 / 1 |
| 128K | 122 880 | 512 | 1 / 1 |

**Окно включает весь вход и выход**, в том числе системный текст и рассуждения.
`max-num-seqs` ограничивает число активных последовательностей,
а доступный KV — их суммарную длину. Восемь клиентов не равны восьми полным окнам.

<details>
<summary>Изменение окна и проверка фактических длин</summary>

В Tune сначала задаётся `max-model-len: 65536`, затем `131072`:

```yaml
vllm:
  max-model-len: 131072
```

После каждого изменения — render, commit/push, Sync и готовность.
В команде раздела 1 вход/выход заменяются по таблице;
обязательно `--num-prompts 1 --max-concurrency 1` и отдельное имя серии.
Критерии: `completed=1`, `failed=0`, заданные длины, без ошибок памяти.

В 128K арифметически входят `122 880 + 8192` токена, но серия проверяет
только 512 выходных. Лимит ответа WebUI настраивается отдельно.
B остаётся на 128K; для нового A/B с A требуется возврат к `16384`.
**256K в расчёте памяти — не результат этого запуска.**

</details>

<a id="placement"></a>
## 4. Размещение моделей на GPU

Даже настроенная модель может не использовать целую карту.
Для небольших сервисов полезнее совместное размещение, чем отдельная GPU каждому.

### Device plugin и DRA

**Device plugin** публикует целочисленный ресурс: `nvidia.com/gpu: 1`
означает одну единицу. Память и режим разделения этим числом не описаны;
поддержка MIG/sharing требует дополнительных ресурсов и настроек плагина.

**DRA (Dynamic Resource Allocation)** добавляет выбор по атрибутам,
заявку **ResourceClaim** и настройку устройства для нагрузки.
Доступные режимы всё равно зависят от оборудования и драйвера.

[Device plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/),
[DRA](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/),
[авторский разбор](https://habr.com/ru/companies/flant/articles/1020276/).

### MIG и MPS на A30

**MIG (Multi-Instance GPU)** аппаратно разделяет память и вычисления карты.
**MPS (Multi-Process Service)** позволяет процессам совместно выполнять работу
внутри выделенной части; он не добавляет память и не заменяет изоляцию MIG.

Здесь проверяются **уже подготовленные сервисы A30**, без изменения геометрии.
Gemma на H100 продолжает работать. [Создание заказов](#a30-orders) разобрано позже.

| Сервис | Назначение | Размещение |
| --- | --- | --- |
| Qwen3 Embedding 4B W4A16 | Векторы текста для поиска | Первая `2g.12gb` |
| Qwen3 Reranker 4B W4A16 | Оценка найденных фрагментов | Та же часть через MPS |
| Whisper large-v3 | Речь в текст | Вторая `2g.12gb` |

W4A16 означает 4-битные веса и 16-битные активации.
`2g.12gb` — профиль именно A30.

![Эмбеддер и реранкер делят часть через MPS, Whisper занимает другую](assets/08-mig-mps.svg)

**Метрики и команды относятся к кластеру A30.** На его ноде:

```bash
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

<details>
<summary>Какая модель получила какую часть, и используется ли MPS</summary>

Список частей ещё не связывает их с моделями. Сначала выбирается Pod
эмбеддера, затем та же проверка повторяется для реранкера и Whisper:

```bash
kubectl --context "$MIG_CONTEXT" -n hardfest-demo get pods -o wide
export A30_POD=REPLACE_EMBEDDING_POD
kubectl --context "$MIG_CONTEXT" -n hardfest-demo get pod "$A30_POD" \
  -o jsonpath='{.spec.resourceClaims}{"\n"}{.status.resourceClaimStatuses}{"\n"}'
export A30_CLAIM=REPLACE_ALLOCATED_CLAIM
kubectl --context "$MIG_CONTEXT" -n hardfest-demo get resourceclaim "$A30_CLAIM" \
  -o jsonpath='{.status.allocation.devices}{"\n"}'
kubectl --context "$MIG_CONTEXT" -n hardfest-demo exec "$A30_POD" \
  -c REPLACE_RUNTIME_CONTAINER -- nvidia-smi -L
```

Заявка показывает выделенное устройство и конфигурацию драйвера.
Идентификатор устройства сопоставляется с MIG UUID — постоянным идентификатором
части — в данных драйвера и `nvidia-smi`. Имя DeviceClass само по себе не доказательство.

Фактических MPS-клиентов показывает управляющий процесс MPS на A30.
В его контейнере, с его `CUDA_MPS_PIPE_DIRECTORY`, доступны read-only команды
[интерфейса MPS v2](https://docs.nvidia.com/deploy/mps/mpsv2-interface.html):

```bash
printf 'get_server_list\n' | nvidia-cuda-mps-control
# PID берётся из предыдущего ответа, не PID процесса внутри runtime-контейнера.
export MPS_SERVER_PID=REPLACE_SERVER_PID
printf 'get_client_list %s\n' "$MPS_SERVER_PID" | nvidia-cuda-mps-control
```

Подключённые процессы сверяются с эмбеддером и реранкером в логах драйвера.
Если список клиентов недоступен, подтверждена геометрия и заявленный режим,
но не фактическое использование MPS. Новый MPS-сервер ради проверки не запускается.

</details>

Эмбеддер и реранкер должны иметь один MIG ID, Whisper — другой.
Отдельная и совместная нагрузка сравнивается по задержкам, ошибкам и памяти части.
График MIG не разделяет вклад MPS-процессов.

### Поиск по документу и голосовой ввод

**RAG (Retrieval-Augmented Generation)** добавляет найденные фрагменты
к входу языковой модели. Эмбеддер кодирует текст в векторы, индекс выполняет поиск,
реранкер уточняет выбор; Gemma формулирует ответ. Веса модели не меняются.

Контрольный документ: «В проекте “Липа” обслуживание начинается во вторник в 16:40».
После индексации база знаний подключается к чату. Один вопрос проверяется
с базой и без неё: нужен верный факт, ссылка и обращения к обоим сервисам.
Голосовой вариант проверяет транскрипцию Whisper, не синтез речи.

Метрики здесь — запросы, задержки и ошибки, не выходные чат-токены.
Смена Gemma на Qwen сохраняет индекс; смена эмбеддера может потребовать переиндексации.

<a id="platform"></a>
## 5. Автоматический запуск через AI Inference

Ручная настройка связывает архитектуру модели, память, вычисления и размещение.
**AI Inference** переносит этот подбор в планировщик.
**InferenceService** — заказ с моделью и требованиями; планировщик сопоставляет
их с оборудованием и **рецептами** — совместимыми конфигурациями runtime.

![Модель, требования, устройства и рецепты определяют план запуска](assets/09-platform.svg)

Пользовательский путь начинается в каталоге **ai-models**:
скачанная модель → **«Запустить инференс»** → стратегия и доступные ресурсы →
расчёт плана → сервис в интерфейсе.
Ниже тот же заказ хранится в Git и применяется Argo CD; создавать его второй раз не нужно.

### Та же Gemma вместо A

Цель — воспроизвести настройки ручной B, а не получить ускорение от смены способа запуска.

**До остановки A проверяется рецепт:** те же веса, 128K, FP8 KV, RAM-offload,
assistant и параметры выполнения. Для двух настроенных экземпляров требуется
не менее **192 GiB RAM** с проверенным распределением.
На 128 GiB B тоже останавливается после сохранения результата.
Для этого до остановки выполняется режим `BENCH_TARGET=manual`
[общего клиента](#gemma-compare); после запуска новой Gemma — `platform`.

Маршрут A отключается, текущие запросы завершаются. В профиле A задаётся
`replicaCount: 0`, затем commit/push и Sync его Application.
Следующий запуск — после исчезновения Pod A и освобождения её GPU-заявки.
После запуска и проверки ответа новая Gemma получает подпись **Gemma A — DP**.
DP здесь — обозначение платформенного запуска, не Data Parallelism.

<details>
<summary>Заказ Gemma и проверка ответа API</summary>

В `$DEMO_DIR/platform/gemma.yaml` задаётся `order.enabled: true`.
В отличие от справочного рецепта 64K, выбранный рецепт должен включать
нужные окно, CPU KV и assistant.
[Проверка поставки](docs/SETUP.md#inference-readiness).

```bash
set -o pipefail
helm template hf-platform-gemma "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

Далее commit/push и Sync `hardfest-gemma-platform`; сервис — `hf-platform-gemma`.
После Ready проверяется **API (Application Programming Interface)** —
программный интерфейс, затем чат.

В отдельном терминале:

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get service hf-platform-gemma
kubectl --context "$GPU_CONTEXT" -n hardfest-demo port-forward svc/hf-platform-gemma 18005:80
```

Порт 80 заменяется фактическим, если Service публикует другой.
Ключ вводится из менеджера секретов в основном терминале:

```bash
set +x
IFS= read -r -s MODEL_API_KEY
curl --fail --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  http://127.0.0.1:18005/v1/models
```

В `model` подставляется ID из `/v1/models`:

```bash
curl --fail-with-body --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  -H 'Content-Type: application/json' http://127.0.0.1:18005/v1/chat/completions \
  -d '{"model":"REPLACE_SERVED_MODEL_ID","max_tokens":512,"temperature":0,"messages":[{"role":"user","content":"Зачем нужен KV-кеш?"}]}'
unset MODEL_API_KEY
```

Нужен законченный ответ без ошибки; затем port-forward закрывается.
Ключ не сохраняется в Git и не включается в аргументы curl.
Для Qwen используются его Service, порт, ID и ключ.

</details>

Сравнение с B использует одинаковые запросы, окно и настройки:
TTFT, ITL, выходные токены/с, ошибки. Готовый план не заменяет ответа модели.

<a id="gemma-compare"></a>
<details>
<summary>Парный замер ручной Tune и автоматической Gemma одним клиентом</summary>

[Готовый CPU Job](examples/gemma-benchmark-job.yaml) последовательно обращается
к двум сервисам с одним токенизатором: по 8 запросов, вход 8192, выход 2048,
параллельность 4. Для каждого сохраняются **первый проход и повтор**.
Это прямой API, без задержек WebUI и шлюза.

Копия готовится вне каталога runtime, из корня частного `k8s-config`:

```bash
export BENCH_DIR="$(mktemp -d)"
cp ../hardfest-gpu-workshop/examples/gemma-benchmark-job.yaml "$BENCH_DIR/job.yaml"
```

В редакторе задаются CPU-нода, ID платформенной модели из
`/v1/models` и ссылки на существующие Secrets в `hardfest-demo`.
`HF_TOKEN` нужен для токенизатора закрытого репозитория Gemma, не для загрузки весов.
У ручного runtime без авторизации optional-ссылка может оставаться на
отсутствующий `replace-manual-runtime-api-secret`. Для выбранной платформенной
цели ключ обязателен, даже если сама ссылка помечена optional для одиночного режима.
Сами ключи в YAML не записываются.

Обе модели должны иметь одинаковые окно 128K и полный профиль Tune.
Режим выбирается полем `env` → `BENCH_TARGET`:

| Режим | Когда используется |
| --- | --- |
| `both` | Обе модели Ready и помещаются на узле; все четыре серии за один запуск |
| `manual` → `platform` | На 128 GiB: два отдельных Job, между ними переключение моделей через GitOps |

В одиночном режиме невыбранная модель и её ключ не требуются.
Клиентской CPU-ноде нужен доступ к выбранным Service. После проверки
каждая копия получает уникальное имя Job и `spec.suspend: false`:

```bash
kubectl --context "$GPU_CONTEXT" create --dry-run=server -f "$BENCH_DIR/job.yaml"
kubectl --context "$GPU_CONTEXT" create -f "$BENCH_DIR/job.yaml"
export BENCH_JOB=gemma-benchmark
kubectl --context "$GPU_CONTEXT" -n hardfest-demo logs -f "job/$BENCH_JOB" \
  --pod-running-timeout=5m | tee "$BENCH_DIR/benchmark.log"
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get job "$BENCH_JOB"
```

`BENCH_JOB` совпадает с выбранным именем. Job не меняет runtime и не запрашивает GPU.
Он завершается ошибкой при неполных сериях. В сумме должны сохраниться четыре блока
`RESULT_JSON_BEGIN` / `RESULT_JSON_END` (по два на цель), у каждого — 8 успешных запросов,
65 536 входных и 16 384 выходных токена. Результаты сохраняются до удаления
Job по TTL (Time to Live — срок хранения), через сутки.

Первый проход не обязательно холодный: серверный кеш не сбрасывается.
Сравниваются отдельно первые проходы и повторы, не первый одной модели с
повтором другой. Для оценки разброса серия повторяется трижды с новыми именами Job.
При последовательном запуске CPU-нода, токенизатор, длины и параллельность не меняются.

</details>

### Когда нужна ещё одна карта

Сначала уменьшаются повторные вычисления, стоимость генерации и потери

с полными ответами и расходом ресурсов.

<a id="results"></a>
## 6. Шлюз и модель на двух GPU

### Запрос, пользователь и расход

**ai-mcp-gateway** на базе Bifrost связывает маршрут, модель, токены и стоимость.
**VK (Virtual Key)** — личный ключ с доступами и лимитами —
создаётся после одобрения пользователя.

Контроль — запросы двух аккаунтов: разные VK и правильные владельцы в журнале.
Ключ подключения шлюза к vLLM не заменяет личный VK.
При смене модели доступы и накопленный расход сохраняются.

**Стоимость условная, списаний нет.** Учитываются фактические токены,
а не весь настроенный контекст. [Выдача доступа, тарифы и ограничения учёта](docs/CHAT_AND_ACCESS.md).

<a id="topology"></a>
Чат обращается к шлюзу, шлюз — к нужному сервису; Argo доставляет конфигурацию,
но не обрабатывает сообщения. [Полная схема стенда](assets/01-topology.svg).

<a id="tp2"></a>
### Qwen с Tensor Parallelism

Последний запуск решает обратную задачу: одна модель использует две GPU.
Целевая модель — **nvidia/Qwen3.8-Flash-Next-NVFP4**.
**TP (Tensor Parallelism)** делит её тензорные вычисления между картами.
**TP2** — две участвующие GPU, не две копии модели и не TensorRT;
сервер остаётся vLLM.

![Одна модель разделена между двумя GPU](assets/10-tp2.svg)

Ориентир — [профиль Qwen](values/qwen-tp2.yaml): `max-model-len: 262144`,
`max-num-seqs: 16`, **16 GiB RAM для KV**. Выбранный рецепт должен воспроизводить
нужные параметры; указание модели и стратегии само по себе их не гарантирует.

**До остановки Gemma проверяются веса Qwen, runtime, рецепт и класс устройств.**
Затем отключаются маршруты Gemma, завершаются запросы и освобождаются обе H100.
Сервисы A30 и чат продолжают работать.

**Удаление платформенной Gemma требует адресного Prune только её заказа
после просмотра diff.** Обычного Sync недостаточно.
Model, PVC (PersistentVolumeClaim — заявка хранилища) и чужие нагрузки сохраняются.

<details>
<summary>Освобождение карт и запуск Qwen</summary>

Ручная B: `replicaCount: 0`; платформенная Gemma: `order.enabled: false`.
После применения через Git/Argo и адресного Prune обе карты должны быть свободны.

В `$DEMO_DIR/platform/qwen.yaml` включается `order.enabled: true`:

```bash
set -o pipefail
helm template hf-qwen-platform "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/qwen.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

Далее commit/push и Sync `hardfest-qwen-platform`.
План должен содержать `acceleratorCount=2`, ResourceClaim — две разные GPU одной ноды,
Pod — `tensor-parallel-size: 2`.
После проверки API по разделу 5 включается **Qwen — TP2** для действующих VK,
без сброса расхода.

У Qwen встроенный MTP; отдельная Gemma assistant не нужна.
Её native KV-offload использует Simple CPU backend,
не конфигурацию Gemma OffloadingConnector.

</details>

Короткие серии используют 8192 входных и 512 выходных токенов,
сначала 1, затем 4 и **8 одновременных запросов**.
Длинная серия — отдельно **один запрос: 122 880 входных + до 8192 выходных токенов**
в пределах 128K. Она проверяет длинный вход, но не заполняет всё окно 256K.
Running/Waiting, занятый KV, фактическая длина и законченный ответ показывают результат.
Восемь обслуженных клиентов не доказывают восемь полных окон одновременно;
наличие NVLink — межкарточного соединения — не заменяет измерения скорости обмена.

Для этих серий предназначен [отдельный CPU-клиент](examples/qwen-benchmark-job.yaml).
При [подготовке](docs/SETUP.md) ему задаются нода, адрес сервиса, авторизация
и длины из этого раздела; до проверки параметров Job остаётся `suspend: true`.

<a id="cleanup"></a>
## Остановка

Сначала отключаются маршруты и завершаются текущие запросы.
Затем ручным профилям задаётся `replicaCount: 0`, заказам — `order.enabled: false`;
изменения применяются через Git/Argo.
Удаление заказа — только адресным Prune по проверенному diff.

**Namespace, Model, PVC, GPUClass/GPUPool, чаты и базы знаний сохраняются.**
Завершение проверяется по отсутствию Pod нагрузки и освобождению заявок.
[Процедура остановки](docs/GITOPS.md#остановка).

## Подготовка и справка

К началу работы A и три сервиса A30 отвечают; B и заказы Gemma/Qwen подготовлены,
но выключены. Веса, маршруты, личный доступ и мониторинг проверяются заранее.

- [Подготовка узлов, переменных и A](docs/SETUP.md)
- [GitOps](docs/GITOPS.md), [ai-models](catalog/README.md), [мониторинг](docs/OBSERVABILITY.md)

Публичные профили по умолчанию выключены. NodeCache хранит веса;
контейнерный образ vLLM имеет отдельный кеш.
