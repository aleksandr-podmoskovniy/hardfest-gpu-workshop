# Инференс без простоя GPU: чиним LLM-сервис руками и делим карту на живом кластере

Александр Подмосковный, Флант / Deckhouse Platform

<a id="ab"></a>
## 1. Базовая модель под нагрузкой

Исходное условие: стенд подготовлен, **`Gemma A — Base` уже запущена**.
Чат доступен по адресу **[ai.ap4y.ru](https://ai.ap4y.ru)**;
личный доступ выдаётся автоматически после регистрации и одобрения аккаунта.

**LLM (Large Language Model)** — большая языковая модель; её работа над запросом
называется **инференсом**. Здесь вычисления выполняет **GPU (Graphics Processing Unit)** —
графический процессор.
Текст обрабатывается **токенами** — частями слов, словами или знаками.

Базовая конфигурация A нужна для сравнения с настроенной B.
Начальная проверка — законченный ответ в чате, затем серия одинаковых запросов
с известными длинами. При росте нагрузки фиксируются очередь, использование памяти
и занятость GPU: медленный ответ сам по себе ещё не указывает на причину.

<a id="chat"></a>
Доступ к чату не даёт прав на консоль кластера, графики и журналы Bifrost.
Изменения конфигурации требуют отдельного административного доступа.
Аккаунты и история сохраняются при переключении моделей.
Условные доллары в интерфейсе нужны для учёта — **реальных списаний нет**.

### Очередь, память и занятость GPU

Дашборды используют namespace `hardfest-demo`, Service `hf-gemma-a`
и один интервал контрольной серии.

| Показатель | Что можно установить |
| --- | --- |
| **Running / Waiting** — активные запросы и очередь | Сколько запросов выполняется, а сколько ждёт |
| Использованная память GPU | Сколько памяти заняли веса, состояние запросов и буферы |
| GPU utilization — занятость GPU | Как меняется вычислительная активность под нагрузкой |

Почти занятая память не означает, что вычисления загружены полностью.
Рост очереди также не доказывает, что нужна ещё одна карта:
запросам может не хватать памяти, вычислительного времени или подходящего размещения.

Дальнейшая настройка разделена на эти три ограничения:

1. **Память:** сколько занимает модель и контекст, что можно переиспользовать.
2. **Вычисления:** как обрабатывается вход и генерируется продолжение.
3. **Размещение:** когда сервису нужна целая карта, а когда достаточно её части.

### Контрольная нагрузка A/B

A сохраняет исходную конфигурацию, изменения применяются к B.
Короткое сравнение выполняется на **одинаковом окне 16K**:
8192 входных + 2048 выходных токенов, 8 запросов, 4 одновременно.
Результат A служит основой для сравнения с B Cache и B Tune.
Проверка длинного контекста — отдельная серия после настройки B.

**Контрольная серия выполняется без свободных запросов в чат.**
Посторонняя нагрузка меняет очередь и делает результаты несопоставимыми.

<details>
<summary>Профиль A и команда контрольного замера</summary>

A — ручной vLLM через Helm.
**vLLM** — сервер модели; Helm превращает настройки в объекты Kubernetes.
Исходная подготовка включает синхронизацию Application `hardfest-gemma-a`
в Argo CD; повторный запуск A не требуется.

Сервисные метрики доступны на дашборде **AI Inference / Service performance**.

В [профиле A](values/gemma-a.yaml) выключены prefix cache, chunked prefill,
CUDA graphs, KV-offload и speculative decoding. Все варианты используют vLLM 0.31.
Без chunked prefill требуется большой рабочий буфер, поэтому окно A — 16 384 токена.

![Одинаковые веса, запросы и предел 16K для сравнения ручных профилей](assets/04-ab.svg)

Команда выполняется из частного `k8s-config` с контекстами, заданными при подготовке.
`SLOT` определяет сервис, `SERIES` — отдельное имя результата:

```bash
export SLOT=a SERIES=a-base-1
# B1: export SLOT=b SERIES=b-cache-1
# B2: export SLOT=b SERIES=b-spec-1
export TOKENIZER_PATH=/data/modelcache/models/gemma-4-31b
mkdir -p "results/hardfest/$SERIES"
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec "deployment/hf-gemma-$SLOT" -- \
  vllm bench serve --backend vllm \
    --base-url "http://hf-gemma-$SLOT.hardfest-demo.svc.cluster.local:8000" \
    --endpoint /v1/completions --model gemma-4-31b --tokenizer "$TOKENIZER_PATH" \
    --dataset-name random --seed 42 \
    --random-input-len 8192 --random-output-len 2048 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 4 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/hardfest/$SERIES/bench.txt"
```

Критерии успешной серии в JSON-результате:

| Поле JSON | Значение |
| --- | --- |
| `failed` | `0` |
| `completed` | `8` |
| `total_input_tokens` | `65536` |
| `total_output_tokens` | `16384` |

Повтор seed — того же начального значения генератора нагрузки — прогревает
prefix cache. Первый проход и повтор сохраняются отдельно.

Клиент в Pod модели делит с ней **CPU (Central Processing Unit)** —
центральный процессор узла. Для итогового сравнения нужен клиент на отдельной CPU-ноде.

<a id="memory"></a>
## 2. Память: веса и KV-кеш

Первое ограничение — память. Веса занимают её независимо от числа запросов,
а сохранённая история растёт с длиной контекста и параллельностью.
При этом у запросов к одному документу часто совпадает начало:
его состояние можно переиспользовать вместо повторного расчёта.

**VRAM (Video Random Access Memory)** — память GPU;
**RAM (Random Access Memory)** — оперативная память узла.

| Что занимает VRAM | Почему меняется объём |
| --- | --- |
| **Веса** — выученные параметры | Общие для всех запросов одного экземпляра |
| **KV (Key–Value) cache** — ключи и значения обработанной истории | Больше независимых историй и токенов — больше сохранённого состояния |
| **Рабочие буферы** | Нужны для промежуточных вычислений и зависят от режима выполнения |

KV хранит **состояние истории, не готовый ответ**. При следующем шаге генерации
модель использует сохранённые K/V вместо повторного расчёта прошлого текста.

### Расчёт KV для 128K и 256K

У Gemma 4 31B одни слои сохраняют всю историю, другие — только последние
1024 токена. **1024 — внутреннее окно этих слоёв, а не длина нашего запроса.**

Для одной истории в **BF16 (Brain Floating Point 16)**,
где элемент KV занимает два байта:

**`KV ≈ 80 KiB × S + 0,78125 GiB`**, если `S ≥ 1024`.

Здесь `S` — весь вход **плюс** уже сгенерированный ответ.
В **FP8 (8-bit Floating Point)** элемент занимает один байт:
полезный KV вдвое меньше, веса от этого не меняются.

| Контекст одной истории | KV в BF16: 1 история | KV в BF16: N=8 | KV в FP8: N=8 |
| --- | ---: | ---: | ---: |
| **128K = 131 072 токена** | 10,78125 GiB | **86,25 GiB** | **43,125 GiB** |
| **256K = 262 144 токена** | 20,78125 GiB | **166,25 GiB** | **83,125 GiB** |

**N=8 — восемь независимых историй.** Если запросы разделяют кешированный префикс,
его общие блоки не нужно автоматически умножать на восемь.
В таблице такое разделение не учитывается.

Это ещё не вся память: нужны веса, буферы и вспомогательная модель.
Поэтому восемь подключённых пользователей не означают восемь полных окон одновременно.

При переходе со 128K на 256K растёт только полная история.
Скользящие слои уже достигли окна 1024, поэтому суммарный KV увеличивается менее чем вдвое.

<details>
<summary>От одного токена к формуле Gemma: архитектура, множители и awk</summary>

**Attention** сопоставляет текущий query Q с ключами K прошлых токенов,
а полученные коэффициенты задают взвешенную сумму значений V.
Q нужен для текущего шага; K/V сохраняются для следующих.

![Attention сохраняет ключи и значения обработанных токенов](assets/13-attention.svg)

Один слой выполняет несколько наборов attention-вычислений — **голов**.
В **GQA (Grouped-Query Attention)** несколько query-голов используют общие K/V.
Память определяется `num_key_value_heads`, не `num_attention_heads`.

![От K/V одного токена и слоя к памяти независимых историй](assets/25-kv-derivation.svg)

1. Два набора векторов одного токена: `2 × Hkv × D` элементов.
2. Объём умножается на байты `b` и число одинаковых слоёв `L`.
3. Длины `N` независимых историй суммируются.

```text
KV_bytes = 2 × L × Hkv × D × b × (S₁ + S₂ + … + Sₙ)
При одинаковой длине: KV_bytes = 2 × N × L × Hkv × D × S × b
```

| Символ | Значение |
| --- | --- |
| `Hkv`, `D` | KV-головы и размерность головы из конфигурации модели |
| `b` | Байты на элемент: BF16/FP16 — 2, FP8 — 1 |
| `S` | Вход и уже сгенерированные токены |
| `L` | Слои, хранящие собственные K/V |
| `N` | Число независимых историй |

BF16 (Brain Floating Point 16), FP16 (16-bit Floating Point) и FP8
(8-bit Floating Point) — форматы чисел. Точность KV выбирается отдельно от весов.

В [закреплённом config.json Gemma](https://huggingface.co/google/gemma-4-31B-it/blob/842da3794eaa0b77d5f08bae87a17459d91ff475/config.json)
параметры находятся в `text_config`:

| Тип слоя | Число | KV-головы | Размерность | Длина сохранённой истории |
| --- | ---: | ---: | ---: | --- |
| Full attention | 10 | 4 | 512 | `S` |
| Sliding attention | 50 | 16 | 256 | `min(S, 1024)` |

![Полная и скользящая части кеша Gemma считаются отдельно](assets/11-gemma-kv.svg)

Один full-слой в BF16: `2 × 4 × 512 × 2 = 8192 байта`.
Десять слоёв дают **80 KiB на токен**.
Один sliding-слой: `2 × 16 × 256 × 2 = 16 KiB`;
пятьдесят слоёв на окне 1024 занимают **0,78125 GiB**.

```text
KV(S) = 2 × b × [10 × 4 × 512 × S + 50 × 16 × 256 × min(S, 1024)] байт
```

```bash
awk -v S=131072 -v N=8 -v b=2 'BEGIN {
  W = S < 1024 ? S : 1024
  full = 2*b*10*4*512*S / 1073741824
  local = 2*b*50*16*256*W / 1073741824
  printf "Full %.5f + sliding %.5f = %.5f GiB/history; %d histories = %.5f GiB\n", full, local, full+local, N, N*(full+local)
}'
```

При 128K: `10 + 0,78125 = 10,78125 GiB` на историю.
При `S=262144` и `N=8` результат равен
`20 + 0,78125 = 20,78125 GiB` на историю и **166,25 GiB** на восемь.
Увеличилось только full-слагаемое; sliding уже достигло своего окна.
При `b=1` оба объёма уменьшаются вдвое.

Для контрольного окна 16K: `1,25 + 0,78125 = 2,03125 GiB`;
четыре полных истории — **8,125 GiB BF16**.

Флаг `attention_k_eq_v` не отменяет множитель 2 в выбранном runtime:
K/V хранятся отдельно после нормализации и RoPE (Rotary Position Embedding),
преобразования с учётом позиции токена.
[Реализация Gemma в vLLM 0.31](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/gemma4.py).

</details>

### Сколько памяти доступно запросам

После весов и буферов запросам доступна часть VRAM — **KV-пул**.
Сервер резервирует его заранее; размер публикуется в логах.
Общая занятость VRAM может не меняться, хотя внутри пула растёт число используемых блоков.

Серия из одного и четырёх запросов на A **в её окне 16K** показывает изменение
занятости KV-пула и очереди. Расчёт 128K/256K выше не описывает текущую нагрузку A;
длинные запросы проверяются после настройки B.

<details>
<summary>Пул, округление блоков и пример оценки вместимости</summary>

**`Kpool ≈ G × u − W − R`**.

`G` — память GPU, `u` — доля для движка, `W` — загруженные веса,
`R` — рабочие буферы и остальные резервы.

![Теоретический KV одной истории при 64K, 128K и 256K](assets/03-memory.svg)

Если в учебном примере `G=96 GiB`, `u=0,90`, `W=64 GiB`, `R=6 GiB`,
остаток равен **16,4 GiB**. Это не характеристика наших H100.

В остаток теоретически входят одна история 128K BF16
или три FP8 по 5,390625 GiB. Реальные блоки и резервы могут уменьшить вместимость.

При условном блоке на 16 токенов истории из 35 токенов нужны три блока;
последний заполнен частично. При совпадении первых 32 токенов два запроса
могут ссылаться на два общих полных блока.

16 — только учебный пример. У гибридной модели размеры и выравнивание
зависят от групп full/sliding attention и runtime.
После завершения запроса блоки могут оставаться в кеше до вытеснения.

Размер GPU KV-пула указан в логах. `nvidia-smi` показывает всю память процесса,
не только полезный KV. **Preemption** — вытеснение запроса из активной обработки
при нехватке ресурсов. [Команды проверки](docs/MEMORY_BUDGET.md#verify-kv).

</details>

<a id="ram"></a>
### Профиль B Cache: prefix caching и RAM offload

**Prefix caching** переиспользует KV одинакового начала запросов.
Нужны одинаковые **токены**, а не только похожий смысл.
Ответ на новый вопрос всё равно генерируется заново.

**KV RAM offload** добавляет второй уровень хранения: вытесненные блоки
можно сохранить в RAM и вернуть на GPU. Веса и активные вычисления остаются на GPU.

**Запуск B требует проверки RAM.** На виртуальной машине со 128 GiB
профили выполняются последовательно: сначала A останавливается через Git/Argo.
Одновременный запуск допускается только при достаточном [бюджете RAM](docs/MEMORY_BUDGET.md#ram-выбрать-порядок-запуска).

Первая конфигурация B — **B Cache**. После готовности сервиса и проверки ответа
его маршрут публикуется в WebUI под подписью **`Gemma B — Tune`**.

Окно остаётся 16K. Профиль включает prefix cache, FP8 KV и 32 GiB RAM для KV;
настройки обработки входа и генерации пока остаются исходными.

### Проверка общего префикса

Проверочная нагрузка на B Cache — два новых чата с одним и тем же буквальным
текстом документа в сообщении; меняется только вопрос в конце.
**Вложения и база знаний не используются:** поиск фрагментов может изменить
начало запроса. Отдельный запрос с изменённым началом служит контролем.

**Prefix-cache hit rate** — доля попаданий в кеш;
**TTFT (Time To First Token)** — время до первого токена.
Вместе они показывают, переиспользован ли общий префикс
и изменилось ли ожидание начала ответа.
Сравнение A/B использует контрольную серию из раздела 1 без посторонней нагрузки,
а не произвольные вопросы из чата.

<details>
<summary>Общий префикс, перенос в RAM и цена восстановления</summary>

![Общий префикс позволяет не пересчитывать одни и те же токены](assets/14-prefix.svg)

Новый вопрос в конце сохраняет общую часть; изменение начала сокращает её.
Первый запрос вычисляет префикс, последующий может переиспользовать блоки.
[Automatic Prefix Caching](https://docs.vllm.ai/en/v0.31.0/features/automatic_prefix_caching/).

![Блоки сохраняются в RAM и возвращаются при повторном обращении](assets/05-kv-ram.svg)

В первом профиле используется Triton attention — реализация attention-вычислений —
и такая конфигурация переноса:

```yaml
kv-transfer-config:
  kv_connector: OffloadingConnector
  kv_role: kv_both
  kv_connector_extra_config:
    cpu_bytes_to_use: 34359738368
```

`Tпереноса ≈ объём / эффективная полоса`.
Для полезного FP8 KV истории 128K пример:
`5,390625 GiB / 25 GiB/с ≈ 0,216 с`.

Это иллюстрация, не измеренная полоса стенда. Реальное время зависит от блоков,
синхронизации и конкуренции за RAM. Его сравнивают с повторной обработкой входа.
[Устройство CPU offload](https://docs.vllm.ai/en/v0.31.0/features/kv_offloading_usage/).

</details>

<details>
<summary>Конфигурация B Cache и применение через GitOps</summary>

Настройки хранятся в частном Git: это **GitOps**.
Argo CD применяет выбранную версию, не участвуя в обработке чат-сообщений.

![Git хранит настройки, Argo применяет выбранную версию в кластере](assets/12-gitops.svg)

В подготовленном `$DEMO_DIR/values/gemma-b.yaml` запуску соответствует
`replicaCount: 1`. Используется целый профиль B Cache: chunked prefill,
CUDA graphs и assistant в нём пока выключены.

```bash
set -o pipefail
helm template hf-gemma-b "$DEMO_DIR/charts/vllm-runtime" -n hardfest-demo \
  -f "$DEMO_DIR/values/gemma-b.yaml" -f "$DEMO_DIR/site/gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После успешной проверки:

```bash
git add -- "$DEMO_DIR/values/gemma-b.yaml"
git diff --cached --check
git diff --cached
git commit -S -s -m "Start Gemma with prefix cache and RAM KV"
git push
git rev-parse HEAD
```

После проверки diff Application `hardfest-gemma-b` синхронизируется
с напечатанным идентификатором коммита **без общего Prune**.
Маршрут в чат включается только после готовности Pod и ответа модели.

Порядок применения последующих изменений тот же:
изменение → render → commit/push → Sync нужного Application → ответ → чат.

</details>

### Проверка восстановления из RAM

Нагрузка последовательно обрабатывает несколько независимых префиксов,
затем повторяет первый после его вытеснения из GPU.
**CPU→GPU bytes — байты из RAM в GPU — и external-prefix hits — попадания
во внешний кеш** показывают восстановление; TTFT — его влияние на задержку.

Занятые 32 GiB RAM показывают только выделенный пул.
GPU→CPU подтверждает сохранение; CPU→GPU при повторном запросе — возврат блоков.
Быстрый ответ без возврата мог прийти из обычного GPU prefix cache.

<a id="speculation"></a>
## 3. Вычисления: prefill и decode

Кеш сокращает повторную работу со знакомым контекстом, но не устраняет вычисления.
Новый вход всё равно нужно обработать, а продолжение — сгенерировать.
Эти фазы создают разную нагрузку и требуют разных оптимизаций.

<a id="latency"></a>
### Из чего складывается время ответа

![Очередь, обработка входа и последовательная генерация складываются во время ответа](assets/02-latency.svg)

| Этап | Что делает модель |
| --- | --- |
| **Queue** | Ждёт возможности начать обработку |
| **Prefill** | Читает весь вход и подготавливает состояние истории |
| **Decode** | Генерирует продолжение шаг за шагом |

`Время ответа ≈ очередь + prefill + decode + прочие задержки`.

**TTFT** показывает время до первого токена,
**ITL (Inter-Token Latency)** — интервалы между следующими токенами.
Большой вход может увеличить TTFT, даже если финальный ответ короткий.
Высокий ITL указывает на медленное продолжение уже начатого ответа.

<details>
<summary>Рассуждение, скорость отдельного ответа и суммарные токены/с</summary>

Если модель рассуждает, reasoning-токены тоже генерируются на decode.
Поэтому первый токен движка и первые слова финального ответа в WebUI могут
появиться в разное время.

**TPOT (Time Per Output Token)** — среднее время на выходной токен после первого.
Суммарные output tokens/s всех запросов — производительность сервиса,
не скорость чтения одного ответа.

Prefill часто хорошо загружает вычисления. Decode при небольшом числе совместно
обрабатываемых запросов может упираться в чтение весов из памяти.
Высокая занятость GPU сама по себе не объясняет задержку.

В прочие задержки входят сеть, шлюз, токенизация и передача потока.
**p95** — порог, ниже которого находятся 95% измерений:
[методика измерений](docs/MEASUREMENTS.md).

</details>

### Chunked prefill: обработка входа порциями

Смешанная нагрузка содержит длинный вход и короткий запрос, отправленный
до завершения первого. Исходная серия выполняется **на B Cache в окне 16K**.
Тексты, параметры генерации и интервал между отправками фиксируются,
чтобы повторить нагрузку после изменения профиля.

TTFT короткого запроса, очередь и ITL уже начатого ответа показывают,
как обработка длинного входа влияет на соседние запросы.

**Chunked prefill** делит обработку большого входа на порции.
Между ними планировщик может продолжать decode уже начатых запросов.

![Порции длинного prefill чередуются с генерацией текущих ответов](assets/06-scheduler.svg)

Размер порции — компромисс: меньше порция даёт больше возможностей продолжить
соседний ответ, но требует больше шагов для обработки нового документа.

### Speculative decoding: предложение и проверка токенов

После prefill основная задержка может приходиться на последовательную генерацию.
Speculative decoding меняет способ выполнения этих шагов.

**Speculative decoding**: небольшой **draft** предлагает продолжение,
основная модель — **target** — проверяет его. Непринятый хвост предложений
не становится ответом.

![Вспомогательная модель предлагает токен, основная проверяет предложение](assets/07-speculation.svg)

У Gemma используется совместимый **assistant** с методом
**MTP (Multi-Token Prediction)** — предсказанием следующих токенов.
Произвольная маленькая модель вместо него не подходит.

Выигрыш возможен, если предложение и проверка обходятся дешевле обычной генерации.
Поэтому время decode оценивается вместе с долей принятых draft-токенов.

### Переход B Cache → B Tune

**Перед заменой B её маршрут отключается, текущие запросы завершаются,
затем B останавливается.** Одновременный запуск двух B не допускается;
настройки A остаются исходными.

Профиль Tune заменяет Cache целиком и подключает совместимый assistant.
После готовности и проверки ответа используется прежний маршрут **`Gemma B — Tune`**.

Tune сохраняет кеширование и добавляет chunked prefill, assistant и CUDA graphs —
переиспользуемые последовательности GPU-операций. **Это сравнение всего набора настроек.**

На Tune повторяются смешанная нагрузка с теми же запросами и интервалом,
затем короткая контрольная серия без фоновых запросов.
Сопоставляются TTFT соседнего запроса, ITL, общие выходные токены/с и ошибки.
Изменение всего профиля не доказывает вклад каждого отдельного механизма.

<details>
<summary>Что ограничивают три параметра и как читать эффект draft</summary>

| Настройка | Ограничение |
| --- | --- |
| `max-model-len` | Вся история: вход и генерация |
| `max-num-seqs` | Число последовательностей в работе |
| `max-num-batched-tokens` | Токены одного шага планировщика |

В `values/gemma-b-spec.yaml` порция prefill — **2048 токенов**.
Prefix cache, FP8 KV и CPU-пул **32 GiB** сохраняются.
CUDA graphs сокращают затраты на запуск операций, но сами тоже занимают память.

Средняя цена токена при speculation приблизительно равна:
`(время draft + время verification) / выданные токены за цикл`.

**Acceptance** — доля принятых предложений. Большая доля не гарантирует выигрыш,
если предложение и проверка дороги. Для отдельного вклада MTP нужен опыт,
меняющий только MTP, а не весь профиль B.
[Gemma assistant и MTP](https://docs.vllm.ai/en/v0.31.0/features/speculative_decoding/mtp/).

</details>

<details>
<summary>Замена профиля B и подключение assistant через GitOps</summary>

1. Остановка: `replicaCount: 0` в рабочем `gemma-b.yaml`,
   commit/push и Sync; следующий шаг — только после завершения Pod.
2. Замена профиля целиком:

```bash
cp "$DEMO_DIR/values/gemma-b-spec.yaml" "$DEMO_DIR/values/gemma-b.yaml"
```

3. Включение: `replicaCount: 1`.
4. Второй `valueFiles` Application B: `../../site/gemma-assistant.yaml`.
   Этот site-файл подключает основную модель и assistant из ai-models.
5. Проверка render и commit/push обоих изменённых файлов.
6. Sync того же Application B; проверка обеих моделей и параметров в Pod.
   Маршрут включается после успешного ответа.

При App-of-Apps сначала синхронизируется родитель; иначе обновляется подготовленный
манифест Application. [Порядок применения](docs/GITOPS.md).

</details>

### Дополнительные подходы при нескольких исполнителях

- **Cache-aware routing** направляет запрос к исполнителю, у которого уже есть
  нужный префикс. [Пример KV-aware routing в NVIDIA Dynamo](https://docs.dynamo.nvidia.com/dynamo/knowledge-base/concepts/system-architecture/kv-aware-routing).
- **Prefill/decode disaggregation** разносит обработку входа и генерацию
  между исполнителями; между ними передаётся KV.
  [Disaggregated prefilling в vLLM](https://docs.vllm.ai/en/v0.31.0/features/disagg_prefill/).

Эти подходы не разворачиваются на данном стенде; их польза зависит в том числе
от цены передачи KV и координации запросов.

<a id="long-context"></a>
### Длинный контекст: 64K, затем 128K

Контрольное сравнение A/B использует общее окно 16K.
Для проверки длинного контекста меняется **только окно B**, остальные параметры
Tune сохраняются. Две последовательные серии используют 64K и 128K.

| Окно B | Вход | Выход | Запросов / одновременно |
| --- | ---: | ---: | ---: |
| 64K | 57 344 | 512 | 1 / 1 |
| 128K | 122 880 | 512 | 1 / 1 |

**Окно — предел, а не фактический вход.**
В эти пределы должны войти системный промпт, документы, история, рассуждение
и финальный текст. Если занять всё окно входом, места на ответ не останется.

Критерии проверки — законченный ответ, заданные длины и отсутствие ошибок;
одновременно фиксируются занятость KV-пула и RAM.
После длинной проверки B остаётся на 128K.
Это не обещание восьми полных историй одновременно; **256K выше — расчёт памяти,
не результат этого запуска**.

<details>
<summary>Настройки окна B и параметры длинных проверок</summary>

В полном профиле Tune последовательно задаются `max-model-len: 65536`,
затем `131072`; остальные настройки остаются прежними:

```yaml
vllm:
  max-model-len: 131072
```

После каждого изменения: render → commit/push → Sync → готовность модели.

В контрольной команде из раздела 1 вход и выход заменяются значениями из таблицы,
число запросов и параллельность — на `--num-prompts 1 --max-concurrency 1`.
Каждому окну соответствует отдельное имя серии.
Нужны `completed=1`, `failed=0` и полные заданные длины.

128K может вмещать, например, `122 880 входных + 8192 сгенерированных = 131 072`.
Проверка выше выдаёт 512 токенов; она не проверяет генерацию всех 8192.
Лимит ответа в WebUI проверяется отдельно от окна сервера.

Повторное сравнение B с A требует `max-model-len: 16384`.
При сравнении с другим экземпляром модели окно и остальные настройки
должны совпадать.

</details>

<a id="placement"></a>
## 4. Размещение моделей на GPU

Настройки runtime определяют, как модель использует выделенные ресурсы.
Следующее ограничение — само выделение: небольшой сервис может занимать
целую GPU, хотя ему достаточно части её памяти и вычислений.

### Device plugin и DRA

**Device plugin** публикует в Kubernetes целочисленные ресурсы устройства.
Например, запрос `nvidia.com/gpu: 1` означает одну единицу ресурса.
Само число не описывает требуемую память или способ совместного использования.
MIG и sharing могут поддерживаться дополнительными ресурсами и настройками плагина;
они не запрещены его интерфейсом.

**DRA (Dynamic Resource Allocation)** добавляет выбор устройства по атрибутам,
заявки и конфигурацию устройства для нагрузки.
**ResourceClaim** связывает нагрузку с выделенным ресурсом.
DRA не делает любую GPU автоматически делимой: доступные режимы определяют
оборудование и драйвер.

[Device plugins в Kubernetes](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/),
[DRA в Kubernetes](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/).
[Авторский разбор device plugin и DRA](https://habr.com/ru/companies/flant/articles/1020276/).

### MIG и MPS: разделение и совместное выполнение

**MIG (Multi-Instance GPU)** аппаратно разделяет карту на части с собственной
памятью и вычислениями. **MPS (Multi-Process Service)** позволяет нескольким
процессам совместно использовать вычисления одной такой части.
DRA отвечает за выдачу ресурса, MIG/MPS — за его устройство и использование.

### Три сервиса на A30

Для проверки размещения используется подготовленная конфигурация трёх сервисов
на A30 в соседнем кластере. Gemma на H100 продолжает работать.
**Сервисы и источник метрик относятся к кластеру A30, не H100.**
Их [декларации запуска](#a30-orders) разобраны в разделе 5.

| Сервис | Для чего нужен | Размещение на A30 |
| --- | --- | --- |
| Qwen3 Embedding 4B W4A16 | Превращает текст в вектор для поиска по смыслу | Первая часть `2g.12gb` |
| Qwen3 Reranker 4B W4A16 | Упорядочивает найденные фрагменты по полезности для вопроса | Та же часть |
| Whisper large-v3 | Преобразует речь в текст | Вторая `2g.12gb` |

![Эмбеддер и реранкер делят первую MIG-часть через MPS, Whisper занимает вторую](assets/08-mig-mps.svg)

Геометрия A30 — состав её аппаратных частей — проверяется без изменения карты.
Здесь рассматривается существующее размещение; сравнение до и после применения
заказов относится к [запуску сервисов](#a30-orders).

Требуемое размещение: эмбеддер и реранкер получают
один идентификатор MIG, Whisper — другой.

<details>
<summary>Команды проверки геометрии и совместной нагрузки</summary>

Для проверки нужны готовые сервисы. Состав устройств на ноде A30:

```bash
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

**W4A16** означает 4-битные веса и 16-битные промежуточные активации.
Реранкер использует sequence classification — оценку пары вопрос/фрагмент.
`2g.12gb` — профиль именно A30, не универсальный размер для любой GPU.

Сначала проверяется каждый сервис отдельно, затем эмбеддер и реранкер одновременно.
Фиксируются задержки, ошибки и пик памяти общей партиции.
График активности MIG не разделяет вклад отдельных MPS-процессов.

</details>

### Проверка поиска по документам и распознавания речи

**RAG (Retrieval-Augmented Generation)** передаёт модели найденные фрагменты
документов. Эмбеддер ищет, реранкер уточняет выбор, языковая модель формулирует ответ.
Документ не превращается в новые веса модели.

Контрольный документ содержит отдельный факт: «В проекте “Липа” окно обслуживания
начинается во вторник в 16:40». Документ добавляется в базу знаний Open WebUI;
после индексации эта база подключается к чату. Один и тот же вопрос о времени
проверяется без подключённой базы и с ней. Проверяется факт, ссылка на источник и обращения
к эмбеддеру/реранкеру. Голосовой вариант того же вопроса проверяет транскрипцию Whisper.

Метрики — **запросы, задержки и ошибки embedding / rerank / transcription**.
Это не генераторы чат-токенов: отсутствие выходных токенов у них не означает отказ.

<details>
<summary>Что сохраняется при смене модели и как проходит запрос по документам</summary>

![Поиск и reranking подготавливают контекст для языковой модели](assets/16-rag.svg)

При смене Gemma на Qwen векторный поиск остаётся прежним, индекс сохраняется.
При смене эмбеддера векторы запросов и документов могут стать несовместимы:
индекс перестраивают, сохраняя документы и права доступа.

Верный факт со ссылкой и запросы к эмбеддеру/реранкеру показывают работу поиска.
Без документа языковая модель может угадать ответ — это не проверка RAG.
Whisper выполняет транскрипцию, а не синтез речи.

</details>

<details>
<summary>Device plugins, DRA и другие способы разделения GPU</summary>

Ни device plugin, ни DRA сами по себе не создают физическую изоляцию.

| Механизм | Граница |
| --- | --- |
| MIG | Аппаратные части памяти и вычислительных ресурсов |
| MPS | Совместное выполнение; не добавляет память и не заменяет изоляцию MIG |
| Time-slicing | Чередование доступа; без аппаратного раздела памяти |

HAMi управляет совместным использованием устройств, Volcano планирует нагрузки.
Vulkan — интерфейс графических и вычислительных приложений, не планировщик Kubernetes.
Это разные уровни, не другие названия MIG.

[Device plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/),
[DRA](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/),
[источники и сравнение решений](docs/SOURCES.md).

</details>

<a id="platform"></a>
## 5. Автоматический запуск через AI Inference

Ручная настройка требует согласовать архитектуру модели, память, параметры
вычислений и способ размещения. Для следующей модели эту работу придётся
повторить. **AI Inference** объединяет выбор в планировщике:
модель, требования запуска, характеристики оборудования и доступные рецепты
определяют план.

**InferenceService** — заказ платформе: какую модель и с какой целью запустить.
Планировщик AI Inference выбирает совместимый **рецепт** — набор условий и настроек —
и рассчитывает необходимые ресурсы.

![Модель, класс устройств и стратегия превращаются в план и управляемый сервис](assets/09-platform.svg)

В каталоге **ai-models** выбирается скачанная модель. Действие **«Запустить инференс»**
ведёт к выбору стратегии и доступных ресурсов, расчёту плана и запуску.
Созданный сервис отображается в интерфейсе: модель, план, состояние готовности.

Это сокращает ручной подбор совместимых параметров. Ниже тот же заказ оформлен
в Git и применяется Argo CD; отдельный дублирующий запуск через интерфейс не нужен.
После готовности Gemma её параметры и ответы сравниваются с ручной B.

### Платформенная Gemma вместо ручной A

Автоматизация должна **повторить подходящую конфигурацию**, а не ускорить сама
по себе vLLM — сервер модели. Эталон сравнения — ручная B Tune.

**До остановки A необходим совместимый рецепт:** те же веса, окно 128K, точность KV,
RAM-offload, assistant и настройки выполнения.
Для двух настроенных моделей одновременно нужно не менее 192 GiB RAM
с проверенным распределением; на 128 GiB допустим только последовательный вариант.

После завершения запросов ручная A останавливается и освобождает первую GPU.
На ней платформа запускает Gemma с подобранной конфигурацией.
При достаточном RAM ручная B остаётся на второй карте;
на 128 GiB B также останавливается после сохранения результата.

У сервиса Gemma доступны модель, рассчитанный план и выделенное устройство.
После готовности и проверки ответа его маршрут в WebUI — **`Gemma A — DP`**.

`DP` здесь — подпись платформенного запуска, не Data Parallelism
(распределение запросов между копиями модели).

### Проверка запуска и сопоставимость с ручной B

Ручная B и платформенная Gemma проверяются одинаковыми запросами.
TTFT, ITL и ошибки сравниваются по двум Service на интервалах контрольных серий.

Статус Sync в Argo подтверждает применение конфигурации, но не работу инференса.
Ответ API проверяет модель, ответ в чате — также маршрут и личный доступ.

<details>
<summary>Что сопоставляет планировщик и что проверить в рецепте</summary>

| Вход планировщика | Для чего нужен |
| --- | --- |
| Model | Архитектура и артефакт модели |
| Стратегия | Цель запуска |
| DeviceClass и характеристики оборудования | Разрешённые устройства и доступные ресурсы |
| Рецепты | Совместимые варианты runtime и настроек |

Планировщик формирует план; Kubernetes выделяет конкретное устройство.
В работающем контейнере окно, KV, offload и assistant должны соответствовать ручной B.

План сопоставляется с бюджетом `W + KV(N,S) + R` и фактическим запуском.
Одной надписи Throughput — «приоритет пропускной способности» — недостаточно:
справочный рецепт Gemma 64K без CPU KV и assistant имеет другие параметры.
[Проверка нужной поставки](docs/SETUP.md#inference-readiness).

</details>

<details>
<summary>Конфигурация платформенной Gemma и проверка API</summary>

Предусловие: маршрут Base отключён, запросы завершены, A остановлена
через Git/Argo, её заявка на GPU освобождена. Ручная B сохраняется
только при достаточном RAM; на 128 GiB её остановка также предшествует запуску.

В подготовленном `$DEMO_DIR/platform/gemma.yaml` включение задаётся `order.enabled: true`.
Это Helm values, не сырой Kubernetes-манифест:

```bash
set -o pipefail
helm template hf-platform-gemma "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После проверки — commit/push и Sync `hardfest-gemma-platform`.
В консоли нужен статус **Ready** у `hf-platform-gemma`.

**API (Application Programming Interface)** — программный интерфейс сервиса.
Сначала проверяется API, затем чат. Подключение в отдельном терминале:

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get service hf-platform-gemma
kubectl --context "$GPU_CONTEXT" -n hardfest-demo port-forward svc/hf-platform-gemma 18005:80
```

При другом порте Service число 80 заменяется фактическим портом.
В основном терминале ключ сервиса вводится из менеджера секретов:

```bash
set +x
IFS= read -r -s MODEL_API_KEY
curl --fail --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  http://127.0.0.1:18005/v1/models
```

Поле `model` содержит ID из ответа `/v1/models`:

```bash
curl --fail-with-body --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  -H 'Content-Type: application/json' http://127.0.0.1:18005/v1/chat/completions \
  -d '{"model":"REPLACE_SERVED_MODEL_ID","max_tokens":512,"temperature":0,"messages":[{"role":"user","content":"Зачем нужен KV-кеш?"}]}'
unset MODEL_API_KEY
```

Критерий — законченный текст без ошибки; после проверки port-forward закрывается.
Для Qwen используются `hf-qwen-platform`, его порт, ID и ключ.
Команды не включают секрет в аргументы curl; сохранение ключа в Git недопустимо.

Для числового сравнения производительности нужен общий CPU-клиент с авторизацией.
Команда ручного A/B из раздела 1 не переносится на платформенный StatefulSet
без адаптации.

</details>

<a id="a30-orders"></a>
<details>
<summary>Подготовка трёх сервисов A30 и сравнение геометрии</summary>

Конфигурация A30 из [раздела 4](#placement) использует тот же ресурс
InferenceService. Это первоначальная подготовка или повторное развёртывание;
к началу основного разбора все три сервиса уже должны отвечать.
Повторный Sync без изменения конфигурации не означает создание новых MIG-частей.

**Для создания новых MIG-частей нужны свободные ресурсы, поддерживаемая конфигурация
и заранее включённый MIG mode. Чужие работающие партиции не переразмечаются.**
Если нужные части уже существуют, проверяется их выделение, а не создание.

Подготовка моделей использует `catalog/a30.yaml`.

| Values | Application |
| --- | --- |
| `platform/embedding.yaml` | `hardfest-embedding-platform` |
| `platform/reranker.yaml` | `hardfest-reranker-platform` |
| `platform/whisper.yaml` | `hardfest-whisper-platform` |

В трёх подготовленных заказах задаётся `order.enabled: true`.
После проверки render и commit/push синхронизируются их Application
в управляющем кластере; destination приложений — кластер A30.
Критерий запуска — три готовых InferenceService и ответы сервисов.

Команды `nvidia-smi` из [раздела 4](#placement) выполняются на одной и той же ноде
до применения заказов и после готовности сервисов. Сравнение связывает изменение
геометрии с запуском; снимок уже готовой карты не показывает процесс создания частей.

</details>

<a id="conclusion"></a>
### Оптимизация перед расширением оборудования

Очередь сама по себе не обосновывает покупку новых карт.
Сначала проверяются объём KV, повторное использование контекста,
стоимость вычислений и размещение небольших сервисов.

Новая GPU обоснована, когда после подходящих оптимизаций измеренная нагрузка
всё ещё не укладывается в требования по задержке, контексту или пропускной способности.
Сравнение опирается на законченные ответы и расход ресурсов, а не только на занятость GPU.
[Методика и шаблон результатов](docs/MEASUREMENTS.md).

<a id="results"></a>
## 6. Шлюз и модель на двух GPU

### Персональный доступ и стоимость запроса

**ai-mcp-gateway** — единая точка входа к моделям на базе Bifrost;
журнал связывает запрос с маршрутом, входными и выходными токенами,
стоимостью и личным ключом.

**VK (Virtual Key)** связывает запрос с пользователем, его доступами и лимитами.
Проверка использует два одобренных аккаунта: у них должны быть разные личные VK,
а записи запросов должны относиться к соответствующим владельцам.
Ключ подключения шлюза к vLLM — другой ключ, он не заменяет личный.

**Деньги условные, списаний нет.** Стоимость запроса не равна цене эксплуатации GPU.
Настроенный максимум контекста не оплачивается:
учёт идёт по фактическим токенам.

<details>
<summary>Тарифы, автоматический доступ и границы учёта</summary>

| Параметр | Значение |
| --- | --- |
| Выдача личного VK | После одобрения аккаунта |
| Бюджет | $500 на 24 часа |
| Входные токены | $10 за миллион |
| Выходные токены | $20 за миллион |

Каждая модель подключена отдельным маршрутом; между A и B отключены
балансировка, незаметная подмена при отказе (fallback) и кеш готовых ответов.

| Подпись WebUI | Запуск |
| --- | --- |
| `Gemma A — Base` | Ручная A |
| `Gemma B — Tune` | Ручная B: Cache, затем Tune |
| `Gemma A — DP` | Gemma через AI Inference |
| `Qwen — TP2` | Одна модель на двух H100 |

Права и расход сохраняются при переходе между моделями.
Индексация и голосовые подключения требуют отдельного учёта;
личный VK чата не делает их автоматически персональными запросами.

В HA-режиме (High Availability, несколько реплик шлюза) есть известный недосчёт
общего бюджета. Стоимость отдельной записи не подтверждает строгий суммарный лимит.
[Границы учёта и проверка доступа](docs/CHAT_AND_ACCESS.md#проверить-выдачу-и-отзыв).

Управление кластером отделено от чата:
администратор входит через OIDC (OpenID Connect), протокол проверки личности,
и использует MCP (Model Context Protocol), подключение внешних инструментов.
Доступ к чату не предоставляет инструменты Kubernetes.

</details>

<a id="topology"></a>
<details>
<summary>Полная схема стенда: какие компоненты в каком кластере</summary>

![Два GPU-кластера: чат и A30, ai-mcp-gateway и две H100](assets/01-topology.svg)

| Место | Компоненты |
| --- | --- |
| Управляющий кластер | Argo CD и подключение к частному GitLab k8s-config |
| Кластер A30 | Open WebUI, эмбеддер, реранкер, Whisper |

Argo доставляет конфигурацию и не находится на пути чат-сообщения.

</details>

<a id="tp2"></a>
### Qwen: один экземпляр на двух GPU

Qwen использует обе H100 для **одного экземпляра модели**.
Это противоположная задача размещению небольших сервисов на общей карте.

**TP (Tensor Parallelism)** делит тензорные вычисления модели между GPU.
При **TP2** каждая из двух карт выполняет свою часть и обменивается результатами
с соседней. Это не две независимые копии; сервером остаётся vLLM, не TensorRT.

![Одна модель распределена по двум GPU; между ними нужен обмен](assets/10-tp2.svg)

**До остановки Gemma необходимы доставленные веса Qwen и совместимый
рецепт на две карты.** Сервисы A30 и сам чат продолжают работать.

**Обычная синхронизация не удалит платформенный InferenceService.**
Нужно проверить список изменений и выполнить адресный Prune — удаление
**только её заказа**. Model, PVC (PersistentVolumeClaim — заявка хранилища)
и чужие нагрузки сохраняются.

Переход начинается с отключения маршрутов обеих Gemma и завершения запросов.
После остановки Gemma должны освободиться обе H100;
запуск Qwen до освобождения устройств недопустим.

У `hf-qwen-platform` проверяются две разные GPU в заявке,
`tensor-parallel-size: 2` в Pod и законченный ответ модели.
После этого используется маршрут **`Qwen — TP2`** в WebUI с прежним личным доступом.

<details>
<summary>Заказ Qwen, два устройства и встроенный MTP</summary>

![После проверки готовности Qwen обе Gemma освобождают две H100](assets/17-qwen-transition.svg)

Предусловия остановки Gemma: проверены артефакт Qwen, доставка весов, runtime,
рецепт и DeviceClass.

Остановка ручной B задаётся `replicaCount: 0`, платформенной Gemma —
`order.enabled: false`. Изменения применяются через Git/Argo;
удаление платформенного заказа требует адресного Prune после просмотра diff.
Следующий шаг возможен только после освобождения обеих H100.

В подготовленном `$DEMO_DIR/platform/qwen.yaml` меняется только `order.enabled: true`.
Model, класс и стратегия уже заданы:

```bash
set -o pipefail
helm template hf-qwen-platform "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/qwen.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После проверки — commit/push и Sync `hardfest-qwen-platform`.

| Проверка | Что должно быть |
| --- | --- |
| План | `acceleratorCount=2` |
| ResourceClaim | Две разные карты одной ноды |
| Движок | `tensor-parallel-size: 2` |

Проверка API включает `/v1/models` и законченный ответ `/v1/chat/completions`;
команды подключения и ключа приведены в разделе 5.
Доступ к Qwen добавляется действующим личным ключам **без обнуления накопленного расхода**.

**NVLink** — межкарточное соединение. Его наличие не заменяет замер обмена и задержек.

![Qwen использует MTP внутри модели, без отдельной Gemma assistant](assets/18-qwen-mtp.svg)

У этой Qwen MTP встроен в модель. Проверке подлежат включение MTP, принятие предложений
и время decode. Отдельная Gemma assistant не нужна.

Для этого рецепта используется native KV-offload с Simple CPU backend:
конфигурация Gemma OffloadingConnector для него не подходит.

</details>

### Параллельность и длинный контекст

Контрольные серии содержат 1, 4 и 8 одновременных коротких запросов.
Длинный вход проверяется отдельной серией в пределах выбранного рецепта.

**Running, waiting, KV, ошибки и законченные ответы** разделяют фактическое
одновременное выполнение и ожидание в очереди.

<details>
<summary>Окно, параллельность и вместимость — три разных числа</summary>

![Сравниваем активные запросы, очередь и задержки при росте числа клиентов](assets/19-qwen-capacity.svg)

Окно ограничивает длину одной истории. `max-num-seqs` — число последовательностей
в работе. Вместимость определяется реальным KV-пулом и длинами этих историй.

«Ответил восьми людям» не означает «держит восемь полных окон одновременно».
Для второго нужны отдельная нагрузка известных длин и измерение памяти.

</details>

<a id="cleanup"></a>
## Остановка после завершения работы

Остановка выполняется после завершения запросов и сохранения результатов.

**Namespace, Model, PVC (PersistentVolumeClaim — заявки хранилища),
GPUClass/GPUPool, чаты и базы знаний сохраняются.**

1. Отключение выключаемых маршрутов и завершение текущих запросов.
2. Ручные workloads: `replicaCount: 0`, commit/push и Sync.
3. Платформенные заказы: `order.enabled: false`, просмотр diff и адресный Prune
   только выбранного InferenceService по [процедуре остановки](docs/GITOPS.md#остановка).
4. Проверка отсутствия Pod нагрузки и освобождения заявок.

## Подготовка своего стенда

Исходное состояние руководства: A отвечает в чате, веса доставлены,
личный доступ и графики проверены. Ручная B и платформенные Gemma/Qwen
подготовлены, но выключены. Три сервиса A30 уже отвечают;
их первоначальный запуск описан в [подготовке заказов A30](#a30-orders).

1. [Инфраструктура и A](docs/SETUP.md) — контексты и переменные команд.
2. [GitOps](docs/GITOPS.md), [каталог моделей](catalog/README.md),
   [чат и доступ](docs/CHAT_AND_ACCESS.md), [мониторинг](docs/OBSERVABILITY.md).
3. [Бюджет RAM](docs/MEMORY_BUDGET.md#ram-выбрать-порядок-запуска):
   для одновременной ручной B и платформенной Gemma нужно не менее 192 GiB.
   На 128 GiB используется последовательный вариант.

Публичные workload-профили по умолчанию выключены; включение выполняется адресно из частного Git.
NodeCache хранит веса на целевой ноде; контейнерный образ vLLM кешируется отдельно.
