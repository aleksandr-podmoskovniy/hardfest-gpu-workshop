# Инференс без простоя видеокарт: ускоряем языковые модели и делим ресурсы

Александр Подмосковный, Флант / Deckhouse Platform

**Почему языковая модель отвечает медленно — и что именно стоит менять?**

**LLM (Large Language Model)** — большая языковая модель, которая принимает
текст и генерирует продолжение. Выполнение модели на пользовательском запросе
называется **инференсом**.

В нашем стенде вычисления выполняют **GPU (Graphics Processing Unit)** —
графические процессоры, приспособленные к параллельной работе с числами.
На работающей Gemma сначала разберём память, затем обработку запросов.

После ручной настройки передадим запуск AI Inference, разместим три сервиса
на одной A30 и завершим моделью Qwen, которой нужны две H100.

> [!TIP]
> Откройте **[ai.ap4y.ru](https://ai.ap4y.ru)**, зарегистрируйтесь и дождитесь
> одобрения. Стенд подготовлен, **`Gemma A — Base` уже запущена**.
> Личный ключ, доступные модели и лимиты выдаются автоматически.
> Пока появляется доступ, посмотрите схему ниже.

| По ходу работы | Что проверяем |
| --- | --- |
| **Gemma A → B Cache → B Tune** | Где уходит время; что дают кеширование и оптимизация вычислений |
| **Ручной запуск → AI Inference** | Как воспроизвести ту же конфигурацию автоматически |
| **Одна A30 → три сервиса** | Как разделить GPU между поиском по документам и распознаванием речи |
| **Две H100 → одна Qwen** | Как запустить модель, не помещающуюся на одну карту |

**Вопросы можно задавать на любом этапе.** Перед опытом выберите свой прогноз,
затем проверьте его по ответу и графикам. Разбор можно раскрыть после проверки.

Аккаунт, чат и базы знаний сохранятся при переходах между моделями.

Для двух RTX 5060 Ti есть [самостоятельный сценарий RTX](RTX5060.md).
У него те же исследуемые механизмы, но свои модели, расчёты памяти и параметры.

<a id="topology"></a>
## Стенд и подключение

На A30 совместим два механизма:

- **MIG (Multi-Instance GPU)** — аппаратное разделение поддерживаемой GPU на части
  со своей памятью и вычислительными ресурсами.
- **MPS (Multi-Process Service)** — совместное выполнение нескольких процессов
  внутри GPU или её MIG-раздела.

![Два кластера: Open WebUI и A30, ai-mcp-gateway и две H100](assets/01-topology.svg)

| Место | Что здесь работает |
| --- | --- |
| Управляющий кластер | Argo CD читает частный GitLab k8s-config |
| Кластер с A30 | Open WebUI, эмбеддер и реранкер в одной MIG-партиции через MPS; Whisper во второй |
| Кластер с двумя H100 | Ручные Gemma, затем сервисы AI Inference; ai-mcp-gateway на базе Bifrost |

**ai-mcp-gateway — единая точка входа к моделям**, здесь на базе Bifrost.
Он проверяет личный ключ, выбирает маршрут и учитывает запрос.

**vLLM** — сервер моделей за шлюзом: именно он выполняет генерацию на GPU.
Приложения обращаются к нему через **API (Application Programming Interface)** —
программный интерфейс для отправки запросов и получения ответов.

Argo CD в обработке сообщения не участвует. Он доставляет конфигурацию сервисов из Git.

<details>
<summary>Границы кластеров и подключений на схеме</summary>

**Управляющий кластер** запускает Argo CD; он может совпадать с кластером A30.

Маршрутизация между чатом, шлюзом и моделями подготовлена заранее.
**TLS (Transport Layer Security)** защищает эти сетевые соединения.

Доступ к модели не даёт прав на
**MCP (Model Context Protocol)** — протокол подключения внешних инструментов
к приложению с моделью. У Kubernetes MCP в нашем стенде отдельная авторизация.

</details>

<a id="chat"></a>
### Один чат на всех этапах

| Название в Open WebUI | Назначение |
| --- | --- |
| `Gemma A — Base` | Ручной запуск без исследуемых оптимизаций |
| `Gemma B — Tune` | Ручная B: сначала Cache, затем полный Tune |
| `Gemma A — DP` | Gemma, созданная через AI Inference |
| `Qwen — TP2` | Финальный сервис: TP (Tensor Parallelism), тензорный параллелизм на двух H100 |

`DP` здесь — метка платформенного запуска, **не Data Parallelism**
(параллелизм по данным, когда запросы распределяются между копиями модели).

Каждая модель подключается отдельным маршрутом Bifrost. Между A и B нет
балансировки, незаметной подмены при отказе (fallback) и кеша готовых ответов.

**VK (Virtual Key)** — персональный ключ шлюза: разрешённые модели, лимиты
и привязка запросов к участнику.

Он появляется после одобрения аккаунта. Копировать общий ключ в браузер не нужно.

**Доллары в этом стенде условные: реальных списаний нет.**

### Как Base уже попала в чат

Откройте Application `hardfest-gemma-a` в Argo CD. Он уже синхронизирован.
Посмотрите применённый commit — сохранённую версию конфигурации, —
[профиль A](values/gemma-a.yaml), Deployment и заявку на GPU.

Это ручная конфигурация vLLM через Helm, **ещё не InferenceService**.
Повторно запускать или перезапускать A сейчас не нужно.

![GitLab хранит Helm values, Argo CD применяет выбранный коммит в целевой кластер](assets/12-gitops.svg)

1. Git хранит параметры запуска.
2. Helm chart превращает параметры в объекты Kubernetes; Argo применяет их.
3. **DRA (Dynamic Resource Allocation)** — механизм выделения устройств —
   предоставляет одну H100 через заявку **ResourceClaim**.
4. vLLM читает веса, доставленные сервисом ai-models.

**Запись в каталоге, запущенный процесс и доступ пользователя — три разных звена.**
Модель видна в каталоге консоли, а её чат-маршрут — в WebUI.

![Честное сравнение: одинаковые веса и запросы, по одной H100 и общий предел 16K](assets/04-ab.svg)

Модель обрабатывает текст **токенами** — небольшими частями, не обязательно словами.

**KV (Key–Value) cache** — сохранённые ключи и значения для продолжения истории.
Модель переиспользует их при генерации, чтобы не рассчитывать уже известный текст заново.

**Base — исходная точка сравнения.** У неё явно выключены prefix cache,
chunked prefill, CUDA graphs, KV-offload и speculative decoding. Каждый механизм
разберём ниже. Это одна версия vLLM 0.31, не сравнение разных движков.

Окно A — **16 384 токена**: без chunked prefill нужен большой рабочий буфер.

### От ответа в чате к графикам

Откройте **AI Inference / Service performance** и выберите:

- Namespace: `hardfest-demo`;
- Service: `hf-gemma-a`;
- период, в который отправляли свои вопросы.

Новые запросы и выходные токены должны попасть на графики. Ручная A наблюдается
здесь же: название дашборда не ограничивает его платформенными заказами.

| Что заметили в чате | На что смотрим |
| --- | --- |
| Ответ ещё не начался | Очередь, активные запросы и **TTFT (Time To First Token)** — время до первого токена |
| Текст идёт медленно | **ITL (Inter-Token Latency)** — интервалы между токенами; **TPOT (Time Per Output Token)** — среднее время на токен после первого |
| Несколько людей ждут одновременно | Running / waiting, ошибки и throughput |
| GPU занята, но ответы не ускоряются | Вычислительная загрузка, видеопамять и KV-пул |

### Опыт 1. Медленный старт или медленный ответ?

1. **Предскажите:** что сильнее изменит длинная история — TTFT или темп следующих токенов?
2. **Попробуйте:** сравните короткий вопрос с длинным входом в контрольной серии ниже.
3. **Проверьте:** **TTFT, очередь и TPOT** на одном интервале. По суммарным tokens/s
   нельзя судить о скорости одного ответа.

<details>
<summary>Разбор: три причины ощущения «тормозит»</summary>

- Запрос может **ждать очереди**.
- Модель может долго **обрабатывать вход** — выполнять prefill.
- Уже начатый ответ может **медленно генерироваться**.

Длинный вход увеличивает работу prefill; под нагрузкой к ней добавляется очередь.
Преобладающий этап определяем по измерению, а не по ощущению в браузере.

</details>

<a id="latency"></a>
## 2. Разбираем время ответа

![Путь запроса: очередь, prefill и последовательная генерация токенов](assets/02-latency.svg)

**У каждого этапа своя причина задержки и свой способ оптимизации.**

| Этап | Простое объяснение | Что разберём |
| --- | --- | --- |
| **Queue** | Запрос ждёт, пока движок возьмёт его в работу | Вместимость и управление нагрузкой |
| **Prefill** | Модель обрабатывает весь вход и подготавливает состояние истории | Prefix caching и chunked prefill |
| **Decode** | Модель генерирует следующие токены шаг за шагом | Speculative decoding |

### Где в ответе находится рассуждение

Если модель рассуждает, её reasoning-токены тоже генерируются на decode
и занимают место в контексте. Поэтому первые слова финального ответа в WebUI
могут появиться позже первого сгенерированного токена.

### Суммарное время и скорость одного ответа

`Tответа ≈ Tочереди + Tprefill + Tdecode + Tпрочее`.

В последнее слагаемое входят сеть, шлюз, токенизация и передача потока.

**TTFT** измеряет время до первого токена на выбранной границе измерения;
первые слова финального ответа в WebUI могут появиться позже.

**Output tokens/s** всего сервиса — суммарная производительность всех его
запросов, не темп одного ответа.

**p95** — порог, ниже которого находятся 95% измерений. Для устойчивой оценки
нужна серия запросов, а не несколько ручных сообщений.

На одном временном интервале сравним три ситуации:

| Что отправляем | Что ищем на графиках |
| --- | --- |
| Короткий вопрос без очереди | Базовую задержку и темп выдачи текста |
| Новый длинный документ, короткий ответ | Время prefill и TTFT |
| Несколько длинных ответов одновременно | Running / waiting, ITL, throughput и ошибки |

### GPU занята — но чем?

**Память и вычисления — разные ограничения.**

- **Prefill** обрабатывает много токенов и часто хорошо загружает вычисления.
- **Decode** при небольшом числе совместно обрабатываемых запросов (batch)
  может упираться в чтение весов из памяти.
- **Занятая видеопамять** не обязательно означает нехватку: движок заранее
  резервирует пул блоков KV.

Поэтому смотрим вместе вычисления, память, очередь и время ответа.
[Как измерять и не ошибиться с p95](docs/MEASUREMENTS.md).

Раз начальный длинный запрос дорог, выясним, какое состояние он оставляет
в памяти и можно ли не вычислять его заново.

<a id="memory"></a>
## 3. Считаем память от одного токена до восьми историй

**VRAM (Video Random Access Memory)** — память видеокарты. В H100 используется
**HBM (High Bandwidth Memory)**, память с высокой пропускной способностью.
Не путайте её с **RAM (Random Access Memory)** — оперативной памятью узла.

Считаем длинные истории **128K и 256K**, затем суммируем расход восьми сессий.
Начнём с одного токена и соберём формулу для всей истории.

| Память GPU занята | От чего зависит объём |
| --- | --- |
| **Весами модели** | Модель и точность хранения; веса общие для запросов и не растут от длины разговора |
| **Рабочими буферами** | Prefill, активации и настройки выполнения, в том числе CUDA graphs |
| **KV cache** | Архитектура, длины и число живых историй, точность KV |

**KV-кеш — сохранённое состояние истории, не готовый ответ.** Разберём,
из чего он состоит, и посчитаем объём от одного токена до нескольких сессий.

![Attention сохраняет ключи и значения предыдущих токенов для продолжения генерации](assets/13-attention.svg)

### Откуда берётся формула

Модель обработала `t1, t2, t3` и сгенерировала `t4`. Следующий шаг уже продолжает
`t1, t2, t3, t4`.

На каждом attention-слое текущий **query Q** сравнивается
с **keys K**, а полученные коэффициенты задают взвешенную сумму **values V**.

- Q нужен для текущего вычисления.
- K/V сохраняем для следующих токенов, чтобы не рассчитывать известный текст заново.

<details>
<summary>Query, Key и Value — простое пояснение</summary>

- **Query** — вектор текущего токена: что ищем в истории.
- **Key** — векторы предыдущих токенов, с которыми его сопоставляют.
- **Value** — векторы информации, которые смешиваются с полученными весами.

**Attention** — этот механизм выбора и смешивания. Это операции с числами,
а не буквальная база вопросов и ответов.

</details>

#### Сколько голов входит в расчёт

Один слой выполняет несколько наборов attention-вычислений; их называют **головами**.

В **GQA (Grouped-Query Attention)** несколько query-голов используют общий
набор K/V. Поэтому для объёма кеша берём `num_key_value_heads`, а не `num_attention_heads`.

Это свойство архитектуры внутри модели. Общий префикс между запросами —
другой механизм; к нему перейдём после расчёта.

![Вывод формулы: от K и V одного токена в одном слое до N независимых историй](assets/25-kv-derivation.svg)

#### Собираем множители

1. У одного токена в одном слое два набора векторов: `2 × Hkv × D` элементов.
2. Умножаем на размер элемента `b` и число одинаковых слоёв `L`.
3. Складываем длины всех `N` независимых историй.

Получаем байты, не гигабайты:

```text
KV_bytes = 2 × L × Hkv × D × b × (S₁ + S₂ + … + Sₙ)
При одинаковой длине: KV_bytes = 2 × N × L × Hkv × D × S × b
```

Размер числа зависит от формата: **BF16 (Brain Floating Point 16)** и
**FP16 (16-bit Floating Point)** занимают по два байта,
**FP8 (8-bit Floating Point)** — один. Точность весов и точность KV задаются отдельно.

| Обозначение | Что подставлять |
| --- | --- |
| `Hkv` | Количество **KV-голов**, не query-голов `num_attention_heads` |
| `D` | Размерность одной KV-головы; не угадываем её по размеру hidden state |
| `b` | Байты на элемент KV: BF16/FP16 — 2, FP8 — 1; точность весов задаётся отдельно |
| `S` | Токены входа **плюс** уже сгенерированные токены; для верхней оценки — их суммарный предел |
| `L` | Слои, хранящие собственные K/V |
| `N` | Число одновременно живущих независимых историй; при разных длинах складываем их расходы |

Формула выше предполагает одинаковые слои с полным вниманием — full attention.
У Gemma есть два типа слоёв, поэтому нужны два слагаемых:

- **Full attention** хранит KV всей истории.
- **Sliding attention** хранит KV ограниченного окна последних токенов.

Общий префикс пока не разделяем между запросами: его переиспользование проверим отдельно.

### Подставляем Gemma 4 31B

В [закреплённом config.json](https://huggingface.co/google/gemma-4-31B-it/blob/842da3794eaa0b77d5f08bae87a17459d91ff475/config.json)
открываем `text_config`, а не конфигурацию vision-энкодера:

| Слои | Число | KV-голов | Размерность | Сколько токенов сохраняем |
| --- | ---: | ---: | ---: | --- |
| Full attention | 10 | 4 | 512 | `S` |
| Sliding attention | 50 | 16 | 256 | `min(S, 1024)` |

**1024 — внутреннее окно sliding-слоёв, не длина запроса.**
Вся история при этом может занимать 128K или 256K: её сохраняют full-слои.

![Формула KV для Gemma учитывает global attention и ограниченное sliding window](assets/11-gemma-kv.svg)

#### Промежуточный шаг: память одного токена

- Один **full-слой** в BF16: `2 × 4 × 512 × 2 = 8192 байта = 8 KiB`.
  Десять слоёв дают **80 KiB на токен истории**.
- Один **sliding-слой**: `2 × 16 × 256 × 2 = 16 KiB`.
  Пятьдесят слоёв дают **800 KiB на токен локального окна**, но только до 1024 токенов.

Для одной истории:

```text
KV(S) = 2 × b × [10 × 4 × 512 × S + 50 × 16 × 256 × min(S, 1024)] байт
```

#### Основной расчёт: 128K, затем 256K

Для **одной истории 128K в BF16**:

1. Full: `2 × 2 × 10 × 4 × 512 × 131072` = **10 GiB**.
2. Sliding: `2 × 2 × 50 × 16 × 256 × 1024` = **0,78125 GiB**.
3. Всего: **10,78125 GiB**. Восемь независимых историй — **86,25 GiB** полезного KV.

Проверяем обычным `awk`. По умолчанию `S=131072`, `N=8`, `b=2`:

```bash
awk -v S=131072 -v N=8 -v b=2 'BEGIN {
  W = S < 1024 ? S : 1024
  full = 2*b*10*4*512*S / 1073741824
  local = 2*b*50*16*256*W / 1073741824
  printf "Full %.5f + sliding %.5f = %.5f GiB/history; %d histories = %.5f GiB\n", full, local, full+local, N, N*(full+local)
}'
```

2. **Посчитайте:** замените `S=131072` на `S=262144`, оставив `N=8`.
   Отдельно попробуйте `b=1` — FP8 для KV.
3. **Сверьте:** результат `awk` в GiB на одну историю и на восемь сессий
   с разбором ниже. Это расчёт; длинные запросы запустим после настройки B.

<details>
<summary>Разбор расчёта и точности KV</summary>

При 256K в BF16 получаем **20 + 0,78125 = 20,78125 GiB на историю**.
Восемь независимых историй занимают **166,25 GiB** полезного KV.

<details>
<summary>Как тот же расчёт связан с короткой контрольной серией A/B</summary>

Для начального окна 16K в BF16:

3. Всего: **2,03125 GiB**. Четыре полных истории — **8,125 GiB**.

В команде расчёта это `S=16384`, `N=4`, `b=2`.

</details>

### Длинный контекст — это вход вместе с генерацией

Возьмём окно 128K: `122 880 входных + 8192 сгенерированных = 131 072 токена`.

- **Во входе:** системный промпт, шаблон чата, документы и история.
- **В генерации:** reasoning и финальный текст.

Если занять всё окно документом, ответу не останется места даже при большом
лимите выходных токенов в WebUI.

#### Суммируем длинные истории

Для 128K мы получили `80 KiB × 131072 + 800 KiB × 1024 = 10,78125 GiB` в BF16.
Сравним два окна без разделения общего префикса:

| Окно одной истории | Историй | KV в BF16 | KV в FP8 |
| --- | ---: | ---: | ---: |
| 128K | 1 | 10,78125 GiB | 5,390625 GiB |
| 128K | 4 | 43,125 GiB | 21,5625 GiB |
| 128K | 8 | 86,25 GiB | 43,125 GiB |
| 256K | 1 | 20,78125 GiB | 10,390625 GiB |
| 256K | 8 | 166,25 GiB | 83,125 GiB |

Ни одно число не включает веса, буферы или assistant.

**Восемь подключённых пользователей — не восемь гарантированных полных окон.**
Для этого полезный KV ещё должен поместиться в реальный GPU-пул.

### Сколько места остаётся после весов

Оценка бюджета: `Kpool ≈ G × u − W − R`.

- `G` — доступная память GPU.
- `u` — доля памяти, отданная движку.
- `W` — фактическая память загруженных весов, не размер файлов на диске.
- `R` — остальные резервы и рабочие буферы.

<details>
<summary>Учебный пример бюджета: от остатка памяти к числу историй</summary>

Это пример арифметики, **не характеристика наших H100**.

| Величина | Значение |
| --- | ---: |
| `G` | 96 GiB |
| `u` | 0,90 |
| `W` | 64 GiB |
| `R` | 6 GiB |

Остаётся `96 × 0,90 − 64 − 6 = 16,4 GiB`.

- В BF16: `floor(16,4 / 10,78125) = 1` история 128K.
- В FP8: `floor(16,4 / 5,390625) = 3` истории 128K.

Это верхняя оценка полезного KV. Реальные блоки и резервы могут уменьшить её;
на своём запуске подставляйте данные движка.

</details>

### Сверяем расчёт с движком

**Формула считает полезные данные, а движок выделяет пул блоков.**
В пуле есть свободные блоки, округление и расходы размещения разных типов attention.
Отдельная память нужна prefill-буферам и вспомогательной модели assistant.

<details>
<summary>Как блоки связывают формулу, prefix cache и offload</summary>

Возьмём учебный блок на 16 токенов. Это не настройка наших профилей.

1. Истории из 35 токенов нужны три блока; последний заполнен частично.
2. Физически блоки могут лежать в разных местах — история ссылается на них через таблицу.
3. При одинаковых первых 32 токенах два запроса могут переиспользовать два полных блока.
4. После завершения запроса его активные ссылки освобождаются, но блоки могут
   оставаться в кеше до вытеснения.

У гибридной модели размеры блоков и выравнивание зависят от групп full/sliding
attention и runtime. В следующем опыте будем возвращать из RAM именно блоки,
а не готовые ответы.

</details>

1. Выпишите из логов размер GPU KV-пула и объявленную вместимость в токенах.
2. Отправьте один запрос, длинный запрос в пределах окна A и четыре параллельных.
3. Сопоставьте занятость KV-пула, очередь и **preemption** — вытеснение

`nvidia-smi` показывает всю занятую память, не только KV этих историй.
[Команды проверки и разбор расхождения](docs/MEMORY_BUDGET.md#verify-kv).

**FP8 уменьшает байты, длина увеличивает full-KV, общий префикс убирает повторную
работу.** Теперь проверим последний механизм и добавим хранение блоков в RAM.

## 4. Первая итерация: prefix cache и KV в RAM

**Не вычислять повторно и не потерять вычисленное — две разные задачи.**

| Механизм | Что делает |
| --- | --- |
| **Prefix caching** | Переиспользует KV одинакового начала запроса, а не готовый ответ |
| **KV RAM offload** | Сохраняет KV-блоки в RAM и возвращает их на GPU, когда они снова нужны |

![Повтор общего префикса позволяет переиспользовать уже рассчитанный KV](assets/14-prefix.svg)

Несколько человек задают вопросы к одному документу. Если документ и всё
до него совпадают **в токенах**, их K/V можно вычислить один раз.

Это **Automatic Prefix Caching**: экономим повторный prefill, но каждый новый
ответ генерируем заново. Изменение системного промпта или начала документа
нарушает совпадение.
[Как работает prefix caching](https://docs.vllm.ai/en/v0.31.0/features/automatic_prefix_caching/).

**KV-offload решает следующую проблему.** GPU-пул конечен: другие документы
могут вытеснить старые блоки. Сохраним копию в RAM, чтобы затем восстановить их.

Веса и активные вычисления остаются на GPU.

### Включаем B Cache

Первый профиль B — `values/gemma-b.yaml`:

- окно остаётся **16K**, как у A;
- chunked prefill и CUDA graphs выключены;
- включены prefix cache, FP8 для KV, Triton attention и CPU-пул **32 GiB**.

Сравниваем весь набор настроек, не только offload.
Triton attention — выбранная реализация вычислений attention на GPU.

**Перед запуском проверьте RAM:** на виртуальной машине со 128 GiB профили с offload выполняются
последовательно — сначала остановите A через Git/Argo. Не называйте такой
замер одновременным A/B. [Бюджет RAM](docs/MEMORY_BUDGET.md#ram-выбрать-порядок-запуска).

```yaml
kv-transfer-config:
  kv_connector: OffloadingConnector
  kv_role: kv_both
  kv_connector_extra_config:
    cpu_bytes_to_use: 34359738368
```

![CPU KV хранит вытесненные блоки и возвращает их при повторном обращении](assets/05-kv-ram.svg)

#### Когда перенос выгоднее пересчёта

`Tпереноса ≈ объём / эффективная полоса`.

Для полезного FP8 KV истории 128K пример выглядит так:
`5,390625 GiB / 25 GiB/с ≈ 0,216 с`.

Это иллюстрация, не измеренная полоса нашего стенда. Реальное время зависит
от блоков, реализации offload, синхронизации и конкуренции за RAM.
Сравним его со временем повторного prefill.
[Устройство CPU offload](https://docs.vllm.ai/en/v0.31.0/features/kv_offloading_usage/).

## 5. Вторая итерация: chunked prefill и speculative decoding

**Быстрее начать ответ и быстрее продолжать его — разные задачи.**

Сначала поделим длинный prefill на порции, затем проверим цену decode.

### Chunked prefill: дать место уже начатым ответам

![Chunked prefill делит большой ввод на порции и чередует его с decode](assets/06-scheduler.svg)

Новый длинный документ приходит, пока модель уже пишет другим пользователям:

- prefill обрабатывает много входных токенов;
- decode продвигает начатые ответы небольшими шагами.

**Chunked prefill** делит вход на порции, чтобы планировщик мог чередовать их
с decode. Меньше порция — чаще возможность продолжить ответы, но больше
шагов на новый документ. Выбираем компромисс между TTFT и ITL.

Не перепутаем три независимых ограничения:

| Настройка | Что ограничивает |
| --- | --- |
| `max-model-len` | Длину одной истории: вход и генерацию |
| `max-num-seqs` | Число одновременно обрабатываемых последовательностей |
| `max-num-batched-tokens` | Бюджет токенов текущего шага планировщика |

#### Что изменится во второй B

Профиль `values/gemma-b-spec.yaml` сохраняет prefix cache, FP8 KV и 32 GiB CPU KV.
К ним добавляются:

- prefill порциями по **2048 токенов**;
- CUDA graphs;
- отдельная Gemma assistant.

**CUDA graphs** — повторное использование подготовленной последовательности
GPU-операций, чтобы тратить меньше времени на их запуск. Оно тоже требует памяти.

### Speculative decoding: предложить и проверить

![Assistant предлагает токен, основная модель проверяет предложение](assets/07-speculation.svg)

**Speculative decoding** меняет цикл генерации: **draft** — вспомогательный
предсказатель — предлагает продолжение; **target**, основная модель, проверяет его.

1. Draft предлагает токены.
2. Target проверяет предложение.
3. При первом отклонении оставшийся хвост не становится ответом.

Средняя цена выданного токена приблизительно равна:

`(время draft + время verification) / число выданных токенов за цикл`.

**Acceptance** — доля принятых предложенных токенов. Измеряем её вместе
с задержкой: проверка дорогого черновика может съесть выигрыш.

**MTP (Multi-Token Prediction)** — предложение последующих токенов
для проверки основной моделью.

У нашей Gemma метод `mtp` в vLLM использует отдельный совместимый **assistant**.
Заменять его произвольной небольшой моделью нельзя. У Qwen позже увидим
MTP в основном checkpoint — файлах весов самой модели.
[Поддержка MTP и Gemma assistant](https://docs.vllm.ai/en/v0.31.0/features/speculative_decoding/mtp/).

<details>
<summary>Что ещё существует: cache-aware routing и prefill/decode disaggregation</summary>

#### Cache-aware routing

При нескольких репликах запрос направляют туда, где вероятнее найти нужный префикс.

#### Prefill/decode disaggregation

Обработку входа и генерацию разносят по разным исполнителям; между ними передают KV.

Эти механизмы сегодня не разворачиваем. [Схемы применения и источники](docs/SOURCES.md).

</details>

### Переключаем B Cache → B Tune

**A не меняем. B останавливаем до замены профиля.**

1. Скройте маршрут B в WebUI и дождитесь завершения её запросов.
2. В рабочем `gemma-b.yaml` поставьте `replicaCount: 0`.
3. Через GitOps примените остановку — сохраните изменение в Git и синхронизируйте Argo.
4. Замените профиль B целиком:

```bash
cp "$DEMO_DIR/values/gemma-b-spec.yaml" "$DEMO_DIR/values/gemma-b.yaml"
```

5. Верните `replicaCount: 1`.
6. Второй `valueFiles` Application B измените на `../../site/gemma-assistant.yaml`:
   подготовленный site-файл подключает основную модель и assistant из ai-models.
7. Проверьте render и отправьте оба изменённых файла в Git.
8. Примените конфигурацию **того же Application B** и новый commit.
9. Проверьте обе модели и параметры в Pod, получите ответ API и снова откройте
   `Gemma B — Tune` участникам.

При App-of-Apps сначала синхронизируйте родителя; иначе обновите подготовленный
манифест Application. [Порядок применения конфигурации](docs/GITOPS.md).

### Опыт 5. Длинный документ рядом с коротким ответом

1. **Предскажите:** что изменит chunked prefill для соседнего короткого ответа,
   а что изменит assistant?
2. **Попробуйте:** на B Tune повторите смешанный опыт, сохранённый перед остановкой
   B Cache: тот же длинный вход и параллельные короткие запросы. Окно всё ещё **16K**.
3. **Проверьте:** **TTFT, ITL, throughput и долю принятых draft-токенов**.
   Сначала сравните темп текста, затем измерения и ошибки.

<details>
<summary>Разбор: принятие токенов ещё не означает ускорение</summary>

**Chunked prefill** чередует части входа с генерацией начатых ответов.
Соседний короткий ответ может продолжаться быстрее, даже если TTFT самого
длинного запроса не уменьшился.

**Assistant** полезна, когда подготовка и проверка предложений дешевле обычного decode.

В B Tune включаются и CUDA graphs: разница B1/B2 — эффект набора настроек.
Для отдельного вклада MTP нужен опыт, меняющий только MTP. Высокий acceptance
без лучшей задержки не доказывает ускорение.

</details>

### Длинный контекст: сначала 64K, затем 128K

Сохранив настройки второй итерации, увеличьте только окно B:
сначала 65 536, затем 131 072 токена.

Это опыт на вместимость, отдельно от сравнения скорости с A.
**Вход + рассуждение + ответ должны поместиться в общее окно.**

```yaml
vllm:
  max-model-len: 131072
```

#### Две ступени проверки

| Окно | Вход | Выход | Запросов / одновременно |
| --- | ---: | ---: | ---: |
| 64K | 57 344 токена | 512 токенов | 1 / 1 |
| 128K | 122 880 токенов | 512 токенов | 1 / 1 |

В команде нагрузки выше поменяйте длины и параллельность, задайте отдельное имя серии.
Сохраните KV-пул, расход RAM и ответ. Проверка успешна при `completed=1`,
`failed=0` и полной заданной длине.

#### Какое окно оставить дальше

- Для нового сравнения с A верните `max-model-len: 16384`.
- Для платформенного опыта можно оставить B на 128K, но автоматическому
  запуску нужно такое же окно и остальные настройки.

256K выше — расчёт по архитектуре Gemma, не результат этого запуска.
Вместимость такого окна проверяют отдельно после подтверждения бюджета памяти.

> [!IMPORTANT]
> **128K — предел одной истории, не обещание восьми полных историй одновременно.**
> Даже при `max-num-seqs: 8` вместимость ограничивает реальный KV-пул.
> Отдельно проверяйте длину законченного ответа, параллельность и очередь.

<a id="platform"></a>
## 6. Gemma через AI Inference

![Model, класс и стратегия превращаются в план и управляемый сервис](assets/09-platform.svg)

**Задача автоматизации — воспроизвести согласованный запуск, а не ускорить
одинаковый vLLM.**

Веса, окно, точность KV, offload, assistant, RAM и GPU
должны совпасть с ручной конфигурацией.

Планировщик AI Inference сопоставляет:

- **Model** — сведения о выбранной модели;
- **стратегию** — цель запуска;
- **DeviceClass** — разрешённые классы устройств;
- **рецепты** — совместимые варианты runtime и параметров.

Результат — расчёт ресурсов и параметры запуска. Затем Kubernetes scheduler
и DRA выделяют конкретные устройства для Pod.

### Сначала рецепт, потом освобождение GPU

Откройте подготовленный `platform/gemma.yaml`: в нём Model, класс и стратегия,
а не командная строка vLLM.

**До остановки A проверьте рецепт:** он должен совпадать с B по окну,
CPU KV, assistant, chunked prefill и остальным параметрам.
Одного названия стратегии Throughput недостаточно.

Справочный Gemma 64K без CPU KV и assistant — другой профиль.
[Как проверить нужную поставку](docs/SETUP.md#inference-readiness).

#### Освобождаем первую H100

1. Скройте Base в WebUI и дождитесь завершения запросов.
2. Остановите ручную A через Git/Argo.
3. Дождитесь освобождения её ResourceClaim.
4. Включите заказ через `charts/inference-service`.

Ручная B остаётся на второй карте. RAM для двух настроенных моделей должна
быть зарезервирована при подготовке стенда.

#### Сопоставляем расчёт и запуск

В Argo проверьте применение заказа, в консоли — InferenceService, план, claim и дочерний Pod.

| Сопоставляем | Что проверяем |
| --- | --- |
| Наш расчёт `W + KV(N,S) + R` | Предположения о весах, истории и резервах |
| План AI Inference | Количество GPU, рецепт, окно и бюджеты |
| Запущенный контейнер | Фактические параметры, offload и assistant |

Если параметры или нагрузка различаются, сначала согласуйте их.

Сначала получим ответ непосредственно от API модели, затем включим маршрут
**`Gemma A — DP`** для `hf-platform-gemma`.
На дашборде меняется Service, не набор показателей.

#### Создаём заказ

В подготовленном `platform/gemma.yaml` включите `order.enabled: true`.
Это Helm values, не сырой Kubernetes-манифест:

```bash
set -o pipefail
helm template hf-platform-gemma "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После проверки — commit/push этого файла и Sync `hardfest-gemma-platform`.

В консоли дождитесь статуса **Ready** у `hf-platform-gemma`.
Откройте его цепочку: Model → план → claim → Pod.
В плане и контейнере должны совпасть окно, кеши и assistant последней ручной B.

## 7. Три сервиса на A30

До сих пор одна модель занимала целую карту. Теперь другая задача:
эмбеддер и реранкер могут делить карту, а голосовой сервис должен работать рядом.

**Переключите консоль и источник данных графиков на кластер A30.**
Сейчас работаем с ним, а H100 пока продолжают обслуживать Gemma.

### Kubernetes выдаёт устройство; MIG и MPS делят его ресурсы

Размещение в Kubernetes и разделение самой карты — разные задачи:

- **Device plugin** сообщает Kubernetes о доступных устройствах, обычно
  в виде целочисленного ресурса: например, «есть две GPU».
- **DRA** позволяет выбрать устройство по свойствам через класс и заявку
  `ResourceClaim`; драйвер подготавливает выбранный ресурс для Pod.

Оба механизма выдают устройство приложению, но сами не создают физическую
изоляцию между соседями. Как разделить память и вычисления, определяет механизм GPU.

[Device plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/),
[DRA](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/).

| Механизм | Что делится | Что важно для соседей |
| --- | --- | --- |
| **MIG — Multi-Instance GPU** | Аппаратные вычислительные ресурсы и память GPU | Фиксированные допустимые профили, отдельные экземпляры |
| **MPS — Multi-Process Service** | Совместное выполнение процессов на GPU или внутри MIG | Не добавляет память и не заменяет аппаратную изоляцию MIG |
| Time-slicing | Доступ контекстов к общему устройству во времени | Само по себе не делит память на изолированные аппаратные части |

В этой работе DRA связывает заказ с MIG/MPS нашего GPU-драйвера.

<details>
<summary>А как с этим связаны HAMi, Volcano и Vulkan?</summary>

Это решения разных уровней:

- **HAMi** управляет совместным использованием устройств в Kubernetes.
- **Volcano** планирует размещение и выполнение нагрузок.
- **Vulkan** — интерфейс для графических и вычислительных приложений,
  а не планировщик Kubernetes.

Они не являются другими названиями MIG или MPS.
Документация каждого проекта собрана в [источниках](docs/SOURCES.md).

</details>

### Что делает каждый сервис

![Одна A30: эмбеддер и реранкер делят 2g.12gb через MPS, Whisper занимает вторую 2g.12gb](assets/08-mig-mps.svg)

| Сервис | Простое объяснение | Модель и размещение |
| --- | --- | --- |
| **Эмбеддер** | Превращает текст в вектор, чтобы находить близкие по смыслу фрагменты | Qwen3 Embedding 4B, W4A16; первая `2g.12gb`, MPS |
| **Реранкер** | Повторно оценивает найденные фрагменты относительно вопроса и меняет их порядок | Qwen3 Reranker 4B, W4A16, sequence classification; та же партиция, MPS |
| **Whisper** | Преобразует речь в текст; это распознавание, не синтез речи | Whisper large-v3; вторая `2g.12gb`, отдельно |

Все три сервиса создаём через **InferenceService в кластере A30**.
Эмбеддер и реранкер будут соседями внутри одной аппаратной партиции;
Whisper получит другую.

**W4A16** — 4-битные веса и 16-битные активации. Профиль `2g.12gb` —
конкретный размер MIG-раздела A30, не универсальный профиль любой карты.

### Проверяем размещение до и после заказа

Чтобы увидеть **создание** MIG-разделов, начальное состояние должно позволять
новую поддерживаемую конфигурацию, а MIG mode должен быть включён.
Если нужные разделы уже существуют, увидим их выделение сервисам.
**Работающие чужие партиции не переразмечаем.**

1. На ноде A30 запишите исходный список устройств и MIG-разделов.
2. Создайте три заказа через Argo по шагам ниже и проследите их `ResourceClaim`.
3. Повторите команды на той же ноде и сравните состав разделов.

Команды для обоих снимков:

```bash
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

![Индексация документов, поиск и reranking подготавливают контекст для выбранной LLM](assets/16-rag.svg)

**RAG (Retrieval-Augmented Generation)** — ответ с найденными фрагментами
документов в контексте. Эмбеддер ищет, реранкер уточняет выбор, LLM формулирует
ответ. Документы не становятся от этого новыми весами модели.

#### Создаём заказы

Модели подготовлены через `catalog/a30.yaml`.
У каждого сервиса свой values и своё приложение Argo:

| Сервис | Values | Application |
| --- | --- | --- |
| Эмбеддер | `platform/embedding.yaml` | `hardfest-embedding-platform` |
| Реранкер | `platform/reranker.yaml` | `hardfest-reranker-platform` |
| Whisper | `platform/whisper.yaml` | `hardfest-whisper-platform` |

1. В трёх values включите `order.enabled: true`.
2. Проверьте Helm render и отправьте commit.
3. Последовательно синхронизируйте три Application; их destination — кластер A30.
4. В консоли этого кластера дождитесь готовности всех трёх InferenceService.

#### Проверяем не только размещение

Это **три разных API**, не три chat completion. Проверьте каждый отдельно,
затем эмбеддер и реранкер одновременно.

- У каждого сервиса проверьте время ответа, ошибки и результат обработки.
- У партиции — пик памяти и общий для эмбеддера и реранкера идентификатор MIG.
- Источник метрик на дашборде — **кластер A30**.

<summary>Разбор: когда индекс нужно перестраивать</summary>

- При переходе **Gemma → Qwen** индекс сохраняется: генератор ответа меняется,

<a id="tp2"></a>
## 8. Qwen через AI Inference на двух H100

**Теперь обе карты работают над одной моделью, а не обслуживают две её копии.**

![После проверки модели и плана обе Gemma останавливаются, две H100 получает Qwen](assets/17-qwen-transition.svg)

### Освобождаем две H100

1. Вернитесь в основной GPU-кластер. **До остановки Gemma** проверьте
   готовность артефакта Qwen, runtime, рецепта и класса устройств DeviceClass.
2. Скройте обе Gemma в WebUI и дождитесь завершения текущих запросов.
3. Остановите обе Gemma через GitOps и убедитесь, что обе H100 свободны.

Сервисы A30 и сам чат остаются включёнными.

### Как одна модель использует две карты

**TP (Tensor Parallelism)** — разделение тензорных вычислений одной модели
между несколькими GPU. **TP2** означает две карты: каждая делает свою часть,
после чего они обмениваются промежуточными результатами.

Это не две независимые копии модели и не название runtime TensorRT.
Наш runtime остаётся vLLM.

Заказ `platform/qwen.yaml` создаёт `hf-qwen-platform`.
Проверяем согласованность трёх уровней:

| Где смотрим | Что должно быть |
| --- | --- |
| План AI Inference | `acceleratorCount=2` |
| DRA claim | Две разные карты одной ноды |
| Конфигурация движка | `tensor-parallel-size: 2` |

![Tensor Parallel делит вычисления модели между двумя GPU и требует межкарточного обмена](assets/10-tp2.svg)

### Запускаем Qwen

В подготовленном `$DEMO_DIR/platform/qwen.yaml` меняем только
`order.enabled: true`; Model, класс и стратегия уже заданы. Не заменяем
этот values сырым InferenceService.

```bash
set -o pipefail
helm template hf-qwen-platform "$DEMO_DIR/charts/inference-service" \
  -n hardfest-demo -f "$DEMO_DIR/platform/qwen.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После успешной проверки:

1. Отправьте commit и выполните Sync `hardfest-qwen-platform`.
2. В консоли дождитесь готовности `hf-qwen-platform`; проверьте две разные GPU
   в claim и `tensor-parallel-size: 2` в Pod.
3. Проверьте `/v1/models` и законченный ответ `/v1/chat/completions`.
4. Добавьте Qwen в разрешённые модели действующих VK **без обнуления расхода**
   и отправьте тот же вопрос из WebUI с личным ключом.

**NVLink** — межкарточное соединение для обмена данными. Его наличие
не заменяет замер: проверяем задержки и скорость реальной нагрузки.

### Draft без отдельного assistant

![Qwen использует собственные MTP-головы без отдельной модели assistant](assets/18-qwen-mtp.svg)

У этой Qwen MTP встроен в модель: отдельная Gemma assistant ей не нужна.
Проверяем, что MTP включён, затем смотрим долю принятых предложений и время decode.

Для этого рецепта применяется native KV-offload с Simple CPU backend.
**Не копируйте в него Gemma OffloadingConnector:** способ переноса KV здесь другой.

![Нагрузка Qwen растёт от одного до восьми клиентов: сравниваем активные запросы, очередь и задержки](assets/19-qwen-capacity.svg)

### Опыт 8. Восемь участников — восемь полных окон?

1. **Предскажите:** если сервис принимает восемь запросов, поместятся ли восемь
   историй предельной длины одновременно на GPU?
2. **Попробуйте:** сначала один короткий запрос, затем concurrency 4 и 8.
   Длинный контекст проверьте отдельной серией.
3. **Проверьте:** **активные запросы, очередь, KV, ошибки и законченные ответы**.

<details>
<summary>Разбор: параллельность, очередь и вместимость KV</summary>

- **Лимит окна** ограничивает длину одной истории.
- **`max-num-seqs`** ограничивает число последовательностей в работе.
- **Размер KV-пула** определяет, какие истории помещаются одновременно;
  остальным запросам, возможно, придётся ждать.

«Ответил восьми людям» и «держит восемь полных длинных историй» — разные
результаты. Для второго нужна отдельная серия с известными длинами запросов.

</details>

## 9. Запрос участника, личный ключ и стоимость

### Находим свой запрос в Bifrost

Qwen и сервисы A30 пока остаются включёнными.

1. Отправьте последний вопрос в WebUI и откройте Bifrost рядом с чатом.
2. Найдите этот запрос: его модель, **личный VK**, входные и выходные токены,
   расчётную стоимость. Ключ подключения Bifrost к модели — другой ключ.
3. Сравните два одобренных аккаунта: личные ключи должны различаться,
   а доступные модели — соответствовать политике.

Остановленная модель не должна незаметно подменяться другой.

В используемой **HA-схеме (High Availability)** с несколькими репликами шлюза
есть ограничение точности общего счётчика расходов.
[Границы учёта и проверка лимита](docs/CHAT_AND_ACCESS.md#проверить-выдачу-и-отзыв).

### Когда действительно нужны ещё карты

Теперь можно вернуться к вопросу из начала. Перед добавлением GPU ответим на три вопроса:

- Сколько длинных историй помещается в память?
- Сколько запросов завершается с нужной задержкой?
- Нужна ли каждому сервису целая карта?

Каждый приём решает свою задачу:

| Приём | Когда нужен | Что сравниваем |
| --- | --- | --- |
| Prefix caching | В запросах повторяется начало | TTFT первого и повторного запроса |
| KV-offload | Рассчитанный KV нужно сохранить вне GPU | Перенос блоков, расход RAM, время повторного запроса |
| Chunked prefill | Длинный вход мешает обслуживать соседние запросы | Очередь, TTFT и ITL |
| Speculative decoding | Нужно ускорить последовательную генерацию | Принятые предложения draft и время decode |
| MIG и MPS | Небольшие сервисы могут делить карту | Размещение, память, задержки и ошибки каждого сервиса |
| TP2 | Одной карте не хватает ресурсов для модели | Распределение по двум GPU и скорость запросов |

AI Inference связывает модель, ресурсы и настройки в воспроизводимый заказ.
При переходе с ручного запуска параметры должны сохраниться — тогда можно
сравнивать ответы и задержки.

**Начинаем с причины ограничения, выбираем подходящий механизм и проверяем
его на той нагрузке, ради которой запускаем модель.** Так становится понятно,
где помогут настройки, а где действительно нужны дополнительные карты.

Для продолжения экспериментов: [методика и шаблон результатов](docs/MEASUREMENTS.md).

<a id="cleanup"></a>
## Остановка после завершения работы

После финальных запросов и сохранения результатов:

1. Скройте останавливаемые маршруты от участников и дождитесь завершения запросов.
2. Для ручных workloads задайте `replicaCount: 0`, выполните commit/push/sync.
3. Для платформенных заказов задайте `order.enabled: false` и проверьте diff в Argo.

**Sync без prune не удаляет существующий InferenceService.**
`order.enabled: false` только убирает его из Helm render. Удалите только выбранный
заказ с его дочерним workload по [инструкции остановки](docs/GITOPS.md#остановка).
Это отдельное явное действие.

Не удаляйте Namespace, Model, заявки хранилища PVC (PersistentVolumeClaim),
GPUClass/GPUPool, чаты и базы знаний.

После остановки проверьте отсутствие Pod нагрузки и освобождение claims.

## Подготовка своего стенда

### Что готово к началу

Основной маршрут начинается с уже работающей Base. До подключения участников:

- A отвечает в чате, модели доставлены на нужные ноды.
- Личные ключи, маршруты и графики проверены.
- B и платформенные заказы подготовлены, но не занимают H100.

### Как воспроизвести стенд

1. [Подготовьте инфраструктуру и запустите A](docs/SETUP.md).
   Здесь определены контексты и переменные команд.
2. Настройте [GitOps](docs/GITOPS.md) и [каталог моделей](catalog/README.md).
3. Подключите [чат и личные ключи](docs/CHAT_AND_ACCESS.md).
4. Настройте [мониторинг](docs/OBSERVABILITY.md) и проверьте его на запросах к A.

Все публичные workload-профили остаются выключенными; запускать их нужно
адресно из частного Git, не включая всё одновременно.

**Для одновременной ручной B и платформенной Gemma нужно не менее 192 GiB RAM
с проверенным распределением памяти.** На 128 GiB используйте последовательный
вариант: [расчёт RAM](docs/MEMORY_BUDGET.md#ram-выбрать-порядок-запуска).

Веса ai-models должны быть готовы на целевой ноде. Контейнерный образ vLLM
скачивается и кешируется отдельно от весов.
