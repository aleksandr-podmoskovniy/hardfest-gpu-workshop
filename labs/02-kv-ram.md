# KV-кэш в RAM

Сравним два способа повторно обработать большой документ после его вытеснения из GPU: выполнить prefill заново или вернуть сохранённый KV-кэш из RAM.

Нужны работающий B и достаточная свободная память узла. После A/B на 64K руководство отдельно увеличивает окно B до 128K, создаёт `.local/site-expanded.json` и набор `.local/long-128k.jsonl`. Эти настройки используются в обеих сериях cache-off/cache-on. Проверьте также лимит памяти контейнера. Подготовка описана в [настройке площадки](../docs/SETUP.md).

## Профиль

[gemma-b-cache.json](../manifests/profiles/gemma-b-cache.json) отличается от tuned-профиля настройкой выгрузки KV:

```json
{"kv-transfer-config":{"kv_connector":"OffloadingConnector","kv_role":"kv_both","kv_connector_extra_config":{"cpu_bytes_to_use":68719476736}}}
```

64 GiB — начальный бюджет эксперимента. Он общий для рабочих процессов и должен укладываться в их лимиты памяти. Это значение не определяется моделью GPU автоматически. Веса остаются на GPU. [Выгрузка KV в vLLM](https://docs.vllm.ai/en/v0.30.0/features/kv_offloading_usage/).

В локальном файле `kv_offload_gib` может переопределить этот бюджет. Для VM с 128 GiB используются 32 GiB и [меньшие базовые requests/limits](../docs/SETUP.md#2-параметры-своего-стенда); A на время обеих серий остановлена. Проверьте итоговый `render b-cache`, а не только исходный JSON профиля.

Генератор прибавляет бюджет к базовым requests/limits и к shared memory. С базой 64/80 GiB и кэшем 64 GiB получится 128/144 GiB RAM и `/dev/shm: 72Gi`. На нашей VM с базой 24/48 GiB и кэшем 32 GiB — 56/80 GiB и `/dev/shm: 40Gi`. KV размещается внутри этой shared memory, а не сверх неё. [Подробный расчёт](../docs/MEMORY_BUDGET.md). После изменения бюджета повторите `stop → apply → start`; для большего кэша заново проверьте вместимость ноды.

Увеличение окна и RAM-кэш — разные опыты. Более длинный активный запрос должен помещаться на GPU; RAM помогает сохранить KV для последующих обращений, но не отменяет эту проверку.

## Последовательность действий

1. Перезапустите B с tuned-профилем, переподключите port-forward.
2. Выполните X → другие документы → X. Сохраните результат в `results/raw/cache-off`.
3. Перезапустите B с cache-профилем, переподключите port-forward.
4. Повторите ту же последовательность в `results/raw/cache-on`.
5. Сопоставьте оба `x-return`: время prefill, ожидание в очереди, TTFT, запись и чтение KV в RAM, состояние GPU-кэша.

[Полные команды для обеих серий](../README.md#ram). Каждая серия начинается с нового процесса движка; для прогрева используется отдельный префикс. Сравнивайте повтор X отдельно от остальных документов нагрузки.

## Проверка

```bash
curl --fail --max-time 15 http://127.0.0.1:18002/metrics
```

Найдите в метриках работающего сервиса счётчики записи и чтения KV-коннектора. Нужно подтвердить три события: сохранение X в RAM, вытеснение из GPU и обратную загрузку. Число документов само по себе не гарантирует полезный опыт: X может остаться на GPU либо уже исчезнуть и из RAM. Число промежуточных документов подбирается по фактической ёмкости обоих кэшей; порядок должен быть одинаковым в контрольной серии. Если X отсутствует в обоих кэшах, повторное полное prefill не доказывает неисправность offload.

При попадании в RAM-кэш префикс возвращается на GPU. Время и объём повторного prefill можно сравнить с контрольной серией. Одна запись о включённом коннекторе в конфигурации попадание не подтверждает.

В проверенном образе отслеживайте приращения `vllm:kv_offload_total_bytes_total{transfer_type="CPU_to_GPU"}`, `vllm:external_prefix_cache_hits_total` и `vllm:prefix_cache_hits_total`. Последний относится к локальному GPU-кэшу. В [зафиксированном опыте](../results/kv-ram/README.md) повтор дал 3 102 474 240 байт CPU → GPU, 65 504 внешних cache-hit токена и нулевое приращение локальных hits. Суммарные счётчики до и после запроса опубликованы вместе с настройками.

Начните с десяти разных документов по 65 536 токенов, с фиксированным выходом 128. Семь документов на нашем GPU-пуле оставили исходный префикс в GPU. Это число не универсально: при изменении размера пула повторно подберите нагрузку по счётчикам. На каждую последовательную серию с десятью холодными документами здесь уходило около десяти минут.

## Если результат не получен

- Не хватило RAM: проверьте бюджет коннектора, лимит cgroup и потребление остальных процессов.
- Не хватает места в shared memory: сверьте размер `/dev/shm` с бюджетом offload; свободная RAM хоста не увеличивает лимит tmpfs автоматически.
- Коннектор не поддержал модель: сохраните ошибку запуска и вернитесь к совместимой конфигурации.
- Префикс остался на GPU: увеличьте разнообразие нагрузки в пределах доступных ресурсов и повторно проверьте вытеснение.
- Нет нужных счётчиков или трассировки: попадание в RAM-кэш пока не подтверждено.
- Время выросло: измерьте затраты на передачу и конкуренцию за память. Выгрузка KV не обязана ускорять холодный запрос.

## Завершение

```bash
python3 scripts/hf.py stop b-cache --ack
```

Это останавливает только B и сохраняет модели/PVC. Следующий профиль применяется к тому же Deployment.
