# Тот же мастер-класс на двух RTX 5060 Ti

См. также: [теория и весь сценарий RTX](../RTX5060.md), [стенд H100](../README.md),
[методика измерений](../docs/MEASUREMENTS.md), [дашборд](../docs/OBSERVABILITY.md).

![Пять этапов: Gemma A, кеш B, speculative B, платформенная Gemma, Qwen TP2](../assets/20-rtx-sequence.svg)

Здесь сохраняется последовательность основного доклада. Уменьшаются модели,
контекст и объём CPU-кеша; prefix cache, настоящий KV-offload, chunked prefill
и speculative decoding остаются. Никаких искусственных задержек в ответах.

## Что запускаем

| Этап | Модель и размещение | Что должно быть видно |
| --- | --- | --- |
| A — Base | Gemma 4 E2B, одна карта, ручной Helm | Ответ без исследуемых оптимизаций |
| B — Cache | Та же Gemma, вторая карта | Повторный префикс и перенос KV в RAM |
| B — Tune | Та же Gemma и её assistant | Chunked prefill, принятые draft-токены, CUDA graphs |
| A — DP | Gemma через AI Inference, первая карта | Заказ → план → DRA → Ready → ответ |
| Qwen — TP2 | Qwen3.5-9B BF16, обе карты | Две выделенные GPU, встроенный MTP и ответ в том же чате |

`DP` — подпись платформенного запуска, не Data Parallel.
RAG и Whisper остаются на A30; MIG/MPS на RTX не воспроизводим.
У RTX нет NVLink: работа TP2 здесь не подтверждает пропускную способность H100/NVLink.

### Почему именно эти модели

- [Gemma 4 E2B](https://huggingface.co/google/gemma-4-E2B-it)
  имеет отдельный [совместимый assistant](https://huggingface.co/google/gemma-4-E2B-it-assistant).
  Это не произвольная маленькая Gemma: assistant обучен для конкретной основной модели.
- [Qwen3.5-9B](https://huggingface.co/Qwen/Qwen3.5-9B) имеет собственный MTP.
  В этом опыте сохраняем BF16: языковые веса вместе с MTP занимают примерно
  17,13 GiB, больше доступной памяти одной RTX. Размещаем их через TP2,
  без выгрузки весов на CPU и без уменьшения их точности.
- Название E2B не означает checkpoint из двух миллиардов параметров:
  полный BF16 checkpoint Gemma занимает около 9,54 GiB. В текстовом запуске
  часть мультимодальных весов не загружается.

Сравниваем **A и B одной Gemma**, не скорость Gemma против Qwen.
Правила [speculative decoding vLLM 0.31](https://docs.vllm.ai/en/v0.31.0/features/speculative_decoding/)
и ограничения совместимости проверяются для выбранной пары.

<a id="setup"></a>
## Перед началом: модели, память и GitOps

Нужны две свободные RTX по 16 GiB, DRA DeviceClass для целой выделенной карты,
runtime vLLM 0.31.0 и AI Inference с компактными рецептами.
Веса готовим заранее: загрузка и первая компиляция не входят во время ответа.

| Ресурс | Настройка этого опыта |
| --- | --- |
| Gemma: контекст / параллельность | 4096 / 2, одинаково у A и B |
| Qwen: контекст / параллельность | 8192 / 2 |
| CPU KV-кеш B | 4 GiB |
| RAM ручного Pod / shared memory B | limit 18 GiB / 6 GiB |
| Доставка моделей | ai-models; backend должен обслуживать RTX-ноду |

Проверьте доступную RAM ноды **для суммы двух Pod и системных служб**.
`/dev/shm` входит в потребление памяти контейнера; это не добавочная память
сверх его limit. Числа H100 из основной схемы KV нельзя переносить на E2B.

> [!IMPORTANT]
> Этот вариант переводит доставку в **ai-models**. Прогон 6 октября выполнен
> с обычными RWO PVC и прямым Hugging Face; он не доказывает новый путь.
> На проверенном стенде NodeCache настроен только на H100. Для RTX нет отдельного
> пустого диска. Общекластерное переключение на SharedPVC затронет другие
> workloads; существующие RWO PVC не являются управляемым RWX backend ai-models.
> До подготовки доставки **не запускайте и не переключайте** рабочие сервисы.
> Для Gemma через AI Inference есть ещё отдельное условие: контроллер должен
> поддерживать внешний assistant из ai-models. Проверенная сборка пока его
> отвергает. У Qwen со встроенным MTP этого ограничения нет.

Три `Model` создаются из [catalog/rtx.yaml](../catalog/rtx.yaml).
Assistant закреплён на ревизии `2d874ef7d29f9a30599a1e4b3c1cbc9595f005df`;
основные модели тоже закреплены. Импорт заполняет каталог, но сам GPU не выделяет.
У ручных A/B укажите один и тот же образ из проверенной сборки AI Inference,
а не образ по умолчанию общего Helm-чарта. В опубликованном замере использован
runtime digest `sha256:f7cb9820c7e92eb78a4b3f60033e240c87a16bf99117471aba347fdd69eaca2d`.
В RTX values он указан явно; замените `REPLACE_RUNTIME_IMAGE` адресом доступного
вам registry и добавьте imagePullSecret при необходимости. Если используете
другую сборку, заново проверьте совместимость и измерьте A/B — результаты ниже
не считаются замером официального образа `vllm/vllm-openai`.
Ревизии нового каталога не приписываются задним числом прежнему замеру.
После смены доставки выполните новую серию A/B, не обновляя веса между сериями.

### 1. Подготовить частный каталог

Рабочая директория — ваша частная репа `k8s-config`; публичная копия находится рядом.
Для существующего стенда переносите изменения через diff, не поверх своих файлов.

```bash
export GPU_CONTEXT=gpu-cluster
export ARGO_CONTEXT=management
export ARGO_NAMESPACE=argocd
export RTX_DIR=argo-projects/gpu-cluster/hardfest-rtx
export NS=hardfest-rtx

mkdir -p "$RTX_DIR/charts" "$RTX_DIR/values" "$RTX_DIR/catalog" "$RTX_DIR/platform" "$RTX_DIR/argo-app"
cp -R ../hardfest-gpu-workshop/charts/vllm-runtime "$RTX_DIR/charts/"
cp -R ../hardfest-gpu-workshop/charts/inference-service "$RTX_DIR/charts/"
cp -R ../hardfest-gpu-workshop/charts/model-catalog "$RTX_DIR/charts/"
cp ../hardfest-gpu-workshop/catalog/rtx.yaml "$RTX_DIR/catalog/"
cp ../hardfest-gpu-workshop/values/rtx/gemma-*.yaml "$RTX_DIR/values/"
cp ../hardfest-gpu-workshop/platform/rtx-*.yaml "$RTX_DIR/platform/"
cp ../hardfest-gpu-workshop/argocd/rtx/*.yaml "$RTX_DIR/argo-app/"
```

В редакторе замените `REPLACE_*`: имя ноды, класс GPU и адрес образа.
Добавьте нужные tolerations и разрешённый ingress от шлюза и мониторинга.
Для закрытых весов добавьте `authSecretName` к записи каталога;
Secret с ключом `token` создайте через менеджер секретов в том же namespace.
Сам токен в Git не хранится.

Ручные профили используют `modelRefs`, без самостоятельно подключённых PVC.
Чарт ставит аннотацию на Deployment; ai-models доставляет Gemma и, для второго B,
assistant в `/data/modelcache/models/<имя-Model>`.

Для платформенных заказов подготовьте два InferenceServiceClass:
single — максимум 1 GPU и модель до 6B; pair — максимум 2 GPU и модель до 10B.
Оба допускают namespace опыта, выделенные WholeDevice и выбранный DeviceClass.
Доставка весов должна быть совместима с размещением на этой RTX-ноде.

### 2. Доставить файлы до выделения GPU

Импорт создаёт реальные загрузки: у каталога нет переключателя `replicaCount`.
Проверьте свободное место в хранилище артефактов и в backend доставки, затем render:

```bash
helm lint "$RTX_DIR/charts/model-catalog" --strict -f "$RTX_DIR/catalog/rtx.yaml"
helm template rtx-models "$RTX_DIR/charts/model-catalog" -n "$NS" -f "$RTX_DIR/catalog/rtx.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

В скопированных [Argo Applications](../argocd/rtx/) заполните repoURL, ветку,
destination и относительный `valueFiles`, как в
[общем GitOps-порядке](../docs/GITOPS.md); autosync и общий prune не включайте.
После commit/push синхронизируйте **конкретный commit**.

Если `rtx-models` уже управлял прежними preload Jobs/PVC, сравните diff смены
чарта. **Prune выключен**: не удаляйте старые тома до приёмки каталожного пути.

```bash
kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" apply -f "$RTX_DIR/argo-app/"
export REVISION=$(git rev-parse HEAD)
kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" patch application rtx-models \
  --type merge -p "{\"operation\":{\"sync\":{\"revision\":\"$REVISION\",\"prune\":false,\"syncStrategy\":{\"apply\":{}}}}}"
```

Для следующих этапов тем же способом синхронизируйте нужное Application:
`rtx-gemma-base`, `rtx-gemma-tune`, `rtx-gemma-platform` или `rtx-qwen35-tp2`.
Перед каждым sync зафиксируйте и отправьте изменения в Git, обновите `REVISION`.

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" get models.ai.deckhouse.io -w
```

После `Ready` остановите наблюдение `Ctrl+C` и проверьте артефакты:

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" get models.ai.deckhouse.io \
  -o custom-columns='NAME:.metadata.name,PHASE:.status.phase,BYTES:.status.artifact.sizeBytes,DIGEST:.status.artifact.digest'
kubectl --context "$GPU_CONTEXT" get moduleconfig ai-models -o jsonpath='{.spec.settings.delivery}'
```

В Console выберите **GPU-кластер → hardfest-rtx → AI-модели → Каталог моделей**.
В «Скачанных» должны быть Gemma, assistant и Qwen. При `Failed`, пустом digest
или несовпадении выбранной RTX-ноды с backend доставки остановитесь:

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" describe model rtx-gemma-e2b
kubectl --context "$GPU_CONTEXT" -n "$NS" describe model rtx-qwen35-9b
kubectl --context "$GPU_CONTEXT" -n "$NS" get modeldeliveries,pods,pvc
```

`Model Ready` означает готовый артефакт, не уже смонтированные веса на каждой ноде.
После старта каждого workload проверяйте его доставку и mounts. Не меняйте
`delivery.type` всего модуля ради обхода этой проверки и не выдавайте отдельный
неиспользуемый `Model` рядом с HF-сервисом за интеграцию.

### 3. Подготовить маршруты и доступ в чате

Настройте регистрацию, адаптер личных VK и тарифы по
[подключению чата](../docs/CHAT_AND_ACCESS.md). Для этого опыта используйте
следующие соответствия; все Service находятся в namespace `hardfest-rtx`.
Адрес upstream — `http://<Service>.hardfest-rtx.svc.cluster.local:<порт>`.

| Этап / название в WebUI | Внешний ID маршрута | Service:порт | Имя модели upstream |
| --- | --- | --- | --- |
| Gemma A — Base | `vllm/rtx-gemma-base` | `rtx-gemma-base:8000` | `rtx-gemma-base` |
| Gemma B — Tune | `vllm/rtx-gemma-tune` | `rtx-gemma-tune:8000` | `rtx-gemma-tune` |
| Gemma A — DP | `vllm/rtx-gemma-base` | `rtx-gemma-platform:80` | `rtx-gemma-e2b` |
| Qwen 9B — TP2 | `vllm/rtx-qwen35-tp2` | `rtx-qwen35-tp2:80` | `rtx-qwen35-9b` |

При `src: ai-models` движок публикует имя объекта Model, не HF-репозиторий.
Перед изменением маршрута проверьте `/v1/models`. Обновите также разрешённые
upstream-имена и тарифную привязку; внешний ID и уже выданный VK сохраните.

При переходе Base → DP меняются upstream существующего маршрута и название
в WebUI, а не пользователь и его ключ. Для всех маршрутов отключите fallback
между A/B и кеш готовых ответов шлюза. Значения `chat_template_kwargs`
с `enable_thinking: false` задайте одинаково для сравниваемых моделей.

В частных values адаптера согласуйте `chat_models`, provider key IDs и
разрешённые модели, включая их фактические upstream-имена. Для уже выданных VK
обновите разрешения административным API с сохранением ID, секрета и накопленного
расхода; перевыпуск ключа или сброс бюджета не нужен. После изменения проверьте
тот же VK на каждой реплике шлюза. Режим MCP участникам не разрешайте.

В WebUI показывайте только модели текущего этапа: сначала A/B, затем DP/B,
в финале Qwen. Остановленные модели скрывайте, не удаляя записи и чаты.
Проверяйте отсутствие обходного доступа через базовое подключение.

<a id="base"></a>
## 1. Gemma A: получить исходную точку

Сначала зафиксируйте ответ и метрики без исследуемых механизмов.

Профиль [gemma-base.yaml](../values/rtx/gemma-base.yaml).
В нём выключены prefix cache, chunked prefill, CUDA graphs, KV-offload и
speculative decoding. Это намеренно упрощённый vLLM 0.31, **не эмуляция старого vLLM**.

Установите `replicaCount: 1`, проверьте Helm render и server dry-run, отправьте
commit и синхронизируйте Application A. Полный цикл изменения — в
[GitOps](../docs/GITOPS.md). Не запускайте `helm upgrade` поверх Argo.

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" rollout status deployment/rtx-gemma-base --timeout=30m
kubectl --context "$GPU_CONTEXT" -n "$NS" get pods,resourceclaims
kubectl --context "$GPU_CONTEXT" -n "$NS" port-forward svc/rtx-gemma-base 18001:8000
```

В другом терминале:

```bash
curl --fail-with-body --max-time 180 \
  http://127.0.0.1:18001/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"rtx-gemma-base","temperature":0,"max_tokens":128,"messages":[{"role":"user","content":"Объясни KV-кеш двумя короткими предложениями."}]}'
```

Проверьте полный осмысленный ответ, рост успешных запросов на дашборде,
нет ошибок CUDA. Runtime предупреждает, что Gemma 4 официально не поддерживает
отключённый chunked prefill. Поэтому одного `Ready` недостаточно:
проверьте несколько запросов и не используйте этот baseline как производственную рекомендацию.

<a id="cache"></a>
## 2. Первая B: повторный префикс и KV в RAM

Разделите два эффекта: повторное использование префикса на GPU и восстановление KV из RAM.

Профиль [gemma-cache.yaml](../values/rtx/gemma-cache.yaml):
prefix cache, FP8 KV, Triton attention и 4 GiB CPU KV.
Chunked prefill, speculative decoding и CUDA graphs пока выключены.
Запустите B на второй свободной карте через отдельный Application.

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" rollout status deployment/rtx-gemma-tune --timeout=30m
kubectl --context "$GPU_CONTEXT" -n "$NS" port-forward svc/rtx-gemma-tune 18002:8000
```

Повторите один длинный префикс с разными короткими вопросами.
Затем отправьте серию разных префиксов, чтобы вытеснить старый GPU KV,
и повторите исходный запрос.

**Проверка на общем дашборде:**

- повтор без вытеснения увеличивает prefix hits;
- запись в RAM увеличивает GPU→CPU bytes;
- повтор после вытеснения увеличивает **CPU→GPU bytes и external-prefix hits**.

Запись в RAM сама по себе не доказывает повторное чтение. Если GPU-кеша хватает
на все запросы, отсутствие CPU→GPU нормально. Для отдельной диагностики можно
ограничить GPU KV до 256 MiB через `kv-cache-memory-bytes`, сохранив тот же
CPU-кеш; после подтверждения чтения лимит обязательно убрать.
Этот диагностический профиль не участвует в сравнении производительности.

<a id="speculate"></a>
## 3. Вторая B: prefill и speculative decoding

![Assistant предлагает токены, основная модель проверяет и принимает последовательность](../assets/07-speculation.svg)

Теперь измените обслуживание запросов, сохранив первую итерацию кешей.

Замените профиль B **целиком** на
[gemma-spec.yaml](../values/rtx/gemma-spec.yaml), верните привязки площадки,
установите `replicaCount: 1`. Service остаётся `rtx-gemma-tune`.
В Application `rtx-gemma-tune` замените единственный `valueFiles` с
`../../values/gemma-cache.yaml` на `../../values/gemma-spec.yaml`.
Включаются chunked prefill с бюджетом 512 токенов, CUDA graphs с capture size 4
и совместимый assistant с одним draft-токеном за цикл.

Проверьте, что в Pod есть assistant mount, а в аргументах —
`method: mtp` и его локальный путь; после запросов растут
`vllm:spec_decode_num_draft_tokens_total` и
`vllm:spec_decode_num_accepted_tokens_total`.
В стартовых логах должны быть захват CUDA graphs и готовность движка.

Число принятых токенов доказывает работу speculative decoding, но **не ускорение**.
FP8 KV, Triton и CUDA graphs тоже входят в изменения A→B.
Нельзя приписывать всю разницу одному assistant.

<a id="benchmark"></a>
### Короткая одинаковая нагрузка

Для каждой серии используйте один вход, выход, seed и параллельность.
Клиент внутри Pod подходит для проверки, но влияет на CPU: для итоговых цифр
вынесите его на отдельную CPU-ноду.

```bash
export SERVICE=rtx-gemma-base
# Для B: export SERVICE=rtx-gemma-tune
kubectl --context "$GPU_CONTEXT" -n "$NS" exec "deployment/$SERVICE" -- \
  vllm bench serve --backend vllm \
    --base-url "http://$SERVICE.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model "$SERVICE" --tokenizer /data/modelcache/models/rtx-gemma-e2b \
    --dataset-name random --seed 42 \
    --random-input-len 2048 --random-output-len 128 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 2 --ignore-eos --temperature 0 \
    --percentile-metrics ttft,tpot,itl --metric-percentiles 95,99 \
    --save-result --result-dir /runtime/bench --result-filename rtx.json
```

Сохраните JSON до замены Pod. Ожидаются completed=8, failed=0,
total_input_tokens=16384, total_output_tokens=1024.
Восемь запросов — короткая проверка, не устойчивый p95.
Для сравнения нужны минимум три повторения и одинаковое состояние кеша.

Замер 6 октября 2026 на двух RTX 5060 Ti, по одной карте на реплику:

| Профиль | Выходные токены/с, три серии | Среднее время на выходной токен |
|---|---|---|
| A — Base | 30,05 / 29,80 / 29,89 | 64,39–64,94 мс |
| B — Tune | 161,33 / 203,07 / 203,60 | 8,77–9,36 мс |

Все серии завершили 8 из 8 запросов. Входы повторяются: последующие серии B
используют прогретый prefix cache. Это сравнение **полных профилей**, а не
отдельный замер выигрыша от MTP и не результат холодного старта.
Клиент работал внутри Pod. [Условия и метрики](../results/rtx5060-gemma-20261006.json),
[исходные результаты vLLM](../results/rtx5060-20261006/).

<a id="platform"></a>
## 4. Та же Gemma через AI Inference

Получите тот же набор механизмов из рецепта, не меняя дочерний Deployment.

> [!WARNING]
> В проверенной сборке внешний assistant требует `HuggingFace` и отвергается
> для `ai-models`. До появления поддержки этого пути не останавливайте A
> ради платформенной Gemma с assistant. Прямая HF-подмена не завершает этот этап.

Остановите ручную A через её values (`replicaCount: 0`) и дождитесь освобождения
первой GPU. B оставьте на второй. В
[rtx-gemma.yaml](../platform/rtx-gemma.yaml) заполните классы и включите заказ.

```bash
helm template rtx-gemma-platform "$RTX_DIR/charts/inference-service" -n "$NS"   -f "$RTX_DIR/platform/rtx-gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После commit/push/sync остановите прежний port-forward A, затем выполните:

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" get inferenceservice rtx-gemma-platform -o yaml
```

```bash
curl --fail-with-body --max-time 30 http://127.0.0.1:18001/v1/models
curl --fail-with-body --max-time 180 http://127.0.0.1:18001/v1/chat/completions \
  -H 'Content-Type: application/json' \

```

Рецепт должен дать 4K, одну GPU, оба кеша, chunked prefill, graphs и assistant
из отдельного артефакта ai-models. Проверьте фактические пути mount и digest
обоих артефактов. Готовность основной Gemma не заменяет готовность assistant.
В Console должны одновременно присутствовать Model и связанный InferenceService.

Проверьте Ready, ответ API, принятые draft-токены; затем повторный запуск
читает оба уже доставленных артефакта. Переключите upstream существующего
маршрута A на новый Service по таблице выше и подпишите его в WebUI `Gemma A — DP`.

## 5. Qwen через AI Inference: две карты, встроенный MTP

![TP2 делит одну модель между двумя RTX 5060 Ti](../assets/24-rtx-tp2.svg)

Перейдите от одной GPU к совместной работе двух, сохранив чат и доступы.

Сначала проверьте каталог, backend доставки и заказ:
`model.src: ai-models`, `ref.kind: Model`, `ref.name: rtx-qwen35-9b`.
Нативному MTP отдельный assistant не нужен. Если доставка на RTX не готова,
не останавливайте работающий сервис и не включайте этот заказ.

Сначала остановите ручную B. Для платформенной Gemma задайте
`order.enabled: false`; в её отдельном Application выполните выборочный
prune **только InferenceService**, как описано в [остановке GitOps](../docs/GITOPS.md#остановка).
PVC и модели не удаляйте. Проверьте, что обе DRA-заявки освободились.

Включите [rtx-qwen.yaml](../platform/rtx-qwen.yaml), отправьте и синхронизируйте commit.
Qwen использует собственные MTP-веса; внешний assistant ему не нужен.

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" get inferenceservice rtx-qwen35-tp2 -o yaml
kubectl --context "$GPU_CONTEXT" -n "$NS" get resourceclaims -o yaml

```

```bash
curl --fail-with-body --max-time 30 http://127.0.0.1:18003/v1/models
curl --fail-with-body --max-time 180 \
  http://127.0.0.1:18003/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"rtx-qwen35-9b","temperature":0,"max_tokens":256,"chat_template_kwargs":{"enable_thinking":false},"messages":[{"role":"user","content":"Объясни разницу между TP2 и двумя независимыми репликами."}]}'
```

Проверьте две **разные** выделенные GPU, tensor-parallel-size=2,
`qwen3_next_mtp`, принятые draft-токены, полный потоковый и обычный ответ.
Потом тот же вопрос через WebUI, где активен `Qwen 9B — TP2`, и запись расхода
на личном VK. Неактивные Gemma скройте из выбора, записи моделей не удаляйте.

В прогоне 6 октября платформенные Gemma и Qwen получили Ready и ответили на
обычные и потоковые запросы. Gemma прошла повторный запуск с попаданием в кеш
основной модели и assistant. Qwen получил две разные RTX; его ответ проверен
через личный VK на каждой из трёх реплик шлюза и через WebUI с перезагрузкой
страницы. [Результат функционального прогона](../results/rtx5060-platform-20261006.json)

## Проверка: дашборд и весь путь

Используйте **тот же** [AI Inference / Service performance](../docs/OBSERVABILITY.md),
не отдельный dashboard на каждый профиль. Фильтры — кластер, namespace, сервис, модель.
Нет данных — это не нулевая нагрузка.

- [ ] Три Model видны в каталоге RTX; InferenceService ссылается именно на них.
- [ ] Фактические mounts соответствуют артефактам ai-models, не прежнему HF PVC.
- [ ] Gemma с assistant и Qwen TP2 видны в сервисах на своих этапах и отвечают.
- [ ] A, B и платформенные сервисы появляются в фильтрах после scrape.
- [ ] После запроса видны токены, TTFT, очередь и завершения.
- [ ] Для B различаются GPU-prefix hits и чтение KV из RAM.
- [ ] Для MTP растут предложенные и принятые токены.
- [ ] Pending-пользователь не получает доступ; после одобрения — один личный VK.
- [ ] Ответ в WebUI завершается и сохраняется после перезагрузки страницы.
- [ ] В шлюзе запрос связан с этим VK, моделью и тарифом; MCP участнику запрещён.
- [ ] После перехода на Qwen старые Gemma не занимают карты; PVC сохранены.

Скриншот Ready не заменяет этот список. Итоги замеров публикуйте только
с профилем, версией runtime, длинами запросов и числом ошибок.
