# 1. Gemma A/B на двух H100

Запустим две копии Gemma на разных H100 одного узла и сравним их на одинаковых запросах. Перед началом [подготовьте площадку](../docs/SETUP.md): обе карты должны быть свободны, файлы моделей — доступны локально.

## Запуск реплик

Для основного сравнения задайте `context_tokens: 65536` в `.local/site.json`.
Вход составит 32 768 токенов, предел выхода — 2048. A использует профиль
`a-chunked`, B — `b-tuned`.

| Параметр | A: `a-chunked` | B: `b-tuned` |
| --- | --- | --- |
| Веса | BF16, только GPU | Те же BF16, только GPU |
| Контекст | 65 536 | 65 536 |
| Предел активных последовательностей | 32 | 32 |
| Доля GPU-памяти движку | 90% | 90% |
| Порция prefill | 4096 | 4096 |
| KV | BF16 | FP8 |
| Prefix cache | Выключен | Включён |
| CUDA graphs | Выключены | Включены |
| `torch.compile` | Выключен через `enforce-eager` | Включён |
| Бэкенд attention на проверенной H100 | FlashAttention 4 | Triton |
| KV в RAM | Нет | Нет |

Чанкирование у A оставлено для вместимости длинного входа. Этот вариант нельзя
называть «все оптимизации выключены». В vLLM 0.30 часть оптимизаций включена по
умолчанию; они появились не одновременно и не только в этой версии. Prefix
cache помогает при повторном входе, но не даёт такого же выигрыша независимым
префиксам.

Для выключения prefix cache записано `no-enable-prefix-caching: true`.
В проверенном запуске `vllm serve --config` положительное имя с `false` не
выключило параметр. Проверяйте строку Engine: у A должны быть
`enable_prefix_caching=False`, `enable_chunked_prefill=True`, `enforce_eager=True`.

B использует FP8 KV и явно выбирает `TRITON_ATTN`: автоматический выбор FlashInfer в проверяемом образе завершился ошибкой CUDA-архитектуры на H100. Бэкенд тоже влияет на скорость; фиксируйте его в отчёте, не приписывайте всю разницу одному формату KV. Успешный запуск и качество ответов этого профиля ещё нужно подтвердить на своей площадке. [Разбор ограничения в upstream](https://github.com/vllm-project/vllm/issues/48848).

Если A уже запущен с другим профилем, сначала выполните `stop a --ack`.
`a` и `a-chunked` используют один Deployment: третья реплика не создаётся.

```bash
python3 scripts/hf.py apply a-chunked --ack
python3 scripts/hf.py apply b-tuned --ack
python3 scripts/hf.py start a-chunked --ack
python3 scripts/hf.py start b-tuned --ack
python3 scripts/hf.py get resourceclaims
python3 scripts/hf.py logs a-chunked
python3 scripts/hf.py logs b-tuned
```

DRA должен назначить разные физические устройства. Сверьте идентификаторы в назначениях ResourceClaim и UUID, которые видит CUDA внутри контейнеров. Вывод `nvidia-smi` на узле не показывает, какая карта доступна каждому контейнеру.

Сохраните из логов фактическую конфигурацию, формат и ёмкость KV-кэша, вычислительную реализацию, сведения о компиляции и захвате графов, доступную память. Выполните короткий пробный запрос к каждой реплике. HTTP 200 на `/health` недостаточно: сервис должен сгенерировать ответ.

## Запросы к двум сервисам

```bash
python3 scripts/hf.py port-forward a-chunked 18001
# В другом терминале:
python3 scripts/hf.py port-forward b-tuned 18002
```

В третьем терминале выполните серии из [методики измерений](../docs/MEASUREMENTS.md). Реплики используют CPU и память одного узла, поэтому нагружайте их последовательно: сначала A, затем B, потом в обратном порядке. Одновременные прогоны будут влиять друг на друга.

## Отдельный опыт: отключить и чанкирование

Профиль `a` выключает prefix cache, chunked prefill и CUDA graphs. Для него
генератор задаёт `max-num-batched-tokens` не меньше контекста: вход обрабатывается
целиком. Память рабочих буферов и раскладка KV могут отличаться от `a-chunked`.
При проверке окна 131 072 движок потребовал 110,01 GiB KV при доступных 6,37 GiB
и отказал в запуске. Это результат проверки вместимости, не измерение скорости.

Посмотреть отличия без изменения кластера:

```bash
python3 scripts/hf.py diff a a-chunked
```

Не смешивайте результаты `a` и `a-chunked`. Если проверяете `a` отдельно,
останавливайте текущий A перед сменой профиля и сохраняйте точную ошибку запуска.

## Если выбранное окно не поместилось

Сохраните ошибку запуска и бюджет памяти. Уменьшите `context_tokens` в `.local/site.json` до общего для обеих реплик значения, остановите оба Deployment и повторите `apply` и `start`. Не добавляйте выгрузку весов в RAM. Скорость сравнивается при одинаковом окне; предельную вместимость каждого профиля измеряйте отдельно.

## Условия сравнения

- Учитываются все ошибки, в том числе нехватка памяти.
- Версии моделей, SHA запросов и параметры генерации совпадают.
- Длина входа подтверждена полем `usage` сервера.
- Префиксы холодной серии различаются; шлюз не возвращает готовые ответы из своего кэша.
- Проверяется, что выбранные оптимизации действительно выключены у A и включены у B; одной записи в JSON недостаточно.
- Пользовательский путь в обоих случаях остаётся Open WebUI → HA Bifrost → vLLM. Прямые замеры API и замеры полного пути с RAG сохраняются отдельно.

После измерений остановите реплики. Модели и общие PVC сохранятся.

```bash
python3 scripts/hf.py stop a --ack
python3 scripts/hf.py stop b-tuned --ack
```
