# Длинные запросы к A и B

Одинаковые веса, окно 65 536, вход 32 768, выход 2048, concurrency 4.
У A BF16 KV и выключены prefix cache/CUDA graphs; у B FP8 KV и обе оптимизации.
Чанкирование 4096 оставлено в обоих вариантах для вместимости.

Развёртывание выполняется [через GitOps](../docs/GITOPS.md).
На ноутбуке не нужны Python, transformers и скачанные веса.
Используем штатный [vllm bench serve](https://docs.vllm.ai/en/latest/cli/bench/serve/)
из закреплённого образа; наличие флагов проверено в работающем runtime.

## Короткая проверка CLI

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec deployment/hf-gemma-a -- \
  vllm bench serve --help=all
```

Тест ниже генерирует **синтетические**, а не осмысленные документы.
Для проверки качества и RAG используйте отдельно одинаковые реальные учебные документы.

## Два прогона

На выделенном стенде, без пользовательских запросов:

```bash
for SLOT in a b; do
  kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec deployment/hf-gemma-a -- \
    vllm bench serve \
      --backend vllm \
      --base-url "http://hf-gemma-$SLOT.hardfest-demo.svc.cluster.local:8000" \
      --endpoint /v1/completions \
      --model gemma-4-31b --tokenizer /models/gemma \
      --dataset-name random --seed 42 \
      --random-input-len 32768 --random-output-len 2048 --random-range-ratio 0 \
      --num-prompts 8 --max-concurrency 4 --ignore-eos --temperature 0 \
      --percentile-metrics ttft,tpot,itl --metric-percentiles 95,99 \
      --save-result --result-dir /runtime/bench --result-filename "$SLOT.json"
done
```

Клиент в этом примере запускается в контейнере A для обеих серий и расходует его CPU/RAM.
Для итоговых больших замеров вынесите клиент в отдельный CPU Pod на отдельной ноде
с тем же токенизатором; не меняйте расположение клиента между A и B.
`--random-range-ratio 0` выключает разброс длин; значение 1 в этом runtime означает
разброс вплоть до нулевой длины, а не фиксированный размер.
CLI выполняет пробный запрос перед серией — не называйте всю серию полностью холодной.
Для строгой холодной/тёплой проверки отдельно контролируйте префиксы и кэш.

`--ignore-eos` заставляет получить заданный объём генерации; это тест скорости,
не настройки пользовательского чата. Связывайте результаты с фактическими
input/output tokens из отчёта. Начните с 8 запросов; для устойчивого p95 нужны
более длинные серии и не менее трёх повторов с одинаковым прогревом.

## Сохранение результатов

Из k8s-config сохраните результаты вне путей, которые Argo применяет как манифесты:

```bash
mkdir -p results/hardfest/ab
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec deployment/hf-gemma-a -- \
  cat /runtime/bench/a.json > results/hardfest/ab/a.json
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec deployment/hf-gemma-a -- \
  cat /runtime/bench/b.json > results/hardfest/ab/b.json
jq . results/hardfest/ab/a.json
jq . results/hardfest/ab/b.json
```

Каталог /runtime временный: выгрузите результаты **до** перезапуска Pod.
Сохраните также SHA коммита и ConfigMap с параметрами. Никаких Secret или kubeconfig в результатах.

TTFT benchmark включает путь клиента до первого токена. Очередь и prefill
берите отдельно из метрик сервера. Не вычитайте p95 очереди из p95 TTFT:
это разные распределения. [Методика](../docs/MEASUREMENTS.md).
