# Измерить Gemma A и две конфигурации B

Сравним время первого токена и скорость генерации при одинаковой нагрузке.
Меняются параметры движка, но не веса, окно контекста или длины запросов.

## Перед началом

- [ ] Рабочий каталог терминала — корень частного `k8s-config`.
- [ ] Контексты и Applications подготовлены по [GitOps](../docs/GITOPS.md).
- [ ] Проверяемый сервис отвечает на короткий запрос; на GPU нет новых ECC/Xid.
- [ ] Токенизатор той же ревизии доступен в каталоге ai-models (или выбранном PVC).
- [ ] Во время серии нет пользовательских запросов и конкурирующей нагрузки.

> [!IMPORTANT]
> На VM с 128 GiB RAM запускайте профили с KV-offload последовательно:
> остановите A через Git/Argo перед запуском B.

## 1. Зафиксировать условия

| Условие | Значение для всех трёх серий |
| --- | --- |
| Окно | 16 384 токена |
| Вход / выход одного запроса | 8192 / 2048 токенов |
| Запросов / параллельно | 8 / 4 |
| Seed / температура | 42 / 0 |

| Серия | Профиль | Что проверяем |
| --- | --- | --- |
| `a-base` | A: BF16 KV, без prefix cache, offload и CUDA graphs | Исходная конфигурация |
| `b-cache` | B: FP8 KV, Triton attention, prefix cache, 32 GiB CPU KV | Первая итерация |
| `b-spec` | B: те же кэши, prefill 2048, CUDA graphs, assistant | Вторая итерация |

У A и первой B chunked prefill выключен явно; бюджет prefill равен 16 384.
A — намеренно упрощённый профиль vLLM 0.31, не его стандартные настройки
и не запуск старой версии движка.

## 2. Выполнить серию

Выберите текущий профиль и путь токенизатора:

```bash
export SLOT=a SERIES=a-base
export TOKENIZER_PATH=/data/modelcache/models/gemma-4-31b
# Для PVC задайте фактический mount, например /models/gemma.
# Первая B: export SLOT=b SERIES=b-cache
# Вторая B: export SLOT=b SERIES=b-spec
```

Сначала проверьте короткий ответ. В отдельном терминале с теми же переменными:

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo port-forward "svc/hf-gemma-$SLOT" 18001:8000
```

В основном терминале:

```bash
curl --fail --max-time 30 http://127.0.0.1:18001/v1/models
curl --fail-with-body --max-time 180 http://127.0.0.1:18001/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"gemma-4-31b","max_tokens":512,"temperature":0,"messages":[{"role":"user","content":"Объясни KV-кеш двумя предложениями."}]}'
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec "deployment/hf-gemma-$SLOT" -- \
  vllm bench serve --help=all
```

Нужен полный ответ без ошибки. Остановите этот port-forward перед переходом
к другому сервису. Bench ниже обращается к Service внутри кластера:

```bash
mkdir -p "results/hardfest/$SERIES"
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec "deployment/hf-gemma-$SLOT" -- \
  vllm bench serve \
    --backend vllm \
    --base-url "http://hf-gemma-$SLOT.hardfest-demo.svc.cluster.local:8000" \
    --endpoint /v1/completions \
    --model gemma-4-31b --tokenizer "$TOKENIZER_PATH" \
    --dataset-name random --seed 42 \
    --random-input-len 8192 --random-output-len 2048 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 4 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --percentile-metrics ttft,tpot,itl --metric-percentiles 95,99 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/hardfest/$SERIES/bench.txt"
```

Эта короткая проверка запускает клиента внутри Pod модели: он тоже потребляет
CPU и RAM. Для итогового сравнения вынесите клиента на одну отдельную CPU-ноду
с тем же токенизатором и не меняйте его размещение между сериями.

| Параметр | Зачем он нужен |
| --- | --- |
| `random` | Синтетические входы для нагрузки, не проверка качества или RAG |
| `--random-range-ratio 0` | Одинаковые длины без разброса |
| `--ignore-eos` | Полная заданная длина генерации; не настройка пользовательского чата |

Эта команда отключает пробный запрос и прогрев клиента. Но кеш сервера она
не сбрасывает: повтор с тем же seed — уже другой опыт. Фиксируйте первый вход
и повторения отдельно; не усредняйте их как одинаково холодные серии.

## 3. Сохранить результат до смены профиля

> [!IMPORTANT]
> Результат CLI уже сохранён локально вместе с JSON. Не заменяйте команду
> выгрузкой через `kubectl cp`: минимальный runtime не содержит `tar` и `cat`.

```bash
mkdir -p "results/hardfest/$SERIES"
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get "deployment/hf-gemma-$SLOT" -o yaml \
  > "results/hardfest/$SERIES/deployment.yaml"
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get "configmap/hf-gemma-$SLOT" \
  -o go-template='{{index .data "profile.yaml"}}' > "results/hardfest/$SERIES/profile.yaml"
git rev-parse HEAD > "results/hardfest/$SERIES/revision.txt"
```

Результаты лежат вне путей Argo. Перед публикацией уберите из копий внутренние
адреса и привязки площадки. Secret и kubeconfig не выгружайте.

## Проверка

Откройте `results/hardfest/$SERIES/bench.txt` редактором и сверьте поля JSON:

| Поле JSON | Требуемое значение |
| --- | --- |
| `failed` | `0` |
| `completed` | `8` |
| `total_input_tokens` | `65536` |
| `total_output_tokens` | `16384` |

Код возврата CLI может быть нулевым даже при ошибках запросов. Оборванный
ответ также не считается полной генерацией. Если любое поле не совпало,
сохраните JSON и логи, устраните причину и повторите серию. Не сравнивайте
её throughput с успешным прогоном.

> [!WARNING]
> Новые неисправимые ECC — причина остановить нагрузку на затронутой карте.
> Перебор флагов vLLM не является проверкой исправности GPU.

Упражнение завершено, когда для проверенного профиля сохранены полный JSON,
настройки и Git SHA. Восемь запросов — короткая проверка, не устойчивый p95:
для итогов нужны более длинные серии и не менее трёх повторов с одинаковым прогревом.

TTFT клиента, очередь и prefill сервера интерпретируются отдельно по
[методике измерений](../docs/MEASUREMENTS.md).
Первая итерация B продолжается [проверкой KV в RAM](02-kv-ram.md).
