# Большая модель на двух GPU

В финальном эксперименте запускаем Qwen через AI Inference по рецепту TP2 с MTP:
две H100, prefix cache, chunked prefill, CUDA graphs и заданный бюджет KV в RAM.
Ручной [профиль Qwen TP2](../deploy/qwen-tp2/configmap.yaml) служит исходной точкой
при подготовке рецепта. Результаты сборки и прогонов — в [STATUS](../docs/STATUS.md).

Перед освобождением Gemma проверьте обе карты, новые ECC-ошибки, NVLink и
межкарточный обмен. Видимый NVLink не доказывает устойчивость длительной нагрузки.
Не меняйте MIG, VFIO или драйверы ради эксперимента без отдельного согласования.

TP2 делит вычисление слоёв между двумя GPU и требует частого обмена.
PP2 распределяет слои по стадиям и иначе зависит от загрузки конвейера.
Лучший вариант определяется измерениями на конкретной модели и топологии;
здесь основной кандидат — TP2 внутри одной VM с NVLink.

Порядок финального этапа:

1. Открыть рецепт Qwen TP2 с MTP и проверить модель, runtime и бюджеты GPU/CPU памяти.
2. Остановить ручные A/B через Git и sync, удалить только свой предыдущий
   платформенный InferenceService через Console.
3. Убедиться, что обе DRA-заявки освобождены.
4. Создать платформенный сервис `hf-platform-qwen` с рецептом Qwen TP2 с MTP
   и стратегией Throughput, запросив обе GPU одной ноды.
5. Проверить фактические TP=2, контекст, MTP, CUDA graphs, prefix cache,
   chunked prefill и бюджет KV-offload.
6. Подключить отдельный маршрут через прежние Bifrost и Open WebUI.

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get pods,resourceclaims
kubectl --context "$GPU_CONTEXT" describe node YOUR_GPU_NODE
```

Проверьте обычный ответ, затем принятие токенов MTP и возврат KV из RAM.
Результаты этих проверок сохраняйте вместе с версией рецепта и образом движка.

Нагрузку повышайте постепенно: 1, 2, 4, 8, 16, 32, 50. Фиксируйте вход, выход,
concurrency, queue, TTFT, скорость и ошибки; прекратите серию при новых аппаратных
ошибках либо превышении приемлемой задержки.
