# Qwen на двух H100

Эту работу можно выполнить после сравнения A/B, когда обе H100 свободны. В `models.lock.json` закреплена `nvidia/Qwen3.8-Flash-Next-NVFP4`. Файлы модели проверены, но успешный запуск на этих H100 пока не подтверждён. Сначала выполните проверки оборудования из [STATUS](../docs/STATUS.md).

Файлы Safetensors занимают 132680249378 байт (~123,57 GiB). Это не объём HBM каждого процесса TP. В модели смешаны представления данных и есть дополнительные тензоры, поэтому простое деление размера файлов на два не даёт полного бюджета памяти.

В [qwen-tp2.json](../manifests/profiles/qwen-tp2.json) заданы TP2, modelopt/Marlin, chunked prefill, префиксный кэш и CUDA graphs. Выгрузка весов engram в RAM отключена. При первом запуске не добавляем одновременно MTP, FP8 KV и выгрузку KV в RAM: их совместимость с гибридным состоянием модели и выбранной реализацией MoE проверяется отдельно.

## Проверка оборудования перед запуском

- На обеих H100 остановлены A/B и сервис Deckhouse. Карты не переданы в VFIO; узел Ready и доступен для планирования.
- CUDA внутри контейнера видит обе карты, назначенные его DRA-заявкой.
- В топологии есть нужная связь NVLink; коллективные операции NCCL проходят без ошибок.
- Движок поддерживает архитектуру и вычислительные ядра для выбранного квантования. HBM и RAM хватает для запуска.
- Для каждого запуска сохраняются логи и хеш профиля.

Чужую нагрузку для этой работы автоматически не останавливаем. Пока проверки не пройдены, Deployment остаётся с `replicas: 0`.

```bash
python3 scripts/hf.py apply tp2 --ack
python3 scripts/hf.py start tp2 --ack
python3 scripts/hf.py logs tp2
python3 scripts/hf.py port-forward tp2 18004
```

```bash
python3 scripts/bench.py --url http://127.0.0.1:18004 --model qwen3.8-flash-next \
  --dataset examples/smoke.jsonl --requests 2 --concurrency 1
```

Длинный набор запросов подготовьте заново с токенизатором Qwen. Число токенов, посчитанное для Gemma, здесь использовать нельзя.

## На сколько сессий рассчитывать

Проведите серии с 1, 2, 4, 8, 16, 32 и 50 одновременными запросами. Для каждой сохраните длины входа и выхода, долю завершённых запросов, ошибки, время в очереди, TTFT, ITL, выходные токены в секунду и число вытеснений. Запросов в серии должно быть больше, чем уровень параллельности: один залп не показывает устойчивую работу. Запишите и интервалы отправки на стороне клиента.

50 пользователей с паузами и 50 одновременно обрабатываемых запросов по 256K — разные нагрузки. Допустимая параллельность зависит от требований ко времени ответа и доле ошибок, а не только от HTTP 200. `max-num-seqs: 16` ограничивает число обрабатываемых последовательностей, но не пользователей: остальные запросы могут ждать в очереди. Этот параметр тоже нужно учитывать в сравнении.

## Сравнение TP2 и PP2

Pipeline parallelism требует поддержки конкретной архитектуры в движке. TP и PP нужно сравнивать при одинаковой модели, точности, окне и нагрузке. Для TP важна скорость коллективных обменов, для PP — разбиение на стадии и заполнение конвейера. Отдельный PP2-профиль можно добавить после проверки `SupportsPP` и успешного запуска. Наличие двух GPU не гарантирует поддержку PP.

## После первого успешного запуска

Дальнейшие изменения проверяйте по одному:

- MTP: память, доля принятых токенов и скорость.
- Выгрузка KV в RAM: обратная загрузка блоков и совместимость с гибридным состоянием модели.
- FP8 KV: совместимость, качество ответов и ёмкость кэша.

Добавляйте настройку в основной профиль после воспроизводимого сравнения.
