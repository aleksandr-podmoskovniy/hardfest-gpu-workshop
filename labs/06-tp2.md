# Qwen на двух H100 через AI Inference

Освобождаем обе карты после Gemma и запускаем один Qwen TP2.
Проверяем ответ, MTP, возврат KV из RAM и инструменты в чате.
[Расчёт ресурсов](../docs/MEMORY_BUDGET.md#qwen-tp2-после-gemma).

![Две Gemma освобождают GPU для одного Qwen TP2](../assets/17-qwen-transition.svg)

Основной финал — запуск, короткий запрос, чат и проверка прав MCP.
Длинные нагрузочные серии и сравнение MTP включён/выключен можно выполнить
после занятия. Команды — из частной GitOps-репы с переменными
[GitOps](../docs/GITOPS.md).

## 1. Проверить рецепт до остановки Gemma

### Модель и параллелизм

Закреплённый checkpoint занимает 123,57 GiB на диске. NVFP4 относится
не ко всем тензорам: эксперты основной модели хранятся в NVFP4, PLE и
эксперты MTP — в FP8, часть остальных весов — в BF16. В 48 слоях сочетаются
36 слоёв линейного и 12 полного внимания; MTP добавляет ещё один слой.
[Конфигурация модели](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json).

На H100 используем `modelopt` и `marlin`: это способ исполнения checkpoint,
не аппаратная арифметика FP4. Расход HBM после загрузки отличается от размера
файлов; формула KV для Gemma к этой гибридной архитектуре неприменима.

TP2 распределяет тензоры между двумя GPU, которые вместе вычисляют один ответ.
PP2 делит слои между стадиями конвейера. Здесь выбран TP2 на NVLink-паре;
две реплики, напротив, хранили бы независимые веса и обслуживали разные очереди.
[Параллелизм vLLM](https://docs.vllm.ai/en/v0.30.0/serving/parallelism_scaling/).

MTP-веса входят в основной checkpoint: отдельный draft скачивать не нужно.
Начинаем с одного предлагаемого токена. Проверяем принятие и скорость
отдельно: высокая доля принятых токенов может не окупить вычисление черновика.
[MTP в vLLM](https://docs.vllm.ai/en/v0.30.0/features/speculative_decoding/mtp/).

### Параметры запуска

Модель `nvidia/Qwen3.8-Flash-Next-NVFP4` уже загружена в каталог;
ревизия совпадает с [models.lock.json](../models.lock.json).
В Console выберите ветку Throughput и DeviceClass целой H100.
Эталон параметров — [values/qwen-tp2.yaml](../values/qwen-tp2.yaml).

| Параметр | Значение |
| --- | --- |
| Runtime | vLLM 0.30.0, образ по digest |
| Размещение | Одна реплика, две GPU одной ноды, TP2 |
| Контекст / активные последовательности | 262 144 / 16 |
| Prefill / prefix cache / CUDA graphs | 4096 / включён / включены |
| Квантование / MoE | modelopt / marlin |
| MTP | `method: mtp`, `num_speculative_tokens: 1` |
| CPU KV / tmpfs | 16 GiB / не менее 24 GiB |
| CPU / RAM request / RAM limit | 12 / 80 GiB / 104 GiB |
| Инструменты | qwen3_xml, auto tool choice включён |

В заказе выбирается список DeviceClass. Количество карт задаётся рецептом,
отражается в плане как `acceleratorCount=2` и переносится контроллером
в DRA-заявку. Оно должно совпадать с TP2 в параметрах движка.

У установленного модуля должен быть собран этот рецепт с бюджетом RAM.
Если план остаётся однокарточным или не содержит MTP/offload, обновите пакет
рецептов штатным процессом поставки **до переключения**. Ручной чарт
не подменяет результат платформенного запуска.

В каталоге параметров платформы CPU KV задаётся как `kvOffloadingSize: 16`
и `kvOffloadingBackend: native`. Они превращаются во флаги
`--kv-offloading-size 16 --kv-offloading-backend native`; vLLM настраивает
тот же OffloadingConnector и общий бюджет 16 GiB для TP2, что указан
в ручном эталоне. Размер tmpfs и лимит контейнера проверяются отдельно.
[Преобразование параметров vLLM](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/config/vllm.py#L1032).

```bash
kubectl --context "$GPU_CONTEXT" get nodes,deviceclasses
kubectl --context "$GPU_CONTEXT" describe node YOUR_H100_NODE
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get pods,resourceclaims,pvc
kubectl --context "$GPU_CONTEXT" explain inferenceservice.spec \
  --api-version=ai.deckhouse.io/v1alpha1
```

CPU/RAM проверяйте по allocatable и уже запрошенным ресурсам, не номиналу VM.
Должны быть проверены обе GPU, NVLink/P2P и отсутствие новых неисправимых
ECC/Xid. Видимая линия NVLink не доказывает исправный обмен под нагрузкой.
При аппаратных ошибках опыт останавливаем, не меняя ECC, VFIO и драйвер.

## 2. Освободить обе карты

Сохраните результаты Gemma до удаления Pod. В обоих GitOps-профилях:

```bash
yq -i '.replicaCount = 0' "$DEMO_DIR/values/gemma-a.yaml"
yq -i '.replicaCount = 0' "$DEMO_DIR/values/gemma-b.yaml"
git diff -- "$DEMO_DIR/values/gemma-a.yaml" "$DEMO_DIR/values/gemma-b.yaml"
git add -- "$DEMO_DIR/values/gemma-a.yaml" "$DEMO_DIR/values/gemma-b.yaml"
git commit -S -s -m "Release both H100 for Qwen TP2"
git push
REVISION=$(git rev-parse HEAD)
for APP in hardfest-gemma-a hardfest-gemma-b; do
  kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" patch application "$APP" \
    --type merge -p "$(jq -nc --arg rev "$REVISION" '{operation:{sync:{revision:$rev,prune:false}}}')"
done
```

Если вместо A работает платформенная Gemma, удалите только её заказ через
его источник управления: файл заказа из GitOps либо заказ в Console.
Не масштабируйте дочерний StatefulSet вручную — контроллер восстановит его.
При GitOps удаление файла само по себе не удаляет объект: обычный sync здесь
идёт с `prune:false`. После отправки изменения выберите в Argo адресный
Prune только InferenceService Gemma и проверьте список удаляемых ресурсов.

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get inferenceservices
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get pods,resourceclaims -o wide
```

У Gemma больше нет работающих Pod и выделенных карт. Не удаляйте занятые
ResourceClaim вручную: дождитесь завершения владельца. PVC, веса,
GPUClass/GPUPool и сервисы A30 остаются на месте.

## 3. Создать заказ

Создайте заказ в Console или сохраните манифест в GitOps Application,
управляющий заказами AI Inference. Для общего каталога вместо `Model`
укажите существующий `ClusterModel`.

```yaml
apiVersion: ai.deckhouse.io/v1alpha1
kind: InferenceService
metadata:
  name: hf-platform-qwen
  namespace: hardfest-demo
spec:
  inferenceServiceClassName: REPLACE_INFERENCE_SERVICE_CLASS
  launchStrategy: Throughput
  model:
    src: ai-models
    ref:
      kind: Model
      name: REPLACE_QWEN_MODEL_RESOURCE
  resources:
    accelerator:
      deviceClasses:
        - REPLACE_GENERATED_H100_DEVICECLASS
```

Имена подставьте из установленного каталога и класса сервиса. Рецепт
выбирается по модели, оборудованию и стратегии — поля `recipeName` в заказе
нет. Для GitOps сохраните файл как `$DEMO_DIR/platform/qwen.yaml`:

```bash
export QWEN_APP=REPLACE_PLATFORM_ARGO_APPLICATION
kubectl --context "$GPU_CONTEXT" apply --dry-run=server \
  -f "$DEMO_DIR/platform/qwen.yaml"
git add -- "$DEMO_DIR/platform/qwen.yaml"
git diff --cached -- "$DEMO_DIR/platform/qwen.yaml"
git commit -S -s -m "Launch Qwen TP2 through AI Inference"
git push
REVISION=$(git rev-parse HEAD)
kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" patch application "$QWEN_APP" \
  --type merge -p "$(jq -nc --arg rev "$REVISION" '{operation:{sync:{revision:$rev,prune:false}}}')"
kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" get application "$QWEN_APP" \
  -o jsonpath='{.status.operationState.phase}{" "}{.status.sync.revision}{"\n"}'
```

Дождитесь успешного завершения sync именно на `$REVISION`.
Для Console эти Git-команды не нужны. У заказа должен быть один владелец.
Ручное Application `hf-qwen-tp2` остаётся с нулём реплик.

## 4. Проверить workload и DRA

Получите созданный контроллером StatefulSet по UID заказа:

```bash
QWEN_UID=$(kubectl --context "$GPU_CONTEXT" -n hardfest-demo \
  get inferenceservice hf-platform-qwen -o jsonpath='{.metadata.uid}')
QWEN_WORKLOAD=$(kubectl --context "$GPU_CONTEXT" -n hardfest-demo \
  get statefulsets,deployments -o json | jq -er --arg uid "$QWEN_UID" '
    [.items[] | select(any(.metadata.ownerReferences[]?; .uid == $uid)) |
      ((.kind | ascii_downcase) + "/" + .metadata.name)] |
    if length == 1 then .[0] else error("Expected one Qwen workload") end')
QWEN_CONTAINER=$(kubectl --context "$GPU_CONTEXT" -n hardfest-demo \
  get "$QWEN_WORKLOAD" -o json | jq -er '
    [.spec.template.spec.containers[] |
      select((.resources.claims // []) | length > 0) | .name] |
    if length == 1 then .[0] else error("Expected one runtime container") end')
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get "$QWEN_WORKLOAD" -o json |
  jq '.spec.template.spec | {nodeSelector, resourceClaims,
    containers: [.containers[] | {name, image, args, resources, volumeMounts}], volumes}'
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get resourceclaims -o yaml
kubectl --context "$GPU_CONTEXT" -n hardfest-demo rollout status \
  "$QWEN_WORKLOAD" --timeout=1800s
kubectl --context "$GPU_CONTEXT" -n hardfest-demo logs "$QWEN_WORKLOAD" \
  -c "$QWEN_CONTAINER" --tail=200
```

В заявке нужны `count: 2` и две разные выделенные GPU, в аргументах/логе —
TP2 и MTP. Проверьте CPU KV, tmpfs, контекст, реальные лимиты RAM и размер GPU
KV-пула после загрузки. `Ready` не доказывает каждый из этих параметров.
Команды не предполагают наличия shell, curl или cat в distroless runtime.

## 5. Выполнить запрос

Найдите Service заказа и его API-порт:

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get services -o json |
  jq --arg uid "$QWEN_UID" '.items[] |
    select(any(.metadata.ownerReferences[]?; .uid == $uid)) |
    {name: .metadata.name, ports: .spec.ports}'
export QWEN_SERVICE=REPLACE_QWEN_SERVICE
export QWEN_PORT=8000
kubectl --context "$GPU_CONTEXT" -n hardfest-demo port-forward \
  "service/$QWEN_SERVICE" "18004:$QWEN_PORT"
```

Для следующих команд класс сервиса использует аутентификацию `Token`.
Контроллер создаёт Secret модельного API; ссылку на него проверьте в
`VLLM_API_KEY.valueFrom.secretKeyRef` контейнера движка. В другом терминале
введите этот серверный ключ из менеджера секретов; это не личный VK Bifrost.
Ввод не отображается. Параметр curl берётся
из отдельного файлового дескриптора, ключ не попадает в argv:

```bash
set +x
printf 'Model API key: ' >&2
IFS= read -r -s QWEN_API_KEY
printf '\n' >&2
QWEN_MODEL=$(curl --fail --silent --show-error --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$QWEN_API_KEY") \
  http://127.0.0.1:18004/v1/models | jq -er '.data[0].id')
jq -n --arg model "$QWEN_MODEL" '{model:$model, stream:false, max_tokens:1024,
  temperature:0, messages:[{role:"user",
  content:"Кратко объясни разницу между TP2 и двумя репликами модели."}]}' |
curl --fail-with-body --silent --show-error --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$QWEN_API_KEY") \
  http://127.0.0.1:18004/v1/chat/completions \
  -H 'Content-Type: application/json' --data-binary @- |
jq '{answer:.choices[0].message, finish_reason:.choices[0].finish_reason, usage, error}'
```

Проверяем содержательный ответ и usage, не только HTTP 200. Если ответ
закончился по лимиту на рассуждении, увеличьте предел генерации и повторите.
Затем проверьте тот же запрос через Bifrost. Добавьте отдельный маршрут
и имя `Qwen TP2` в Open WebUI; остановленные Gemma скройте из списка.
Личные VK, бюджеты и накопленный расход участников сохраняются.

## 6. Подтвердить MTP и возврат KV из RAM

![Принятие черновика и скорость — отдельные измерения](../assets/18-qwen-mtp.svg)

Снимите метрики до и после серии без посторонних запросов и кэша готовых
ответов Bifrost:

```bash
mkdir -p results/hardfest/qwen
curl --fail --silent --show-error --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$QWEN_API_KEY") \
  http://127.0.0.1:18004/metrics > results/hardfest/qwen/before.prom
```

После серии повторите команду с именем `after.prom`. Доля принятия MTP:

```promql
sum(increase(vllm:spec_decode_num_accepted_tokens_total{model_name="$model",instance="$instance"}[5m]))
/
sum(increase(vllm:spec_decode_num_draft_tokens_total{model_name="$model",instance="$instance"}[5m]))
```

Нулевой знаменатель означает отсутствие данных. Для сравнения MTP удалите
`speculative-config` в отдельном варианте рецепта и повторите тот же тест.
Сравнивайте также output tokens/s, TPOT и ошибки, а не только долю принятия.
[Счётчики MTP](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/spec_decode/metrics.py#L180).

Для RAM: длинный запрос P → другие префиксы до вытеснения P из GPU → повтор P.
Нужен положительный прирост `kv_offload_load_bytes` на повторе, а не только
`kv_offload_store_bytes` или высокий prefix hit rate. Имена с суффиксами
счётчиков и labels сверяйте по HELP/TYPE в /metrics. Размер вытесняющей серии
выбирается по GPU KV-пулу Qwen, не по результатам Gemma.

## 7. Найти предел параллельности

![256K контекста не означает 50 одновременно вычисляемых историй](../assets/19-qwen-capacity.svg)

Во время занятия достаточно короткой серии при concurrency 1 и 4: вход
8192, выход 512. После занятия пройдите полную сетку 1, 2, 4, 8, 16, 32, 50.
Для длинной серии — вход 131 072 и выход 2048,
начиная с одной сессии. Окно 256K дополнительно проверяется запросом на
границе: вход, шаблон чата и выход вместе не превышают 262 144.

Клиент запускается отдельным CPU Job из
[examples/qwen-benchmark-job.yaml](../examples/qwen-benchmark-job.yaml),
не в distroless-контейнере Qwen и не на H100. Порядок запуска приведён ниже.
Результаты других длин входа не объединяйте в одну цифру «поддерживает N сессий».

Скопируйте пример в каталог результатов, **не в путь Application**:

```bash
cp ../hardfest-gpu-workshop/examples/qwen-benchmark-job.yaml \
  results/hardfest/qwen/client.yaml
```

В `client.yaml` замените CPU-ноду (не ноду H100), Service, имя модели из
`/v1/models` и ссылку на существующий Secret модельного API. Имя и ключ
Secret видны в `VLLM_API_KEY.valueFrom.secretKeyRef` контейнера Qwen;
содержимое Secret копировать в YAML не нужно. Нода клиента должна иметь
доступ к Service, DNS и Hugging Face: Job скачивает только закреплённый
токенизатор, не веса. Для изолированной площадки подготовьте эти файлы
на доступном CPU-ноде томе и замените шаг скачивания.

Это временный клиент измерений, не изменение GPU workload. Каждый запуск
получает уникальное имя; `suspend: true` снимается только в подготовленной копии:

```bash
export CONCURRENCY=1
export RUN_ID=$(date -u +%Y%m%dT%H%M%SZ)
export BENCH_JOB="qwen-bench-c$CONCURRENCY-$RUN_ID"
yq '.metadata.name = strenv(BENCH_JOB) | .spec.suspend = false |
  (.spec.template.spec.containers[0].env[] |
    select(.name == "CONCURRENCY").value) = strenv(CONCURRENCY)' \
  results/hardfest/qwen/client.yaml > "results/hardfest/qwen/$BENCH_JOB.yaml"
kubectl --context "$GPU_CONTEXT" apply --dry-run=server \
  -f "results/hardfest/qwen/$BENCH_JOB.yaml"
kubectl --context "$GPU_CONTEXT" apply -f "results/hardfest/qwen/$BENCH_JOB.yaml"
kubectl --context "$GPU_CONTEXT" -n hardfest-demo wait \
  --for=condition=complete "job/$BENCH_JOB" --timeout=3600s
kubectl --context "$GPU_CONTEXT" -n hardfest-demo logs "job/$BENCH_JOB" \
  > "results/hardfest/qwen/$BENCH_JOB.log"
awk '/^RESULT_JSON_BEGIN$/{copy=1;next} /^RESULT_JSON_END$/{copy=0} copy' \
  "results/hardfest/qwen/$BENCH_JOB.log" > "results/hardfest/qwen/$BENCH_JOB.json"
jq -e . "results/hardfest/qwen/$BENCH_JOB.json"
```

Сначала убедитесь, что Job завершился успешно и JSON непустой, затем
повторите с другим `CONCURRENCY`. При ошибке сохраните logs и
`kubectl describe job`, не продолжайте сетку автоматически.
В примере всего `NUM_PROMPTS=8` для короткой проверки на 1 и 4 клиентах.
Перед полной сеткой до 50 увеличьте `NUM_PROMPTS` как минимум до 100;
для длинной серии меняются также `INPUT_TOKENS`, `OUTPUT_TOKENS` и имя файла.
Даже 100 запросов не гарантируют устойчивый p95: нужны повторные серии
и одинаковые условия прогрева. Следите за CPU и сетью клиента — они
не должны ограничивать измеряемую пропускную способность сервера.
CLI делает пробный запрос до измерения — не называйте всю серию холодной.
Результат сохраняется до удаления временного Job; TTL равен суткам.

При concurrency=50 и `max-num-seqs=16` ожидаема очередь. Рабочее число сессий —
последняя точка, в которой выдержаны выбранные ограничения TTFT/TPOT и ошибок.
[Как читать и сохранять измерения](../docs/MEASUREMENTS.md).

## 8. Проверить MCP и права

Парсер `qwen3_xml` превращает ответ модели в вызов инструмента.
vLLM не получает kubeconfig: действие выполняет Bifrost/MCP с отдельными правами.

Участникам доступны чат, учебные базы знаний и голос; их VK не имеют MCP-доступа.
Административная OIDC-группа получает отдельный маршрут с Kubernetes MCP
и ограниченной областью управления. Вход через OIDC сам по себе не выдаёт
административных прав.

Сначала запросите список Pod учебного namespace и сравните с kubectl.
Затем выполните обратимое изменение заранее выбранного учебного объекта.
Повтор той же операции от участника должен быть запрещён на шлюзе,
а не только скрыт в UI. [Схема доступа](../docs/CHAT_AND_ACCESS.md).

## Возврат к Gemma

Сохраните отчёт, метрики, digest образа, ревизию модели и параметры рецепта.
Удалите только заказ Qwen через его источник управления, дождитесь удаления
Pod и освобождения GPU, затем верните нужный профиль Gemma через Git/Argo.
PVC, Namespace, модели, GPU-классы и A30 не удаляются.

Для показанного GitOps-заказа сначала удалите его декларацию, затем выполните
адресный Prune этого одного объекта. Общий Prune всего namespace не нужен:

```bash
git rm -- "$DEMO_DIR/platform/qwen.yaml"
git diff --cached -- "$DEMO_DIR/platform/qwen.yaml"
git commit -S -s -m "Remove the Qwen TP2 order"
git push
REVISION=$(git rev-parse HEAD)
kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" patch application "$QWEN_APP" \
  --type merge -p "$(jq -nc --arg rev "$REVISION" '{operation:{sync:{
    revision:$rev,prune:true,resources:[{group:"ai.deckhouse.io",
```
