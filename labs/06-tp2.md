# Запустить Qwen TP2 через AI Inference

Освободим обе H100 после Gemma и запустим один Qwen с тензорным
параллелизмом. Затем проверим MTP, возврат KV из RAM и инструменты
в прежнем чате.

![Две Gemma освобождают GPU для одного Qwen TP2](../assets/17-qwen-transition.svg)

## Перед началом

- [ ] Рабочий каталог — `k8s-config`; переменные заданы по [GitOps](../docs/GITOPS.md).
- [ ] Результаты Gemma сохранены до удаления Pod.
- [ ] В ai-models готов `qwen3-8-flash-next-nvfp4` нужной ревизии.
- [ ] Установленный AI Inference содержит рецепт Qwen TP2/MTP и достаточный RAM-бюджет.
- [ ] Обе GPU проверены: нет новых неисправимых ECC/Xid; проверен обмен NVLink/P2P.
- [ ] `PLATFORM_APP=hardfest-qwen-platform` — отдельный Helm Application этого заказа.

> [!WARNING]
> Видимая линия NVLink не доказывает исправность обмена под нагрузкой.
> После ECC/Xid сначала нужна отдельная проверка аппаратуры.
> В этом упражнении не меняем ECC, VFIO, драйвер или MIG mode.

## 1. Сверить модель и рецепт

Checkpoint `nvidia/Qwen3.8-Flash-Next-NVFP4` занимает 123,57 GiB на диске.
Эксперты основной модели хранятся в NVFP4, PLE и эксперты MTP — в FP8,
часть остальных весов — в BF16. В 48 слоях сочетаются 36 слоёв линейного
и 12 полного внимания; MTP добавляет ещё один слой.
[Закреплённая конфигурация модели](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json).

На H100 используется `modelopt` с `marlin`: это способ исполнения
checkpoint, не аппаратная арифметика FP4. Расход HBM отличается от размера
файлов. Формула KV для Gemma к этой гибридной архитектуре неприменима.

| Вариант | Как использует две GPU |
| --- | --- |
| TP2 | Тензоры разделены между картами; обе вычисляют один ответ |
| PP2 | Слои разделены между стадиями конвейера |
| Две реплики | Независимые веса и очереди запросов |

Здесь выбран TP2 на NVLink-паре.
[Параллелизм vLLM](https://docs.vllm.ai/en/v0.31.0/serving/parallelism_scaling/).
MTP-веса входят в основной checkpoint: отдельный draft не нужен.
Начинаем с одного предлагаемого токена.
[MTP в vLLM](https://docs.vllm.ai/en/v0.31.0/features/speculative_decoding/mtp/).

Эталон — [values/qwen-tp2.yaml](../values/qwen-tp2.yaml);
[расчёт памяти](../docs/MEMORY_BUDGET.md#qwen-tp2-после-gemma).

| Параметр рецепта | Значение |
| --- | --- |
| Runtime | vLLM 0.31.0, образ по digest |
| Размещение | Одна реплика, две GPU одной ноды, TP2 |
| Контекст / активные последовательности | 262 144 / 16 |
| Prefill / prefix cache / CUDA graphs | 4096 / включён / включены |
| Квантование / MoE | modelopt / marlin |
| MTP | `method: mtp`, `num_speculative_tokens: 1` |
| CPU KV / tmpfs | 16 GiB / не менее 24 GiB |
| CPU / RAM request / RAM limit | 12 / 80 GiB / 104 GiB |
| Парсер инструментов | `qwen3_xml`, auto tool choice включён |

```bash
kubectl --context "$GPU_CONTEXT" get nodes,deviceclasses
kubectl --context "$GPU_CONTEXT" describe node REPLACE_H100_NODE
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get models.ai.deckhouse.io
kubectl --context "$GPU_CONTEXT" -n hardfest-demo describe model qwen3-8-flash-next-nvfp4
kubectl --context "$GPU_CONTEXT" explain inferenceservice.spec \
  --api-version=ai.deckhouse.io/v1alpha1
```

Сверьте ревизию с [models.lock.json](../models.lock.json).
CPU/RAM считайте по `allocatable` и уже запрошенным ресурсам, не номиналу VM.

До остановки Gemma выберите и проверьте класс сервиса:

```bash
export INFERENCE_CLASS=REPLACE_INFERENCE_SERVICE_CLASS
kubectl --context "$GPU_CONTEXT" get inferenceserviceclass "$INFERENCE_CLASS" -o yaml
```

| Поле в `spec` | Требование |
| --- | --- |
| `scalingPolicy.minReplicas`, `scalingPolicy.maxReplicas` | Оба `1`: создаём один TP2-сервис |
| `acceleratorPolicy.maxAcceleratorCount` | Не меньше `2` |
| `acceleratorPolicy.allowedSharingModes` | Только `Dedicated` для этого опыта |
| `acceleratorPolicy.allowedPlacementTypes` | Только `WholeDevice` |
| `exposurePolicy.authentication` | `Token`, как в API-командах ниже |

> [!IMPORTANT]
> Штатный `default-llm` ограничен одной GPU на реплику и разрешает две реплики.
> Для TP2 подготовьте отдельный InferenceServiceClass через GitOps по схеме
> установленной версии. Не расширяйте общий класс чужих сервисов.
> При неподходящей политике не переходите к остановке Gemma.

Количество карт задаёт рецепт. В плане должно быть `acceleratorCount=2`,
в DRA-заявке — две GPU, в движке — TP2. Если план однокарточный или в нём
нет MTP/offload, сначала исправьте поставку рецепта. Ручной чарт не заменяет
платформенный запуск.

В каталоге параметров CPU KV задаётся как `kvOffloadingSize: 16` и
`kvOffloadingBackend: native`. Они превращаются во флаги
`--kv-offloading-size 16 --kv-offloading-backend native`: в этом рецепте дополнительно задан `VLLM_USE_SIMPLE_KV_OFFLOAD=1`.
Используется Simple CPU backend, а не Gemma OffloadingConnector.
Штатный коннектор делит 16 GiB на world_size: при TP2 получается по 8 GiB
на rank. Это бюджет KV, не суммарный RSS двух процессов.
[Исходник v0.31.0](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/distributed/kv_transfer/kv_connector/v1/simple_cpu_offload_connector.py#L85).

## 2. Освободить обе H100

В редакторе установите `replicaCount: 0` в двух файлах:

- `$DEMO_DIR/values/gemma-a.yaml`;
- `$DEMO_DIR/values/gemma-b.yaml`.

```bash
git diff -- "$DEMO_DIR/values/gemma-a.yaml" "$DEMO_DIR/values/gemma-b.yaml"
git add -- "$DEMO_DIR/values/gemma-a.yaml" "$DEMO_DIR/values/gemma-b.yaml"
git diff --cached --check
git commit -S -s -m "Release both H100 for Qwen TP2"
git push
REVISION=$(git rev-parse HEAD)
for APP in hardfest-gemma-a hardfest-gemma-b; do
  kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" patch application "$APP" \
    --type merge \
    --patch "{\"operation\":{\"sync\":{\"revision\":\"$REVISION\",\"prune\":false}}}"
done
```

Если работает платформенная Gemma, удалите **только её заказ** через
его источник управления. Для GitOps задайте `order.enabled: false` в `platform/gemma.yaml`,
отправьте коммит и выполните в Argo адресный Prune объекта
`InferenceService/hf-platform-gemma`. Проверьте список удаления перед подтверждением:
обычный sync с `prune:false` не удаляет исчезнувший из Git объект.
Для заказа из Console удаление выполняется в Console.

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get inferenceservices
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get pods,resourceclaims -o wide
```

Дождитесь исчезновения Pod Gemma и освобождения обеих GPU.
Дочерний StatefulSet не масштабируйте вручную: контроллер восстановит его.
PVC, веса, GPUClass/GPUPool и A30 остаются на месте.

## 3. Создать platform/qwen.yaml

Создайте редактором `$DEMO_DIR/platform/qwen.yaml`:

```yaml
apiVersion: ai.deckhouse.io/v1alpha1
kind: InferenceService
metadata:
  name: hf-qwen-platform
  namespace: hardfest-demo
spec:
  inferenceServiceClassName: REPLACE_INFERENCE_SERVICE_CLASS
  launchStrategy: Throughput
  model:
    src: ai-models
    ref:
      kind: Model
      name: qwen3-8-flash-next-nvfp4
  resources:
    accelerator:
      deviceClasses:
        - REPLACE_GENERATED_H100_DEVICECLASS
```

Замените класс сервиса проверенным `$INFERENCE_CLASS`, DeviceClass — фактическим именем.
Для общего каталога укажите существующий `ClusterModel`.
Поля `recipeName` нет: рецепт подбирается по модели, GPU и стратегии.

```bash
kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f "$DEMO_DIR/platform/qwen.yaml"
```

После успешной проверки:

```bash
git add -- "$DEMO_DIR/platform/qwen.yaml"
git diff --cached --check
git diff --cached
git commit -S -s -m "Launch Qwen TP2 through AI Inference"
git push
REVISION=$(git rev-parse HEAD)
kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" patch application "$PLATFORM_APP" \
  --type merge \
  --patch "{\"operation\":{\"sync\":{\"revision\":\"$REVISION\",\"prune\":false}}}"
kubectl --context "$ARGO_CONTEXT" -n "$ARGO_NAMESPACE" get application "$PLATFORM_APP" \
  -o jsonpath='{.status.operationState.phase}{" "}{.status.sync.revision}{"\n"}'
```

Дождитесь `Succeeded` для `$REVISION`.
У заказа один владелец. Ручное Application Qwen остаётся с нулём реплик.

## 5. Выполнить запрос через API

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo get services \
  -o custom-columns='NAME:.metadata.name,OWNER:.metadata.ownerReferences[*].name,PORT:.spec.ports[*].port'
```

Выберите Service с владельцем `hf-qwen-platform` и его API-порт.
В отдельном терминале:

```bash
export QWEN_SERVICE=REPLACE_QWEN_SERVICE
export QWEN_PORT=8000
kubectl --context "$GPU_CONTEXT" -n hardfest-demo port-forward \
  "service/$QWEN_SERVICE" "18004:$QWEN_PORT"
```

Следующие команды рассчитаны на класс сервиса с аутентификацией `Token`.
Контроллер создаёт Secret; его ссылка видна в
`VLLM_API_KEY.valueFrom.secretKeyRef` контейнера.
В основном терминале введите серверный ключ из менеджера секретов
— не личный VK шлюза:

```bash
set +x
printf 'Model API key: ' >&2
IFS= read -r -s QWEN_API_KEY
printf '\n' >&2
curl --fail --silent --show-error --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$QWEN_API_KEY") \
  http://127.0.0.1:18004/v1/models
```

Ввод скрыт; ключ передаётся curl через файловый дескриптор, не argv.
Скопируйте `data[].id` нужной модели в поле `model` следующего запроса:

```bash
curl --fail-with-body --silent --show-error --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$QWEN_API_KEY") \
  http://127.0.0.1:18004/v1/chat/completions \
  -H 'Content-Type: application/json' \
  --data-binary '{
    "model": "REPLACE_SERVED_MODEL_ID",
    "stream": false,
    "max_tokens": 1024,
    "temperature": 0,
    "messages": [{
      "role": "user",
      "content": "Кратко объясни разницу между TP2 и двумя репликами модели."
    }]
  }'
```

Проверьте содержательный ответ и `usage`, не только HTTP 200.
Если лимит исчерпан на рассуждениях, увеличьте `max_tokens` и повторите.

Подключите отдельный маршрут ai-mcp-gateway и модель `Qwen — TP2` в Open WebUI
по [инструкции доступа](../docs/CHAT_AND_ACCESS.md).
Остановленные Gemma скройте. Личные VK, бюджеты и накопленный расход
участников сохраняются.

## 6. Подтвердить MTP и возврат KV из RAM

![Принятие черновика и скорость — отдельные измерения](../assets/18-qwen-mtp.svg)

Без посторонних запросов снимите метрики:

```bash
mkdir -p results/hardfest/qwen
curl --fail --silent --show-error --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$QWEN_API_KEY") \
  http://127.0.0.1:18004/metrics > results/hardfest/qwen/before.prom
```

После серии повторите команду, заменив имя файла на `after.prom`.
Кэш готовых ответов шлюза не должен подменять обращения к движку.

| Механизм | Подтверждение |
| --- | --- |
| MTP | Растут счётчики предложенных и принятых токенов |
| Польза MTP | Лучше TPOT/throughput при сопоставимых ошибках в парном тесте без MTP |
| KV-offload | При повторе вытесненного префикса растут байты загрузки из RAM |

Доля принятия за интервал:

```promql
sum(increase(vllm:spec_decode_num_accepted_tokens_total{model_name="$model",instance="$instance"}[5m]))
/
sum(increase(vllm:spec_decode_num_draft_tokens_total{model_name="$model",instance="$instance"}[5m]))
```

Нулевой знаменатель — нет данных, а не 0%.
Для парного сравнения повторите тот же тест с рецептом, в котором
выключен только `speculative-config`.
[Счётчики MTP](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/v1/spec_decode/metrics.py#L180).

Для RAM: длинный запрос P → другие префиксы до вытеснения P из GPU → повтор P.
Для Simple CPU backend нужны счётчики сохранения и загрузки блоков
`simple_kv_offload_*`; для OffloadingConnector — `kv_offload_*`.
Выберите фактически экспортируемый набор. Заполненный CPU-пул без load не доказывает reuse.
Имена с суффиксами и labels сверяйте с `HELP/TYPE`.
Размер вытесняющей серии зависит от KV-пула Qwen, не от результатов Gemma.

## 7. Измерить параллельные запросы

![256K контекста не означает 50 одновременно вычисляемых историй](../assets/19-qwen-capacity.svg)

Для короткой проверки достаточно concurrency 1 и 4, входа 8192 и выхода 512.
Полная сетка — 1, 2, 4, 8, 16, 32, 50. Для длинной серии используйте
вход 131 072 и выход 2048, начиная с одной сессии.
В проверке границы окна вход, шаблон чата и ответ вместе не превышают 262 144.

Клиент — отдельный CPU Job, не контейнер Qwen и не нода H100:

```bash
cp ../hardfest-gpu-workshop/examples/qwen-benchmark-job.yaml \
  results/hardfest/qwen/client.yaml
```

В редакторе подготовьте `results/hardfest/qwen/client.yaml`:

| Поле | Что установить |
| --- | --- |
| `metadata.name` | Уникальное имя, например `qwen-bench-c1-r1` |
| `spec.suspend` | `false` |
| `nodeSelector.kubernetes.io/hostname` | CPU-нода, не H100 |
| Env `TARGET_BASE_URL`, `TARGET_MODEL` | Service и ID из шага 5 |
| Env `OPENAI_API_KEY.valueFrom.secretKeyRef` | Ссылка на существующий Secret, не сам ключ |
| Env `CONCURRENCY` | `"1"`, затем `"4"` |
| Env `NUM_PROMPTS` | `"8"` для короткой проверки |

У Job должен быть доступ к Service, DNS и Hugging Face. Он скачивает
закреплённый токенизатор, не веса. В изолированной сети заранее разместите
токенизатор на доступном CPU-ноде томе и замените шаг скачивания.

```bash
export BENCH_JOB=qwen-bench-c1-r1
kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f results/hardfest/qwen/client.yaml
```

После успешного dry-run запустите временный клиент:

```bash
kubectl --context "$GPU_CONTEXT" apply -f results/hardfest/qwen/client.yaml
kubectl --context "$GPU_CONTEXT" -n hardfest-demo wait \
  --for=condition=complete "job/$BENCH_JOB" --timeout=3600s
kubectl --context "$GPU_CONTEXT" -n hardfest-demo logs "job/$BENCH_JOB" \
  > "results/hardfest/qwen/$BENCH_JOB.log"
awk '/^RESULT_JSON_BEGIN$/{copy=1;next} /^RESULT_JSON_END$/{copy=0} copy' \
  "results/hardfest/qwen/$BENCH_JOB.log" > "results/hardfest/qwen/$BENCH_JOB.json"
```

Проверьте JSON в редакторе: `failed=0`, `completed=8`,
`total_input_tokens=65536`, `total_output_tokens=4096`.
Сохраните копию использованного `client.yaml` рядом с результатом.
При ошибке сохраните logs и `kubectl describe job`; не продолжайте сетку автоматически.

Для следующего запуска меняйте имя Job, `BENCH_JOB` и `CONCURRENCY`.
Не переиспользуйте завершённый Job для новой серии.

Для полной сетки до 50 увеличьте `NUM_PROMPTS` хотя бы до 100.
Для длинных запросов меняются также `INPUT_TOKENS` и `OUTPUT_TOKENS`;
ожидаемые суммы вычисляются как число запросов × соответствующая длина.
Нужны повторные серии и одинаковый прогрев: даже 100 запросов не гарантируют
устойчивого p95. Следите, чтобы CPU/сеть клиента не ограничивали сервер.
CLI выполняет пробный запрос до измерений; TTL Job — сутки.

При 50 клиентах и `max-num-seqs=16` часть запросов ожидает.
Ёмкость сервиса — последняя повторяемая ступень, выдерживающая заранее
выбранные TTFT, TPOT и долю ошибок.
[Методика измерений](../docs/MEASUREMENTS.md).

## 8. Проверить MCP и права

Парсер `qwen3_xml` превращает ответ модели в вызов инструмента.
vLLM не получает kubeconfig: действие выполняет ai-mcp-gateway/MCP
с отдельными правами.

| Учётная запись | Проверка |
| --- | --- |
| Участник | Чат, учебные базы знаний и голос доступны; MCP запрещён на шлюзе |
| Администратор из разрешённой OIDC-группы | Доступен Kubernetes MCP в выделенной области управления |

Вход через OIDC сам по себе не выдаёт административных прав.

Сначала запросите список Pod учебного namespace и сравните с kubectl.
Затем выполните обратимое изменение заранее выбранного учебного объекта.
Повтор операции от участника должен быть запрещён на шлюзе,
а не только скрыт в UI. [Настройка доступа](../docs/CHAT_AND_ACCESS.md).
