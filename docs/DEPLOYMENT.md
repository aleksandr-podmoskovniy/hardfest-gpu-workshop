# Порядок развёртывания

План для первого прогона: две H100 под Gemma A/B, отдельная A30 под динамический MIG и MPS, затем обе H100 под Qwen TP2. Модели и PVC сохраняются при переходах. После проверки прямого API каждый сервис подключается к одному HA Bifrost и прежнему Open WebUI; сами vLLM наружу не публикуются.

Все команды выполняются из корня репозитория. Настройки площадки находятся в `.local/site.json`. Команды с `--ack` меняют только выбранные ресурсы мастер-класса, но запускать их нужно после проверки предпосылок соответствующего этапа. План не снимает cordon и не останавливает чужую нагрузку.

## 1. Доступ, нода и размещение

```bash
python3 scripts/hf.py preflight
python3 scripts/hf.py get gpuclasses
python3 scripts/hf.py get deviceclasses
python3 scripts/hf.py get resourceslices
```

Если установленный API использует GPUPool вместо GPUClass, выполните `python3 scripts/hf.py get gpupools`. Не создавайте ресурс по предположению о его названии: нужны CRD установленного модуля и классы, созданные его контроллером.

До запуска проверьте:

- Нода Ready, нет MemoryPressure, DiskPressure и неразобранных ошибок GPU. Причина существующего cordon выяснена; разрешение планирования согласовано отдельно.
- Класс H100 выбирает только две выделенные карты, не A100 и не виртуальные устройства. DRA видит обе карты.
- Инвентаризация Pod выполнена во всех namespace, не только в `hardfest-demo`; карты свободны и нет чужого автосинхронизатора, который восстановит нагрузку.
- Актуальные `MemAvailable`, allocatable, requests и limits других Pod оставляют запас по [расчёту памяти](MEMORY_BUDGET.md). Одного вывода `kubectl top` недостаточно для оценки пика.
- PVC Bound, ревизии и файлы совпадают с `models.lock.json`, образ по digest доступен с ноды. Имеющиеся PVC не пересоздаются.

Версии GPU-модуля, ai-models, ai-inference, Console, драйвера и движка запишите до экспериментов. Несовместимость модулей исправляется отдельно, не посреди сравнительной серии. Если API или Dex доступны через VPN, проверьте, что прокси не перехватывает эти внутренние адреса; глобальную сетевую конфигурацию менять не требуется.

## 2. Первая Gemma на одной H100

Сначала проверяем только A. B ещё не запускаем, чтобы не смешать причины ошибок и пики загрузки. Для основного сравнения задайте `context_tokens: 65536` и используйте `a-chunked`: BF16 KV, prefix cache и CUDA graphs выключены, чанкирование оставлено для вместимости.

```bash
python3 scripts/hf.py render a-chunked
python3 scripts/hf.py apply a-chunked --ack
python3 scripts/hf.py start a-chunked --ack
python3 scripts/hf.py logs a-chunked
python3 scripts/hf.py model-info a-chunked
python3 scripts/hf.py snapshot a-chunked --out .local/runs/a-first.json
```

`apply` сохраняет `replicas: 0`; `start` запускает одну реплику. Таймаут ожидания не удаляет Pod и не доказывает ошибку: загрузка и компиляция могут длиться дольше. В таком случае сначала прочитайте логи.

Дальше нужны не только `/health`, но и короткий ответ модели. В отдельном терминале:

```bash
python3 scripts/hf.py port-forward a-chunked 18001
```

В основном терминале:

```bash
python3 scripts/bench.py --url http://127.0.0.1:18001 --model gemma-4-31b \
  --dataset examples/smoke.jsonl --requests 2 --concurrency 1
```

Сверьте UUID назначенной карты, видимость CUDA, память весов и KV-пула, формат KV и фактические настройки графов и prefill. Сохраните потребление памяти контейнера: anon/RSS, файловый кэш, shmem и пик cgroup. `MemAvailable` хоста и лимит контейнера — разные ограничения.

Если A не помещается с выбранным окном, сохраните точную ошибку. Общее окно для сравнения меняется у обеих реплик; выгрузку весов не добавляем. Полностью отключённый профиль `a` проверяется отдельно и не подменяет `a-chunked` в результатах. Если падает загрузка или драйвер, B не запускаем до выяснения причины.

## 3. A/B на двух картах

После успешного A запускаем B с профилем tuned:

```bash
python3 scripts/hf.py apply b-tuned --ack
python3 scripts/hf.py start b-tuned --ack
python3 scripts/hf.py logs b-tuned
python3 scripts/hf.py get resourceclaims
python3 scripts/hf.py snapshot b-tuned --out .local/runs/b-tuned-first.json
```

У A и B должны быть разные физические H100. Проверьте короткий ответ B через `port-forward b-tuned 18002`, затем подготовьте один набор длинных запросов:

```bash
python3 scripts/hf.py dataset a-chunked --input-fraction 0.5 --output-tokens 2048 \
  --documents 32 --out .local/long.jsonl
```

Файл повторно не создавайте, если он уже есть и соответствует контексту и токенизатору. Для нового набора выберите другое имя. Один и тот же файл используется для обеих реплик.

Сначала проверяем один длинный запрос, затем 4 и 8 конкурентных. A и B нагружаем по очереди, с одинаковым прогревом на других документах. Сохраняем ошибки, очередь, prefill, TTFT, скорость выхода, вытеснения и память. Холодные и повторные запросы считаем раздельно. [Команды и методика](MEASUREMENTS.md).

## 4. KV в RAM, затем assistant

После A/B на одинаковых 64K отдельно увеличиваем окно B до 128K. Создайте `.local/site-expanded.json` по [командам основного руководства](../README.md#ram), проверьте B tuned с новым окном и только затем включайте offload. A на VM с 128 GiB должна быть остановлена перед обеими сериями cache-off/cache-on.

```bash
python3 scripts/hf.py --site .local/site-expanded.json stop b-tuned --ack
python3 scripts/hf.py --site .local/site-expanded.json render b-cache
python3 scripts/hf.py --site .local/site-expanded.json apply b-cache --ack
python3 scripts/hf.py --site .local/site-expanded.json start b-cache --ack
python3 scripts/hf.py --site .local/site-expanded.json logs b-cache
```

Проверьте внутри нового Pod размер `/dev/shm`, фактический CPU KV-бюджет и память cgroup. При бюджете 64 GiB ожидаются shared memory 72 GiB и лимит RAM 144 GiB. Этот вариант требует достаточно большой ноды: сумма limits A + B cache — 224 GiB. На VM с 128 GiB A остановлен, у B cache CPU KV=32 GiB, shared memory=40 GiB и limit=80 GiB. Малые сервисы A30 на другой ноде имеют отдельный бюджет.

Бюджеты 24/48 GiB задаются [в настройках площадки](SETUP.md#2-параметры-своего-стенда). Не переносите в VM с 128 GiB вариант с 64 GiB offload без нового расчёта.

Проведите [X → другие документы → X](../labs/02-kv-ram.md) и подтвердите чтение из RAM после вытеснения из GPU. Только быстрый повтор без этих метрик не считается проверкой offload.

Assistant проверяется отдельно от offload, снова на исходном окне 64K. Только после проверки совместимости его модели и runtime остановите B cache и примените B spec:

```bash
python3 scripts/hf.py stop b-cache --ack
python3 scripts/hf.py apply b-spec --ack
python3 scripts/hf.py start b-spec --ack
```

В B spec CPU KV-offload не включён: сравниваем assistant с B tuned. Проверяем долю принятых черновых токенов, качество и итоговую скорость. При отсутствии выигрыша сохраняем результат, а для основного сервиса оставляем более быстрый проверенный профиль.

## 5. Сервис Deckhouse

Остановите A и дождитесь освобождения его ResourceClaim. Через Console создайте только `hf-platform-gemma` на освободившейся H100 по [инструкции платформенного запуска](../labs/04-deckhouse.md).

Перед запуском проверьте память плана вместе с оставшимся B. Requests и limits ручных профилей не переносятся в план контроллера автоматически. Сверьте модель, движок, контекст, FP8 KV, prefill и CUDA graphs по фактическим аргументам. Offload и assistant включайте только при поддержке установленной CRD и runtime. Ручной Deployment контроллера не патчите.

Сравните ответы и метрики на том же наборе. Экспортируйте проверенный манифест без секретов. Если runtime или функции отличаются, это отдельное сравнение, а не повтор идентичной конфигурации.

## 6. Динамический MIG и MPS на A30

Сохраните проверенный LLM для пользовательского чата. Малые сервисы запускаются на отдельной ноде A30; остановка платформенной Gemma для освобождения их памяти не требуется. Варианты MIG/MPS переключайте без накопления лишних Deployment, но рабочий эмбеддер и реранкер не отключайте до проверки заменяющих сервисов.

Заполните `mig_node`, созданные контроллером DeviceClass и квоты MPS в `.local/site-mig.json`, явно указывая его в каждой команде. Режим MIG должен быть подготовлен и согласован заранее; сами разделы создаются динамически по заявкам, а не ручной преднарезкой. Выполните [работу с MIG/MPS](../labs/05-mig-mps.md): проверьте назначенные разделы, квоты, метрики, ответы API и освобождение ресурсов после остановки.

Не переходите к реранкеру, пока не проверены его модель, API и параметры преобразования для выбранного vLLM. Поле `reranker_config_verified` не заменяет эту проверку.

## 7. Qwen TP2

Остановите обе ручные Gemma и платформенный сервис Gemma. Нужные чату эмбеддер и реранкер на A30 сохраните. Убедитесь, что H100 Pod завершились, их заявки освобождены, а RAM не удерживается другими процессами. Не удаляйте PVC.

Перед стартом проверьте CUDA на обеих назначенных картах, NVLink/NCCL, поддержку архитектуры и квантования, а также отдельный бюджет RAM/VRAM Qwen. Расчёт Gemma на неё не переносится. [Ручной план TP2](../labs/06-tp2.md) служит предварительной проверкой; итоговый запуск выполняется через AI Inference, после подтверждения рецепта, с подключением к прежнему Bifrost и Open WebUI.

Начинаем с короткого запроса, затем длинный контекст и параллельность 1, 2, 4, 8, 16, 32, 50. Переходим к следующему уровню только после завершения предыдущего без OOM и ошибок, сохраняя очередь и задержки. 50 открытых сессий не равны 50 одновременно вычисляемым контекстам 256K.

## Остановка и откат

При OOM, eviction, ошибках CUDA/NCCL или нестабильной ноде остановите новый профиль. Сохраните логи, события, снимок ресурсов и метрики до перезапуска. Не увеличивайте лимиты и не снимайте cordon автоматически.

Например, если B cache не прошёл проверку, верните B tuned, только если он уже был проверен:

```bash
python3 scripts/hf.py snapshot b-cache --out .local/runs/b-cache-failed.json
python3 scripts/hf.py stop b-cache --ack
python3 scripts/hf.py apply b-tuned --ack
python3 scripts/hf.py start b-tuned --ack
```

Для других этапов останавливается соответствующий Deployment; `hf-platform-gemma` управляется отдельно через Console. Namespace, Model, PVC и GPUClass/GPUPool остаются. Ресурсы неизвестного владельца и finalizers не удаляются. Файлы снимков не перезаписываются: для следующей попытки выберите новые имена.

Существующие Open WebUI, шлюз и пользовательские данные сохраняются. Новые маршруты подключаются после проверки прямого API. Если внешнего доступа ещё нет, его подготовка требует отдельной настройки сети и аутентификации. Измерения движка выполняются напрямую, без кэша ответов шлюза.
