# Чат, доступ и базы знаний

Open WebUI может работать в одном кластере, а Bifrost, MCP и модели — в другом.
Для переключения ручного vLLM на AI Inference достаточно заменить маршрут модели
в Bifrost. История чатов, пользователи и базы знаний остаются в WebUI.

## Маршруты

Создайте отдельные маршруты A и B к соответствующим Service vLLM. В WebUI назовите
их `Gemma A — Base` и `Gemma B — Tune`. Не объединяйте их балансировкой, fallback
или кэшем готовых ответов шлюза: запрос должен попадать в выбранную конфигурацию.
Prefix cache внутри vLLM при этом работает согласно профилю.

Одинаковые параметры генерации задаются у обеих моделей. Для короткой проверки
без reasoning можно передать `chat_template_kwargs: {"enable_thinking": false}`.
При замерах сохраняйте весь запрос, а не только текст сообщения.

## Локальная регистрация и личные ключи

Включите регистрацию с начальной ролью `pending`. После одобрения администратором
[адаптер доступа](../integrations/webui-access/README.md) выдаёт пользователю
отдельный Bifrost Virtual Key и подставляет его на сервере. Общий ключ участников
не нужен. [Пример values](../examples/webui-access.yaml) задаёт две Gemma,
бюджет $500/24 часа и тариф $10/$20 за миллион входных/выходных токенов.
Это условная стоимость для упражнения, без списания денег.

Разрешите чтение базовых моделей группе участников через ACL Open WebUI.
Права на псевдоним сами по себе могут не давать доступ к базовому подключению.
Другие модели скройте правами доступа, не удаляя их серверы и чужие настройки.

Проверьте с обычной учётной записью:

- отказ до одобрения, ответ обеих моделей после него;
- отдельный VK у каждого пользователя и расход в фильтре «Виртуальные ключи»;
- отзыв доступа и повторное одобрение без нового ключа и обнуления бюджета;
- отсутствие MCP и возможности выбрать постороннюю модель.

API-ключ Open WebUI и Virtual Key Bifrost — разные сущности. Выдавать их браузеру
для этого подключения не требуется. Стоимость служебных запросов, например
генерации заголовка чата, тоже относится к пользователю.

## OIDC и MCP

Сохраните отдельное подключение OIDC/System OAuth для административной работы.
MCP получает права через персональный OAuth grant и RBAC целевого кластера:
сам факт OIDC-входа не даёт право менять Kubernetes. Существующие OAuth credentials
не заменяются ключом адаптера. Локальным участникам MCP не предоставляется.

Проверку изменяющей операции выполняйте только в выделенном namespace с
заранее выбранным обратимым действием. Административные инструменты не должны
попадать в общую группу моделей участников.

## Документы и голос

Для каждой базы знаний храните источник, версию документа и ACL. Загружайте
учебные или публичные материалы; не используйте рабочие документы компании.
Проверьте поиск и цитаты по вопросу с известным ответом, затем двумя аккаунтами
проверьте изоляцию закрытых документов.

Whisper, эмбеддер и реранкер подключаются отдельно. При смене LLM индекс не нужно
перестраивать; при смене embedding-модели — нужно. Адаптер персонализирует только
чат: индексация, reranking и распознавание голоса не становятся персонально
оплаченными автоматически. Контекст RAG внутри сообщения входит в токены чата.

## Подключить Qwen в финале

Перед остановкой Gemma завершите активные запросы. Создайте отдельный маршрут
Qwen в Bifrost и проверьте его фактическую модель через `/v1/models`.
Базовые документы, история чатов и embedding-индекс при этом сохраняются.

Для обычных пользователей добавьте маршрут Qwen в `chat_models`, разрешённые
модели и provider key IDs адаптера, настройте тариф и ACL модели в WebUI.
Политики уже выданных VK должны быть обновлены через API управления Bifrost
с сохранением бюджетов и расхода: смена values не переписывает их автоматически.
Не создавайте новые ключи только из-за смены модели. Скройте остановленные Gemma
после проверки Qwen обычной одобренной учётной записью.

Администратор обращается к Qwen через отдельное OIDC/System OAuth подключение
с разрешённым MCP. `qwen3_xml` разбирает вызов инструмента, но не выдаёт права
на кластер и не запускает MCP-сервер. Проверьте весь путь: модель вернула вызов,
шлюз разрешил инструмент, Kubernetes применил RBAC, результат вернулся в чат.
Участник с личным VK по-прежнему получает только чат и разрешённые базы знаний.
