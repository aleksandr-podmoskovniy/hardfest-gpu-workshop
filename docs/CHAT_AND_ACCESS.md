# Подключение чата и персонального доступа

Open WebUI хранит пользователей, чаты и базы знаний. ai-mcp-gateway на базе
Bifrost маршрутизирует запросы, проверяет права и учитывает расход. Эти сервисы
могут работать в разных кластерах. При переходе с ручного vLLM на AI Inference
меняется адрес модели за шлюзом, а не учётные записи в чате.

## Перед началом

- Развёрнуты Open WebUI и ai-mcp-gateway; между ними проверены сеть и TLS.
- Шлюзу доступны Service моделей в GPU-кластере.
- Есть административный доступ к настройкам обоих сервисов.
- Подготовлены обычная тестовая учётная запись и административная OIDC-учётка.

| Пользователь | Вход | Доступ |
| --- | --- | --- |
| Участник до одобрения | Логин и пароль, роль `pending` | Нет доступа к моделям |
| Одобренный участник | Логин и пароль, роль `user` | Разрешённые модели, базы знаний, голос |
| Администратор | OIDC | Модели и отдельное MCP-подключение в пределах OAuth/RBAC |

## 1. Создать два независимых маршрута моделей

В ai-mcp-gateway создайте отдельные маршруты к Service A и B.
В Open WebUI дайте им короткие имена:

| Модель в чате | Куда отправлять запросы |
| --- | --- |
| `Gemma A — Base` | Service базовой Gemma |
| `Gemma B — Tune` | Service оптимизированной Gemma |

> [!IMPORTANT]
> Не включайте балансировку, fallback A↔B и кэш готовых ответов шлюза для этих
> маршрутов. Иначе выбранная в чате модель не будет соответствовать измеряемому профилю.

Prefix cache внутри vLLM работает согласно values. Параметры генерации задайте
одинаковыми у обеих моделей. Для короткого запроса без reasoning можно передать
`chat_template_kwargs: {"enable_thinking": false}`.

Проверьте отдельным запросом каждый маршрут и сопоставьте его с логами нужного
Service. При замерах сохраняйте весь запрос, включая параметры генерации.

## 2. Настроить регистрацию и личные ключи

1. В Open WebUI включите регистрацию с начальной ролью `pending`.
2. Настройте [адаптер персональных ключей](../integrations/webui-access/README.md)
   в namespace WebUI. Пример его политики — [webui-access.yaml](../examples/webui-access.yaml).
3. Подключите WebUI к адаптеру, включив передачу подписанного JWT пользователя.
4. Через ACL WebUI разрешите участникам только две Gemma и нужные базы знаний.
   Проверьте права как на псевдонимы, так и на базовое подключение.
5. Остальные модели скройте ACL. Не удаляйте их серверы и чужие подключения.

В частных values адаптера заполните:

| Поле | Что указать |
| --- | --- |
| `image` | Digest опубликованного образа адаптера |
| `existingSecret` | Secret со служебными ключами, созданный отдельно от Git |
| `config.webui_url`, `config.gateway_url` | Адреса WebUI и шлюза, доступные адаптеру |
| `config.service_user_id` | UUID служебной учётной записи WebUI |
| `config.managed_by` | Уникальный постоянный ID установки |
| `config.chat_models`, `config.providers` | Два маршрута и точные ID их ключей провайдера |
| `config.provisioning_mode` | `create` — создавать личный VK после одобрения |
| `config.budget_usd`, `config.budget_reset` | `500` и `24h` |
| `config.pricing` | $10 за миллион входных и $20 за миллион выходных токенов |

Начните с `replicaCount: 0`. Проверьте Secret, адреса и Helm render, затем включите
адаптер через [GitOps](GITOPS.md). Полная конфигурация и четыре поля Secret приведены
в [инструкции адаптера](../integrations/webui-access/README.md#сборка-и-развёртывание).

После одобрения адаптер создаёт отдельный Bifrost Virtual Key и подставляет его
на сервере. Пользователь не копирует ключ в браузер и не выпускает API-ключ WebUI.
Сверка выполняется периодически; первый запрос также проверяет наличие VK.

Тарифы нужны для демонстрационного учёта, **деньги не списываются**. Служебные
запросы WebUI, например генерация заголовка чата, тоже учитываются у пользователя.

### Проверить выдачу и отзыв

Проведите проверку с двумя обычными аккаунтами:

| Действие | Что проверить в WebUI и шлюзе |
| --- | --- |
| Зарегистрировать аккаунт | Роль `pending`, запросы к моделям запрещены |
| Одобрить его | Обе Gemma доступны, появился личный VK |
| Отправить сообщения от двух пользователей | Разные ID VK, отдельные токены и стоимость |
| Вернуть первого пользователя в `pending` | Новые запросы через адаптер запрещены, в том числе со старым JWT |
| Одобрить повторно | Прежний ID VK, расход и бюджет не обнулились |
| Запросить MCP или постороннюю модель | Доступ запрещён |

В логах Bifrost выбирайте фильтр **«Виртуальные ключи»**, а не «Ключи провайдера».
На HA-шлюзе проверьте доступ и учёт через каждую реплику.
API-ключ WebUI, ключ провайдера и личный VK — разные сущности.

В [прогоне 6 октября](../results/rtx5060-access-20261006.json) личный VK
создавался после одобрения, запросы и тарифы записывались, но общий счётчик
бюджета расходился с журналом: $0,00309 против $0,00947.
Поэтому наличие политики `$500 / 24h` пока не подтверждает строгий общий
лимит на HA-установке. Проверяйте сумму журналов, счётчик VK и отказ
после достижения лимита отдельно; не заменяйте эту проверку одним успешным запросом.

Блокировка пользователя в адаптере и отзыв ключа в Bifrost — разные проверки.
VK не передаётся в браузер. Если используемый API выдачи не позволяет адаптеру
отключать ключ, отзовите его административным API Bifrost и отдельно проверьте
отказ прямого запроса с этим ключом. Не считайте смену роли доказательством отзыва VK.

> [!IMPORTANT]
> Смена values не переписывает политики уже выданных VK. При изменении списка
> моделей или квот обновите действующие политики через API управления Bifrost
> с сохранением расхода, затем согласуйте values. Не перевыпускайте ключи ради этого.

## 3. Оставить MCP только административному подключению

Сохраните отдельное OIDC/System OAuth подключение для администратора.
Локальных участников направляйте через адаптер: этот путь не выдаёт MCP grants
и отклоняет запросы с инструментами. Существующие OAuth credentials не заменяйте
ключом адаптера.

Проверяйте весь путь административного запроса:

1. Модель возвращает вызов инструмента.
2. Шлюз разрешает нужный MCP-сервер и инструмент.
3. Kubernetes применяет RBAC пользователя в целевом кластере.
4. Результат операции возвращается в чат.

Вход по OIDC сам по себе не даёт прав на изменение Kubernetes. Первую изменяющую
операцию выполняйте в выделенном namespace, на заранее выбранном тестовом ресурсе
с понятным откатом. Не добавляйте это подключение в общую группу участников.

## 4. Подключить базы знаний и Whisper

![Документы проходят эмбеддер и индекс, а вопрос — поиск, реранкер и LLM](../assets/16-rag.svg)

1. Подключите эмбеддер, реранкер и Whisper отдельными настройками WebUI по таблице ниже.
2. Создайте базу знаний из учебных или публичных документов. Зафиксируйте источник,
   версию и ACL; рабочие документы компании не загружайте.
3. Задайте вопрос с известным ответом. Проверьте найденные фрагменты и ссылки.
4. Двумя аккаунтами проверьте изоляцию закрытых документов и доступ к голосу.

При смене LLM индекс сохраняется. При смене embedding-модели его нужно построить
заново. RAG-контекст внутри сообщения входит во входные токены чата.

### Настройки трёх API

Для проверенной связки Open WebUI 0.11.0 и ai-mcp-gateway используются:

| Настройка WebUI | Режим | URL | Имя модели |
| --- | --- | --- | --- |
| Эмбеддер | OpenAI | `https://GATEWAY/v1` | `vllm/EMBEDDING_MODEL_ID` |
| Реранкер | External | `https://GATEWAY/cohere/v2/rerank` | `vllm/RERANKER_MODEL_ID` |
| Распознавание речи | OpenAI | `https://GATEWAY/v1` | `vllm/WHISPER_MODEL_ID` |

Замените `GATEWAY` адресом шлюза, а `*_MODEL_ID` — точными ID из `/v1/models`
соответствующих InferenceService. Это не отображаемые названия в чате.
Разрешите эти модели служебному VK WebUI; credential передавайте через защищённые
настройки, не через Git. Три API не становятся чат-моделями в списке участников.

WebUI отправляет реранкеру массив строк. Указанный Cohere-совместимый endpoint
принимает такой формат; нативный `/v1/rerank` шлюза ожидает объекты документов
и в этой связке возвращает `400`. За шлюзом модель остаётся на vLLM.

### Переход на другой эмбеддер

1. Закройте запись в WebUI на время миграции. Сохраните настройки, исходные
   документы, связи с базами знаний и резервную копию векторного хранилища.
2. Проверьте новый эмбеддер, реранкер и Whisper через шлюз. На HA-установке
   повторите запросы через каждую реплику, а не только через общий адрес.
3. Обновите модель эмбеддера и переиндексируйте связанные с базами знаний файлы
   и метаданные самих баз. Не запускайте глобальный сброс данных WebUI.
4. Проверьте размерность, число документов, неизменность ACL и поиск по вопросу
   с известным ответом. Отдельно проверьте поиск с реранкером и голосовой ввод.
5. Откройте доступ после проверок. Сохраните резервную копию до завершения прогона.

Qwen3 Embedding 4B в этом профиле выдаёт векторы размерности **2560**. Старый
индекс из 1024-мерных векторов с ним несовместим; смена только названия модели
не выполняет миграцию. Задержки и ошибки трёх сервисов смотрите в
[дашборде кластера A30](OBSERVABILITY.md).

Адаптер персонализирует **чат**, а не все фоновые операции WebUI. Индексация,
reranking и распознавание голоса не начинают учитываться по личному VK автоматически;
их отдельный учёт нужно настроить и проверить отдельно.

## 5. Переключить чат на Qwen

После проверки [Qwen через AI Inference](../README.md#tp2):

1. Создайте отдельный маршрут Qwen и проверьте фактическую модель через `/v1/models`.
2. Добавьте маршрут в `chat_models`, разрешённые модели и provider key IDs адаптера.
3. Настройте тариф и обновите политики существующих VK без обнуления расхода.
4. Разрешите модель через ACL WebUI и проверьте ответ обычной одобренной учёткой.
5. Скройте остановленные Gemma. Не удаляйте чаты, пользователей и базы знаний.

Администратор использует Qwen через прежнее отдельное OAuth/MCP-подключение.
Парсер `qwen3_xml` разбирает вызовы инструментов, но не выдаёт прав на кластер
и не запускает MCP-сервер. Повторите проверку из шага 3.
