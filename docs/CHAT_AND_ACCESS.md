# Чат и личный доступ

Запрос участника проходит через Open WebUI → адаптер личных ключей → Bifrost →
Service модели. WebUI хранит диалоги; Bifrost выбирает backend и учитывает расход.
Смена модели сохраняет аккаунт, чаты и личный ключ.

## Связать модель с маршрутом

Подпись в WebUI, псевдоним Bifrost, Kubernetes Service и поле `model` API —
разные имена. Их соответствие задаётся при подготовке. Для A/B отключите
fallback, балансировку между сравниваемыми сервисами и кеш готовых ответов шлюза.
Prefix cache самого vLLM определяется профилем.

| Площадка | Deployment / Service | `model` прямого API |
| --- | --- | --- |
| PRO 6000: A / Cache / Tune | `selectel-gemma-a` / `selectel-gemma-cache` / `selectel-gemma-b`, порт 8000 | Совпадает с именем выбранного Service |
| H100: A / Cache / Tune | `hf-gemma-a` / `hf-gemma-cache` / `hf-gemma-b`, порт 8000 | `gemma-4-31b` |
| RTX 5060 | [Таблица маршрутов](SETUP.md#rtx) | По той же таблице |

У H100 маршруты A и Tune — `vllm/gemma-a` и `vllm/gemma-b`;
для отдельного Cache заранее добавляется `vllm/gemma-cache` → `hf-gemma-cache:8000`.
Upstream-имя одинаковое, Service разные. На всех площадках Cache/Tune —
отдельные Deployment, работающие по очереди.

Для созданного в Console InferenceService проверьте цепочку целиком:

1. Имя заказа совпадает с [подготовленным](SETUP.md#inference-readiness).
2. Созданный Service выбирает Ready Pod; проверены его порт и `/v1/models`.
3. Bifrost направляет нужный псевдоним в этот Service с его backend credential.
4. Личная политика разрешает маршрут, WebUI показывает модель и получает ответ.

Произвольное имя заказа не подключает его к чату. На PRO 6000 соответствие
платформенного Service, gateway route и WebUI ещё требует проверки после входа.
Наличие прямых результатов runtime не подтверждает готовность этого пути.

## Выдать и проверить личный доступ

Virtual Key (VK) — ключ Bifrost с разрешёнными моделями, лимитами и учётом
пользователя. Provider key — отдельный ключ, которым шлюз обращается к backend.
В [values адаптера](../examples/webui-access.yaml) указываются ID provider keys,
псевдонимы и upstream-имена; секретные значения доставляются отдельно.

В WebUI включите регистрацию с ролью `pending`, установите
[webui-access](../integrations/webui-access/README.md#сборка-и-развёртывание)
и настройте ACL моделей. После одобрения адаптер создаёт личный VK и добавляет
его к запросам на сервере. Копировать ключ в браузер не требуется.

| Проверка обычным аккаунтом | Результат |
| --- | --- |
| Новый `pending` | Запрос запрещён |
| Одобренный `user` | Ответ и запись по личному VK |
| Два пользователя | Разные VK и раздельный расход |
| Возврат в `pending` | Новые запросы запрещены, в том числе со старым JWT |
| Повторное одобрение | Сохраняются ID VK и расход |
| Чужая модель или MCP | Отказ |

Проверяйте браузерный чат вместе с фоновыми запросами названия диалога.
Для этой интеграции настройки Function Calling и инструментов заданы в
[инструкции WebUI](../integrations/webui-access/README.md#подключение-webui).
В Bifrost фильтруйте по «Виртуальным ключам», не по «Ключам провайдера».

Тариф стенда — $10/$20 за миллион входных/выходных токенов, бюджет $500/24 часа;
реальных списаний нет. [Историческая проверка RTX](../results/rtx5060-access-20261006.json)
обнаружила отставание счётчика от журнала: строгий общий HA-бюджет не подтверждён.
Обновление values не меняет уже выданные VK; новые модели и лимиты добавляйте
[с сохранением ID и расхода](../integrations/webui-access/README.md#добавление-модели-в-работающую-установку).
Блокировка в адаптере и отзыв самого VK проверяются отдельно, включая прямой запрос.

## Длинный ответ в чате

В параметрах настроенной модели WebUI задайте верхний предел выхода **32768**
(`max_tokens` либо эквивалент текущего подключения), без `ignore_eos`.
Окно движка, вход и продолжение согласуются по [бюджету](MEMORY_BUDGET.md).
Base с контрольным окном 4K/16K этот лимит принять не может.

Проверьте фактический запрос в журнале: сохранённые параметры старого чата
могут перекрыть новые настройки модели. `finish_reason=length` означает
достижение лимита; сетевой обрыв и штатный `stop` — другие результаты.
Повышение лимита не исправляет таймаут шлюза и не доказывает успешный длинный ответ.

## Документы и голос

RAG добавляет найденные фрагменты документа к вопросу. Эмбеддер строит векторы
для поиска, реранкер уточняет порядок результатов, Whisper переводит голос в текст.
Путь документа и вопроса показан на [схеме RAG](../assets/16-rag.svg).
Для WebUI 0.11.0 и ai-mcp-gateway используются такие подключения:

| Настройка WebUI | Режим / URL | Model ID |
| --- | --- | --- |
| Эмбеддер | OpenAI / `https://GATEWAY/v1` | `vllm/EMBEDDING_MODEL_ID` |
| Реранкер | External / `https://GATEWAY/cohere/v2/rerank` | `vllm/RERANKER_MODEL_ID` |
| Голос | OpenAI / `https://GATEWAY/v1` | `vllm/WHISPER_MODEL_ID` |

Замените адрес и ID значениями площадки. Здесь реранкеру нужен Cohere endpoint:
WebUI отправляет строки, а нативный `/v1/rerank` шлюза ожидает объекты документов.
Разрешите сервисы служебному VK WebUI; их расход не наследует личный VK автоматически.

Проверка — публичный документ с известным фактом, ответ со ссылками и голосовой ввод
под двумя аккаунтами. При смене эмбеддера переиндексируйте данные: у Qwen3
Embedding 4B размерность 2560, индекс из 1024 несовместим. Сначала сохраните
документы, ACL и резервную копию; глобальный сброс WebUI не требуется.
После пересоздания сервиса проверьте DNS и сохранённый токен прокси.

## Административные инструменты

MCP использует отдельное OIDC/OAuth-подключение администратора и права Kubernetes
RBAC. Участникам MCP grants не выдаются. Вход через OIDC сам по себе не даёт
прав менять кластер; проверяйте разрешение вызова на каждом слое.

Чтобы добавить Qwen, сначала проверьте его API, затем маршрут, тариф,
действующие VK и ACL WebUI. Скройте остановленные Gemma, сохранив диалоги и ключи.
Парсер `qwen3_xml` распознаёт вызовы инструментов, но не выдаёт права.
