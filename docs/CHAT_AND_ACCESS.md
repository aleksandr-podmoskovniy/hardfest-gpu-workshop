# Чат и личный доступ

Участник отправляет сообщение в Open WebUI. Адаптер добавляет его личный ключ,
а Bifrost проверяет разрешения и направляет запрос в Service выбранной модели.
WebUI хранит диалоги; шлюз учитывает запросы и расход токенов.
При переключении модели аккаунт, чаты и личный ключ сохраняются.

## Связать модель с маршрутом

Подпись в WebUI, псевдоним Bifrost, Kubernetes Service и поле `model` API —
разные имена. Их соответствие задаётся при подготовке.

Для сравнения A/B каждый маршрут должен вести только в свой экземпляр модели.
Отключите fallback, балансировку между A и B и кеш готовых ответов шлюза:
иначе ответ может прийти не от того сервиса, который измеряется.
Prefix cache самого vLLM остаётся частью сравниваемого профиля.

| Площадка | Deployment / Service | `model` прямого API |
| --- | --- | --- |
| PRO 6000: A / Cache / Tune | `selectel-gemma-a` / `selectel-gemma-cache` / `selectel-gemma-b`, порт 8000 | Совпадает с именем выбранного Service |
| H100: A / Cache / Tune | `hf-gemma-a` / `hf-gemma-cache` / `hf-gemma-b`, порт 8000 | `gemma-4-31b` |
| RTX 5060 | [Таблица маршрутов](SETUP.md#rtx) | По той же таблице |

У H100 маршруты A и Tune — `vllm/gemma-a` и `vllm/gemma-b`;
для Cache маршрут `vllm/gemma-cache` направляется в `hf-gemma-cache:8000`.
Все три API принимают одно upstream-имя модели, но работают в разных Service.
На всех площадках Cache и Tune развёрнуты отдельными Deployment
и используют одну карту по очереди.

Для созданного в Console InferenceService проверьте цепочку целиком:

1. Имя заказа совпадает с [подготовленным](SETUP.md#inference-readiness).
2. Созданный Service выбирает Ready Pod; проверены его порт и `/v1/models`.
3. Bifrost направляет нужный псевдоним в этот Service с его backend credential.
4. Личная политика разрешает маршрут, WebUI показывает модель и получает ответ.

Карточка в WebUI не запускает модель и может оставаться видимой, когда
сервис остановлен. В таком случае в описании указывается, что ответ будет
доступен после запуска. Готовность проверяется запросом через Bifrost,
а видимость карточки и разрешения участника управляются отдельно.
Смена этапа не требует перевыпуска личных ключей участников.

Для платформенной Gemma используются три отдельные карточки:

| Карточка участника | Имя InferenceService и псевдоним Bifrost | `model` backend |
| --- | --- | --- |
| Gemma — H100 · платформа | `hf-platform-gemma` | `gemma-4-31b` |
| Gemma — RTX 5060 Ti · платформа | `rtx-gemma-platform` | `rtx-gemma-e2b` |
| Gemma — PRO 6000 · платформа | `selectel-gemma31` | `gemma-4-31b` |

Одного разрешения в WebUI недостаточно: маршрут должен быть разрешён и в
личной политике Bifrost. Проверяйте её обычным аккаунтом, не только администратором.
При добавлении маршрута проверьте его тариф в Bifrost.

## Открыть или закрыть модель участникам

В Open WebUI 0.12.2 используйте **«Доступ»** в настройках модели.
Программных доработок WebUI для этого не требуется.

У каждой модели стенда есть два элемента: базовая модель из подключения
и карточка с понятным названием, промптом и параметрами ответа.
**Закрывать нужно оба.** Закрытая база запрещает запросы, а закрытая карточка
убирает модель из списка участников.

| Карточка в «Рабочее пространство → Модели» | База в «Администрирование → Модели» |
| --- | --- |
| Gemma A — RTX 5060 Ti · Base | `workshop.vllm/rtx-gemma-base` |
| Gemma B — RTX 5060 Ti · Cache | `workshop.vllm/rtx-gemma-cache` |
| Gemma B — RTX 5060 Ti · Tune | `workshop.vllm/rtx-gemma-tune` |
| Gemma A — PRO 6000 · базовая | `workshop.vllm/selectel-gemma-a` |
| Gemma B — PRO 6000 · KV cache | `workshop.vllm/selectel-gemma-cache` |
| Gemma B — PRO 6000 · полный тюнинг | `workshop.vllm/selectel-gemma-b` |
| Gemma — H100 · платформа | `workshop.vllm/hf-platform-gemma` |
| Gemma — RTX 5060 Ti · платформа | `workshop.vllm/rtx-gemma-platform` |
| Gemma — PRO 6000 · платформа | `workshop.vllm/selectel-gemma31` |
| Qwen 9B — RTX 5060 Ti · TP2 | `workshop.vllm/rtx-qwen35-tp2` |
| Qwen 3.8 — PRO 6000 · TP2 · 256K | `workshop.vllm/selectel-qwen38-tp2` |

**Закрыть:** сначала откройте настройки базы, затем настройки карточки. У каждого элемента
выберите **«Доступ → Частное»**, удалите разрешения участников и их групп
из списка доступов и сохраните изменения. Администратор сохраняет доступ;
владелец модели тоже имеет особые права, поэтому владельцем должен быть администратор.

**Открыть:** сначала разрешите карточку, затем базу. В обоих местах выберите
**«Публичное»** для всех одобренных участников либо добавьте нужную группу
с правом чтения. Не выдавайте публичное право записи. Карточка и база должны быть
включены (`Enabled`), а сервис модели — запущен.

Переключатель `Enabled` и значок глаза не заменяют права доступа.
Скрытая база может обслуживать публичную карточку. Чтобы проверить запрет,
используйте обычный аккаунт: после обновления страницы карточка исчезает,
а новый запрос из прежнего чата отклоняется. Уже выполняющийся запрос
изменение прав не отменяет.

Закрытие доступа **не останавливает GPU-сервис**. Реплики меняются отдельно
в Console. Не удаляйте модель, чтобы временно закрыть её участникам.
Подробнее — [штатное управление моделями WebUI](https://docs.openwebui.com/features/workspace/models/).

### Что полезно в новой версии

- **История настроек модели:** можно сравнить и вернуть прежний промпт или
  параметры. Права доступа, видимость и `Enabled` проверяются отдельно —
  откат версии их не восстанавливает.
- **Элементы управления моделью:** администратор может подготовить несколько
  разрешённых вариантов параметров для выбора в чате. Используйте только
  параметры, поддерживаемые конкретной моделью; это не замена лимитам шлюза.
- **Ссылки в превью базы знаний:** участник может открыть коллекцию и исходные
  документы, чтобы проверить, на чём основан ответ.

Первые две возможности описаны в [руководстве по моделям](https://docs.openwebui.com/features/workspace/models/),
изменения превью — в [релизе 0.12.2](https://github.com/open-webui/open-webui/releases/tag/v0.12.2).

## Выдать и проверить личный доступ

Virtual Key (VK) — ключ Bifrost с разрешёнными моделями, лимитами и учётом
пользователя. Provider key — отдельный ключ, которым шлюз обращается к backend.
В [values адаптера](../examples/webui-access.yaml) указываются ID provider keys,
псевдонимы и upstream-имена; секретные значения доставляются отдельно.

В WebUI включите регистрацию с ролью `pending`, установите
[webui-access](../integrations/webui-access/README.md#сборка-и-развёртывание)
и настройте ACL моделей. После одобрения адаптер создаёт личный VK и добавляет
его к запросам на сервере. Копировать ключ в браузер не требуется.

| Проверка обычным аккаунтом | Результат |
| --- | --- |
| Новый `pending` | Запрос запрещён |
| Одобренный `user` | Ответ и запись по личному VK |
| Два пользователя | Разные VK и раздельный расход |
| Возврат в `pending` | Новые запросы запрещены, в том числе со старым JWT |
| Повторное одобрение | Сохраняются ID VK и расход |
| Чужая модель или MCP | Отказ |

Проверяйте браузерный чат вместе с фоновыми запросами названия диалога.
Для этой интеграции настройки Function Calling и инструментов заданы в
[инструкции WebUI](../integrations/webui-access/README.md#подключение-webui).
В Bifrost фильтруйте по «Виртуальным ключам», не по «Ключам провайдера».

Демонстрационный тариф — $10 за миллион входных токенов и $20 за миллион
выходных; бюджет пользователя — $500 на 24 часа. **Реальных списаний нет.**

Суммарный счётчик нескольких реплик Bifrost может отставать от журнала.
В этой конфигурации он не обеспечивает строгий общий лимит расходов.
Обновление values не меняет уже выданные VK; новые модели и лимиты добавляйте
[с сохранением ID и расхода](../integrations/webui-access/README.md#добавление-модели-в-работающую-установку).
Блокировка в адаптере и отзыв самого VK проверяются отдельно, включая прямой запрос.

## Длинный ответ в чате

В параметрах настроенной модели WebUI задайте верхний предел выхода **32768**
(`max_tokens` либо эквивалент текущего подключения), без `ignore_eos`.
Окно движка, вход и продолжение согласуются по [бюджету](MEMORY_BUDGET.md).
Base с контрольным окном 4K/16K этот лимит принять не может.

Проверьте фактический запрос в журнале: сохранённые параметры старого чата
могут перекрыть новые настройки модели. `finish_reason=length` означает
достижение лимита; сетевой обрыв и штатный `stop` — другие результаты.

## Документы и голос

RAG — поиск подходящих фрагментов документа, которые модель получает вместе
с вопросом. Эмбеддер переводит текст в векторы для поиска, а реранкер
сравнивает найденные фрагменты с вопросом и выбирает наиболее подходящие.
Whisper обслуживает отдельную задачу: переводит голос в текст.
Путь документа и вопроса показан на [схеме RAG](../assets/16-rag.svg).
Для WebUI 0.12.2 и ai-mcp-gateway используются такие подключения:

| Настройка WebUI | Режим / URL | Model ID |
| --- | --- | --- |
| Эмбеддер | OpenAI / `https://GATEWAY/v1` | `vllm/EMBEDDING_MODEL_ID` |
| Реранкер | External / `https://GATEWAY/cohere/v2/rerank` | `vllm/RERANKER_MODEL_ID` |
| Голос | OpenAI / `https://GATEWAY/v1` | `vllm/WHISPER_MODEL_ID` |

Замените адрес и ID значениями площадки. Здесь реранкеру нужен Cohere endpoint:
WebUI отправляет строки, а нативный `/v1/rerank` шлюза ожидает объекты документов.
Разрешите сервисы служебному VK WebUI; их расход не наследует личный VK автоматически.

Проверка — публичный документ с известным фактом, ответ со ссылками и голосовой ввод
под двумя аккаунтами. При смене эмбеддера переиндексируйте данные: у Qwen3
Embedding 4B размерность 2560, индекс из 1024 несовместим. Сначала сохраните
документы, ACL и резервную копию; глобальный сброс WebUI не требуется.
После пересоздания сервиса проверьте DNS и сохранённый токен прокси.

### Что спросить у базы знаний

База выбирается через `#` в поле сообщения. Для знакомства с поиском достаточно
трёх небольших подборок:

| Подборка | Вопрос для проверки |
| --- | --- |
| Kubernetes: память, CPU и проверки здоровья | «Чем readiness отличается от liveness? Приведи пример и ссылку на источник». |
| HardFest: KV-кеш, GPU и время ответа | «Посчитай KV-кеш Gemma для 256K. Какие параметры архитектуры нужны и чего не учитывает эта оценка?» |
| Учебный инцидент «Север» | «Сопоставь журнал изменений, метрики и логи. Какое изменение объясняет рост 502? Что остаётся недоказанным?» |

«Север» — вымышленный набор документов, а не данные рабочего кластера.
Он позволяет проверить, умеет ли модель сопоставлять источники, а не только
находить одну фразу. Ссылка на документ не гарантирует правильного вывода:
например, несколько медленных запросов нельзя выдавать за задержку всех запросов.

Общие базы доступны одобренным участникам на чтение; добавлять и менять документы
может администратор. Личные вложения должны сохранять свои права доступа;
их изоляция, включая поиск через RAG, проверяется отдельно.
Проверка текстового PDF не доказывает распознавание сканов: OCR проверяется отдельно.

## Административные инструменты

MCP использует отдельное OIDC/OAuth-подключение администратора и права Kubernetes
RBAC. Участникам MCP grants не выдаются. Вход через OIDC сам по себе не даёт
прав менять кластер; проверяйте разрешение вызова на каждом слое.

Парсер `qwen3_xml` распознаёт вызовы инструментов, но не выдаёт права.
