# Чат, документы и доступ участников

Open WebUI хранит пользователей, диалоги и базы знаний. Bifrost направляет запросы
к моделям и учитывает расход. Замена модели за шлюзом не требует нового аккаунта
или переноса чатов.

| Путь запроса | Для чего нужен |
| --- | --- |
| WebUI → адаптер личных ключей → Bifrost → vLLM | Чат участника с персональными правами и учётом |
| WebUI → Bifrost → эмбеддер, реранкер, Whisper | Поиск по документам и голосовой ввод |
| Отдельное подключение WebUI → Bifrost → MCP | Инструменты администратора, например обращения к Kubernetes |

Настройка требует административного доступа к WebUI и Bifrost, рабочей сети
между ними и проверенных API моделей. Схема всего стенда — в [подготовке](SETUP.md).

## 1. Разделить маршруты A и B

В Bifrost создаются два маршрута, в WebUI — две модели:

| Имя в чате | Backend |
| --- | --- |
| `Gemma A — Base` | Service базовой Gemma |
| `Gemma B — Tune` | Service оптимизированной Gemma |

> [!IMPORTANT]
> Для A/B отключены балансировка, fallback между ними и кэш готовых ответов
> шлюза. Иначе выбор модели в чате не соответствует измеряемому сервису.

Prefix cache внутри vLLM остаётся включённым или выключенным согласно профилю.
Он сохраняет вычисления начала запроса, а не готовый ответ.

Параметры генерации у A и B должны совпадать. Для опыта без внутренних рассуждений
можно передать `chat_template_kwargs: {"enable_thinking": false}`, если это
поддерживает выбранная модель. После короткого запроса проверьте в Bifrost
маршрут и в логах vLLM — нужный Service.

## 2. Настроить регистрацию и личные ключи

**Virtual Key (VK)** — личный ключ Bifrost: разрешённые модели, лимиты и связь
запросов с участником. Это не ключ провайдера, которым шлюз обращается к vLLM.

1. Включите регистрацию WebUI с начальной ролью `pending`.
2. Установите [адаптер личных ключей](../integrations/webui-access/README.md#сборка-и-развёртывание)
   в namespace WebUI и подключите передачу подписанного JWT пользователя.
3. Задайте маршруты, provider key IDs, квоты и тарифы в
   [values адаптера](../examples/webui-access.yaml). Секреты создаются отдельно,
   не попадают в Git, values или историю shell.
4. Через ACL — настройки доступа WebUI — разрешите участникам нужные модели
   и базы знаний. Проверьте и псевдонимы, и базовое подключение; чужие подключения
   скрывайте, не удаляйте.

После одобрения аккаунта адаптер создаёт VK и подставляет его **на сервере**.
Копировать ключ в браузер или выпускать API-ключ WebUI не нужно.
Фоновые запросы названия чата тоже занимают слоты параллельности и учитываются.

### Проверка обычным аккаунтом

| Действие | Ожидаемое поведение |
| --- | --- |
| Регистрация, роль `pending` | Запрос запрещён |
| Одобрение, роль `user` | Ответ модели; личный VK появился в Bifrost |
| Сообщения от двух аккаунтов | Разные ID VK и отдельные записи расхода |
| Возврат в `pending` | Новые запросы запрещены даже со старым JWT |
| Повторное одобрение | Прежний ID VK и накопленный расход |
| Запрос посторонней модели или MCP | Отказ |

Проверьте именно браузерный чат с фоновыми задачами, не только одиночный API-запрос.
Настройки `Function Calling: Legacy` и отключённые встроенные инструменты
описаны в [инструкции адаптера](../integrations/webui-access/README.md#подключение-webui).
В Bifrost нужен фильтр **«Виртуальные ключи»**, не «Ключи провайдера».

### Бюджет и отзыв

Тариф стенда — $10 за миллион входных и $20 за миллион выходных токенов;
бюджет — $500 на 24 часа. **Реальных списаний нет.**

На шлюзе с несколькими репликами проверяйте каждую: доступ, сумму журналов,
счётчик VK и отказ по лимиту. В [сохранённой проверке](../results/rtx5060-access-20261006.json)
счётчик расхода отставал от журнала. Поэтому строгий общий HA-бюджет не подтверждён.

Запрет пользователя в адаптере и **отзыв самого VK** — разные действия.
Если адаптер не может выключить ключ через API Bifrost, выполните административный
отзыв и проверьте отказ прямого запроса. Смена роли сама по себе этого не доказывает.

> [!IMPORTANT]
> Новые values не переписывают уже выданные VK. Изменение моделей и лимитов
> требует согласованного обновления политик Bifrost с сохранением ID и расхода.
> Перевыпускать ключи для этого не нужно.

## 3. Отделить административные инструменты

Участники получают чат, документы и голос. Их адаптер отклоняет вызовы
инструментов и не выдаёт MCP grants.

Администратор использует отдельное OIDC/OAuth-подключение. MCP подключает
инструменты к модели; права на Kubernetes по-прежнему определяются RBAC.
Вход по OIDC не даёт права менять кластер автоматически.

Проверка пути: модель предложила вызов → шлюз разрешил инструмент → Kubernetes
проверил права → результат вернулся в чат. Первую изменяющую операцию выполняйте
только на согласованном тестовом ресурсе с понятным откатом.

## 4. Подключить документы и голос

**RAG** добавляет найденные документы к вопросу. Эмбеддер превращает текст
в векторы для поиска, реранкер уточняет порядок результатов. Whisper переводит
голос в текст; это отдельный сервис.

![Путь документов и вопроса через поиск к модели](../assets/16-rag.svg)

Для проверенной связки WebUI 0.11.0 и ai-mcp-gateway:

| Настройка WebUI | Режим | URL | Model ID |
| --- | --- | --- | --- |
| Эмбеддер | OpenAI | `https://GATEWAY/v1` | `vllm/EMBEDDING_MODEL_ID` |
| Реранкер | External | `https://GATEWAY/cohere/v2/rerank` | `vllm/RERANKER_MODEL_ID` |
| Голосовой ввод | OpenAI | `https://GATEWAY/v1` | `vllm/WHISPER_MODEL_ID` |

Замените адрес и ID значениями площадки. ID берётся из API сервиса, не из
отображаемого имени чата. Доступ к трём моделям разрешается служебному VK WebUI;
credential хранится в защищённых настройках. Эти API не добавляются как чат-модели.

WebUI отправляет реранкеру строки. Здесь нужен Cohere-совместимый endpoint:
нативный `/v1/rerank` шлюза ожидает объекты документов и возвращает `400`.

После подключения загрузите публичный учебный документ и задайте вопрос
с известным ответом. Проверьте найденные фрагменты, ссылки, голосовой ввод
и права двумя аккаунтами. Рабочие документы компании для опыта не нужны.

**Учёт:** найденные фрагменты входят во входные токены чата, но индексация,
reranking и голос не наследуют личный VK автоматически. Их учёт проверяется отдельно.

### Если меняется сервис или эмбеддер

- После пересоздания сервиса обновите сохранённый токен прокси, если он есть,
  и проверьте повторное разрешение DNS: адрес Service мог измениться.
- Замена чат-модели не требует перестройки индекса. Замена эмбеддера — требует:
  у Qwen3 Embedding 4B размерность 2560, старые векторы размерности 1024 несовместимы.
- На время миграции закройте запись, сохраните документы, связи, настройки,
  ACL и резервную копию индекса. Переиндексируйте связанные файлы и базы,
  не выполняя глобальный сброс WebUI.
- До открытия записи проверьте число документов, размерность, поиск с реранкером,
  права и голос. Сохраните резервную копию до завершения проверки.

## 5. Добавить Qwen, сохранив доступы

1. Проверьте Qwen через API, затем создайте отдельный маршрут Bifrost и тариф.
2. Согласуйте `chat_models`, `providers`, профиль выдачи и действующие VK
   по [порядку обновления адаптера](../integrations/webui-access/README.md#добавление-модели-в-работающую-установку).
3. Разрешите Qwen в WebUI и проверьте ответ обычной учёткой.
4. Скройте остановленные Gemma, сохранив чаты, ключи и базы знаний.

Административное подключение остаётся отдельным. Парсер `qwen3_xml` распознаёт
вызовы инструментов, но не выдаёт права и не запускает MCP-сервер.
