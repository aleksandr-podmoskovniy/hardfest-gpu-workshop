## Память — это несколько разных ограничений

В HBM живут веса, рабочие буферы, состояния графов и активный KV. RAM может хранить неактивные cache-блоки, но перед вычислением нужные данные должны попасть туда, где работает attention. S3/PVC решают доставку и сохранность весов, а не пропускную способность GPU.

Полезная модель бюджета:

`HBM для KV ≈ допустимая HBM процесса − веса − workspace − графы − резерв`.

Каждый член проверяется по логам и наблюдениям. Ни размер скачанного файла, ни `gpu-memory-utilization: 0.90` не говорят, сколько длинных сессий поместится. Число 0.90 — настройка бюджета процесса, не 90% вычислительной загрузки.

Для **обычного full-attention** одного sequence грубая формула:

`KV bytes ≈ 2 × layers × KV_heads × head_dim × bytes_per_element × tokens`.

Двойка — K и V. GQA уменьшает число KV-heads относительно query-heads. У sliding-window/hybrid attention, MLA и recurrent-state моделей расчёт другой: нужны фактическая архитектура и реализация cache manager. Поэтому пример GPT-OSS из старой презентации нельзя механически подписать «Gemma» или «Qwen».

Для доклада подготовить таблицу **реальных** весов, graph/workspace, GPU KV capacity и свободной RAM из репетиции. Если нет измерений — показываем формулу, не выдуманные GiB.

## Время: четыре разных вопроса

1. **Queue:** сколько запрос ждал возможности работы?
2. **Prefill:** сколько потребовала обработка входа?
3. **TTFT:** когда клиент увидел первый генерируемый токен? Включает не только prefill, но и очереди/транспорт/планирование.
4. **Decode / ITL:** как быстро приходят следующие токены?

Reasoning-токен тоже выход модели, хотя UI может скрывать его. «Первый токен API» и «первое видимое слово итогового ответа» — разные метрики. SSE heartbeat/role-only chunk вообще не токен ответа.

Мы измеряем client TTFT отдельно от server queue/prefill. На агрегатах нельзя получить p95 чистого вычисления вычитанием двух p95: худшие запросы могут быть разными. [Подробная методика](MEASUREMENTS.md).

## Prefill, decode и батчинг

Prefill обрабатывает вход, decode последовательно дописывает выход. Их требования к вычислениям и обмену памятью отличаются. Chunking ограничивает объём входа за один шаг scheduler, чтобы длинный prompt не монополизировал все шаги. Размер chunk — не длина контекста и не число одновременных клиентов.

В vLLM V1 часть оптимизаций уже включается по умолчанию. Малый token budget может улучшать отзывчивость decode ценой более долгого прохождения большого входа; большой — менять баланс обратно. Выбор подтверждаем профилем нагрузки. [vLLM: optimization](https://docs.vllm.ai/en/v0.30.0/configuration/optimization/).

CUDA graphs уменьшают стоимость повторяющегося запуска вычислений, но занимают память и требуют подготовленных форм/размеров. Включение графов не гарантирует, что каждый шаг будет выполнен graph replay. Проверять effective config и startup logs; `enforce-eager: false` — разрешение, не замер ускорения.

## Три разных «кэша»

| Механизм | Что повторно используется | Чего он не доказывает |
| --- | --- | --- |
| Кэш ответа gateway | Уже готовый ответ на запрос | Скорость вычислений модели |
| Prefix cache в GPU | Вычисленные KV-блоки одинакового префикса | Использование RAM |
| KV offload / CPU-tier | Сохранённые KV-блоки вне HBM и их возврат | Неограниченное число активных длинных запросов |

В эксперименте CPU offload нужны наблюдаемые store/load и повтор после вытеснения из GPU. Иначе объяснение «данные вернулись из RAM» не обосновано. Budget `cpu_bytes_to_use` в выбранном connector задаётся суммарно на workers, включая TP, а не умножается на карты. [OffloadingConnector](https://docs.vllm.ai/en/v0.30.0/features/kv_offloading_usage/).

В этом кейсе **не** выгружаем веса через `--cpu-offload-gb`. Это другой механизм, влияющий на обмен при вычислении. Также не обещаем хранить VIP-сессии в HBM по роли пользователя: такой слой политики этот workshop не реализует.

## Speculation

Assistant предлагает несколько продолжений, основная модель проверяет их. Польза возникает, если стоимость предложения и проверки меньше экономии последовательных шагов. Поэтому нужны acceptance, длина принятого продолжения и итоговая скорость на том же workload. Большое значение acceptance может сопровождаться нулевым или отрицательным ускорением.

Для выбранной Gemma assistant используется механизм `mtp`, не перенос старого EAGLE3-рецепта GPT-OSS. Runtime должен реально поддерживать эту пару. [Документация speculation](https://docs.vllm.ai/en/v0.30.0/features/speculative_decoding/).

## TP, PP, MIG и MPS — не одно и то же

**TP** распределяет работу слоёв модели между GPU; требует обмена между ranks. **PP** распределяет участки модели по стадиям; работает с другой картиной обмена и pipeline bubbles. Поддержка архитектуры движком обязательна. NVLink — преимущество топологии, но не обещание линейного ускорения. Сначала проверяются физическое соединение, NCCL и kernels данной модели.

**MIG** даёт аппаратные GPU-инстансы допустимых геометрий. **MPS внутри MIG** позволяет нескольким клиентам разделять вычислительные ресурсы одного инстанса. MPS не заменяет границу аппаратной изоляции MIG; процент активных threads нельзя напрямую переводить в процент tok/s. [NVIDIA: deployment considerations](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/deployment-considerations.html).

В нашей реализации controller создаёт DeviceClass из GPUClass/GPUPool, а драйвер по claim динамически создаёт подходящий MIG instance. Это свойство установленного Deckhouse-драйвера, не утверждение о любом Kubernetes/NVIDIA setup. Режим MIG предварительно включён; статической преднарезки разделов на сцене нет.
