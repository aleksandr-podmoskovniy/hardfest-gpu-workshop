## Что обнаружил прогон

При переходе на Helm сервисы переведены по очереди через ноль реплик:
сначала A, после её ответа — B. Адреса и UID обоих Service, а также UID,
том и ёмкость PVC не изменились. У новых Pod нет перезапусков; счётчики
неисправимых ECC-ошибок не выросли. Это не закрывает прежнее расследование ECC.

Два прежних ConfigMap с хешем и два ResourceClaimTemplate удалены только после
проверки ссылок и готовности новых Pod. Общий prune не включался.
Исходники Kustomize убраны из действующего GitOps-каталога и сохранены в истории Git.
Мониторинг остался отдельным приложением с обычными YAML; Prometheus подтвердил
`up=1` для обеих Gemma после миграции. В WebUI проверены названия
«Gemma A — Base» и «Gemma B — Tune» и ответы обеих моделей для двух ролей.
Эти короткие запросы проверяют доступность, а не производительность.

Основное сравнение переведено на одинаковое окно 65 536 и вход 32 768 токенов.
Веса обеих реплик заняли по 57,91 GiB. В логах бюджет GPU KV-пула у A —
26,72 GiB, у B — 24,55 GiB; это ёмкость всего пула, а не память одного запроса.
Оценка движка для полных контекстов — 2,22 у A и 4,08 у B. Она не доказывает
число пользователей с приемлемой задержкой. Выгрузки весов и KV в RAM в этих
двух профилях нет.

Первые длинные запросы сопровождались JIT-компиляцией. Их сырые результаты
сохранены как проверка работоспособности; они не заменяют прогретую серию
или p95 под нагрузкой. Чанкирование у A оставлено явно, а не скрыто под
названием «без оптимизаций».

Штатный `vllm bench serve` внутри закреплённого образа проверен отдельным коротким
запросом: 64 токена входа, 16 выхода, без ошибок. В этой версии для фиксированных
длин нужен `--random-range-ratio 0`; значение 1 означает разброс ±100%.
Это проверка команды, не новый результат сравнения производительности.

В отдельном запуске B 128K с 32 GiB CPU KV движок выделил GPU KV-пул
26,49 GiB и оценил вместимость как 407 410 токенов. Это другой профиль и
другой запуск, не поправка к цифрам A/B выше. Коннектор создал mmap-регион
32 GiB в shared memory. На время этой проверки A остановлена, модели и PVC
сохранены. Первый старт превысил 300-секундное ожидание скрипта, затем Pod
стал Ready без перезапуска; таймаут не был ошибкой загрузки.

В проверенном образе автоматический выбор FlashInfer для Gemma с FP8 KV завершился ошибкой неподдерживаемой CUDA-архитектуры. Явный `TRITON_ATTN` позволил выполнить запросы на H100. Это часть измеряемой конфигурации, а не универсальная рекомендация для всех GPU.

В запуске `vllm serve --config` положительные имена параметров с `false` не выключили prefix cache и chunked prefill. Профиль A теперь использует отрицательные имена с `true`; фактические значения нужно сверять по строке инициализации Engine. Тот запуск с неожиданно включёнными параметрами остановлен и исключён из сравнения.

Генератор длинного входа исправлен под используемый образ: вызывается `python3`, а токенизатору явно задан возврат списка ID вместо словаря. Размер входа подтверждён `usage.prompt_tokens` сервера, а не оценкой по символам.

Настройки Open WebUI в базе данных имеют приоритет над переменными окружения. Поэтому выключенная переменная `ENABLE_SIGNUP` не доказывает, что регистрация закрыта: проверены и сохранённое значение, и публичный `/api/config`. Одобрение пользователя само по себе не обеспечивает работу текущего подключения `System OAuth` для локальной учётной записи.

Для двух Gemma проверены отдельные маршруты основного HA Bifrost. Управляющий
API-ключ получил возможность читать созданные объекты; повторного создания
административного ключа не потребовалось. Отдельный HardFest VK ограничен двумя
provider key, не имеет MCP grants и хранится на сервере. Исходное подключение
System OAuth сохранено. В Open WebUI предоставлены права чтения непосредственно
на базовые маршруты моделей: одного разрешения на псевдоним оказалось недостаточно.
Обе Gemma ответили через `/api/chat/completions` с ролями admin и одобренного user.
Это API-проверка доступа, не проверка интерактивного входа через браузер.

Первоначальное подключение с общим VK заменено на серверный адаптер:
оба маршрута Gemma используют личный ключ одобренного пользователя.
Проверены запросы через API WebUI, SSE и стоимость на всех трёх репликах
Bifrost. Для выдачи используется конечный резерв отключённых VK, а не
неограниченное создание. [Проверки и ограничения](../integrations/webui-access/tasks.md).
Персональный учёт Whisper и полный сценарий RAG/MCP этим не подтверждены.

Результаты единичных запросов используются для проверки работоспособности. Они не показывают p95 под нагрузкой или число обслуживаемых сессий. Исторические результаты RTX в таблицы H100 не переносятся.

## Следующие проверки

1. На подтверждённом общем окне 65 536 выполнить одинаковые холодные и повторные серии без параллельного тестирования. Не сравнивать скорость A с маленьким входом и B с большим.
2. Повторить подтверждённый перенос KV в парной серии без offload / с offload, затем отдельно проверить assistant и принятие токенов.
3. Проверить второй клиент MPS, освобождение разделов и реранкер до переключения маршрутов RAG.
4. Проверить конечный образ AI Inference и воспроизвести измеренные параметры через платформу.
5. Пройти проверки локальной регистрации, персональных ключей, баз знаний и OIDC/MCP из [описания доступа](CHAT_AND_ACCESS.md).
6. Перед бонусом TP2 повторно проверить ошибки GPU. При новой неисправимой ECC-ошибке остановить тест, не считать перезапуск исправлением оборудования.

Порядок развёртывания и откат — в [DEPLOYMENT.md](DEPLOYMENT.md), расчёты памяти — в [MEMORY_BUDGET.md](MEMORY_BUDGET.md), условия итогового прогона — в [REHEARSAL.md](REHEARSAL.md). Подготовленный манифест или успешный dry-run не заменяет ответ модели.
