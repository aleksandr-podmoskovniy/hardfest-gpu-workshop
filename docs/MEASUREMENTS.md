# Измерения, которые можно сравнивать

## Условия сравнения A/B

Для каждого прогона запишите:

- модель GPU, объём VRAM, частоты, энергопотребление и температуру;
- версии драйвера, CUDA и vLLM, digest образа;
- ревизии весов и токенизатора, формат весов;
- `max-model-len`, параметры генерации и фактическую длину входа и выхода;
- число параллельных запросов, адрес API и фактические параметры запуска.

A и B должны работать на разных физических GPU без конкурирующей нагрузки. Проверьте также CPU: его нехватка может ограничить оба запуска.

В опубликованном `values/gemma-a.yaml` выключены prefix cache и CUDA graphs,
KV хранится в BF16. Чанкирование оставлено для вместимости: у A и B одинаковые
порции prefill по 4096 токенов. Это намеренно выбранная исходная конфигурация,
не штатные настройки vLLM 0.30 и не запуск старой версии движка.

Для сравнения скорости используйте одинаковое окно 65 536, вход 32 768 и выход
2 048 токенов. Расширение B до 128K — отдельный опыт вместимости. Не объединяйте
его с A/B в одну цифру ускорения. Отказ по памяти показывает границу вместимости,
но не даёт числовой скорости отказавшей конфигурации.

Полезная серия:

| Серия | Вход | Выход | Параллельных запросов | Условие |
| --- | --- | --- | --- | --- |
| Проверка API | Короткий | до 128 | 1 | Проверить корректность ответа |
| Длинный холодный вход | Около половины согласованного окна | до 2048 | 1, 4, 8 | Разные префиксы, одинаковый набор запросов для A/B |
| Повтор длинного входа | Те же документы | до 2048 | 1, 4, 8 | Записать порядок запросов и состояние кэша в GPU и RAM |
| Длинная генерация | Умеренный вход | до 8192 | 1, 8 | Учесть фактический выход, а не только `max_tokens` |
| Рост нагрузки | Фиксированная длина | Фиксированный предел | 1, 2, 4, 8, 16, 32, 50 | Остановиться при ошибках или неприемлемом времени ответа |

Таблица задаёт серии для измерения. Основной A/B использует окно 65 536 и вход 32 768 токенов. Вход, служебные токены шаблона чата и ответ должны вместе помещаться в окно.

## Подготовка синтетической нагрузки

Основной инструмент — штатный `vllm bench serve` из того же runtime.
[Готовые команды](../labs/01-ab.md) задают seed, длины и concurrency.
Токенизатор читается из PVC внутри контейнера, локально устанавливать его не нужно.

Синтетические документы проверяют нагрузку, не качество ответов. Проверяйте
фактическое число входных и выходных токенов в отчёте. Chat API добавляет шаблон,
а completions API обрабатывает другой формат входа: не смешивайте эти серии.

У benchmark есть пробный запрос перед серией. Для строгой проверки холодного
входа зафиксируйте прогрев отдельно, используйте другие префиксы и не считайте
повторную обработку прогретого документа холодным prefill.
`--ignore-eos` нужен только синтетической серии с фиксированным выходом;
в пользовательском чате естественное завершение ответа сохраняется.

Старые `scripts/bench.py` и `make_workload.py` оставлены для воспроизведения
исторических операторских измерений. Они не управляют установленными Argo
приложениями и не являются зависимостью участника. Результаты разных клиентов
сравнивайте только после повторного замера **обоих** профилей одним клиентом.

## Очередь, prefill и первый токен

Сохраняйте /metrics до и после серии и вычисляйте среднее по приращениям
sum/count. При сбросе счётчика или нулевом количестве завершений результата нет,
а не «0 секунд». Клиентский TTFT хранится в JSON штатного benchmark отдельно.

```bash
curl --fail http://127.0.0.1:18001/metrics > results/hardfest/ab/a-metrics.txt
curl --fail http://127.0.0.1:18002/metrics > results/hardfest/ab/b-metrics.txt
```

Во время серии сервер не должен обрабатывать другие запросы. Названия и смысл метрик сверяйте с `HELP/TYPE` в `/metrics` и [справочником установленной версии vLLM](https://docs.vllm.ai/en/v0.30.0/usage/metrics/).

Среднее время очереди для завершённых за интервал запросов:

```promql
sum(increase(vllm:request_queue_time_seconds_sum{model_name="$model",instance="$instance"}[5m]))
/
sum(increase(vllm:request_queue_time_seconds_count{model_name="$model",instance="$instance"}[5m]))
```

Для prefill замените имя метрики на `vllm:request_prefill_time_seconds`. A и B имеют одинаковый model_name, поэтому фильтр instance обязателен; выберите адрес конкретного scrape target. Не объединяйте разные реплики и прогоны. При нулевом `count` результат — «нет данных», а не ноль секунд.

Серверный TTFT p95:

```promql
histogram_quantile(0.95,
  sum by (le) (rate(vllm:time_to_first_token_seconds_bucket{model_name="$model",instance="$instance"}[5m]))
)
```

Разность `TTFT_p95 − queue_p95` не даёт prefill: эти процентили могут относиться к разным запросам. Чтобы получить время до первого токена после выхода из очереди, нужны временные отметки одного и того же запроса из трассировки. При вытеснении запроса могут возникнуть дополнительные интервалы ожидания; проверьте, как их учитывает ваша версия vLLM.

## Отчёт

Повторите основную серию не менее трёх раз. Сохраните каждый замер и медиану результатов прогонов, не усредняйте p95. Для A и B одинаково учитывайте прогрев, ошибки и отменённые запросы. Записывайте, какие ответы были оборваны лимитом токенов.

Попадание в кэш RAM подтверждается загрузкой блоков после их вытеснения из GPU. Одного быстрого повтора или высокого процента попаданий в префиксный кэш для этого недостаточно. Кэш готовых ответов шлюза на пути A/B отключите либо обращайтесь к vLLM напрямую.

Заполните [REPORT.template.md](../results/REPORT.template.md), приложив исходные результаты и конфигурацию. Числа из другого стенда не входят в это сравнение.

## Qwen: ёмкость сервиса и эффект MTP

Qwen TP2 — другая модель и другой способ использования двух GPU. Его скорость
не является коэффициентом ускорения Gemma. Сначала получите один корректный
ответ, затем проверьте несколько одновременных запросов по [лабораторной](../labs/06-tp2.md).

Полная серия 1, 2, 4, 8, 16, 32, 50 concurrency выполняется отдельно от короткой
проверки запуска. При переходе между ступенями сохраняйте длины запросов,
параметры генерации, состояние кэша и число запросов в серии. Записывайте
`max-num-seqs`: 50 клиентов могут включать ожидающие запросы, а не 50 одновременно
вычисляемых последовательностей. Окно 256K не означает 50 заполненных окон.

До серии выберите допустимые TTFT/TPOT и долю ошибок для своего чата. Ёмкость —
наибольшая повторяемая ступень, удовлетворяющая этим условиям. Не задавайте
предел после просмотра красивого результата.

Для оценки MTP нужны два запуска одного Qwen с одинаковыми параметрами, кроме
`speculative-config`. Доля принятых токенов — приращение принятых, делённое на
приращение предложенных за тот же интервал. Высокая доля принятия сама по себе
не доказывает ускорения: сравните TPOT, суммарный output throughput и ошибки.
При нулевом числе предложений результата нет, а не 0%.
