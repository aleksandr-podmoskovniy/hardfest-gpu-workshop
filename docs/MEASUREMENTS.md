# Измерения, которые можно сравнивать

## Условия сравнения A/B

Для каждого прогона запишите:

- модель GPU, объём VRAM, частоты, энергопотребление и температуру;
- версии драйвера, CUDA и vLLM, digest образа;
- ревизии весов и токенизатора, формат весов;
- `max-model-len`, параметры генерации и фактическую длину входа и выхода;
- число параллельных запросов, адрес API и фактические параметры запуска.

A и B должны работать на разных физических GPU без конкурирующей нагрузки. Проверьте также CPU: его нехватка может ограничить оба запуска.

Исходный профиль `a` явно выключает prefix cache, chunked prefill и CUDA graphs; это не штатные настройки выбранной версии vLLM. Если он не запускается с выбранным большим контекстом, разделите сравнение на два опыта:

- **Скорость:** общее реально работающее окно A и B. Не менять одновременно длину входа.
- **Вместимость:** насколько увеличивается доступное окно/число сессий. OOM — результат вместимости, но не числовая скорость A.

Отдельный baseline `a-chunked` сохраняет только чанкирование входа для
вместимости: BF16 KV, prefix cache выключен, CUDA graphs выключены, оффлоада нет.
Не объединяйте его результаты с профилем `a`. Для серии с окном 65 536 токенов
у обеих реплик задайте вход 32 768 и выход 2 048; размер порции prefill у
`a-chunked` и `b-tuned` одинаковый — 4096 токенов.

Полезная серия:

| Серия | Вход | Выход | Параллельных запросов | Условие |
| --- | --- | --- | --- | --- |
| Проверка API | Короткий | до 128 | 1 | Проверить корректность ответа |
| Длинный холодный вход | Около половины согласованного окна | до 2048 | 1, 4, 8 | Разные префиксы, одинаковый набор запросов для A/B |
| Повтор длинного входа | Те же документы | до 2048 | 1, 4, 8 | Записать порядок запросов и состояние кэша в GPU и RAM |
| Длинная генерация | Умеренный вход | до 8192 | 1, 8 | Учесть фактический выход, а не только `max_tokens` |
| Рост нагрузки | Фиксированная длина | Фиксированный предел | 1, 2, 4, 8, 16, 32, 50 | Остановиться при ошибках или неприемлемом времени ответа |

Таблица задаёт серии для измерения. Основной A/B использует окно 65 536 и вход 32 768 токенов. Вход, служебные токены шаблона чата и ответ должны вместе помещаться в окно.

## Подготовка синтетической нагрузки

После готовности Pod выполните из корня проекта:

```bash
python3 scripts/hf.py dataset a-chunked --input-fraction 0.5 --output-tokens 2048 \
  --documents 32 --out .local/long.jsonl
```

Скрипт выполняет генератор внутри контейнера с токенизатором модели, а результат сохраняет на вашем компьютере.

Если работаете без `hf.py`, генератор можно вызвать напрямую в среде с тем же токенизатором и совместимой версией transformers:

```bash
python3 scripts/make_workload.py --tokenizer /models/gemma \
  --input-tokens 32768 --output-tokens 2048 --context 65536 \
  --documents 32 > .local/long.jsonl
```

Этот пример требует файлов модели в `/models/gemma` именно там, где выполняется команда. Каталог внутри Pod не доступен с ноутбука; для такого случая используйте первую команду с `hf.py`.

Генератор читает локальные файлы токенизатора, добавляет уникальный ID в начало каждого документа и считает длину с учётом шаблона чата. Перед серией сверьте её с `usage.prompt_tokens` в ответе сервера. Синтетические документы подходят для измерения нагрузки; качество ответов проверяйте на отдельном наборе содержательных вопросов.

Если запросов больше строк в файле, скрипт повторяет документы по кругу. Для холодной серии подготовьте не меньше уникальных строк, чем запросов. Перезапустите сервер или очистите кэш проверенным способом, затем прогрейте вычисления на другом префиксе. Время перезапуска не включайте во время обработки запросов.

## Что считает scripts/bench.py

Скрипт отправляет запросы в `chat/completions` и читает поток SSE. Число одновременно выполняемых HTTP-запросов ограничено `--concurrency`, температура равна 0. В отчёт попадает SHA256 файла с запросами.

TTFT отсчитывается от отправки запроса и не включает ожидание свободного потока на стороне клиента. Такой режим нагрузки называется замкнутым: следующий запрос занимает освободившееся место предыдущего. Он не моделирует независимый поток обращений пользователей.

Клиентский TTFT фиксируется по первому непустому фрагменту текста, рассуждения или вызова инструмента. Один фрагмент SSE может содержать несколько токенов, поэтому скорость генерации считается только по `usage` сервера. Если этих данных нет, результат равен `null`. Ошибки, обрывы и `finish_reason` сохраняются. P95 по нескольким запросам подходит для проверки метода, но недостаточен для оценки задержек рабочего сервиса.

В JSON отдельно сохраняются `first_content_s` — время первого фрагмента итогового ответа — и `ttft_s`, которое может начаться с рассуждения. Для проверки содержательности записываются первые 2000 символов ответа и SHA256 всего текста. Эти результаты приватные: не отправляйте рабочие документы компании в синтетический тест.

`max_tokens: 2048` задаёт верхний предел, а не гарантирует ответ ровно в 2048 токенов. Для отдельного синтетического замера с фиксированной длиной используйте `--fixed-output` в **обеих** командах A/B. Скрипт передаст vLLM `ignore_eos: true` и `min_tokens`, равный пределу. Такой ответ может продолжаться после естественного завершения; для проверки качества этот режим не подходит. В отчёте режим фиксируется в `sampling`, а длина всё равно проверяется по `usage.completion_tokens`.

Для более крупного теста можно использовать [vLLM bench serve](https://docs.vllm.ai/en/v0.30.0/cli/bench/serve/) той же версии. Если меняете инструмент, повторите им обе конфигурации: запросы к `/completions` с готовыми ID токенов и запросы к chat API проходят разную обработку.

## Очередь, prefill и первый токен

Добавьте `--metrics` к `bench.py`. Скрипт сохранит снимки метрик до и после серии и вычислит среднее время очереди и prefill по разнице `sum` и `count`. Если метрик нет или счётчики сбросились, среднее не вычисляется. Команда `python3 scripts/report.py --directory results/raw/ab` выведет эти значения рядом с клиентским TTFT p95.

Во время серии сервер не должен обрабатывать другие запросы. Названия и смысл метрик сверяйте с `HELP/TYPE` в `/metrics` и [справочником установленной версии vLLM](https://docs.vllm.ai/en/v0.30.0/usage/metrics/).

Среднее время очереди для завершённых за интервал запросов:

```promql
sum(increase(vllm:request_queue_time_seconds_sum{model_name="$model"}[5m]))
/
sum(increase(vllm:request_queue_time_seconds_count{model_name="$model"}[5m]))
```

Для prefill замените имя метрики на `vllm:request_prefill_time_seconds`. Уточните фильтр по меткам, чтобы не объединить разные реплики и прогоны. При нулевом `count` результат — «нет данных», а не ноль секунд.

Серверный TTFT p95:

```promql
histogram_quantile(0.95,
  sum by (le) (rate(vllm:time_to_first_token_seconds_bucket{model_name="$model"}[5m]))
)
```

Разность `TTFT_p95 − queue_p95` не даёт prefill: эти процентили могут относиться к разным запросам. Чтобы получить время до первого токена после выхода из очереди, нужны временные отметки одного и того же запроса из трассировки. При вытеснении запроса могут возникнуть дополнительные интервалы ожидания; проверьте, как их учитывает ваша версия vLLM.

## Отчёт

Повторите основную серию не менее трёх раз. Сохраните каждый замер и медиану результатов прогонов, не усредняйте p95. Для A и B одинаково учитывайте прогрев, ошибки и отменённые запросы. Записывайте, какие ответы были оборваны лимитом токенов.

Попадание в кэш RAM подтверждается загрузкой блоков после их вытеснения из GPU. Одного быстрого повтора или высокого процента попаданий в префиксный кэш для этого недостаточно. Кэш готовых ответов шлюза на пути A/B отключите либо обращайтесь к vLLM напрямую.

Заполните [REPORT.template.md](../results/REPORT.template.md), приложив исходные результаты и конфигурацию. Числа из другого стенда не входят в это сравнение.
