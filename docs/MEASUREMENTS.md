# Измерения

Для сравнения скорости с фиксированным выходом профили получают одинаковые
входы и создают одинаковый объём текста. Состояние кеша тоже влияет на результат:
первое обращение к документу сравнивается с первым, повтор — с повтором.
Обычные ответы с естественным завершением проверяются отдельно: их длины
могут различаться и сохраняются вместе с задержками.

Прямые запросы в vLLM и запросы через WebUI/Bifrost измеряются отдельно.
Сырые результаты сохраняются вместе с конфигурацией в [отчёте](../results/REPORT.template.md).

## Где посмотреть результат

| Площадка | Что измерено | Чего это не доказывает |
| --- | --- | --- |
| [H100](../README.md#h100-result) | Диагностика возврата KV из RAM на одном запросе | Десять сессий с полным окном и выходом 32K: отчёта нет |
| [RTX 5060 Ti](../results/rtx5060-heavy/README.md) | Qwen: десять завершённых запросов 128K, каждый с выходом 32K; отдельно короткие Gemma | Десять активных полных окон: не подтверждены. Тяжёлые серии Gemma пока не завершены |
| [PRO 6000](../results/pro6000-heavy/README.md) | Base, Cache, Tune и Qwen TP2: по десять завершённых полных окон с фактическим выходом 32K; клиентские результаты, конфигурации и метрики | Разные окна, модели и пересекающиеся нагрузки не дают сопоставимого A/B. Десять поданных запросов не означают десять активных полных окон |

Карточки и таблицы пересчитываются из опубликованных JSON. H100/RTX и PRO
проверяются отдельно; для этой поставки обязательны обе команды:

```bash
python3 scripts/article_results.py --scope h100-rtx --check
python3 scripts/article_results.py --scope pro-capacity-only --check
```

Проверка PRO требует все четыре полные серии с фиксированным выходом
и завершается ошибкой при неполных данных. Сопоставимый тест обычных ответов в эту поставку
не входит; старые измерения не подставляются вместо него. Для полного
сравнения используется отдельная строгая проверка `--scope pro --check`.
Без `--check` команда обновляет только иллюстрации и блоки чисел в статьях.
Она не запускает нагрузку. Подробные результаты и графики хранятся рядом
с исходными JSON; статьи показывают основные показатели и условия измерения.

## Что проверяет серия

| Серия | Что можно заключить |
| --- | --- |
| A/B с одинаковой нагрузкой | Разницу задержки, скорости и ошибок целых профилей |
| Длинный вход и фиксированный выход | Возможность закончить эту нагрузку, включая очередь |
| Повтор общего префикса | Эффект повторного использования кеша при этих условиях |
| [Повтор после вытеснения](#offload-replay) | Возврат KV из RAM при подтверждённом чтении |
| [Длинный и короткий запрос вместе](#mixed-prefill) | Поведение короткого запроса при конкуренции с длинным |

Для воспроизводимого сравнения сохраните:

- GPU UUID, версии драйвера и vLLM, ревизии модели и токенизатора;
- параметры vLLM, размер GPU KV-пула, лимиты RAM и `/dev/shm`;
- адрес API, клиентскую ноду, длины входов и выходов, число запросов
  и число одновременно отправляющих их клиентов.

До запуска задайте допустимые задержки и долю ошибок.
Исключите постороннюю нагрузку и кеш готовых ответов шлюза.

`--ready-check-timeout-sec 0` убирает пробный запрос, `--num-warmups 0` — прогрев.
Они не очищают серверный кеш. Новый префикс и повтор того же входа — разные серии.
`--ignore-eos` принудительно продолжает генерацию до заданной длины;
обычный пользовательский ответ может закончиться раньше.

<a id="h100-reference"></a>
## H100: имеющийся ориентир, не новый тяжёлый прогон

Сохранён один запрос к Gemma 31B в каждой из двух конфигураций.
Вход в обоих случаях — **32 768**, фактический выход — **2048** токенов.
Обе использовали chunked prefill, окно 64K и одну H100.

| Измерение | BF16 KV, eager, без prefix cache | FP8 KV, prefix cache, CUDA graphs |
| --- | ---: | ---: |
| До первого токена | 16,10 с | 19,28 с |
| Полный ответ | 151,07 с | 96,76 с |
| Выход / время всей серии | 13,56 токена/с | 21,15 токена/с |
| Завершено | 1/1 | 1/1 |

Полный ответ во втором опыте закончился раньше, **первый токен — позже**.
Offload и speculative decoding в этих двух конфигурациях не включались.
Это не текущие Base/Tune и не оценка для десяти клиентов.
[Числа, настройки и хеши исходных свидетельств](../results/h100-reference.json).

Для десяти полных историй 256K у Gemma 31B получается **103,91 GiB только FP8 KV**,
для 128K — **53,91 GiB**. Это [расчёт архитектуры](MEMORY_BUDGET.md),
не измеренная занятость и не обещание разместить истории одновременно.
Время серии по одному запросу не масштабируется линейно: меняются очередь,
объём prefill, стоимость attention и вытеснения. Нового прогона H100 здесь нет.

<a id="heavy-load"></a>
## Основной замер: десять сессий с длинным входом и выходом

**Цель — заполненное рабочее окно и 32 768 фактически сгенерированных токенов
на каждую из десяти сессий.** Это обязательный минимум длинного выхода,
не утверждение о максимальной длине ответа, поддерживаемой моделью.
Короткие запросы ниже нужны для диагностики и не заменяют этот замер.

### Окно и параллельность — два ограничения

Для каждого профиля фиксируются три величины: предел архитектуры модели,
настроенное окно и наибольшее окно, на котором завершён весь прогон.
Запуск с `max-model-len=131072` ещё не доказывает предел карты.
При окне **C** вход занимает **C − 32768** токенов, выход — **32768**.
В chat API вход включает шаблон, системное сообщение и историю.

| Площадка / модель | Начальное полное окно для проверки | Вход / выход на сессию | Клиентов |
| --- | ---: | ---: | ---: |
| H100, Gemma Tune | 128K; затем 256K, если позволяет память | 98304 / 32768; затем 229376 / 32768 | 10 |
| H100, Qwen TP2 | 256K | 229376 / 32768 | 10 |
| RTX 5060 Ti, Gemma E2B | 128K, предел закреплённой модели | 98304 / 32768 | 10 |
| RTX 5060 Ti, Qwen TP2 | 128K в описанном рецепте; 256K после проверки нового рецепта AI Inference | 98304 / 32768; затем 229376 / 32768 | 10 |
| PRO 6000, Gemma Tune / Qwen TP2 | 256K | 229376 / 32768 | 10 |
| Base на каждой площадке | Наибольшее работающее окно без оптимизаций | C − 32768 / 32768 | 10 |

Это **план проверок, не новые результаты**. Если запрос не помещается, сохраняется
причина: ограничение API/рецепта, недостаточный KV-пул, OOM или ошибка транспорта.
Меньшее окно проверяется отдельно, с новым именем результата. Его нельзя выдавать
за успешно пройденное большее окно.

Состояние новых серий PRO фиксируется в [сводке с исходными файлами](../results/pro6000-heavy/README.md).
Для H100 здесь остаются отдельно подписанный исторический опыт и расчёт памяти.
Наличие параметров в таблице не означает, что соответствующий прогон выполнен.

**Исходные Base/Cache H100 ограничены 16K, RTX — 4K.** Они не способны выдать
32K по самой конфигурации. Для тяжёлого опыта создаются отдельные профили
`Base-long` и `Cache-long`: окно расширяется после расчёта памяти, отличия
от исходных values сохраняются. Base не получает prefix cache, FP8 KV,
offload или speculative decoding ради того, чтобы «пройти» тест.

Десять клиентов подают запросы одновременно. На сервере проверяются лимит
`max-num-seqs`, размер KV-пула и **Running/Waiting во времени**.
Если лимит меньше десяти, это прямо записывается как ограничение профиля.
RAM-offload не означает автоматического расширения активного GPU KV-пула.
Очередь не выполняет требование десяти активных сессий; единичный пик Running=10
также не доказывает, что десять длинных ответов генерировались вместе.

### Два сравнения, которые нельзя смешивать

1. **Вместимость:** у каждого профиля своё наибольшее проверенное окно,
   десять независимых входов и выход 32K. Показываются активность и очередь.
2. **Скорость A/B:** те же десять входов, токенизатор и параметры генерации,
   одинаковые длины входа/выхода и состояние кеша. Общее окно не превышает
   меньший из проверенных пределов A/B. Только здесь считается ускорение.

У обычного чата выход не принуждается к 32K. Для него сравниваются одинаковые
задания и лимиты генерации, но отдельно показываются фактические длины ответов.
Такой тест не смешивается с фиксированным выходом или проверкой вместимости.

В основной серии нет общего длинного префикса: нельзя заменить десять разных
разговоров одним общим документом. Повтор тех же входов — отдельный warm-опыт.
Прямой vLLM и путь WebUI/Bifrost публикуются отдельно, без смешивания задержек.

**Способ запуска и путь запроса — две разные характеристики.** Gemma Base/Cache/Tune
создаются вручную для сравнения оптимизаций. Qwen в финальной части создаётся
через `InferenceService`: сохраняются заказ, выбранный план и цепочка владельцев
до Pod. Прямой запрос к такому Pod измеряет платформенный runtime без шлюза.
Отдельный ручной Deployment с теми же аргументами не проверяет планировщик и
жизненный цикл AI Inference; его результат подписывается как вспомогательный.

Перед платформенной серией проверяется не только имя модели: актуальный заказ
должен владеть workload, а его Service — направлять запросы в проверенный Pod.
В клиенте используется именно адрес этого Service. Снимок повторяется после
нагрузки; замена Pod или маршрута не должна остаться незамеченной.
[Клиент новых прогонов](../examples/capacity-load-client/) запрещает HTTP-перенаправления.
В отчёте сохраняются хеши **фактически запущенных** скриптов, а не файлов,
которые оказались в рабочем каталоге после теста.

Клиент проверки вместимости повторяет синтетический фрагмент после уникального
начала каждой сессии. Это заполняет память, но предсказуемое продолжение может
давать завышенную долю принятых draft-токенов. Такие токены/с не объявляются
производительностью обычного чата. Для её оценки нужны отдельные содержательные
запросы и проверка ответов без принудительного продолжения после EOS.

### Запуск и критерии

Перед нагрузкой сохраняются runtime и состояние GPU. Изолируется тестовый
сервис от пользовательских запросов; клиент работает на отдельной CPU-ноде.
Все десять результатов сохраняются, включая ошибки и незавершённые запросы.

Для `vllm bench serve` явно задаются:

```text
--num-prompts 10 --max-concurrency 10 --request-rate inf
--random-prefix-len 0 --random-range-ratio 0
--random-input-len C_MINUS_32768 --random-output-len 32768
--ignore-eos --save-result --save-detailed
--ready-check-timeout-sec 0 --num-warmups 0
```

`C_MINUS_32768` заменяется числом из таблицы или фактического окна.
Смысл параметров описан в [vLLM 0.31](https://docs.vllm.ai/en/v0.31.0/cli/bench/serve/).
Клиентская concurrency не равна серверной активности:
[метрики движка](https://docs.vllm.ai/en/v0.31.0/usage/metrics/).
Отключённый прогрев не очищает уже существующий кеш.

Серия принимается по **каждому из десяти** ответов: точный вход и выход,
успешный конец потока, без ошибок и перезапусков. Для capacity-клиента это
`finish_reason=length` и `[DONE]`; одного `HTTP 200` недостаточно.
Суммарный выход — **327680**, но правильная сумма без поштучной проверки
не доказывает правильные длины всех ответов.

В итоговой карточке нужны:

- фактические вход/выход, завершённые/ошибочные запросы и длительность серии;
- TTFT и TPOT по запросам, медиана и максимум; суммарный output tokens/s;
- Running/Waiting, сколько времени все десять генерировали вместе, preemptions;
- GPU utilization, VRAM, занятый KV, RAM и возврат KV из RAM на том же интервале.

До начала согласуются время и стоимость. Общий верхний дедлайн — **12 часов
на волну**, без автоматического повтора; это предохранитель, не допустимая
задержка для пользователя. Пример Job с `vllm bench` получает
`activeDeadlineSeconds: 43200`. У capacity-клиента отдельный дедлайн запросов —
43200 секунд; в выполненном RTX-прогоне Job ограничен 47000 секундами, включая
до часа на чтение готового отчёта. Это время не добавляется к длительности серии.
Новые ECC/Xid, OOM/restart, исчерпание RAM/диска или бюджета останавливают серию.
Частичный отчёт сохраняется. Обрыв SSE/heartbeat не выдаётся за предел памяти.

`ignore_eos` принудительно продолжает текст, поэтому успешная серия подтверждает
нагрузку, а не качество ответа или готовность к production. Отдельно нужны
реальные длинные задания через пользовательский путь, естественное завершение
ответов и заранее выбранные допустимые задержки. Максимальная занятость GPU
при многочасовой очереди не является хорошим результатом для чата.

## Короткие диагностические серии

Короткий A/B сравнивает настройки. Полное окно проверяет вместимость;
разные входы A/B нельзя использовать для расчёта ускорения.

| Профиль | H100 | RTX 5060 |
| --- | --- | --- |
| Base | 16K, BF16 KV, без prefix/offload/graphs/chunking | Тот же контроль, окно 4K |
| Cache | 16K, FP8 KV, Triton, prefix cache, CPU KV 32 GiB | 4K, CPU KV 4 GiB |
| Tune | 128K, кеши Cache, assistant, graphs, prefill 2048 | 128K, prefill 512 |
| Короткий A/B | 8192/2048, 8 запросов, concurrency 4 | 2048/128, 8 запросов, concurrency 2 |
| Полное окно Tune 128K | 98304/32768, 10 запросов, concurrency 10 | Те же длины и 10 клиентов |

Для PRO 6000 [сводка](../results/pro6000-heavy/README.md) показывает вместимость
с фактическим выходом 32K. Сопоставимая серия обычных ответов Base/Cache/Tune
в неё не входит. Короткий запрос, длинный, его повтор и смешанная нагрузка —
отдельная методика; её описание ниже не является результатом прогона.

На H100 с RAM 128 GiB A/B запускаются последовательно. Для одновременного
запуска нужны разные физические GPU и запас RAM. Короткая нагрузка одинакова,
но профили меняют несколько параметров, включая окно: результат относится
к профилю целиком, не к отдельной оптимизации.

Проверьте фактические input/output tokens, `completed`, `failed`, обрывы,
отмены и новые ECC/Xid. `max_tokens` — предел, а не фактическая длина.
Сохраните метрики до/после серии, TTFT, очередь, TPOT/ITL и throughput.
Процентили разных величин не вычитаются; p95 разных прогонов не усредняются.

<a id="mixed-prefill"></a>
## Длинный и короткий запрос вместе

Клиент vLLM 0.31 `timed_trace` отправляет длинный вход в момент 0,
короткий через 50 мс. Сравниваются Cache/Tune. Пример H100 выполняется в Bash.
Для RTX: `NS=hardfest-rtx`, `SERVICE=rtx-gemma-cache`, `MODEL=rtx-gemma-cache`,
`LONG_INPUT=3072`, `OUTPUT=128`.

Оба следующих опыта выполняются из **работающего CPU Pod на отдельной ноде**,
не из контейнера модели. В нём нужны vLLM 0.31 и токенизатор проверяемой модели
с закреплённой ревизией. Подготовка образа и токенизатора показана в
[CPU-клиенте](#gemma-client-h100); завершённый Job для `exec` не подходит.
Перед запуском проверьте ноду клиента через `kubectl get pod -o wide`.
`BENCH_POD`, `BENCH_CONTAINER` и путь токенизатора ниже заменяются на фактические.

```bash
export NS=hardfest-demo SERVICE=hf-gemma-cache MODEL=gemma-4-31b
export BENCH_POD=REPLACE_RUNNING_CPU_CLIENT_POD BENCH_CONTAINER=benchmark
export TOKENIZER_PATH=/work/tokenizer
export LONG_INPUT=8192 OUTPUT=512 PHASE=cache
export TRACE_ID=$(date +%s)
export TRACE="results/mixed-$TRACE_ID.jsonl"
mkdir -p results
printf '{"timestamp":0,"input_length":%s,"output_length":%s,"hash_ids":[%s]}\n' \
  "$LONG_INPUT" "$OUTPUT" "$TRACE_ID" > "$TRACE"
printf '{"timestamp":0.05,"input_length":128,"output_length":%s,"hash_ids":[%s]}\n' \
  "$OUTPUT" "$((TRACE_ID + 1))" >> "$TRACE"
```

Создайте trace один раз на пару. Выполните блок на Cache, переключите профиль
и повторите с `PHASE=tune SERVICE=hf-gemma-b`;
на RTX — `PHASE=tune SERVICE=rtx-gemma-tune MODEL=rtx-gemma-tune`.

```bash
export RESULT="mixed-$TRACE_ID-$PHASE.json"
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec -i "pod/$BENCH_POD" -c "$BENCH_CONTAINER" -- \
  env PYTHONHASHSEED=0 vllm bench serve \
    --backend vllm --base-url "http://$SERVICE.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model "$MODEL" --tokenizer "$TOKENIZER_PATH" \
    --dataset-name timed_trace --dataset-path /dev/stdin \
    --timed-trace-chunk-hash-size "$LONG_INPUT" --self-timed \
    --num-prompts 2 --max-concurrency 2 --temperature 0 --ignore-eos \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --save-detailed --result-dir /tmp --result-filename "$RESULT" \
  < "$TRACE" 2>&1 | tee "results/mixed-$TRACE_ID-$PHASE.log"
kubectl --context "$GPU_CONTEXT" -n "$NS" exec "pod/$BENCH_POD" -c "$BENCH_CONTAINER" -- \
  cat "/tmp/$RESULT" > "results/$RESULT"
```

Нужны два успешных ответа с заданными длинами и перекрытием:

```text
end[i] = start_times[i] + latencies[i]
overlap = min(end[0], end[1]) − max(start_times[0], start_times[1]) > 0
start_times[1] < start_times[0] + ttfts[0]
```

Последнее условие означает, что короткий стартовал до первого токена длинного.
Иначе уменьшите задержку и используйте новый trace. Клиентские отметки не задают
границы GPU-prefill. Сравните TTFT короткого, ITL и время обоих ответов.
[Формат trace](https://github.com/vllm-project/vllm/blob/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/benchmarks/datasets/datasets.py),
[поля JSON](https://github.com/vllm-project/vllm/blob/db9527a46873454610df6dbedf79a36d6bf1a7f6/vllm/benchmarks/serve.py).

<a id="offload-replay"></a>
## Повтор после вытеснения из GPU

Опыт на ручной B Cache подтверждает перенос KV, не ускорение. Исключите
посторонние запросы. Через Git/Argo временно добавьте `kv-cache-memory-bytes`
в `vllm:`; поле заменяет расчёт пула по доле GPU:

| Площадка | GPU KV-пул, байт | Вход | Штатный RAM KV |
| --- | ---: | ---: | ---: |
| H100 | `2147483648` | 8192 | 32 GiB |
| RTX 5060 | `268435456` | 3072 | 4 GiB |

Окно остаётся 16K/4K, KV — FP8. После Ready проверьте в логах, что один запрос
помещается. Для RTX задайте `NS=hardfest-rtx`, `SERVICE=rtx-gemma-cache`,
`MODEL=rtx-gemma-cache`, `INPUT=3072` и путь к его токенизатору в CPU Pod.
Используется отдельный CPU-клиент, как в [предыдущем опыте](#mixed-prefill).
Локально нужен `jq` для проверки сохранённого результата.

```bash
export NS=hardfest-demo SERVICE=hf-gemma-cache MODEL=gemma-4-31b
export BENCH_POD=REPLACE_RUNNING_CPU_CLIENT_POD BENCH_CONTAINER=benchmark
export TOKENIZER=/work/tokenizer INPUT=8192
mkdir -p results/offload
set -o pipefail
offload_request() {
  kubectl --context "$GPU_CONTEXT" -n "$NS" exec "pod/$BENCH_POD" -c "$BENCH_CONTAINER" -- \
    vllm bench serve --backend vllm \
      --base-url "http://$SERVICE.$NS.svc.cluster.local:8000" \
      --endpoint /v1/completions --model "$MODEL" --tokenizer "$TOKENIZER" \
      --dataset-name random --seed "$1" \
      --random-input-len "$INPUT" --random-output-len 1 --random-range-ratio 0 \
      --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
      --ready-check-timeout-sec 0 --num-warmups 0 \
      --save-result --save-detailed --result-dir /tmp --result-filename "offload-$2.json" \
    2>&1 | tee "results/offload/$2.txt" || return 1
  kubectl --context "$GPU_CONTEXT" -n "$NS" exec "pod/$BENCH_POD" -c "$BENCH_CONTAINER" -- \
    cat "/tmp/offload-$2.json" > "results/offload/$2.json" || return 1
  jq -e --argjson input "$INPUT" \
    '.completed == 1 and .failed == 0 and .total_input_tokens == $input and .total_output_tokens == 1' \
    "results/offload/$2.json" > /dev/null
}
offload_request 9001 original || exit 1
for SEED in $(seq 9002 9033); do
  offload_request "$SEED" "evict-$SEED" || exit 1
done
```

После исходного запроса идут 32 независимых префикса. Если результат неполный,
проверка останавливает опыт даже при успешном exit code клиента.
В отдельном терминале откройте метрики той же B:

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" port-forward "svc/$SERVICE" 18002:8000
```

Затем в основном терминале:

```bash
curl --fail --max-time 10 http://127.0.0.1:18002/metrics > results/offload/before.prom || exit 1
offload_request 9001 replay || exit 1
curl --fail --max-time 10 http://127.0.0.1:18002/metrics > results/offload/after.prom || exit 1
```

У OffloadingConnector нужны приращения `CPU_to_GPU` и external-prefix hits
именно при replay. У Simple CPU — `vllm:simple_kv_offload_load_blocks_total`.
Без чтения возврат не показан: префикс мог остаться на GPU или исчезнуть из RAM.
Удалите временный лимит через Git/Argo и проверьте штатный пул после Ready.
Дисковый NodeCache весов сохраняется.

<a id="qwen-load"></a>
## Qwen: окно и параллельные запросы

TP2 распределяет одну модель между двумя GPU. Скорость Qwen не является
ускорением Gemma. Для PRO 6000 план полного окна — десять запросов с окном 262144;
фактическое завершение, наблюдавшийся пик Running и очередь проверяются по
[серии Qwen](../results/pro6000-heavy/README.md), а не по замерам другой конфигурации.

| Площадка | Полное окно, вход/выход | Отдельная проверка параллельности |
| --- | --- | --- |
| H100 | 229376/32768, 10 запросов | Running/Waiting и перекрытие генерации всех десяти |
| RTX 5060 | 98304/32768, 10 запросов | Running/Waiting; исходный лимит 8 не позволяет 10 активных |

В копии [CPU Job H100](../examples/qwen-benchmark-job.yaml) для полного окна
задаются `INPUT_TOKENS=229376 OUTPUT_TOKENS=32768 NUM_PROMPTS=10 CONCURRENCY=10`,
`activeDeadlineSeconds: 43200` и отдельное имя Job. По умолчанию шаблон
остаётся короткой диагностикой. Для RTX меняются модель/токенизатор и вход 98304.
Каждый ответ проверяется отдельно, общий выход — 327680 токенов.

Для поиска рабочей нагрузки число одновременно отправляющих клиентов
увеличивается ступенями: 1, 2, 4, 8, 10, 16, 32, 50. Длины запросов, параметры
генерации и условия кеширования остаются прежними. Рабочим считается уровень,
который повторно укладывается в выбранные задержки и долю ошибок.

<a id="gemma-client-h100"></a>
## CPU-клиент: ручная и платформенная Gemma

[Job](../examples/gemma-benchmark-job.yaml) сравнивает прямые API с полным Tune 128K:
первый проход и повтор для каждой цели. Клиент GPU не запрашивает.
Из частного `k8s-config` подготовьте копию:

```bash
export BENCH_DIR="$(mktemp -d)"
cp ../hardfest-gpu-workshop/examples/gemma-benchmark-job.yaml "$BENCH_DIR/job.yaml"
```

Задайте CPU-ноду с доступом к Service, уникальное имя Job, платформенный Model ID
из `/v1/models` и ссылки на Secrets. `HF_TOKEN` нужен токенизатору, ключ платформы
обязателен даже при optional-ссылке. Ручному API без авторизации ключ не требуется.
Секретные значения в YAML не записываются.

H100: `hardfest-demo`, вход 8192, выход 2048, 8 запросов, concurrency 4.
`BENCH_TARGET=both` используется, только когда обе цели готовы и помещаются;
на 128 GiB выполните отдельные Job `manual` и `platform` последовательно.

<a id="gemma-client-rtx"></a>
### RTX 5060

В той же копии сохраните `NUM_PROMPTS=8`, выберите готовые цели и замените:

| Поле | Значение |
| --- | --- |
| `metadata.namespace` | `hardfest-rtx` |
| `MANUAL_BASE_URL` / `MANUAL_MODEL` | `http://rtx-gemma-tune.hardfest-rtx.svc.cluster.local:8000` / `rtx-gemma-tune` |
| `PLATFORM_BASE_URL` / `PLATFORM_MODEL` | `http://rtx-gemma-platform.hardfest-rtx.svc.cluster.local:80` / `rtx-gemma-e2b` |
| `TOKENIZER_ID` | `google/gemma-4-E2B-it` |
| `TOKENIZER_REVISION` | `3e22461f65e89153144f8adb70e3b8c2cc9845a7` |
| `INPUT_TOKENS` / `OUTPUT_TOKENS` / `CONCURRENCY` | `2048` / `128` / `2` |

### Запуск и проверка

Проверьте копию, задайте `spec.suspend: false`, namespace и имя Job:

```bash
export NS=hardfest-demo BENCH_JOB=gemma-benchmark
kubectl --context "$GPU_CONTEXT" create --dry-run=server -f "$BENCH_DIR/job.yaml" || exit 1
kubectl --context "$GPU_CONTEXT" create -f "$BENCH_DIR/job.yaml" || exit 1
kubectl --context "$GPU_CONTEXT" -n "$NS" logs -f "job/$BENCH_JOB" \
  --pod-running-timeout=5m | tee "$BENCH_DIR/benchmark.log"
kubectl --context "$GPU_CONTEXT" -n "$NS" get job "$BENCH_JOB"
```

Сохраните блоки `RESULT_JSON_BEGIN` / `RESULT_JSON_END` до удаления Job по TTL:
по два на цель. В каждом `completed=8`, `failed=0`; H100 — 65536/16384 токенов,
RTX — 16384/1024. Повторите трижды с новыми именами, сохраняя условия.
Первый проход не гарантирует холодный кеш, а короткая серия не проверяет длинный вход.
