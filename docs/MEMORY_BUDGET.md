# Память для Gemma A/B

## VM с 128 GiB

После переноса H100 в VM у гостя 128 GiB назначенной RAM и 16 vCPU. Это другой бюджет, чем у физической ноды ниже. На проверке перед прогоном Linux видел около 125,8 GiB, `MemAvailable` — около 118 GiB; эти значения нужно перечитывать перед каждой загрузкой.

Для VM используется [явная настройка ресурсов](SETUP.md#2-параметры-своего-стенда):

| Режим | requests RAM | limits RAM | CPU requests | Порядок |
| --- | ---: | ---: | ---: | --- |
| A + B tuned/spec | 48 GiB | 96 GiB | 8 | Загрузить A, проверить ответ, затем B |
| Только B cache, KV в RAM 32 GiB | 56 GiB | 80 GiB | 4 | Сначала остановить A |

Два одинаковых read-only монтирования одного локального PVC могут переиспользовать файловые страницы, но лимит 48 GiB меньше полного размера файлов Gemma. Загрузка `lazy` должна освобождать файловый кэш; подтверждаем это по cgroup, а не предположением о наличии 58 GiB свободной RAM на каждую копию. Сумма лимитов A + B cache была бы 128 GiB, без запаса системе, поэтому одновременно их здесь не запускаем.

32 GiB CPU-кэша должны быть больше фактического GPU KV-пула для полезного опыта с вытеснением. Если GPU-пул больше, сначала пересчитываем эксперимент: уменьшаем GPU KV-бюджет одинаково в cache-off/cache-on либо используем более вместительный узел. Не называем простое дублирование GPU-кэша выигрышем от RAM.

## Вариант с 256 GiB

Здесь рассчитан запуск двух копий `google/gemma-4-31B-it`: A без CPU KV-кэша и B с 64 GiB KV в RAM. Это не бюджет Qwen TP2 и не обещание вместимости всех запросов в VRAM.

## Что занимает RAM

Веса обеих Gemma остаются на GPU. Оперативная память нужна процессам vLLM, файловому кэшу при чтении весов, межпроцессному обмену и CPU KV-кэшу B. Загрузка и компиляция создают временные пики, которые нужно отделять от установившегося расхода.

В профилях Gemma закреплён `safetensors-load-strategy: lazy`. Загрузчик отображает safetensors в память и читает тензоры; это не постоянная копия всех весов в анонимной RAM. Файловые страницы могут переиспользоваться и освобождаться. Режим `eager` загружает файл целиком и требует отдельного расчёта пиков. [Загрузчик vLLM 0.30.0](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/model_executor/model_loader/weight_utils.py#L800).

Для расчёта взята ревизия `842da3794eaa0b77d5f08bae87a17459d91ff475`. Проверенные файлы safetensors занимают 62 546 338 248 байт, или 58,25 GiB, включая мультимодальные веса. Запуск текстовый; полный размер файлов используется как консервативный бюджет чтения, не как точное потребление VRAM.

Для исходной физической ноды были измерены 251,51 GiB RAM, allocatable 244,76 GiB и `MemAvailable` 239,81 GiB. Расчёт ниже относится только к ней, не к VM с проброшенными H100. Swap отсутствовал.

| Статья для двух реплик | GiB | Как учитывается |
| --- | ---: | --- |
| CPU KV у B | 64 | Заданный бюджет коннектора, одна копия |
| Два комплекта файлов Gemma | 116,50 | Консервативный бюджет файловых страниц; не полагаемся на их совместное использование |
| Прочая shared memory | 16 | До 8 GiB на Pod, сверх CPU KV |
| Процессы, компиляция и запас | 43,31 | Остаток: `239,81 − 64 − 116,50 − 16` |

43,31 GiB — оставшийся бюджет, не измеренный расход процессов и не доказанный верхний предел пика. Последовательный запуск A, затем B уменьшает наложение загрузки и компиляции. Ограничения контейнеров проверяются отдельно: свободная память хоста не отменяет OOM внутри cgroup.

## Запросы, лимиты и shared memory

| Профиль | `requests.memory` | `limits.memory` | `/dev/shm` |
| --- | ---: | ---: | ---: |
| A, B tuned, B spec | 64 GiB | 80 GiB | 8 GiB |
| B cache | 128 GiB | 144 GiB | 72 GiB |

Для A + B cache сумма requests составляет 192 GiB, сумма limits — 224 GiB. Это выбранные ограничения, а не прогноз фактического RSS. При исходных requests остальных Pod 2,51 GiB остаётся `244,76 − 192 − 2,51 = 50,25 GiB` для планирования. Даже сумма limits ниже физической RAM; оставшийся запас нельзя сразу занять другими сервисами: учитывайте систему и фактический расход соседних Pod.

Профиль B получает базовые 64/80 GiB плюс бюджет CPU KV, округлённый вверх до GiB. Размер `/dev/shm` вычисляется как `CPU KV + 8 GiB`. При изменении `cpu_bytes_to_use` генератор пересчитывает все три величины. После изменения остановите B, заново выполните `apply`, затем `start`; старый манифест скрипт запускать не разрешит. Больший offload требует нового расчёта памяти всей ноды.

В vLLM 0.30.0 CPU offload использует mmap-файл в `/dev/shm`. Поэтому лимит shared memory 8 GiB не подходит для кэша 64 GiB. Значение 72 GiB — вместимость tmpfs, не немедленное выделение всей памяти. Использованные страницы входят в память контейнера: складывать 72 GiB shared memory и 64 GiB KV как два отдельных расхода нельзя. [Реализация SharedOffloadRegion](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/kv_offload/cpu/shared_offload_region.py#L64).

При `lazy` файловый кэш может сокращаться под давлением памяти. Если контейнер всё равно достигает 80/144 GiB, сохраните разбивку расхода, проверьте временные копии и только затем пересчитывайте лимиты. Увеличивать оба потолка сверх вместимости ноды нельзя. Одновременный старт крупных моделей без этого расчёта не предусмотрен.

## KV для нашей Gemma

Параметры берём из [закреплённого config.json](https://huggingface.co/google/gemma-4-31B-it/blob/842da3794eaa0b77d5f08bae87a17459d91ff475/config.json):

- 10 слоёв полного внимания: 4 KV-головы, размерность 512;
- 50 слоёв локального внимания: 16 KV-голов, размерность 256, окно 1024;
- общий контекст до 262 144 токенов; KV между слоями не разделяется.

Для одной независимой истории длиной `S`, при `b` байтах на элемент:

```text
KV(S) = 2 × b × (10 × 4 × 512 × S
                 + 50 × 16 × 256 × min(S, 1024))
```

Двойка означает K и V. Флаг `attention_k_eq_v` в checkpoint не позволяет убрать её: выбранная реализация vLLM сохраняет оба тензора. [Обработка Gemma в vLLM](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/model_executor/models/gemma4.py#L513).

| Вход + выход | BF16, 2 байта | FP8, 1 байт |
| --- | ---: | ---: |
| 131 072 + 2 048 | 10,9375 GiB | 5,46875 GiB |
| Всего 262 144 | 20,78125 GiB | 10,390625 GiB |

Проверить числа без кластера:

```bash
python3 scripts/kv_math.py --model gemma-4-31b --tokens 133120
python3 scripts/kv_math.py --model gemma-4-31b --tokens 133120 --element-bytes 1
python3 scripts/kv_math.py --model gemma-4-31b --tokens 262144 --element-bytes 1
```

Это полезные данные активного KV при сохранении только локального окна. Формула не учитывает выравнивание блоков, устройство гибридного пула, временное выделение во время prefill и историю блоков, сохраняемых offload-коннектором. Деление 64 GiB на число из таблицы не даёт гарантированного количества сохранённых или одновременно работающих сессий.

Для восьми независимых историй по 133 120 токенов даже FP8 даёт 43,75 GiB активного KV. Его нужно сопоставить с реальным GPU KV-пулом после весов, буферов и графов. RAM-кэш не превращает эту память в дополнительную HBM для вычислений. [Как работает OffloadingConnector](https://docs.vllm.ai/en/v0.30.0/features/kv_offloading_usage/).
