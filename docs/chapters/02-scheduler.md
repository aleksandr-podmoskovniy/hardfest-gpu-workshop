# Время ответа: очередь, prefill, decode и перенос KV

[Память](01-memory.md) · [Speculation](03-speculation.md)

## Пользователь видит один спиннер, система выполняет несколько фаз

```text
Отправка → сеть → очередь → prefill → первый токен → reasoning/ответ → конец
                              ↕ могут вклиниваться шаги других сессий
```

TTFT клиента — время от отправки до первого содержательного фрагмента stream. В UI reasoning может быть скрыт: первое слово итогового ответа появится позже. Не смешиваем эти две истории под одной подписью графика.

Рассмотрим пример: запрос 70 секунд ждал и 5 секунд обрабатывался. Пользователь ждал примерно 75 секунд плюс накладные расходы; называть это «модель считает 75 секунд» неверно. Но и показывать только 5 секунд как latency пользователя — тоже неверно. Это **пример объяснения**, не результат стенда.

Чтобы говорить «работающие сессии отвечают так-то», сначала определяем событие начала работы и связываем timestamps конкретного request. `p95(TTFT) − p95(queue)` не даёт p95 вычислений. Два хвоста распределения могут принадлежать разным запросам.

## Chunking: делим время, а не документ навсегда

Prefill обрабатывает входные tokens. Decode дописывает последовательность; новые позиции зависят от уже сгенерированных. В одном scheduler step движок может совместить работу нескольких запросов.

Учебная картинка из презентации, без speculation и сложностей scheduler:

| Общий token budget шага | Три decode-сессии | Остаётся для нового prefill |
| --- | --- | --- |
| 8192 | 3 × 1 токен | 8189 |
| 2048 | 3 × 1 токен | 2045 |

Меньше prefill за один шаг — больше шагов до окончания нового документа. Зато шаг может меньше мешать уже генерируемым ответам. Поэтому не обещаем одновременно минимальные TTFT, ITL и максимальный throughput при любом batch size.

В учебном B-профиле начальная точка — 4096, а 8192 → 2048 остаётся отдельным объясняющим примером. Чтобы сравнить именно budget шага, сохранить всё остальное и выполнить самостоятельную серию. Базовые возможности chunking уже могут быть включены по умолчанию в этой версии vLLM. [Optimization guide](https://docs.vllm.ai/en/v0.30.0/configuration/optimization/).

## Три ручки, которые постоянно путают

| Ручка | Ограничивает | Не означает |
| --- | --- | --- |
| max-model-len | Длину одной истории | Столько памяти заранее выделено каждому клиенту |
| max-num-seqs | Число обрабатываемых scheduler sequences | Столько пользователей можно зарегистрировать |
| max-num-batched-tokens | Token budget одного шага | Общую длину документа |

CUDA graphs относятся ещё к другому уровню: повторный запуск подготовленного вычислительного графа. Их полезность и расход памяти надо измерять. Разрешённый graph capture в конфигурации не доказывает replay на каждом шаге.

## RAM — второй уровень, не вторая видеокарта

Сохраняем KV документа X в host RAM. Обрабатываем другие документы, X вытесняется из GPU-кэша. Затем приходит новый вопрос по X: если необходимые blocks доступны в CPU-tier, загружаем их обратно вместо полного повторного prefill.

```text
X завершён → CPU store → Y, Z, … занимают GPU cache → снова X
                                                   ↓
                                    CPU load → GPU attention
```

Для сравнения нужна та же последовательность документов у A и B. Обычный второй запрос подряд по X часто измеряет **GPU hit**, а не пользу RAM.

### Оценка передачи из презентации

При идеальных `4.5044 GiB / 25 GiB/s ≈ 0.1802 s` получаем **только однонаправленную передачу**. Это не TTFT и не измеренная PCIe bandwidth. Накладные расходы поиска blocks, очередей, синхронизации и конкуренции за memory bus добавляются сверху. При возврате части префикса объём иной.

```bash
python3 scripts/kv_math.py --sessions 1
```

Число `RAM: 256 GiB` из схемы презентации означало условную ёмкость host-памяти. Оно не предписывает отдать все 256 GiB connector. Наш стартовый CPU budget 64 GiB — отдельная настройка эксперимента, требует проверки allocatable и memory limits.

В используемом OffloadingConnector CPU budget задаётся суммарно на workers. Смена TP не означает, что автоматически нужно умножить это значение на число GPU. [Connector guide](https://docs.vllm.ai/en/v0.30.0/features/kv_offloading_usage/).

## Как читать графики

Для каждого прогона рядом: errors, завершённые запросы, queue mean, prefill mean, client TTFT p95, output tokens/s. Дополнительно — lengths, preemptions, CPU store/load, GPU cache usage. Ноль завершённых запросов означает «нет выборки», а не «0 секунд».

```bash
python3 scripts/report.py --directory results/raw/ab
```

Команда строит строки по реальным JSON-прогонам. Если model/dataset/concurrency различаются, выводит предупреждение. Метрики разных запусков не склеиваются в выдуманный «средний p95».
