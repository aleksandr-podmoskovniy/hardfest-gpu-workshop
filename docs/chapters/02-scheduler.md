## Из чего складывается время ответа

![Фазы запроса и отличие первого токена от видимого текста ответа](../../assets/02-latency.svg)

TTFT клиента — время от отправки запроса до первого содержательного фрагмента потока. Интерфейс может скрывать рассуждение модели; тогда первое слово итогового ответа появится позже. На графиках эти два события нужно различать.

Допустим, запрос 70 секунд ждал в очереди и 5 секунд обрабатывался до первого токена. Для пользователя задержка составила около 75 секунд плюс накладные расходы. Ни 75 секунд вычислений, ни 5 секунд общего ожидания здесь нет. Это условный пример, не результат замера стенда.

Чтобы измерить время обработки после выхода из очереди, нужны связанные отметки времени одного запроса. Выражение `p95(TTFT) − p95(queue)` не даёт p95 времени вычислений: значения этих перцентилей могут относиться к разным запросам.

## Chunked prefill

На этапе prefill движок обрабатывает входные токены, на этапе decode — генерирует новые. Каждый новый токен зависит от предыдущих. За один шаг планировщик может совместить обработку входа одного запроса с генерацией ответов на другие.

Упрощённый пример без спекулятивного декодирования:

| Бюджет токенов на шаг | Три запроса на этапе decode | Остаётся для нового prefill |
| --- | --- | --- |
| 8192 | 3 × 1 токен | 8189 |
| 2048 | 3 × 1 токен | 2045 |

Если обрабатывать меньшую часть входа за шаг, весь документ потребует больше шагов. Зато отдельный шаг будет меньше задерживать уже генерируемые ответы. Размер порции приходится выбирать между скоростью приёма новых запросов, интервалом между выходными токенами (ITL) и общей пропускной способностью.

В B-профиле задан бюджет 4096 токенов; значения 8192 и 2048 выше служат только примером. Для проверки влияния бюджета меняйте только его, сохранив остальные параметры. Chunked prefill уже может быть включён по умолчанию в используемой версии vLLM — это нужно проверить в фактической конфигурации. [Руководство по оптимизации vLLM](https://docs.vllm.ai/en/v0.30.0/configuration/optimization/).

## Ограничения планировщика

| Параметр | Ограничивает | Не означает |
| --- | --- | --- |
| max-model-len | Длину одной истории | Столько памяти заранее выделено каждому клиенту |
| max-num-seqs | Число одновременно обрабатываемых последовательностей | Предельное число пользователей сервиса |
| max-num-batched-tokens | Бюджет токенов одного шага | Общую длину документа |

CUDA graphs позволяют повторно запускать подготовленный вычислительный граф. Они тоже занимают память, поэтому полезность нужно оценивать вместе с расходом HBM. Разрешённый захват графов в конфигурации ещё не означает, что движок использует их на каждом шаге.

## Выгрузка KV-кэша в RAM

KV документа X можно сохранить в оперативной памяти узла. Пока обрабатываются другие документы, X вытесняется из GPU-кэша. При следующем вопросе по X сохранённые блоки возвращаются на GPU, и соответствующую часть prefill не приходится выполнять заново.

![Сохранение KV в RAM, вытеснение из GPU и возврат для повторного запроса](../../assets/05-kv-ram.svg)

Для сравнения нужна одинаковая последовательность документов в обеих сериях. Второй запрос подряд по X часто находит блоки ещё на GPU и ничего не говорит о пользе выгрузки в RAM.

### Сколько занимает передача

Если передавать 4,5044 GiB со скоростью 25 GiB/s, получим `4.5044 GiB / 25 GiB/s ≈ 0.1802 s`. Это время передачи в одну сторону при условной постоянной скорости, не TTFT и не замер PCIe. Поиск блоков, очереди, синхронизация и конкуренция за шину памяти добавят задержку. Если возвращается только часть префикса, объём передачи будет меньше.

```bash
awk 'BEGIN { print 4.5044/25, "seconds (copy only)" }'
```

Даже если у узла 256 GiB RAM, отдавать всю память под KV-кэш нельзя: она нужна движку и другим процессам. В опубликованном опыте на VM 128 GiB бюджет — 32 GiB с остановленной A. Перед запуском его нужно сверить с доступной памятью узла и лимитом контейнера.

В используемом OffloadingConnector бюджет RAM задаётся суммарно для рабочих процессов. При смене TP его не нужно автоматически умножать на число GPU. [Выгрузка KV-кэша в vLLM](https://docs.vllm.ai/en/v0.30.0/features/kv_offloading_usage/).

## Как читать графики

Для каждого прогона записывайте число ошибок и завершённых запросов, среднее ожидание в очереди, среднее время prefill, клиентский TTFT p95 и число выходных токенов в секунду. Рядом нужны длины запросов, число вытеснений, запись и чтение KV в RAM, заполнение GPU-кэша. Если ни один запрос не завершился, выборки для времени ответа нет — значение «0 секунд» будет ошибочным.

```bash
jq . results/hardfest/ab/a.json
jq . results/hardfest/ab/b.json
```

Команды показывают JSON штатного benchmark. Перед сравнением вручную сверьте модель, набор запросов, длины и параллельность. p95 каждого запуска остаётся отдельным значением: усреднение перцентилей не даёт перцентиль общей выборки.
