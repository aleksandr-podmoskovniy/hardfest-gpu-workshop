## От одного токена к состоянию сессии

Авторегрессионная модель дописывает текст по шагам. Получив `t1 t2 t3`, она выдаёт `t4`; следующий шаг уже учитывает `t1 t2 t3 t4`. Веса модели между такими шагами не переобучаются. Меняется состояние конкретного запроса.

В механизме внимания (attention) текущая позиция формирует Q — запрос к истории. K прошлых позиций помогают оценить их релевантность, а V содержат значения, из которых складывается результат:

```text
Q текущей позиции
    ↓ сравнение с K1, K2, K3 + нормализация
w1, w2, w3
    ↓
w1·V1 + w2·V2 + w3·V3 → результат attention
```

Формально это `softmax(QKᵀ / sqrt(d))V`, с масками и деталями конкретной архитектуры. Q нужен для текущего вычисления; старые K/V сохраняются, чтобы не вычислять их заново при каждом следующем токене. KV-кэш хранит эти промежуточные данные, а не готовые ответы.

У сервиса одна копия весов, но каждому запросу нужно хранить своё состояние. Если веса уже заняли большую часть GPU, несколько длинных запросов могут исчерпать память для KV-кэша. Новые запросы останутся в очереди, даже если вычислительные блоки GPU загружены слабо.

## GQA: почему нельзя считать по всем Q-головам

При Grouped Query Attention несколько голов запросов используют общие головы K/V. Например, при 64 головах Q и 8 головах KV на одну пару K/V приходится восемь голов Q. В формулу памяти KV нужно подставить 8, а не 64.

Для расчёта и проверки понадобятся три источника:

| Источник | Что берём | Что не следует подставлять автоматически |
| --- | --- | --- |
| `config.json` модели | Число слоёв и голов KV, размерность головы, типы внимания | Фактически выделенную память GPU |
| Конфигурация запуска | Формат KV, размер окна, степень TP | Текущую длину каждого запроса |
| Логи и метрики движка | Ёмкость кэша, число блоков, рабочую память, память графов | Размер модели только по её имени |

Посмотреть конфигурацию запущенной модели и логи:

```bash
kubectl --context "$GPU_CONTEXT" -n hardfest-demo exec deployment/hf-gemma-a -- cat /models/gemma/config.json
kubectl --context "$GPU_CONTEXT" -n hardfest-demo logs deployment/hf-gemma-a --tail=100
```

Первая команда читает config.json внутри Pod и ничего не скачивает. У мультимодальной модели параметры текста могут находиться в `text_config`. Значение `head_dim` нужно брать из конфигурации: оно не всегда равно `hidden_size / heads`.

## Расчёт KV-кэша для GPT-OSS-120B

У GPT-OSS-120B есть полное и локальное внимание, поэтому на его примере удобно разобрать обе части расчёта. Эти числа не описывают Gemma, запущенную в лабораторной работе: для неё нужны параметры собственной архитектуры.

Параметры GPT-OSS: 36 слоёв, 8 голов KV, размерность головы 64, локальное окно 128; 18 слоёв с полным вниманием и 18 с локальным. Они указаны в [конфигурации модели](https://huggingface.co/openai/gpt-oss-120b/raw/main/config.json). Возьмём BF16 KV: два байта на элемент.

Одна позиция одного слоя занимает:

`2 × 8 × 64 × 2 = 2048 bytes = 2 KiB`.

Первая двойка — K и V, вторая — байты BF16. Слой с полным вниманием хранит всю длину S, слой с локальным — в идеальном случае `min(S, 128)`:

`KV(S) = 2 KiB × [18 × S + 18 × min(S, 128)]`.

Для `S = 131072`:

| Часть | Расчёт | Объём |
| --- | --- | --- |
| Полное внимание | 36 KiB × 131072 | 4608 MiB |
| Локальное внимание | 36 KiB × 128 | 4,5 MiB |
| Всего | (4608 + 4,5) / 1024 | 4,50439453125 GiB |

Это объём самих K/V. Движок выделяет память блоками; округления, группировка слоёв, выравнивание и временные буферы увеличивают расход. У гибридного кэша могут быть дополнительные ограничения. Реальную ёмкость нужно сверить с числом доступных блоков в логах движка.

### Четыре и восемь независимых запросов

Память независимых историй складывается. Если часть префикса общая и движок переиспользует её блоки, суммарный расход будет меньше. Для этого префиксы должны совпадать на уровне токенов, а движок — действительно разделять блоки между запросами.

## Контекст включает и вопрос, и ответ

128K в этой модели — 131072 токена суммарно на вход и выход. Например, 122880 токенов входа после применения шаблона чата и 8192 токена на генерацию. Системный промпт, документы, история и результаты инструментов относятся ко входу; рассуждение модели тоже расходует выходной бюджет.

Для Gemma и Qwen расчёт нужно повторить с их токенизаторами, окном и архитектурой. Поддержка окна 256K не означает, что на выбранных GPU поместятся 50 таких запросов одновременно.

## Как из HBM получить предел размещения

Возьмём условную GPU с `G=96 GiB`, долей памяти процесса `u=0.90`, весами `W=64 GiB` и рабочими расходами `R=6 GiB`:

`Kpool = G × u − W − R = 16.4 GiB`.

`floor(16.4 / 4.50439453125) = 3` полных независимых истории по 128K в идеальной модели. Остатка ≈2,89 GiB недостаточно для четвёртой полной истории. Планировщик может обслуживать другое число активных запросов: оно зависит от их длины, общих префиксов и вытеснения.

Приведите все значения к одной единице: GB = 10⁹ байт, GiB = 2³⁰ байт. Ёмкость в названии карты и показание `nvidia-smi` в MiB нельзя подставлять как взаимозаменяемые числа. 96 GiB здесь — условие примера, а не измеренная память стенда.

## Что меняет FP8 KV

Переход с двух байтов на элемент K/V на один вдвое уменьшает объём самих K/V. Размер весов, рабочих буферов и памяти CUDA graphs при этом не меняется. Для выбранного варианта FP8 нужно проверить поддержку вычислительных ядер, способ получения коэффициентов масштабирования и качество ответов. [Квантованный KV-кэш в vLLM](https://docs.vllm.ai/en/v0.30.0/features/quantization/quantized_kvcache/).

```bash
awk 'BEGIN { print 8*1024*(18*131072+18*128)/1024^3, "GiB FP8" }'
```

В предыдущей формуле использован GPT-OSS. Для Gemma есть отдельный [расчёт по её конфигурации](../MEMORY_BUDGET.md):

```bash
awk 'BEGIN { print (81920*133120+16384*50*1024)/2/1024^3, "GiB FP8" }'
```

Результат — 5,46875 GiB полезных данных KV одной истории. Это не сумма RAM процесса и не размер выделенного GPU-пула. Ёмкость кэша и служебные расходы сверяются при старте движка.

## Общий документ: выигрыш начинается с одинакового начала

```text
Запрос 1: [общий system][документ X][вопрос 1]
Запрос 2: [общий system][документ X][вопрос 2]
Запрос 3: [новая дата  ][документ X][вопрос 3]
```

Первые два запроса могут переиспользовать длинный префикс. У третьего начало изменилось, поэтому такого же попадания в кэш может не быть. Важны точные токены: шаблон, порядок блоков, пробелы и метаданные. Семантический кэш ответов на шлюзе решает другую задачу — ищет готовый ответ на похожий запрос, а не совпавшие блоки KV.

Для оценки вместимости сервиса нужны три величины: память весов, рабочая память движка и доступный объём KV-кэша. Последний определяет, какие истории и сколько активных запросов можно держать одновременно.
