# Почему свободных гигабайт мало, даже если GPU почти не считает

[Маршрут мастер-класса](../../WORKSHOP.md) · [Следующая глава: время и scheduler](02-scheduler.md)

## От одного токена к состоянию сессии

Авторегрессионная модель дописывает текст по шагам. Получив `t1 t2 t3`, она выдаёт `t4`; следующий шаг уже учитывает `t1 t2 t3 t4`. Веса модели между такими шагами не переобучаются. Меняется состояние конкретного запроса.

В attention текущая позиция формирует **Q** — запрос к истории. **K** прошлых позиций помогают оценить их релевантность, а **V** несут смешиваемое содержимое. Упрощённо:

```text
Q текущей позиции
    ↓ сравнение с K1, K2, K3 + нормализация
w1, w2, w3
    ↓
w1·V1 + w2·V2 + w3·V3 → результат attention
```

Формально это `softmax(QKᵀ / sqrt(d))V`, с масками и деталями конкретной архитектуры. Q нужен для текущего вычисления; старые K/V удобно сохранить, чтобы не вычислять их заново при каждом следующем токене. Поэтому **KV-кэш не является кэшем готовых ответов**.

Один сервис держит копию весов; запросы держат свои состояния. Если веса уже заняли большую часть GPU, несколько длинных запросов могут исчерпать оставшийся KV-пул. В это время новые запросы стоят в очереди — небольшой процент GPU utilization сам по себе не объясняет причину ожидания.

## GQA: почему нельзя считать по всем Q-головам

При Grouped Query Attention несколько query-heads используют общие K/V-heads. В учебном примере презентации — 64 Q-heads и 8 KV-heads: на одну пару K/V приходится восемь Q-heads. В формулу памяти KV подставляем **8**, а не 64.

Теперь отделим три источника чисел:

| Источник | Что берём | Что не следует подставлять автоматически |
| --- | --- | --- |
| `config.json` модели | Layers, KV-heads, head dimension, типы attention | Фактический объём GPU allocations |
| Конфигурация запуска | KV dtype, разрешённое окно, TP | Текущую длину каждого запроса |
| Логи / метрики runtime | Capacity, blocks, workspace, graph memory | Размер модели только по имени |

Для живой модели на стенде:

```bash
python3 scripts/hf.py model-info a
python3 scripts/hf.py logs a
```

Команда читает выбранные поля локального config внутри нашего Pod, ничего не скачивает. У мультимодальной модели параметры текста могут находиться в `text_config`. `hidden_size / heads` не всегда заменяет явный `head_dim`.

## Разбираем расчёт из презентации до байта

> Ниже **учебный пример GPT-OSS-120B**, а не план памяти Gemma. Именно его числа были на слайдах. Переносим способ рассуждения, не подпись модели.

Параметры GPT-OSS: 36 слоёв, 8 KV-heads, head dimension 64, локальное окно 128; 18 full и 18 sliding слоёв. Их можно проверить в [config модели](https://huggingface.co/openai/gpt-oss-120b/raw/main/config.json). Для примера выбираем BF16 KV: два байта на элемент.

**Одна позиция одного слоя:**

`2 × 8 × 64 × 2 = 2048 bytes = 2 KiB`.

Первая двойка — K и V, вторая — байты BF16. Для full-attention слоя нужно хранить всю длину S; для идеализированного local-attention — `min(S, 128)`:

`KV(S) = 2 KiB × [18 × S + 18 × min(S, 128)]`.

Для `S = 131072`:

| Часть | Расчёт | Объём |
| --- | --- | --- |
| Full layers | 36 KiB × 131072 | 4608 MiB |
| Sliding layers | 36 KiB × 128 | 4,5 MiB |
| Всего | (4608 + 4,5) / 1024 | 4,50439453125 GiB |

Это идеальная полезная нагрузка KV. Реальный allocator выделяет блоки; округления, группировка слоёв, alignment и временные буферы увеличивают расход. Runtime может иметь дополнительные ограничения на hybrid cache. Рассчитанное число **не равно автоматически** свободным blocks движка.

## Контекст включает и вопрос, и ответ

128K в этой модели — 131072 токена **всего**, а не 128K входа плюс бесплатный ответ. Пример: вход после chat template 122880 и бюджет генерации 8192. Системный промпт, документы, история и tool outputs относятся ко входу; reasoning тоже расходует выходной бюджет модели.

Для Gemma/Qwen используем **их** tokenizer, окно и architecture. Публикуемые 256K — цель проверки, а не разрешение запустить 50 таких сессий без расчёта.

## Как из HBM получить предел размещения

Пример со слайдов содержит **условные** `G=96 GiB`, долю процесса `u=0.90`, `W=64 GiB` весов и `R=6 GiB` рабочих расходов:

`Kpool = G × u − W − R = 16.4 GiB`.

`floor(16.4 / 4.50439453125) = 3` полных независимых 128K истории в идеальной модели. Остаток ≈2,89 GiB недостаточен для четвёртой полной истории. Это не обещание ровно трёх активных запросов в реальном scheduler: короткие запросы, общие префиксы и preemption меняют картину.

Не смешивать GB и GiB: GB = 10⁹ байт, GiB = 2³⁰. Маркетинговое имя SKU, показание `nvidia-smi` в MiB и расчёт выше должны быть приведены к одной единице. **96 GiB здесь учебное допущение**, не результат обнаружения нашей карты.

## Что меняет FP8 KV

Если только полезные K/V переходят с двух байтов на один, их идеальный payload уменьшается вдвое. Но весам, workspace и graph pools от этого не становится вдвое меньше. Scaling/поддержка kernels/качество — отдельные вопросы; проверить вариант FP8 и способ получения scales в выбранной версии. [vLLM: quantized KV](https://docs.vllm.ai/en/v0.30.0/features/quantization/quantized_kvcache/).

```bash
python3 scripts/kv_math.py --sessions 8 --element-bytes 1
```

Числа калькулятора — арифметика GPT-OSS из презентации. Для решения о запуске Gemma нужны реальные startup capacity и замер.

## Общий документ: выигрыш начинается с одинакового начала

```text
Запрос 1: [общий system][документ X][вопрос 1]
Запрос 2: [общий system][документ X][вопрос 2]
Запрос 3: [новая дата  ][документ X][вопрос 3]
```

Первые два могут переиспользовать длинный префикс. Третий изменил начало, поэтому не обязан получить тот же hit. Одинаковый смысл документа не гарантирует одинаковые tokens: важны шаблон, порядок блоков, пробелы и metadata. Поэтому semantic response cache gateway и prefix KV-cache engine — разные технологии.

**Вывод главы:** прежде чем покупать ещё карту, измеряем веса, рабочую память и KV; понимаем, какой размер истории и какое число одновременно активных запросов действительно требуются.
