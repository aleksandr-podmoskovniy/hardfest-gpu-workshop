## Сервисы RAG

```text
Документы → embedding → векторный индекс
Вопрос → embedding → поиск кандидатов → reranker → отобранные фрагменты
                                                     ↓
                                  вопрос + фрагменты → LLM → ответ
```

Модель эмбеддингов превращает текст в числовое представление для поиска. Реранкер оценивает найденные пары «вопрос–фрагмент» и уточняет их порядок. LLM формирует ответ по отобранному контексту. Этим моделям нужны разные объёмы памяти и вычислений; небольшой модели поиска может не требоваться целая H100.

В этом мастер-классе индекс может работать на CPU, модели эмбеддингов и реранкинга — на части A100, LLM — на H100. Для другой нагрузки размещение нужно рассчитывать заново. Число и длина фрагментов, их отбор и итоговый промпт влияют и на качество ответа, и на время prefill.

На стенде используются Qwen3 Embedding/Reranker 0.6B. Если индекс уже построен другой моделью, например bge-m3, после замены модели эмбеддингов потребуется переиндексация: документы и запросы должны быть представлены в одном векторном пространстве.

## MIG, MPS, time-slicing

| Механизм | Как работает | Ограничения |
| --- | --- | --- |
| MIG | Аппаратные разделы с определёнными ресурсами | Допустимые сочетания разделов зависят от GPU |
| MPS | Несколько клиентов совместно работают через MPS-сервер | Доля вычислений не гарантирует время ответа и не обеспечивает полную аппаратную изоляцию |
| Time-slicing | Несколько нагрузок поочерёдно используют общую GPU | Нет отдельной памяти, как у MIG; возможны конкуренция и нехватка памяти |

MPS внутри MIG разделяет ресурсы одного MIG-раздела, а не всей карты. Две заявки одного DeviceClass могут попасть на разные разделы. Проверьте назначенные устройства и процессы: для совместного использования они должны иметь один MIG UUID.

Свойства и ограничения MIG/MPS описаны в [документации NVIDIA](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/deployment-considerations.html). Динамическое создание разделов по ResourceClaim в этом упражнении обеспечивает установленный DRA-драйвер Deckhouse. Одной установки драйвера NVIDIA для такого поведения недостаточно.

## Жизненный цикл заявки

```text
GPUClass/GPUPool → DeviceClass контроллера
                           ↓
Pod → ResourceClaim → назначение устройства → подготовка драйвером → MIG-раздел → контейнер
                           ↓ после остановки последнего потребителя
                заявка освобождена → драйвер обновил состояние → ресурс снова доступен
```

Режим MIG включён заранее, но сами разделы заранее не создаются. Нагрузка запрашивает размер, а планировщик и драйвер выбирают допустимое размещение. Разделы появляются и освобождаются по мере создания и завершения заявок. Предварительное создание разделов через `nvidia-smi -cgi` обошло бы этот механизм.

Если геометрия карты не допускает ещё один раздел, заявка останется Pending. Проверьте её причину: свободные GiB сами по себе не означают, что нужная комбинация разделов допустима.

## Проверяем API отдельно и вместе

Измерьте время ответа, ошибки и пиковую память сначала у модели эмбеддингов, затем у реранкера, потом у обоих одновременно. Так видно, насколько процессы мешают друг другу; средняя загрузка всей GPU может этого не показать. У реранкера проверьте не только HTTP 200, но и порядок результатов.

Команды запросов и освобождения ресурсов приведены в [лабораторной работе MIG/MPS](../../labs/05-mig-mps.md). Распознавание речи можно добавить отдельным упражнением после проверки движка и бюджета памяти.

## Перенос настроек в сервис платформы

После ручного подбора настроек их нужно воспроизвести через InferenceService. Важно проверить не только заполненные поля интерфейса, но и параметры, с которыми платформа запустила контейнер.

Сверяем три уровня:

| Уровень | Что проверить |
| --- | --- |
| Расчёт | Предположения о весах, KV, рабочих расходах |
| План | Выбранные GPU, движок, контекст, параметры запуска и причины выбора |
| Контейнер | Фактические аргументы, imageID, ResourceClaim и успешный ответ API |

Проверьте одной нагрузкой три запуска: исходный A, настроенный вручную B и новый сервис платформы на карте A. Если платформа не поддерживает спекулятивное декодирование или выгрузку KV, укажите это как различие условий сравнения.

После замены адреса LLM повторите вопрос в чате. Модель эмбеддингов, индекс и реранкер должны остаться прежними, если сравнивается только генерация.

## Когда нужна ещё одна карта

Для ответа нужны измерения: хватает ли памяти активным историям, сколько запросов укладывается в допустимое время и сколько ресурсов занимают вспомогательные модели. В заключительной работе с TP2 две карты нужны для размещения большой модели. Это отдельный эксперимент, не продолжение сравнения одной модели на A и B.
