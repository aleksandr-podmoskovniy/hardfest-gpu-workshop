# Не каждой модели нужна целая карта

[Speculation](03-speculation.md) · [Основной сценарий](../../README.md)

## Сначала разложим RAG на сервисы

```text
Документы → embedding → векторный индекс
Вопрос → embedding → поиск кандидатов → reranker → отобранные фрагменты
                                                     ↓
                                  вопрос + фрагменты → LLM → ответ
```

Embedding превращает текст в числовое представление для поиска. Reranker рассматривает найденные пары «вопрос–фрагмент» и уточняет порядок. LLM формирует ответ по поданному контексту. Размеры, время работы и требования этих моделей различаются; выдавать каждой целую H100 часто не лучший первый выбор.

Индекс может работать на CPU, embedding/reranker — на выделенной части A100, LLM — на H100. Это схема мастер-класса, не универсальная рекомендация для любого RAG. Количество фрагментов, длина chunk, ranking и prompt влияют как на качество, так и на затраты prefill.

В презентации пример embedding — bge-m3. В закреплённом наборе стенда — Qwen3 Embedding/Reranker 0.6B. Не меняем embedding у уже построенного индекса без переиндексации: размерность и семантика пространства должны соответствовать запросам.

## MIG, MPS, time-slicing

| Механизм | Идея | О чём предупредить |
| --- | --- | --- |
| MIG | Аппаратные instances с определёнными ресурсами | Геометрии дискретны и зависят от GPU |
| MPS | Несколько клиентов совместно работают через MPS-сервер | Compute-share не равен SLA и полной аппаратной изоляции |
| Time-slicing | Несколько workloads получают доступ к общей GPU во времени | Не создаёт отдельную память как MIG, возможна конкуренция/OOM |

MPS внутри одного MIG добавляет совместное использование **ресурсов этого instance**, а не всей исходной карты. Две заявки одного DeviceClass ещё не доказывают, что процессы попали на один MIG UUID: проверяем allocation и процессы.

Публичные свойства MIG/MPS сверяем с [NVIDIA](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/deployment-considerations.html). Динамическое создание instances по нашим claims — реализация установленного Deckhouse DRA-драйвера, не магическое свойство произвольного NVIDIA setup.

## Жизненный цикл заявки — главный кадр демо

```text
GPUClass/GPUPool → generated DeviceClass
                           ↓
Pod → ResourceClaim → scheduler allocation → driver prepare → MIG instance → контейнер
                           ↓ после остановки последнего потребителя
                claim освобождён → driver reconcile → ресурс снова доступен
```

Мы заранее включаем MIG mode, но **не создаём статически геометрию всех разделов**. Во время показа workload запрашивает размер, allocator/драйвер выбирают допустимое размещение. Выигрыш платформы — в управляемом жизненном цикле, а не в том, что ведущий заранее выполнил скрытый `nvidia-smi -cgi`.

Если аппаратная геометрия не допускает ещё один instance — честно показываем Pending и его причину. Нельзя обещать разместить произвольную комбинацию только потому, что арифметически осталось несколько GiB.

## Проверяем API отдельно и вместе

Сначала response time/errors/peak memory embedding, затем reranker, потом оба одновременно. Разница показывает interference, который средний utilization всей GPU скрывает. Для reranker проверяем не только 200, но и осмысленный порядок результатов.

Рабочие curl-примеры и последовательность освобождения — в [лабораторной MIG/MPS](../../labs/05-mig-mps.md). STT остаётся возможным дополнительным сервисом, но не обязательной частью 13-минутного слота.

## Автоматизация завершает ручной эксперимент

Ручной профиль отвечает на вопрос **«что работает?»**. InferenceService и план платформы — **«как это повторить и сопровождать?»**.

Сверяем три уровня:

| Уровень | Что предъявить аудитории |
| --- | --- |
| Расчёт | Предположения о весах, KV, рабочих расходах |
| План | Выбранные GPU/runtime/context/параметры и причины |
| Контейнер | Реальные args, imageID, claim, успешный ответ API |

Проверяем три запуска одной нагрузкой: исходный A, ручной B, новый платформенный A. Если платформа не поддерживает speculation или connector, это явное различие условий, не повод скрывать параметр за словом «рецепт».

После замены LLM endpoint повторяем вопрос в чате. Если embedding/index/reranker остались теми же, проверяем, что менялся именно путь генерации, а не весь RAG целиком.

## «А нам точно нужны ещё карты?»

Отвечаем раздельно: хватает ли памяти активным историям; сколько запросов завершается вовремя; какая часть GPU нужна вспомогательным моделям; сколько стоит управление всем этим. Финальный TP2 — уже другая задача: разместить и эффективно обслуживать большую модель, а не просто показать две занятые карты.
