# Одна большая модель вместо двух реплик

Gemma A/B отвечали на вопрос, что меняют настройки одного движка на одной карте.
Теперь обе H100 обслуживают один экземпляр Qwen: проверяем другую границу —
вместимость большой модели и число пользователей при заданной задержке.
Это финальный этап мастер-класса, а не продолжение сравнения скорости Gemma A/B.

![Две независимые Gemma освобождают GPU для одного Qwen TP2](../../assets/17-qwen-transition.svg)

## Какие веса запускаем

В [models.lock.json](../../models.lock.json) закреплён
`nvidia/Qwen3.8-Flash-Next-NVFP4`, ревизия
`fc694b54fb0174e0913e6adf86691ef85a4ead47`. Контекст модели — 262 144 токена.
Файлы safetensors занимают 132 680 249 378 байт, или 123,57 GiB.
Размер файлов не равен ни пику RAM загрузчика, ни окончательному расходу GPU.

Название NVFP4 не означает, что каждый тензор занимает четыре бита:
эксперты основной модели хранятся в NVFP4, PLE и эксперты MTP — в FP8,
часть остальных весов — в BF16. У модели 48 слоёв: 36 линейного и 12 полного
внимания; MTP содержит ещё один слой. Поэтому расчёт KV для Gemma сюда
не переносится. [Конфигурация закреплённой модели](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/blob/fc694b54fb0174e0913e6adf86691ef85a4ead47/config.json).

На H100 профиль использует `quantization: modelopt` и `moe-backend: marlin`.
Это способ исполнения конкретного checkpoint, а не обещание аппаратной
арифметики FP4 на H100. Квантование весов и dtype KV — разные настройки.

## TP2 и две реплики решают разные задачи

У двух реплик каждая GPU хранит собственные веса и обслуживает свою очередь.
У TP2 два процесса совместно выполняют одну модель: тензоры распределены
между GPU, а результаты вычислений регулярно обмениваются. Обе карты нужны
одновременно и должны попасть в одну VM/ноду.

PP2 делит слои между стадиями конвейера. В этом опыте выбран TP2 на связанной
NVLink паре; «PP2 невозможен» из этого не следует. Поддержка модели и выигрыш
конкретного режима проверяются отдельно. TP2 тоже не означает ускорение ровно
вдвое. [Режимы параллелизма vLLM](https://docs.vllm.ai/en/v0.30.0/serving/parallelism_scaling/).

В платформенном запуске согласованы три вещи: DeviceClass целой H100,
две карты в плане размещения и `tensor-parallel-size: 2` в движке.
Количество реплик сервиса при этом равно одному. DRA выделяет два устройства
одному Pod.

## MTP предлагает продолжение, основная модель проверяет

Встроенный блок Multi-Token Prediction предлагает следующий токен, основная
модель проверяет его. Профиль начинает с одного чернового токена:

```yaml
speculative-config:
  method: mtp
  num_speculative_tokens: 1
```

Отдельный draft checkpoint здесь не скачивается: MTP-веса уже входят в Qwen.
Увеличение числа предложенных токенов не гарантирует ускорение. Дополнительное
вычисление окупается, когда достаточно предложений принимается; на большой
параллельности оно может снизить общую пропускную способность.
[MTP в vLLM](https://docs.vllm.ai/en/v0.30.0/features/speculative_decoding/mtp/).

![MTP предлагает токен, Qwen проверяет его; принятие и скорость измеряются отдельно](../../assets/18-qwen-mtp.svg)

Нужны оба результата: доля принятых черновых токенов и скорость полезного
выхода. Сравниваем запуск без `speculative-config` и MTP=1 при одинаковых запросах, контексте,
числе сессий и состоянии кэша. «Высокое принятие» само по себе не результат
теста производительности.

## Бюджет памяти

Стартовый [профиль Qwen](../../values/qwen-tp2.yaml) рассчитан на узел
с 16 vCPU и 128 GiB RAM, без одновременно работающих Gemma.
Расход RAM загрузчика, CPU KV и shared memory сведён в
[едином расчёте памяти](../MEMORY_BUDGET.md#qwen-tp2-после-gemma).
Лимит контейнера — граница, а не измеренный расход: если модель не помещается,
сначала измеряем пик, затем меняем бюджет кэша и параметры, не ставя limit
выше всей памяти VM.

Для двух карт по 97 871 MiB номинальная сумма — 191,15 GiB, а при 0,9 —
172,04 GiB. Из этого нельзя просто вычесть размер checkpoint и объявить
остаток KV-пулом: раскладка весов, временные буферы, MTP и графы меняют расход.
Реальный размер пула берём из лога запуска. На паре H100 80 GB запас другой —
проверяйте фактические `memory.total`, а не только название GPU.

## Что даёт RAM-кэш Qwen

`OffloadingConnector` сохраняет и возвращает блоки состояния, освобождая GPU
кэш для других префиксов. Вычисления модели остаются на GPU, PLE-offload
выключен. Для гибридной модели сохраняем prefix caching и согласованное
выравнивание; произвольный `block_size` в этом профиле не задаём.
[Поддержка гибридных групп](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/distributed/kv_transfer/kv_connector/v1/offloading/config.py),
[расчёт общего CPU-бюджета для TP](https://github.com/vllm-project/vllm/blob/v0.30.0/vllm/v1/kv_offload/cpu/spec.py).

Задача опыта — после вытеснения из GPU получить положительный объём загрузки
из RAM и сравнить задержку с холодным prefill. Быстрый повтор без вытеснения
может целиком обслужиться GPU-кэшем и не доказывает пользу RAM.

![Окно модели, активные последовательности и подключённые пользователи — три разные величины](../../assets/19-qwen-capacity.svg)

256K — максимальная длина одной последовательности, а не обещание 50 активных
сессий по 256K. При concurrency=50 и `max-num-seqs=16` часть запросов ожидает.
Рабочая ёмкость сервиса — наибольшая проверенная нагрузка, при которой
выполнены требования к TTFT, времени между токенами и ошибкам.
