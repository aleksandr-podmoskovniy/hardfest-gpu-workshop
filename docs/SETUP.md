# Подготовка площадки

## 1. Требования к окружению

Для упражнений нужны выделенные GPU. Если на них работают другие сервисы, согласуйте время остановки и сохраните число реплик и настройки автосинхронизации: они понадобятся для восстановления. Не снимайте `cordon`, пока не выясните причину блокировки ноды.

Для A/B используются две сопоставимые H100 на одной ноде, для разделения GPU — отдельная A30 с поддержкой MIG. Оба H100-запуска и TP2 закреплены за `h100_node`. В варианте с 256 GiB RAM бюджет KV-offload — 64 GiB, в варианте с 128 GiB — 32 GiB с остановкой A. Проверьте не только установленную RAM, но и доступную для Pod память, лимиты контейнеров и потребление других сервисов. Закреплённая память CUDA также входит в этот расход.

Манифесты задают следующие запросы и лимиты RAM на один Pod:

| Конфигурация | Запрос памяти | Лимит памяти | `/dev/shm` |
| --- | --- | --- | --- |
| A, B tuned, B spec | 64 GiB | 80 GiB | 8 GiB |
| B cache | 128 GiB | 144 GiB | 72 GiB |
| Qwen TP2 | 96 GiB | 200 GiB | 8 GiB |
| Эмбеддер или реранкер | 4 GiB | 12 GiB | 8 GiB |

Для одновременного A и B cache планировщику нужно 192 GiB доступных запросов памяти; сумма лимитов — 224 GiB. Эти числа задают резервирование и ограничения, а не обязательный расход модели. Оставьте память системе и другим Pod. На ноде с 251,51 GiB RAM такой A/B помещается в рассчитанный бюджет; одновременные дополнительные сервисы нужно считать отдельно. [Расчёт RAM, shared memory и KV Gemma](MEMORY_BUDGET.md).

`/dev/shm` у B cache включает 64 GiB offload и 8 GiB для прочего межпроцессного обмена. KV уже учтён в лимите контейнера, прибавлять его повторно не нужно. Генератор пересчитывает память из `cpu_bytes_to_use`; увеличение этого параметра не означает, что на ноде автоматически найдётся место. Gemma читает safetensors в режиме `lazy`, A и B запускаются по очереди, а не одновременно.

Запишите версии Kubernetes, DRA API, GPU-драйвера, ai-models, ai-inference и Console. Между сравниваемыми запусками их не меняйте. Название GPUClass или GPUPool проверяйте в установленном API: подпись в интерфейсе может отличаться от имени ресурса.

## 2. Параметры своего стенда

Создайте `.local/site.json` на основе [примера](../config/site.example.json). В нём хранятся адреса и имена ресурсов, но не токены и закрытые ключи.

Таблица выше относится к варианту с 256 GiB RAM. На VM с 128 GiB RAM и 16 vCPU эти настройки не подходят: два запроса по 16 CPU не запланируются, а B cache запросит всю оперативную память. Для такой VM добавьте в локальный файл:

```json
{
  "resources": {
    "gemma": {"cpu_request": "4", "memory_request_gib": 24, "memory_limit_gib": 48},
    "tp2": {"cpu_request": "8", "memory_request_gib": 64, "memory_limit_gib": 112}
  },
  "kv_offload_gib": 32
}
```

Это поля существующего файла, не его полная замена. A и B tuned/spec получают одинаковые 4 CPU, request 24 GiB и limit 48 GiB. Для B cache бюджет 32 GiB прибавляется один раз: request 56 GiB, limit 80 GiB, `/dev/shm` 40 GiB. **Перед запуском B cache на 128 GiB остановите A.** Ограничения выбраны для проверки; успешное планирование не подтверждает, что модель выдержит нагрузку без OOM. Пики измеряются при прогоне. Веса по-прежнему не выгружаются в RAM.

Можно хранить несколько площадок отдельно и явно выбирать нужную во всех командах: `python3 scripts/hf.py --site .local/site-ce.json preflight`. Старый файл с другим kubeconfig нельзя использовать после переноса GPU в VM.

Если A30 находится в другом кластере, подготовьте отдельный `.local/site-mig.json` с его kubeconfig, context, ожидаемым API и PVC малых моделей. Все команды MIG/MPS, включая остановку, выполняйте с `--site .local/site-mig.json`. Память сервисов на отдельной ноде не вычитается из RAM H100-VM.

| Поле | Откуда взять |
| --- | --- |
| kubeconfig, context, expected_server | Явно выбранный kubeconfig; API должен совпадать точно |
| bypass_proxy | Необязательно: `true` убирает proxy-переменные только у процесса kubectl и его OIDC-плагина при прямом доступе через VPN |
| namespace | `hardfest-demo`; этот выпуск скриптов ограничен этим namespace |
| h100_node / mig_node | Имена нод; допускается одна нода с разными GPU |
| h100_device_class | Созданный контроллером класс выделенных H100, без общих долей и посторонних GPU |
| mig_device_class / mps_device_class | Сгенерированные классы A30: выделенный `1g.6gb` и `2g.12gb` с MPS |
| image | Образ для amd64, закреплённый по digest; исходное значение в models.lock.json |
| image_pull_secrets | Имена заранее созданных Secret в namespace; не их содержимое |
| models.*.pvc / sub_path | Реальный Bound PVC и путь к корню модели внутри него |
| context_tokens | Одинаковое окно A/B: 65536 для основного сравнения с `a-chunked`; более длинные окна проверяются отдельно |
| resources.gemma / tp2 / small | Планируемые CPU requests и базовые memory request/limit в GiB; offload прибавляется отдельно |
| kv_offload_gib | Необязательный бюджет RAM-кэша; переопределяет 64 GiB из профиля |
| mps_percent / mps_memory_limit | Доля вычислительных ресурсов и лимит памяти одного MPS-клиента |
| reranker_profile | Проверенные параметры `conversion`/`pooling` для модели и версии vLLM |
| reranker_config_verified | Только после успешного `/rerank` и проверки правильного ранжирования |

Проверьте, что PVC содержит именно выбранную модель. В ai-models её файлы могут находиться в `store/sha256:<digest>/model`, а не в корне тома. Убедитесь, что доставка завершена и все части модели, перечисленные в индексе safetensors, доступны.

Для H100 нужны две свободные физические GPU, доступные через DRA. Если DeviceClass допускает совместное использование, разные ResourceClaim могут получить одну карту. Проверьте селектор класса и идентификаторы выделенных устройств. PCI-адреса своего стенда храните только в локальных настройках.

## 3. Модели и образ vLLM

[models.lock.json](../models.lock.json) фиксирует репозитории и ревизии моделей, а также digest образа vLLM. Веса не входят в Git. Для моделей с ограниченным доступом заранее примите лицензию и получите доступ. Токен Hugging Face не должен попадать в публичные YAML, историю команд или снимки экрана.

Упражнения используют уже заполненные PVC и подключают их только для чтения. Команда `apply` модели не скачивает. На своём кластере сначала настройте доставку через ai-models по документации установленной версии либо загрузите файлы в отдельные PVC. Сверьте ревизии и пути с `models.lock.json`.

Размер файлов safetensors не равен расходу VRAM: движку нужны временные буферы, CUDA graphs и KV-кэш; при загрузке он также может преобразовать веса. NVFP4-модель на Hopper не получает аппаратную производительность FP4, доступную на Blackwell.

В ручных запусках используется образ vLLM с закреплённой версией. Для автоматического повторения готовится совместимая сборка runtime в демоветви ai-inference; работоспособность upstream-контейнера не доказывает работоспособность конечного образа модуля. Исходные профили хранятся в JSON. Генератор монтирует их как `profile.yaml`: JSON совместим с YAML, но vLLM 0.30 проверяет расширение файла `--config` и отвергает `.json`.

## 4. Доступ и безопасный запуск

```bash
python3 scripts/hf.py preflight
python3 scripts/hf.py render a-chunked
python3 scripts/hf.py apply a-chunked --ack
```

Последняя команда проверит адрес API и принадлежность ресурсов мастер-классу, выполнит `server-side dry-run` и создаст Deployment с нулём реплик. Namespace, GPUClass, Secret и PVC она не создаёт — подготовьте их заранее.

`start` запускает Pod после проверки состояния ноды, актуальности профиля, памяти и `/dev/shm` в манифесте и конфликта A/B с TP2. Это не автоматическая оценка свободной RAM: скрипт отслеживает только свои Deployment. Перед запуском администратор стенда должен проверить Pod и занятые GPU во всех пространствах имён, включая сервисы, созданные модулем ai-inference.

Первый запуск выполняйте по [плану развёртывания](DEPLOYMENT.md): сначала одна Gemma, затем A/B, после этого KV-offload и assistant. TP2 проверяется отдельно, после освобождения обеих H100.

Сервисы имеют тип ClusterIP, входящий трафик ограничен пространством имён, а `port-forward` слушает только localhost. Публикация API, настройка VPN и авторизация не входят в эти манифесты. Если подключаете внешний шлюз, проверьте его кэширование и лимиты: они могут повлиять на результаты измерений.

## 5. Перезапуски и диагностика GPU

Скрипты не включают режим MIG, не меняют VFIO и политики безопасности, не перезагружают карты или ноды. Если GPU недоступна, сначала разберитесь с причиной вместе с администратором стенда. Для привилегированной диагностики нужен отдельный согласованный порядок работ.

Кэш компиляции в `emptyDir` исчезает вместе с Pod. После перезапуска компиляция может повториться; учитывайте её время отдельно от обработки запросов. Если сохраняете кэш на постоянном томе, разделяйте его по версии образа, модели и профилю запуска.
