# Подготовка площадки

## 1. Требования к окружению

Для упражнений нужны выделенные GPU. Если на них работают другие сервисы, согласуйте время остановки и сохраните число реплик и настройки автосинхронизации: они понадобятся для восстановления. Не снимайте `cordon`, пока не выясните причину блокировки ноды.

Для A/B используются две сопоставимые H100 на одной ноде, для разделения GPU — отдельная A100 с поддержкой MIG. Оба H100-запуска и TP2 закреплены за `h100_node`. В опыте с KV-кэшем понадобится 64 GiB оперативной памяти сверх памяти самих процессов. Проверьте не только установленную RAM, но и доступную для Pod память, лимиты контейнеров и потребление других сервисов. Закреплённая память CUDA также входит в этот расход.

Манифесты задают следующие запросы и лимиты RAM на один Pod:

| Конфигурация | Запрос памяти | Лимит памяти |
| --- | --- | --- |
| A, B tuned, B spec | 64 GiB | 128 GiB |
| B cache | 128 GiB | 224 GiB |
| Qwen TP2 | 96 GiB | 200 GiB |
| Эмбеддер или реранкер | 4 GiB | 12 GiB |

Для одновременного A и B cache планировщику нужно как минимум 192 GiB доступных запросов памяти. Фактическое потребление может быть выше, вплоть до лимитов; проверьте запас перед запуском.

Запишите версии Kubernetes, DRA API, GPU-драйвера, ai-models, ai-inference и Console. Между сравниваемыми запусками их не меняйте. Название GPUClass или GPUPool проверяйте в установленном API: подпись в интерфейсе может отличаться от имени ресурса.

## 2. Параметры своего стенда

Создайте `.local/site.json` на основе [примера](../config/site.example.json). В нём хранятся адреса и имена ресурсов, но не токены и закрытые ключи.

| Поле | Откуда взять |
| --- | --- |
| kubeconfig, context, expected_server | Явно выбранный kubeconfig; API должен совпадать точно |
| namespace | `hardfest-demo`; этот выпуск скриптов ограничен этим namespace |
| h100_node / mig_node | Имена нод; допускается одна нода с разными GPU |
| h100_device_class | Созданный контроллером класс именно выделенных H100, без A100/VFIO |
| mig_device_class / mps_device_class | Два сгенерированных класса выбранного A100 MIG-профиля |
| image | Образ для amd64, закреплённый по digest; исходное значение в models.lock.json |
| image_pull_secrets | Имена заранее созданных Secret в namespace; не их содержимое |
| models.*.pvc / sub_path | Реальный Bound PVC и путь к корню модели внутри него |
| context_tokens | Одинаковое реально запускаемое окно A/B; 262144 — первоначальная цель |
| mps_percent / mps_memory_limit | Доля вычислительных ресурсов и лимит памяти одного MPS-клиента |
| reranker_profile | Проверенные параметры `conversion`/`pooling` для модели и версии vLLM |
| reranker_config_verified | Только после успешного `/rerank` и проверки правильного ранжирования |

Проверьте, что PVC содержит именно выбранную модель. В ai-models её файлы могут находиться в `store/sha256:<digest>/model`, а не в корне тома. Убедитесь, что доставка завершена и все части модели, перечисленные в индексе safetensors, доступны.

Для H100 нужны две свободные физические GPU, доступные через DRA. Если DeviceClass допускает совместное использование, разные ResourceClaim могут получить одну карту. Проверьте селектор класса и идентификаторы выделенных устройств. PCI-адреса своего стенда храните только в локальных настройках.

## 3. Модели и образ vLLM

[models.lock.json](../models.lock.json) фиксирует репозитории и ревизии моделей, а также digest образа vLLM. Веса не входят в Git. Для моделей с ограниченным доступом заранее примите лицензию и получите доступ. Токен Hugging Face не должен попадать в публичные YAML, историю команд или снимки экрана.

Упражнения используют уже заполненные PVC и подключают их только для чтения. Команда `apply` модели не скачивает. На своём кластере сначала настройте доставку через ai-models по документации установленной версии либо загрузите файлы в отдельные PVC. Сверьте ревизии и пути с `models.lock.json`.

Размер файлов safetensors не равен расходу VRAM: движку нужны временные буферы, CUDA graphs и KV-кэш; при загрузке он также может преобразовать веса. NVFP4-модель на Hopper не получает аппаратную производительность FP4, доступную на Blackwell.

В ручных запусках используется отдельный образ vLLM с закреплённой версией. Образ по умолчанию в ai-inference не меняется; его совместимость с моделями проверяется отдельно. Файлы профилей записаны в JSON — этот формат принимает `vllm serve --config`.

## 4. Доступ и безопасный запуск

```bash
python3 scripts/hf.py preflight
python3 scripts/hf.py render a
python3 scripts/hf.py apply a --ack
```

Последняя команда проверит адрес API и принадлежность ресурсов мастер-классу, выполнит `server-side dry-run` и создаст Deployment с нулём реплик. Namespace, GPUClass, Secret и PVC она не создаёт — подготовьте их заранее.

`start` запускает Pod после проверки состояния ноды и конфликта A/B с TP2. Скрипт отслеживает только свои Deployment. Перед запуском администратор стенда должен проверить Pod и занятые GPU во всех пространствах имён, включая сервисы, созданные модулем ai-inference.

Сервисы имеют тип ClusterIP, входящий трафик ограничен пространством имён, а `port-forward` слушает только localhost. Публикация API, настройка VPN и авторизация не входят в эти манифесты. Если подключаете внешний шлюз, проверьте его кэширование и лимиты: они могут повлиять на результаты измерений.

## 5. Перезапуски и диагностика GPU

Скрипты не включают режим MIG, не меняют VFIO и политики безопасности, не перезагружают карты или ноды. Если GPU недоступна, сначала разберитесь с причиной вместе с администратором стенда. Для привилегированной диагностики нужен отдельный согласованный порядок работ.

Кэш компиляции в `emptyDir` исчезает вместе с Pod. После перезапуска компиляция может повториться; учитывайте её время отдельно от обработки запросов. Если сохраняете кэш на постоянном томе, разделяйте его по версии образа, модели и профилю запуска.
