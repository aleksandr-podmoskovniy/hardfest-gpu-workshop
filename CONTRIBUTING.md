# Изменения руководства и исходников

Этот файл — для авторов проекта. Для прохождения мастер-класса достаточно
[README](README.md), Git, Helm, kubectl и curl; запускать Python-скрипты не нужно.

## Куда вносить правку

| Что меняется | Файлы | Что проверить |
| --- | --- | --- |
| Последовательность запуска | `README.md` и `RTX5060.md` | Полное руководство на одной странице, команды рядом с объяснением |
| Подготовка инфраструктуры | `docs/SETUP.md`, `docs/GITOPS.md` | Явные контексты, пути и действия в редакторе, без привязки к личному стенду |
| Настройки runtime | `values/`, `charts/vllm-runtime/` | Helm render, schema, ConfigMap checksum, DRA и нулевые реплики |
| Веса моделей | `models.lock.json`, `catalog/models.yaml`, `catalog/rtx.yaml`, `catalog/a30.yaml` | Одинаковые закреплённые ревизии, доступ и лицензии |
| Иллюстрации | `scripts/build_diagrams.py`, `assets/` | Пересборка и визуальная проверка SVG |
| Результаты замеров | Отчёт и исходные файлы результата | Одинаковая нагрузка A/B, конфигурации и все ошибки серии сохранены |

Текст пишется для того, кто разбирается в работе системы и воспроизводит запуск.
Нужны исходная конфигурация, причина изменения, точный файл, команда и проверка —
не реплики докладчика, задания аудитории и не отчёт о нашей работе.
Обязательные условия размещайте **перед** командой, а не в конце длинного абзаца.
Планы и dry-run не описывайте как проверенный инференс.

## Как сделать раздел понятным

- Начальное условие — подготовленная A. Её поведение объясняется до топологии,
  перечня всех моделей и механизмов следующих этапов.
- Сохраняйте причинную последовательность: нагрузка Base и симптомы → память
  и B Cache → вычисления и B Tune → распределение GPU и A30 → автоматизация
  ручной сборки → вывод о ресурсах → gateway и большая модель TP2.
  Сначала возникает проблема, затем вводится механизм её решения.
- InferenceService объясняется только после ручной настройки и размещения A30.
  Фраза «ещё не InferenceService» в начале не помогает понять Base.
  Подробный prefill/decode относится к вычислениям после разбора памяти;
  начальная диагностика показывает очередь, занятость памяти и вычислений.
- Описывайте состояние и поведение системы: какие настройки применяются,
  что после этого меняется и какая метрика позволяет проверить результат.
  Заголовок обозначает предмет раздела; один абзац — одна мысль.
- При первом упоминании выделите **термин** и сразу объясните его простыми словами.
  Ссылка на документацию дополняет объяснение, а не заменяет его.
- Отделяйте объяснение от действия. Для шагов используйте нумерованный список,
  для сравнения настроек — небольшую таблицу. Не выделяйте жирным весь абзац.
- Живой переход к объяснению допустим; просьбы договориться и указания,
  какой экран показывает администратор, не нужны. У графика должны быть понятны
  метрика, фильтры и смысл изменения. Ожидаемый эффект не равен измеренному:
  описание запуска не должно превращаться в заявление об успехе.
- Подробный вывод формулы или разбор результата можно поместить в
  `<details><summary>Понятная подпись</summary>…</details>`. Сама формула, единицы
  и ключевое ограничение должны оставаться доступными. Между HTML-тегами и
  Markdown оставляйте пустые строки. Не вкладывайте раскрывающиеся блоки друг
  в друга и не скрывайте в них предупреждения о потере данных.
- GitHub-подсказки должны работать без JavaScript и наведения мыши. Проверяйте
  раскрытие с клавиатуры и на узком экране. Цветные alerts оставляйте для
  действительно важных ограничений; не превращайте ими каждый абзац в карточку.
- На схеме выделяйте одну главную связь. Обозначения расшифровывайте рядом;
  число сессий пишите как `N`, чтобы буква `B` не выглядела как `8` или `В`.
  У стрелки должны быть однозначные начало и конец. Числа сверяйте с профилем,
  а результаты — с опубликованным замером, не с предполагаемой конфигурацией.

Примеры и основания этих приёмов:

- [GitHub Docs: заголовки, списки и alerts](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)
  и [раскрывающиеся разделы](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections)
  — оформление, которое поддерживает сама площадка.
- [CESE: Cognitive load theory in practice](https://education.nsw.gov.au/about-us/education-data-and-research/cese/publications/practical-guides-for-educators-/cognitive-load-theory-in-practice)
  — разобранный пример перед самостоятельной задачей; необходимые сведения
  рядом с действием, необязательные подробности вне основного пути.
- [Nielsen Norman Group: чтение веб-страниц](https://www.nngroup.com/articles/how-users-read-on-the-web/)
  — смысловые подзаголовки и текст, который можно быстро просмотреть.

## Перед проверками

- Нужны Python 3 и Helm 3+ — это зависимости разработки, не рабочего маршрута участника.
- Для отдельного Go-адаптера нужны инструменты из его [инструкции](integrations/webui-access/README.md).
- Тесты запускаются локально и не должны обращаться к GPU или Kubernetes скрытно.
- Не добавляйте реальные адреса площадки, токены, веса и персональные данные.

## 1. Проверить чарт и профили

Из корня публичного репозитория:

```bash
python3 -m pip install -r requirements-dev.txt
for profile in values/*.yaml; do
  helm lint charts/vllm-runtime --strict -f "$profile" || exit 1
done
helm lint charts/model-catalog --strict -f catalog/models.yaml
python3 scripts/check_manifests.py
python3 -m unittest discover -s tests -v
```

Тесты проверяют рендер профилей, checksum и ссылки DRA. Это не доказательство
загрузки модели, отсутствия ECC и производительности на GPU.

## 2. Проверить текст и иллюстрации

```bash
python3 scripts/build_diagrams.py
python3 scripts/check_public.py
python3 scripts/check_docs.py
git diff --check
git diff --stat
```

Откройте изменённые SVG в браузере. Проверьте текст, стрелки и поля при обычном
масштабе чтения README: автоматические проверки этого не заменяют.
Общий холст — 1200×760, отступ — 48, шрифты и палитра едины.
QR `assets/workshop-qr.svg` должен вести на главную страницу этого GitHub-проекта.

Просмотрите README и RTX5060 в GitHub Markdown на широком и узком экранах:
таблицы, раскрывающиеся ответы, оглавление и иллюстрации. Прочитайте маршрут
сначала с закрытыми раскрытиями, затем с открытыми. В первом проходе должны быть
понятны исходное состояние, изменение, его смысл и проверка результата. Во втором —
все условия воспроизведения. Формула и смысл результата остаются видимыми;
доказательство и полные команды раскрываются рядом. Если без чтения длинного
абзаца нельзя понять следующий шаг, переработайте этот участок. Число слов
и автоматические проверки — только подсказки для редактора, не доказательство
того, что читатель понял материал.

Проверьте скриншоты отдельно: в адресной строке и настройках не должно быть
токенов. У чужих документов и изображений должны быть права на распространение.

## 3. Подготовить commit

Добавляйте только файлы своей правки, затем просмотрите staged diff:

```bash
git diff --cached --check
git diff --cached
git commit -S -s -m "Describe one workshop change"
```

`-S` подписывает commit настроенным ключом автора, `-s` добавляет
[DCO sign-off](https://developercertificate.org/). Используйте собственные имя,
email и ключ; не копируйте чужую identity и закрытый ключ в fork.

Публикация в GitHub и развёртывание на стенде — отдельные действия.
Проверка документации не должна автоматически менять работающий кластер.
