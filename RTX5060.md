# Инференс без простоя GPU: чиним LLM-сервис руками и делим карту на живом кластере

Александр Подмосковный, Флант / Deckhouse Platform

Вариант стенда: **две RTX 5060 Ti по 16 GiB и A30**.
[Вариант с двумя H100 и A30](README.md) — аналогичная конфигурация на других картах.

Исходное состояние: `Gemma A — Base` уже работает на первой RTX,
вторая карта свободна. После регистрации и одобрения аккаунта в
[ai.ap4y.ru](https://ai.ap4y.ru) модель доступна в чате; личный ключ
подставляется автоматически.

Операции GitOps, консоли и мониторинг требуют административного доступа;
личный ключ чата его не предоставляет. [Подготовка стенда](#setup).

## 1. Базовая модель под нагрузкой

Исходная проверка — восемь одновременных запросов к `Gemma A — Base`.
Развёрнутый ответ позволяет различить ожидание начала и темп продолжения.
Сохранение ответа после обновления страницы отдельно проверяет историю чата.

**LLM (Large Language Model)** — большая языковая модель.
Получение ответа от обученной модели называется **инференсом**.
Его выполняет GPU (Graphics Processing Unit — графический процессор).
**Токен** — слово, часть слова или знак в представлении модели.

<a id="monitoring"></a>
### Очередь, вычисления и память

Дашборд **Service performance**: namespace `hardfest-rtx`,
Service `rtx-gemma-base`, интервал времени проверяемых запросов.
У A разрешены две активные последовательности: восемь клиентов
не означают восемь одновременно исполняемых запросов.

| Показатель | Что он позволяет увидеть |
| --- | --- |
| Running / Waiting | Сколько запросов выполняется и сколько стоит в очереди |
| Вычислительная утилизация GPU | Когда GPU занята вычислениями и когда простаивает |
| Занятость памяти GPU | Сколько памяти выделено; это не процент вычислительной загрузки |
| Пауза до ответа и темп текста | Как ограничения сказываются на запросе пользователя |

Очередь сама по себе не объясняет причину ожидания. Заполненная память
не доказывает загрузку вычислений, а высокая утилизация GPU — достаточную
скорость ответа. Проверка разделяется на три группы ограничений:

| Ограничение | Что предстоит выяснить |
| --- | --- |
| Память | Сколько занимают веса и история запросов; что можно переиспользовать |
| Вычисления | Что происходит при обработке входа и генерации продолжения |
| Размещение на железе | Нужна ли модели вся карта, часть карты или несколько GPU |

Это три группы ограничений GPU в данном разборе, не полный перечень причин
задержки. Недостаток CPU, сеть и очередь шлюза также могут ограничивать ответ.

### Контрольная нагрузка

Для сравнения настроек используется отдельная серия без фоновых вопросов:
**8 запросов, по 2048 входных и 128 выходных токенов, параллельность 2**.
Нагрузка одинакова для Base и последующих ручных профилей B.
128 — лимит замера, не обычного ответа в чате.

<details>
<summary>Команда одинакового замера для A, Cache и Tune</summary>

Помимо running/waiting в результат включаются:

| Метрика | Что измеряет |
| --- | --- |
| TTFT (Time to First Token) | Время до первого токена |
| ITL (Inter-Token Latency) | Паузу между токенами |
| TPOT (Time per Output Token) | Среднее время на выходной токен после первого |

Вычислительная загрузка GPU и занятость её памяти — разные показатели:
заполненная память ещё не означает непрерывные вычисления.

Команды выполняются в частном `k8s-config`. `GPU_CONTEXT`, `RTX_DIR`
и `NS=hardfest-rtx` заданы при [подготовке](docs/SETUP.md#rtx).
Каждой серии соответствует отдельное имя файла результата.

```bash
export SERVICE=rtx-gemma-base SERIES=base-4k-1
# B1: export SERVICE=rtx-gemma-cache SERIES=cache-4k-1
# B2: export SERVICE=rtx-gemma-tune SERIES=tune-4k-1
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec "deployment/$SERVICE" -c vllm -- \
  vllm bench serve --backend vllm \
    --base-url "http://$SERVICE.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model "$SERVICE" \
    --tokenizer /data/modelcache/models/rtx-gemma-e2b \
    --dataset-name random --seed 42 \
    --random-input-len 2048 --random-output-len 128 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 2 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$SERIES.txt"
```

Успешная серия содержит в JSON: completed=8, failed=0,
total_input_tokens=16384, total_output_tokens=1024.
Код завершения команды не заменяет проверку этих полей.

Первый проход и повтор с тем же seed учитываются отдельно: повтор прогревает
кеш. Клиент внутри Pod делит с движком CPU (Central Processing Unit —
центральный процессор), поэтому это не независимый нагрузочный стенд.

</details>

A работает на **vLLM 0.31**, окне **4K** и без оптимизаций.
vLLM — движок обслуживания модели; окно ограничивает сумму входа и ответа.

> [!IMPORTANT]
> Для Gemma E2B отключение chunked prefill официально не поддерживается.
> A — контрольный опыт на 4K, не рекомендуемый рабочий профиль.
> Длинный контекст требует профиля B с chunked prefill.

<details>
<summary>Ресурсы Base и диагностика отсутствующих метрик</summary>

Argo CD Application `rtx-gemma-base` содержит применённый commit,
[values A](values/rtx/gemma-base.yaml) и Deployment на одной RTX.

| Объект | Назначение |
| --- | --- |
| Pod | Контейнер с vLLM |
| Deployment | Поддерживает нужное число Pod |
| Helm values | Настройки, из которых чарт собирает объекты Kubernetes |

**GitOps** — настройки хранятся в Git, Argo CD применяет выбранную ревизию.
Повторно запускать A не нужно. У неё выключены prefix cache, chunked prefill,
CUDA graphs, KV-offload и speculative decoding. Искусственной задержки нет.

Пустой график не означает нулевую нагрузку: возможны неверные Service,
интервал или источник сбора метрик. Мониторинг должен собирать метрики ручного
runtime. У RTX нет NVLink-метрик.

Для сравнения отключены fallback — автоматическая подмена модели при ошибке —
и кеш готовых ответов шлюза. Иначе запрос может попасть не в выбранный экземпляр.

</details>

Первое ограничение — память: свободные вычислительные ресурсы не помогут,
если для следующего запроса не хватает места.

<a id="memory"></a>
## 2. Память: веса и KV-кеш

При запуске модель занимает память весами — параметрами, полученными
при обучении. Эти веса общие для всех запросов экземпляра. Истории чатов,
напротив, различаются и растут по мере поступления и генерации токенов.

**KV cache (Key/Value cache)** хранит ключи и значения уже обработанных
токенов. Благодаря ему модель продолжает историю, не пересчитывая прошлые K/V.
Чем длиннее история, тем больше памяти нужно.

| Что занимает память GPU | Как меняется |
| --- | --- |
| Веса | Общие для всех запросов экземпляра |
| KV-кеш | Зависит от длины и числа историй |
| Рабочие буферы и резервы | Зависят от движка и настроек |

VRAM (Video Random Access Memory) — память видеокарты.
RAM (Random Access Memory) — оперативная память сервера.

Грубая оценка весов: `W ≈ число параметров × байт на параметр`.
Для BF16 это два байта, но фактический runtime дополнительно выделяет
буферы и может загружать не все части checkpoint. Для вместимости нужен
замер занятой VRAM, а не только размер файлов.

### Объём KV для 64K и 128K

У Gemma E2B три слоя хранят всю историю, двенадцать — последние 512 токенов.
Остальные переиспользуют KV более ранних слоёв. Поэтому весь кеш нельзя
считать как «все слои × вся история».

Для истории от 512 токенов полезный KV равен:
**`KV ≈ 6 KiB × S + 6 MiB` в BF16**, где `S` — вход **плюс** ответ.
Первая часть растёт вместе с историей, вторая хранит только недавние токены.

BF16 (Brain Floating Point 16) требует 2 байта на элемент;
FP8 (Floating Point 8) — 1, поэтому полезный KV вдвое меньше.
Формат KV выбирается отдельно от формата весов.

| Вся история | Одна история BF16 / FP8 | Восемь независимых, BF16 / FP8 |
| --- | ---: | ---: |
| 64K | 390 / 195 MiB | 3120 / 1560 MiB |
| 128K | 774 / 387 MiB | 6192 / 3096 MiB |

Для 128K: `122880 входных + 8192 генерации = 131072 токена`.
Шаблон чата входит во вход, reasoning — в выход.

**Это полезный KV основной модели, не вся занятая память.**
Профиль Gemma допускает две последовательности; восемь в таблице — расчёт,
не обещание такого запуска. Максимум закреплённой E2B — 128K;
контекст 256K этой конфигурацией не поддерживается.

При росте с 64K до 128K удваивается только полная история.
Локальная часть остаётся 6 MiB, поэтому итог — **774, а не 780 MiB**.

<details>
<summary>Вывод формулы, архитектура E2B и проверка через awk</summary>

**Attention** связывает текущий токен с частями контекста: запрос Q сравнивается
с ключами K, по результату смешиваются значения V. Q нужен текущему шагу,
K/V сохраняются. Головы — несколько таких наборов вычислений внутри слоя.

В **GQA (Grouped-Query Attention)** несколько query-голов используют общие K/V.
Для памяти нужны именно KV-головы, не число query-голов.

![От двух векторов одного токена к KV нескольких независимых историй](assets/25-kv-derivation.svg)

Для одинаковых full-attention слоёв:

```text
KV = 2 × b × L × Hkv × D × S × N
```

| Символ | Значение |
| --- | --- |
| `2` | K и V |
| `b` | Байт на элемент |
| `L` | Слои с собственным KV |
| `Hkv`, `D` | KV-головы и размерность головы |
| `S` | Длина всей истории |
| `N` | Число независимых историй; для восьми `N=8` |

При разных длинах вместо `S × N` используется `S₁ + … + Sₙ`.
Общий переиспользуемый префикс нельзя автоматически умножать на восемь:
учитываются его уникальные блоки и отдельные продолжения.

В [закреплённом config.json E2B](https://huggingface.co/google/gemma-4-E2B-it/blob/3e22461f65e89153144f8adb70e3b8c2cc9845a7/config.json)
35 слоёв, `num_kv_shared_layers=20`. Последние 20 переиспользуют KV первых;
собственные K/V создают 15 слоёв:

| Тип | Слоёв | KV-голов | Размерность | Длина |
| --- | ---: | ---: | ---: | --- |
| Full attention | 3 | 1 | 512 | `S` |
| Sliding attention | 12 | 1 | 256 | `min(S,512)` |

Полная формула учитывает оба типа слоёв:

```text
KV(S) = 2 × b × [3 × 512 × S + 12 × 256 × min(S, 512)] байт
```

![Gemma E2B: для 128K full занимает 768 MiB, sliding — 6 MiB](assets/26-rtx-kv.svg)

Первый множитель `2` — K и V, `b` — байт на элемент.
`512` после тройки — размерность full-головы, `256` — sliding-головы;
`min(S,512)` ограничивает историю локального слоя последними 512 токенами.

Это межслойное разделение внутри модели, не prefix cache между запросами.
[Реализация sharing в vLLM](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/gemma4.py#L473).

В BF16 один токен full-слоя занимает `2 × 1 × 512 × 2 = 2048 байт`.
Три слоя дают 6 KiB на токен; `6 KiB × 131072 = 768 MiB`.

Один sliding-слой требует `2 × 1 × 256 × 2 = 1 KiB` на токен.
Двенадцать слоёв на последних 512 токенах — 6 MiB.
Итого 768 + 6 = **774 MiB BF16**, или **387 MiB FP8**.

```bash
awk -v S=131072 -v N=1 -v b=2 'BEGIN {
  W = S < 512 ? S : 512
  full = 2*b*3*1*512*S / 1048576
  local = 2*b*12*1*256*W / 1048576
  printf "Full %.0f + sliding %.0f = %.0f MiB/history; %d histories = %.0f MiB\n", full, local, full+local, N, N*(full+local)
}'
```

Для 64K значение `S=65536`: full — 384 MiB, sliding — прежние 6 MiB.
Именно поэтому удваивается не весь кеш.

| Независимые истории 128K | BF16 | FP8 |
| --- | ---: | ---: |
| 1 | 774 MiB | 387 MiB |
| 2 | 1548 MiB | 774 MiB |
| 4 | 3096 MiB | 1548 MiB |
| 8 | 6192 MiB | 3096 MiB |

Для контрольных 4K: full 24 MiB + sliding 6 MiB = 30 MiB BF16
на историю, 60 MiB на две; FP8 — 15 и 30 MiB.

</details>

После весов и рабочих буферов запросам доступна только часть VRAM — KV-пул.
Размер пула указан в логах runtime, его занятость — на графике.
RAM не увеличивает VRAM, доступную вычислениям.

<details>
<summary>Почему nvidia-smi показывает больше памяти, чем формула KV</summary>

Свободный пул для KV приблизительно равен `Kpool ≈ G × u − W − R`:
память GPU `G`, разрешённая доля `u`, загруженные веса `W`, прочие резервы `R`.

![Бюджет RTX: веса и рабочие данные на GPU, отдельный кеш в RAM](assets/22-rtx-memory.svg)

Полный BF16 checkpoint E2B — файлы весов — занимает около 9,54 GiB.
Кроме весов нужны пул KV, промежуточные вычисления, графы и память assistant.

Кеш выделяется блоками. При условных 16 токенах на блок история из 35 токенов
занимает три блока; реальные размеры и группы attention зависят от runtime.
Совпавшие полные блоки можно переиспользовать, а после завершения запроса —
сохранить до вытеснения.

Если в GPU-пуле осталось 1 GiB, две истории FP8 по 128K требуют 774 MiB,
а три — 1161 MiB и уже не помещаются. Это арифметический пример:
округление и организация пула дополнительно влияют на вместимость.

Размер выделенного пула может не меняться при новом запросе,
хотя число занятых блоков растёт.
[Команды сверки формулы, логов и графиков](docs/MEMORY_BUDGET.md#verify-kv).

</details>

<a id="ram"></a>
### Профиль B Cache: prefix caching и RAM-offload

**Prefix caching** переиспользует KV одинакового начала запросов.
Нужны одинаковые **токены**, не просто похожий смысл. Готовый ответ не кешируется.

![Общий документ обрабатывается один раз, вопросы продолжаются отдельно](assets/14-prefix.svg)

**KV-offload** сохраняет блоки кеша в RAM сервера и возвращает при повторе.
Веса остаются на GPU. Возврат выгоден, если передать блоки дешевле,
чем заново обработать вход.

Отдельный `rtx-gemma-cache` предназначен для второй карты.
[Профиль Cache](values/rtx/gemma-cache.yaml): окно 4K, две последовательности,
prefix cache, FP8 KV и 4 GiB CPU KV; остальные оптимизации пока выключены.

**Запуск требует запаса RAM для обеих Gemma.**
A остаётся на первой карте только при достаточной памяти узла.

<details>
<summary>Включение B Cache через Git и Argo CD</summary>

Для запуска в `$RTX_DIR/values/gemma-cache.yaml` задаётся `replicaCount: 1`.

```bash
set -o pipefail
helm template rtx-gemma-cache "$RTX_DIR/charts/vllm-runtime" -n "$NS" \
  -f "$RTX_DIR/values/gemma-cache.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После успешной проверки:

```bash
git add -- "$RTX_DIR/values/gemma-cache.yaml"
git diff --cached --check
git diff --cached
git commit -S -s -m "Start RTX Gemma with prefix cache and RAM KV"
git push
git rev-parse HEAD
```

В Argo CD diff приложения `rtx-gemma-cache` должен соответствовать
подготовленному изменению. **Sync** применяется к этому SHA без общего Prune.
Маршрут `Gemma B — Cache` в WebUI включается после Ready и успешного ответа
API (Application Programming Interface — программный интерфейс модели).

Для следующих профилей порядок тот же: полный профиль → render →
commit/push → адресный Sync. Прямые `helm upgrade` и `kubectl scale`
поверх Argo не используются.

</details>

Проверка prefix cache использует два новых чата с **одинаковым текстом**
примерно на 2000 токенов в начале сообщения. Различается только вопрос
**в конце**. Текст передаётся целиком, не вложением и не через базу знаний.

Эффект оценивается по **TTFT (Time to First Token)** — времени до первого
токена — и prefix-cache hits на Service `rtx-gemma-cache`.
Изменение начала текста даёт контрольный случай: совпадение префикса
пропадает, и соответствующая часть входа обрабатывается заново.

Общий сохранённый префикс занимает общие блоки, а не восемь обязательных копий.
Таблица независимых историй выше относится к запросам без такого разделения.

Для RAM есть отдельное доказательство: **рост CPU→GPU bytes и
external-prefix hits** после вытеснения префикса из GPU. Только GPU→CPU
показывает запись, но ещё не использование сохранённого кеша.

<details>
<summary>Проверка возврата кеша из RAM</summary>

![Блоки KV сохраняются в RAM и восстанавливаются на GPU](assets/05-kv-ram.svg)

Исходный префикс повторяется после вытеснения из GPU-кеша другими префиксами.
Если обычного пула хватает на всё, диагностическая проверка использует пул
256 MiB с последующим восстановлением штатного размера.
Её результаты учитываются отдельно от A/B.

Цена восстановления приближённо равна `объём / эффективная полоса`.
387 MiB FP8 для истории 128K нужно передать и синхронизировать.
В расчёт входит измеренная скорость PCIe, не паспортная.

Нужный backend определяется по конфигурации и `/metrics`.
У OffloadingConnector нужны CPU→GPU bytes и external-prefix hits,
у Simple CPU — `vllm:simple_kv_offload_load_blocks_total`.
Отсутствие счётчика другого backend не означает отказ offload.

</details>

После включения Cache повторяется контрольная серия с теми же входами,
числом запросов и параллельностью. Сравниваются TTFT, очередь, занятость KV
и счётчики повторного использования. Изменение очереди имеет смысл только
при одинаковой нагрузке; выигрыш повторного префикса не означает ускорение
любого нового запроса.

Кеш устраняет часть повторной обработки знакомого входа. Новый документ
и генерация ответа всё ещё требуют вычислений — это следующее ограничение.

<a id="speculation"></a>
## 3. Вычисления: prefill и decode

Обработка нового входа и генерация ответа по-разному используют GPU.
Их полезно разделять: настройка, уменьшающая ожидание первого токена,
не обязательно ускоряет последующие.

<a id="latency"></a>
### Состав времени ответа

![Время ответа: очередь, обработка входа и генерация продолжения](assets/02-latency.svg)

```text
Tответа ≈ Tочереди + Tprefill + Tdecode + Tпрочее
```

| Часть времени | Что происходит |
| --- | --- |
| Очередь | Запрос ждёт свободного места для выполнения |
| **Prefill** | Модель обрабатывает вход: вопрос и историю чата |
| **Decode** | Модель генерирует продолжение токен за токеном |
| Прочее | Токенизация, сеть, шлюз |

Reasoning, если модель его выдаёт, тоже генерируется на стадии decode:
первый видимый ответ может появиться позже первого токена движка.

Prefill обрабатывает много входных токенов параллельно. Decode продолжает
каждую историю последовательно: следующий токен зависит от предыдущих.
При нескольких активных запросах движок объединяет их шаги, но длинная
обработка нового входа может задерживать продолжение уже начатых ответов.

До остановки Cache снимается результат смешанной нагрузки:
длинный вход и короткий запрос, отправленный до завершения первого.
Вход вместе с ответом каждого запроса должен помещаться в 4K.

Тексты, параметры генерации и интервал отправки фиксируются для повторения
на Tune. Показатели сравнения — задержка короткого запроса, очередь
и **ITL (Inter-Token Latency)**, пауза между выходными токенами.

### Chunked prefill и speculative decoding

**Chunked prefill** обрабатывает длинный вход порциями.
Между ними планировщик может продолжать генерацию уже начатых ответов.

![Длинный prefill выполняется порциями между шагами decode](assets/06-scheduler.svg)

В **speculative decoding** маленькая draft-модель предлагает токены,
основная модель проверяет их. У Gemma это совместимый
**assistant**, не произвольная маленькая модель.

![Assistant предлагает продолжение, основная Gemma его проверяет](assets/07-speculation.svg)

В профиле assistant предлагает один токен за цикл методом
**MTP (Multi-Token Prediction)**. Счётчики отражают предложенные и принятые токены,
ITL — задержку продолжения. Высокая доля принятия сама по себе не гарантирует
ускорения.

### Замена Cache на Tune

После завершения текущих запросов Cache останавливается.
На освободившейся карте запускается `Gemma B — Tune`; A остаётся прежней.

**Два профиля B одновременно не работают.** Tune сохраняет настройки Cache
и добавляет chunked prefill, assistant и CUDA graphs — переиспользование
подготовленной последовательности операций GPU. CUDA (Compute Unified Device
Architecture) — вычислительная платформа NVIDIA.

На Tune повторяются сохранённая смешанная нагрузка и контрольная серия
без фоновых вопросов. Сравниваются ожидание короткого запроса и скорость
продолжения. **Это сравнение наборов настроек, не изолированный эффект
draft-модели.**

<details>
<summary>Профиль Tune, переключение приложений и первый прогрев</summary>

1. Маршрут Cache скрывается в WebUI; текущие запросы завершаются.
2. Изменение в Git и Sync останавливают `rtx-gemma-cache`.
3. После освобождения GPU включается отдельный `rtx-gemma-tune`.
4. Успешный ответ подтверждает готовность маршрута `Gemma B — Tune`.

| Параметр | Значение |
| --- | ---: |
| `max-model-len` — вся история | 4096 |
| `max-num-seqs` — активные истории | 2 |
| `max-num-batched-tokens` — бюджет одного шага | 512 |
| CUDA graphs, capture size | 4 |
| CPU KV | 4 GiB |

В шаге на 512 токенов два обычных decode-запроса могут занять по токену,
остаток — часть prefill. Это схема без деталей speculation,
не фиксированное распределение каждого шага.

| Файл в частном Git | Изменение | Application |
| --- | --- | --- |
| `gemma-cache.yaml` | `replicaCount: 0` | `rtx-gemma-cache` |
| После освобождения claim: `gemma-spec.yaml` | `replicaCount: 1` | `rtx-gemma-tune` |

Каждое изменение проходит render, commit/push и Sync.
Tune читает `../../values/gemma-spec.yaml`; приложения не управляют одним workload.

При первом старте компилируются модель и assistant, захватываются графы.
**NodeCache** хранит локальные веса, не результаты компиляции из временного
каталога Pod. Готовность — Ready и успешный запрос, не окончание чтения файлов.

</details>

<a id="long-context"></a>
### Контекст 128K

После короткого A/B окно Tune увеличивается до **131 072**.
Две последовательности, бюджет prefill 512, FP8 KV, 4 GiB RAM KV,
assistant и graphs сохраняются.

Соответствующий лимит WebUI — `max_tokens: 8192`:
большое серверное окно само по себе не удлиняет ответ чата.
Вход, шаблон и допустимый выход должны вместе помещаться в окно.

![Короткий контроль и отдельные проверки контекста 64K и 128K](assets/27-rtx-long-context.svg)

Проверка включает по одному входу **57 344**, затем **122 880** токенов,
каждый с выходом 512. Окно сервера всё время 128K.
Фиксируются TTFT, занятость KV, память, ошибки и перезапуски.

**Отказ A принять такой вход означает её лимит 4K**, а не доказанную нехватку
VRAM. Короткий замер сравнивает скорость, длинные запросы — вместимость.

<details>
<summary>Настройка окна Tune и команды длинных запросов</summary>

Изменяемые поля полного `values/gemma-spec.yaml`:

```yaml
# Фрагмент существующего values; остальные поля сохраняются.
vllm:
  max-model-len: 131072
  gpu-memory-utilization: 0.95
  max-num-seqs: 2
  enable-chunked-prefill: true
  max-num-batched-tokens: 512
```

Изменение проходит render, commit/push и Sync `rtx-gemma-tune`.
После Ready фактические окно, KV-пул и assistant должны соответствовать
профилю. Значение `0.95` взято из успешного длинного прогона:
при `0.90` первоначальная проверка ёмкости KV не прошла.

Пресет `Gemma B — Tune` также получает описание окна 128K
и `max_tokens: 8192`.

```bash
export INPUT_TOKENS=57344
export RUN_NAME=gemma-64k
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec deployment/rtx-gemma-tune -c vllm -- \
  vllm bench serve --backend vllm \
    --base-url "http://rtx-gemma-tune.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model rtx-gemma-tune \
    --tokenizer /data/modelcache/models/rtx-gemma-e2b \
    --dataset-name random --seed 73 \
    --random-input-len "$INPUT_TOKENS" --random-output-len 512 --random-range-ratio 0 \
    --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$RUN_NAME.txt"
```

Критерии первой серии: completed=1, failed=0, **57 344 + 512** токенов.
Для второй задаются `INPUT_TOKENS=122880`, `RUN_NAME=gemma-128k`;
ожидаемое число токенов — **122 880 + 512**.
Длину подтверждают поля JSON, не размер файла.

</details>

Отдельная проверка извлечения факта использует **полный текст** в сообщении,
контрольную запись в середине и вопрос в конце. Критерии — точный ответ
и число входных токенов в журнале шлюза. Большое вложение само по себе
длинный вход не доказывает.

<details>
<summary>Текст с контрольным фактом и критерии ответа</summary>

Команда создаёт синтетический текст без чужих документов:

```bash
mkdir -p results/rtx
awk 'BEGIN {
  for (i=0; i<4681; i++) {
    if (i==2340)
      printf "SPECIAL RECORD: The secret verification phrase for project Orion is COPPER-ORCHID-742. "
    else
      printf "Record %d: This routine report describes a successful scheduled health check. There are no special instructions in this record. ", i
  }
  printf "Question: What is the exact verification phrase for project Orion? Reply with only the phrase."
}' > results/rtx/long-context.txt
```

В новый чат Tune передаётся всё содержимое файла, не вложение базы знаний.
Для поиска одной фразы достаточно `max_tokens: 128`; ожидаемый ответ —
`COPPER-ORCHID-742`. Вход после шаблона вместе с лимитом выхода
не должен превышать 131 072; длина определяется токенизатором.

На время проверки у тестового пользователя выключены автоматические
заголовки, теги и подсказки продолжения: они могут повторить большой вход.
Обычный чат сохраняет лимит до 8192 выходных токенов, включая reasoning.

</details>

### Разделение стадий и маршрутизация

**Prefill/decode disaggregation** размещает обработку входа и генерацию
на разных исполнителях, передавая между ними KV. Это позволяет настраивать
ресурсы стадий отдельно, но добавляет передачу данных и координацию.
[Disaggregated prefilling в vLLM](https://docs.vllm.ai/en/v0.31.0/features/disagg_prefill/).

**Cache-aware routing** выбирает реплику с подходящим кешем и доступной
ёмкостью, уменьшая повторный расчёт знакомого контекста.
[KV-aware routing в NVIDIA Dynamo](https://docs.dynamo.nvidia.com/dynamo/knowledge-base/concepts/system-architecture/kv-aware-routing).

Эти механизмы здесь не разворачиваются. Настроенные ручные профили решают
задачу внутри одного экземпляра; отдельно остаётся выбор того, какую долю
железа этому экземпляру выделить.

<a id="placement"></a>
## 4. Размещение моделей на GPU

Для большой Gemma выделяется целая RTX. Небольшие модели могут оставлять
большую часть такой карты свободной, хотя ресурс уже занят их Pod.
Здесь важны не параметры генерации, а способ выдачи GPU приложению.

### Device Plugin и DRA

**Device Plugin** сообщает Kubernetes о доступных устройствах.
Приложение запрашивает целое число extended resources, например
`nvidia.com/gpu: 1`. Такой запрос задаёт количество, но не выражает
выбор устройства по набору его атрибутов. Это ограничение стандартного
интерфейса, не запрет на MIG или sharing в реализации плагина.
[Device plugins в Kubernetes](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/).

**DRA (Dynamic Resource Allocation)** отделяет заявку на устройство
от Pod: **ResourceClaim** описывает запрос, **DeviceClass** — класс
подходящих устройств. Поддерживаются выбор по атрибутам и vendor-настройки
для workload. Драйвер подготавливает выделенное устройство.
[DRA в Kubernetes](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/).

Это не автоматическая нарезка любой GPU: результат зависит от возможностей
карты и драйвера. В этом стенде DRA используется для выдачи устройств,
а MIG и MPS — для их разделения и совместного использования.
[Авторский разбор device plugin и DRA](https://habr.com/ru/companies/flant/articles/1020276/).

### MIG и MPS на A30

**MIG (Multi-Instance GPU)** делит поддерживаемую GPU на аппаратные части.
**MPS (Multi-Process Service)** позволяет процессам совместно использовать
вычисления. Целевая конфигурация: эмбеддер и реранкер через MPS в одной
части MIG, Whisper — в другой.

![Эмбеддер и реранкер разделяют первую MIG-часть A30, Whisper занимает вторую](assets/08-mig-mps.svg)

MIG даёт аппаратные границы памяти и вычислительных ресурсов.
MPS внутри такой части позволяет нескольким процессам использовать вычисления
совместно, но не создаёт новую аппаратную границу памяти.

Модели поиска по документам и распознавания речи размещаются
в **соседнем кластере A30**. Консоль и источник метрик этого этапа
должны относиться к нему, а не к кластеру RTX.

| Сервис | Зачем нужен |
| --- | --- |
| Qwen3 Embedding 4B W4A16 | Превращает текст в вектор для поиска по смыслу |
| Qwen3 Reranker 4B W4A16 | Пересортировывает найденные фрагменты по полезности |
| Whisper large-v3 | Преобразует речь в текст — STT (Speech-to-Text) |

W4A16 — 4-битные веса и 16-битные активации, промежуточные значения вычислений.
Это не точность KV-кеша.

**Динамическое создание MIG требует свободной геометрии,
поддержки драйвера и заранее включённого MIG mode.**
Изменение режима и вытеснение чужих workloads не входят в процедуру.
Если части уже созданы, выдача готовых устройств не доказывает
динамическое изменение геометрии.

Проверка размещения ниже относится к трём уже работающим сервисам.
У эмбеддера и реранкера должен быть один MIG UUID — идентификатор части,
у Whisper другой. Готовая геометрия не подтверждает её динамическое создание:
для этого нужны снимки до и после применения заказов.

[Создание сервисов и сравнение до/после](#a30-orders) описаны после
механизма автоматического запуска. Здесь проверяется фактическое размещение.

<details>
<summary>Проверка геометрии A30 через nvidia-smi</summary>

Команды чтения состояния на ноде:

```bash
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

Статус Ready дополняется проверкой запросами ниже.

Time-slicing чередует доступ, но не создаёт аппаратную границу памяти.
HAMi и Volcano предлагают другие механизмы планирования и sharing;
выбор DRA здесь нужен для проверки цепочки «заявка → устройство»,
а не для утверждения превосходства над ними.
[Различия и источники](docs/SOURCES.md#hami-и-volcano).

</details>

### Проверка поиска и распознавания речи

**RAG (Retrieval-Augmented Generation)** — поиск подходящих фрагментов
перед генерацией ответа. Эмбеддер помогает найти их, реранкер выбирает
полезные, модель чата отвечает с этим контекстом.

![Документ проходит индексирование, вопрос — поиск и реранкер, затем модель чата](assets/16-rag.svg)

Контрольный документ содержит факт: «В проекте “Липа” окно обслуживания
начинается во вторник в 16:40». Документ добавляется в базу знаний Open WebUI;
после индексации эта база подключается к чату. Один и тот же вопрос о времени
проверяется без подключённой базы и с ней.

Работу поиска подтверждают **точный факт и ссылка на источник**,
а также обращения к эмбеддеру, реранкеру и модели на графиках.
Для голосового варианта дополнительно проверяются распознанный текст
и запрос Whisper.

Без документа модель может угадать — это ещё не работающий поиск.
После смены модели чата пользователь и база знаний должны сохраниться.

Параметры модели, размер кеша, режим совместного использования и ресурсы
узла связаны между собой. Ручная сборка этих настроек для каждого сервиса
становится отдельной задачей — её можно передать автоматизации.

<a id="platform"></a>
## 5. Автоматический запуск через AI Inference

После ручной настройки известны рабочие параметры Gemma и способы
размещения разных моделей. Переносить их по памяти в каждый новый Deployment
не требуется: **InferenceService** описывает заказ на запуск модели.

**ai-models** ведёт каталог и доставляет закреплённые веса, в том числе
для ручного запуска. **AI Inference** связывает модель с требованиями,
оборудованием и рецептом — проверенным набором параметров движка.

| Вход планировщика AI Inference | Для чего нужен |
| --- | --- |
| Модель и её архитектура | Определить совместимость и требования к памяти |
| Требования заказа | Выбрать стратегию, окно и ограничения запуска |
| Доступный класс оборудования | Учесть объём VRAM, число GPU и поддерживаемые возможности |
| Рецепты | Получить конкретные параметры runtime для этих условий |

Результат — план запуска. Затем Kubernetes выделяет конкретное устройство
через DRA и создаёт Pod. Совместимый план не заменяет проверку фактических
параметров, Ready и ответа модели.

![Модель из каталога, заказ InferenceService, план ресурсов и работающий сервис](assets/23-rtx-platform.svg)

Условия запуска: Gemma **и assistant** доставлены, доступен рецепт
RTX 5060 Ti / vLLM 0.31 / Throughput: **128K, FP8 KV, 4 GiB RAM KV,
две последовательности и assistant**. Throughput — приоритет пропускной способности.

В интерфейсе путь начинается с **Каталога моделей** проекта `hardfest-rtx`:
у Gemma должен быть статус «Скачана». Кнопка **«Запустить инференс»** ведёт
к созданию заказа. Для него выбираются доступные стратегия и класс ресурсов;
в данном случае они должны приводить к указанному длинному рецепту.

В этом руководстве тот же заказ хранится в Git и применяется Argo CD,
а не создаётся второй раз поверх GitOps. После применения в разделе
**Сервисы инференса** появляется `rtx-gemma-platform`: сначала рассчитанный
план и подготовка, затем работающий сервис. Статус готовности дополняется
проверкой ответа модели.

**Узлу требуется RAM для двух экземпляров.** Платформенная Gemma заменяет
Base после завершения её запросов и освобождения GPU.
Ручная B остаётся для сравнения.

Заказ, рассчитанный план и Pod доступны в консоли:
**GPU-кластер → hardfest-rtx → AI-модели**. Их параметры должны
соответствовать расчёту и ручной B. Фактическое окно 4096 вместо 128K
означает необходимость исправить выбор рецепта.

После успешного ответа API (Application Programming Interface — программный
интерфейс модели) маршрут становится доступен в чате как **Gemma A — DP**.
DP — подпись платформенного запуска, не Data Parallelism.
Одинаковые короткие и длинные запросы к A и B позволяют сравнить задержки,
ошибки, assistant и кеши. Цель — воспроизвести подобранную конфигурацию
того же движка. Время от заказа до Ready измеряется отдельно: готовый
рецепт сокращает ручные настройки, но не доказывает ускорение загрузки.

Ручная B и платформенная A должны присутствовать в одном фильтре дашборда.
Иначе сравнение профилей теряет половину данных.

<summary>Заказ Gemma и маршрут WebUI</summary>

Маршрут Base скрывается до остановки ручной A через GitOps.
Текущие запросы должны завершиться, GPU — освободиться.

В `$RTX_DIR/platform/rtx-gemma.yaml` задаётся `order.enabled: true`.

| Маршрут | Service | Имя модели в runtime | WebUI |
| --- | --- | --- | --- |
| `rtx-gemma-platform` | `rtx-gemma-platform:80` | `rtx-gemma-e2b` | `Gemma A — DP` |

Подготовленный маршрут включается вместо остановленной Base.
Пользователь и личный ключ сохраняются. Ревизии Model и assistant

<details>
<summary>Проверка API платформенной Gemma и Qwen</summary>

В отдельном терминале:

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" port-forward svc/rtx-gemma-platform 18005:80
```

При аутентификации Token ключ сервиса вводится из менеджера секретов
через скрытый ввод в основном терминале. Ключ не попадает в Git
или аргументы командной строки.

```bash

IFS= read -r -s MODEL_API_KEY
curl --fail --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  http://127.0.0.1:18005/v1/models
curl --fail-with-body --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  -H 'Content-Type: application/json' http://127.0.0.1:18005/v1/chat/completions \
  -d '{"model":"rtx-gemma-e2b","max_tokens":512,"temperature":0,"messages":[{"role":"user","content":"Зачем нужен KV-кеш?"}]}'
unset MODEL_API_KEY
```

Для API без Token ввод ключа и обе строки `--header` отсутствуют.
Политика доступа ради проверки не меняется.

Для последующей проверки Qwen текущий port-forward завершается.
Аналогичный вызов использует `svc/rtx-qwen35-tp2`, его ключ
и `"model":"rtx-qwen35-9b"`. Критерий — содержательный ответ,
не только HTTP 200.

Команда ручного A/B не переносится буквально на платформенный StatefulSet.
Для строгого замера нужен общий CPU-клиент с нужной авторизацией.

</details>

<a id="a30-orders"></a>
<details>
<summary>Создание трёх сервисов A30 и проверка изменения геометрии</summary>

[Конфигурация размещения](#placement) использует тот же InferenceService,
что и автоматическая Gemma. Это не ручной запуск runtime.
Модели заранее импортируются через ai-models в namespace **кластера A30**.

Это процедура первоначальной подготовки или повторного развёртывания:
к началу основного разбора три сервиса A30 уже должны отвечать.
Повторный Sync без изменения конфигурации не означает создание новых MIG-частей.

Для изменения геометрии требуются свободные ресурсы, поддержка драйвера
и уже включённый MIG mode. Режим и чужие workloads не изменяются.

1. До применения заказов сохраняется вывод `nvidia-smi`
   из [проверки A30](#placement).
2. В `platform/embedding.yaml`, `reranker.yaml`, `whisper.yaml` задаётся
   `order.enabled: true`; render проверяется до commit/push.
3. Изменения применяются адресным Sync приложений `hardfest-embedding-platform`,
   `hardfest-reranker-platform` и `hardfest-whisper-platform`;
   destination — кластер A30.
4. После Ready всех трёх InferenceService повторяются снимок геометрии
   и проверки поиска и речи.

Разница двух снимков подтверждает изменение геометрии только при фактическом
создании новых частей. Выдача уже существовавших MIG-устройств — другой случай.

</details>

### Когда нужно больше оборудования

Сначала оценивается результат настройки имеющихся GPU: очередь, задержки,
пропускная способность, вместимость KV и занятость карт. Если требуемая
нагрузка всё ещё не укладывается в эти ограничения, измерения дают основание
для расширения. Сам по себе высокий процент GPU utilization не объясняет,
нужны ли дополнительные карты.

Следующая часть связывает запуски с пользовательским доступом и показывает
случай, когда веса одной модели действительно требуют двух GPU.

## 6. Шлюз и модель на двух GPU

Готовый runtime решает задачу вычисления ответа. Шлюз **ai-mcp-gateway**
с Bifrost добавляет маршруты моделей, персональный доступ и учёт запросов.
Open WebUI обращается к нему от имени пользователя, а не напрямую
к каждому новому экземпляру vLLM.

### Персональный доступ и учёт токенов

Журнал Bifrost содержит модель, время, входные и выходные токены,
расчётную стоимость каждого запроса.

**VK (Virtual Key)** — личный ключ шлюза, связывающий запрос с пользователем
и разрешёнными моделями. У двух одобренных аккаунтов должны быть разные VK.
Привязку к пользователю подтверждает личный ключ,
не ключ подключения шлюза к vLLM.
Смена Gemma на Qwen не создаёт новый аккаунт и не обнуляет расход.

| Демонстрационная политика | Значение |
| --- | --- |
| Выдача VK | После одобрения аккаунта |
| Вход / выход | $10 / $20 за миллион токенов |
| Бюджет VK | $500, период сброса 24 часа |

**Деньги не списываются**: тарифы из [примера политики](examples/webui-access.yaml)
нужны для учебного учёта, не расчёта себестоимости GPU.
Для 122 880 входных и 8192 выходных токенов:

```text
122880 × 10 / 1000000 + 8192 × 20 / 1000000 = $1,39264
```

На HA-шлюзе (High Availability — несколько реплик для отказоустойчивости)
есть [ограничение общего счётчика](docs/CHAT_AND_ACCESS.md#проверить-выдачу-и-отзыв):
строгий общий лимит расходов $500 этим опытом не подтверждён.

<details>
<summary>Какие запросы относятся к пользователю и что доступно администратору</summary>

Стоимость считают по фактическим токенам, не максимальному окну.
Фоновые чат-запросы WebUI, например заголовок, тоже расходуют бюджет пользователя.

Индексация, reranking и голос используют служебные подключения:
личный VK чата не персонализирует эти операции автоматически.

Пользователю доступны модели, базы знаний и голос, но не управление Kubernetes.
Администратор входит через OIDC (OpenID Connect — проверка личности провайдером
входа). MCP (Model Context Protocol) подключает инструменты; доступ к кластеру
проверяется отдельно. Новый аккаунт для каждой модели не нужен.

</details>

<a id="tp2"></a>
### Qwen на двух GPU

У Qwen3.5-9B языковые веса вместе с MTP занимают примерно **17,13 GiB**;
одна RTX предоставляет около **15,93 GiB**.
**TP2 (Tensor Parallelism на двух GPU)** распределяет одну модель
между картами. Это не две реплики и не TensorRT.

![Одна Qwen распределена между двумя RTX 5060 Ti](assets/24-rtx-tp2.svg)

В отличие от Gemma, MTP-веса Qwen находятся в её checkpoint:
отдельный assistant не нужен. Профиль задаёт один предлагаемый токен.
Счётчики подтверждают работу MTP; ускорение требует отдельного сравнения
MTP on/off.

### Освобождение GPU и запуск Qwen

До остановки Gemma должны быть готовы `rtx-qwen35-9b` в каталоге,
доставка на RTX и рецепт **128K / TP2 / MTP**. Если доступен только
старый рецепт 8K, он обновляется до освобождения карт.

Qwen запускается после завершения текущих запросов, остановки обеих Gemma
и освобождения **обеих** GPU. Пользовательская история чата сохраняется.

Для платформенной Gemma нужен адресный **Prune — удаление только её
InferenceService**. Models, PVC (PersistentVolumeClaim — заявки на тома)
и данные не удаляются.

| Параметр | Длинный Throughput-рецепт |
| --- | --- |
| Карты | `acceleratorCount=2`, `tensor-parallel-size: 2` |
| Веса / KV | BF16 / FP8 |
| Окно / активные последовательности | 131 072 / до 8 |
| RAM KV-offload | 16 GiB |
| MTP | Одно предложение за цикл |

В заказе, claim и Pod должны совпасть две GPU.
Прежнее окно 8192 вместо 128K указывает на неверно выбранный рецепт.
Маршрут **Qwen 9B — TP2** включается в том же WebUI после успешного ответа API.

<details>
<summary>Заказ Qwen, маршрут и первый запуск</summary>

1. Оба маршрута Gemma скрываются в WebUI; текущие запросы завершаются.
2. Ручная B останавливается через `replicaCount: 0`, commit/push и Sync.
3. Платформенной Gemma задаётся `order.enabled: false`; адресный Prune
   удаляет только её InferenceService. Обычный Sync его не удаляет.
4. Перед следующим заказом обе GPU должны освободиться.

В `$RTX_DIR/platform/rtx-qwen.yaml` задаётся `order.enabled: true`.
Параметры движка приходят из рецепта; дочерний StatefulSet не изменяется вручную.

```bash

```

Commit/push и Sync `rtx-qwen35-tp2`. DeviceClass выбирает тип GPU,
число карт задаёт рецепт и подтверждает ResourceClaim.

Маршрут `Qwen 9B — TP2` ведёт на `rtx-qwen35-tp2:80`,
имя runtime-модели — `rtx-qwen35-9b`.
[Проверка API](#platform) требует содержательного и полного потокового ответа.

![Встроенный MTP предлагает продолжение, основная Qwen проверяет его](assets/18-qwen-mtp.svg)

В [прежнем запуске с окном 8K](results/rtx5060-qwen-nodecache-20261006.json)

за 6 секунд. Остальное — инициализация, компиляция и прогрев.
Это не измерение старта 128K. NodeCache этих этапов не устраняет.

На RTX нет NVLink; обмен TP2 нельзя оценивать по цифрам H100.

</details>

<a id="qwen-long-context"></a>
### Вместимость KV и восемь одновременных запросов

У Qwen девять full-attention слоёв с учётом MTP.
При FP8 и TP2 один токен их KV занимает **9 KiB на каждой GPU**:
история 128K — **1,125 GiB**, восемь независимых — **9 GiB на карту**.

| Вся история | KV одной истории на GPU | Восьми независимых |
| --- | ---: | ---: |
| 32K | 0,28125 GiB | 2,25 GiB |
| 64K | 0,5625 GiB | 4,5 GiB |
| 128K — окно сервиса | 1,125 GiB | 9 GiB |
| 256K — только расчёт | 2,25 GiB | 18 GiB |

> [!IMPORTANT]
> Восемь историй по 128K вместе с весами не помещаются в VRAM этих RTX.
> RAM-offload сохраняет кеш, но не расширяет рабочую память attention.
> Проверка разделена на один длинный вход и восемь входов по 32K.

<details>
<summary>Расчёт гибридного KV Qwen, MTP и граница 256K</summary>

В [закреплённой конфигурации Qwen](https://huggingface.co/Qwen/Qwen3.5-9B/blob/c202236235762e1c871ad0ccb60c8ee5ba337b9a/config.json)
8 full-attention и 24 linear-attention слоя. У full — 4 KV-головы по 256
элементов; TP2 размещает по две головы на GPU.
[Слой MTP](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/qwen3_5_mtp.py#L111)
добавляет ещё один full-attention слой.

```text
KV на GPU = 2 × 1 × 9 × (4 / 2) × 256 × S × N байт
```

`S` — вход и ответ, `N` — независимые истории.
`2 × 1 × 9 × 2 × 256 = 9216 байт = 9 KiB` на токен;
`9 KiB × 131072 = 1,125 GiB` на историю на GPU.

Linear attention хранит состояние иначе, не полный K/V всей истории.
Его нельзя умножать на `S` этой формулой. Кроме full KV нужны его состояние,
веса, буферы и округление блоков.

Конфигурация допускает 262 144 позиции, но рецепт и опыт здесь — 128K.
Восемь историй 256K требуют 18 GiB на карту даже без весов.

</details>

Первая серия на InferenceService использует входы **57 344** и **122 880**
токенов, по 512 выходных. Вторая — **восемь разных входов по 32K**.
Окно всё время 128K; оно не равно фактической длине каждого запроса.

Показатели — running, waiting и preemptions: активные запросы, очередь
и вытеснения. Восемь успешных клиентов ещё не доказывают восемь одновременно
исполняемых историй. Возврат KV из RAM проверяется отдельным повтором
вытесненного префикса.

<details>
<summary>Команды длинного Qwen и восьми параллельных запросов</summary>

При нескольких контейнерах runtime указывается через `-c`.
Аутентификация Token требует `OPENAI_API_KEY` в окружении клиента;
он заранее передаётся через Secret. Если ключа в runtime нет, требуется
подготовленный CPU-клиент с авторизацией, а не отключение проверки доступа.

```bash
export INPUT_TOKENS=57344 RUN_NAME=qwen-64k
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec rtx-qwen35-tp2-0 -- \
  vllm bench serve --backend vllm \
    --base-url "http://rtx-qwen35-tp2.$NS.svc.cluster.local" \
    --endpoint /v1/completions --model rtx-qwen35-9b \
    --tokenizer /data/modelcache/models/rtx-qwen35-9b \
    --dataset-name random --seed 73 \
    --random-input-len "$INPUT_TOKENS" --random-output-len 512 --random-range-ratio 0 \
    --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$RUN_NAME.txt"
```

Первая серия: completed=1, failed=0, **57 344 + 512** токенов.
Вторая серия: `INPUT_TOKENS=122880 RUN_NAME=qwen-128k`; рецепт не меняется.

Для восьми сессий: `INPUT_TOKENS=32768`, seed 107,
`--num-prompts 8 --max-concurrency 8`, `RUN_NAME=qwen-8-sessions`.
Критерии: completed=8, failed=0, **262144 входных и 4096 выходных** токенов.

В результат включаются running, waiting, TTFT, preemptions и перезапуски.
При OffloadingConnector возврат RAM подтверждают CPU→GPU bytes
и external-prefix hits; при Simple CPU — `vllm:simple_kv_offload_load_blocks_total`.

В [записанном опыте](results/rtx5060-rehearsal-20261008.json) восемь запросов
по 32K одновременно были running, без вытеснений. Средний TTFT — 60,3 секунды.
Выходные 512 токенов тоже занимают KV; это не опыт 8 × 128K.

</details>

### Проверка через WebUI

Проверка Qwen в WebUI использует длинный текст и полный ответ.

<a id="cleanup"></a>
## Остановка

Остановка выполняется после завершения текущих запросов
и сохранения результатов:

1. Выключаемые маршруты скрываются в WebUI.
2. Ручные профили получают `replicaCount: 0` через GitOps.
3. Платформенные профили получают `order.enabled: false`; адресный Prune
   удаляет **только нужные InferenceService** по [процедуре](docs/GITOPS.md#остановка).
4. Завершение остановки подтверждается освобождением заявок.

**Namespace, Models, PVC, пользователи и история чатов сохраняются.**

Повторный A/B требует исходной конфигурации выключенного Tune:
окно 4096, `gpu-memory-utilization: 0.90`, пресет WebUI 4K
и ответ до 1024. Перед повторным A/B через GitOps запускается только Base.
