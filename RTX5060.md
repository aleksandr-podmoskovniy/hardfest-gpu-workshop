# Инференс без простоя GPU — две RTX 5060 Ti

Александр Подмосковный, Флант / Deckhouse Platform

[Основной стенд: две H100](README.md) | Этот стенд: две RTX 5060 Ti по 16 GiB

Сегодня разберём сервис на двух RTX 5060 Ti по 16 GiB.
Начинаем с подготовленного стенда: **Gemma A — Base уже запущена** на первой
карте, веса остальных моделей доставлены, чат и графики подключены.
Откроем Gemma E2B без исследуемых оптимизаций, создадим нагрузку, увидим задержку,
посчитаем KV cache и последовательно изменим хранение кеша и обработку запросов.
Цель — длинные документы, законченная генерация и понятные границы параллельной работы.

Откройте **[ai.ap4y.ru](https://ai.ap4y.ru)**, зарегистрируйтесь и дождитесь
одобрения. Личный Virtual Key и права выдаются автоматически; вставлять общий
ключ не нужно. Пока аккаунты одобряются, посмотрим, как связаны чат, шлюз,
каталог моделей, GPU и графики.

После ручной настройки повторим Gemma через AI Inference, подключим поиск
и голос на A30 соседнего кластера, а в финале запустим Qwen3.5-9B на обеих RTX.
Это самостоятельная программа: расчёты относятся к E2B и Qwen3.5,
а не к уменьшенным параметрам H100. Участники создают запросы
в чате; GitOps-команды выполняет администратор стенда.

![От уже работающей базовой Gemma через две итерации B к платформенной Gemma и Qwen TP2](assets/20-rtx-sequence.svg)

Модели подготавливаются через **ai-models**. Платформенные Gemma и Qwen запускаются
через **InferenceService**, со ссылкой на `Model` из каталога. Ручная A/B-пара нужна
для разбора настроек; её Deployment тоже получает веса из ai-models.
Helm values и заказы хранятся в Git, выбранный commit применяет Argo CD.

## Стенд и чат

![Два кластера: Open WebUI и A30, ai-mcp-gateway и две RTX 5060 Ti](assets/21-rtx-topology.svg)

| Компонент | Назначение |
| --- | --- |
| Две RTX 5060 Ti по 16 GiB на одной ноде | Две отдельные Gemma; в финале один Qwen с TP2 |
| ai-mcp-gateway | Маршруты моделей, личные Virtual Key, лимиты и учёт |
| Open WebUI | Один вход, история чатов, базы знаний и голос |
| A30 в соседнем кластере | Эмбеддер, реранкер и Whisper через AI Inference |
| Argo CD | Применение Helm values и заказов из частной репы k8s-config |

В WebUI сначала доступна `Gemma A — Base`, затем добавляем `Gemma B — Cache`.
После первого опыта Cache сменит `Gemma B — Tune`.
При переходе к платформе A меняется на `Gemma A — DP`, затем обе Gemma уступают
место `Qwen 9B — TP2`. `DP` — подпись платформенного запуска, не Data Parallel.
Не включайте fallback между A/B и кеш готовых ответов шлюза: они скроют различие профилей.

Участник регистрируется с паролем и ждёт одобрения. Затем получает один личный VK,
доступ к моделям, базам знаний и голосу, но не к Kubernetes MCP.
Администратор входит по OIDC; доступ MCP к кластеру проверяется отдельно.
Имена моделей меняются, пользователь и его накопленный расход — нет.

Сначала работаем с Base. Остальные модели появятся по мере запуска;
остановленные маршруты скрываются без удаления чатов и личных ключей.

## 1. Пробуем уже работающую Gemma A

После одобрения аккаунта выберите `Gemma A — Base` в WebUI.
Спросите: «Почему длинная история чата занимает память GPU, если веса модели
не меняются?» Затем задайте свой вопрос и попросите подробное объяснение.
Понаблюдаем, когда начинается ответ и насколько быстро появляется текст.

Пока модель отвечает, откроем `rtx-gemma-base` в Argo CD. Application уже
синхронизирован. Посмотрим применённый commit, [профиль A](values/rtx/gemma-base.yaml),
Deployment и claim на одну RTX. Это ручной vLLM через Helm, ещё не InferenceService.
Повторный sync с изменением числа реплик сейчас не нужен.

В vLLM 0.31 отключены prefix cache, chunked prefill, CUDA graphs,
KV-offload и speculative decoding. Искусственной задержки нет.
Окно — 4096 токенов, активных последовательностей — две. Это контрольная
конфигурация одной версии движка, не эмуляция старого vLLM.
Длинное окно проверим после настройки B; сейчас нам важна одинаковая нагрузка.

Для этой архитектуры vLLM предупреждает, что отключение chunked prefill
официально не поддерживается. Поэтому A — проверенный контрольный опыт на 4K,
а не рекомендуемая рабочая конфигурация; длинное окно так не запускаем.

Каталог `hardfest-rtx` уже содержит основную Gemma, совместимый assistant
и Qwen. A использует только основную модель из ai-models. Наличие весов
в каталоге не заменяет работающий API, поэтому при подготовке проверены
и ответ API, и тот же путь через личный VK в WebUI.

<a id="monitoring"></a>
### От ответа в чате к графикам

Перейдём в **AI Inference / Service performance**, выберем namespace
`hardfest-rtx` и Service `rtx-gemma-base`. На интервале только что заданных
вопросов должны быть новые запросы и токены. В дальнейшем A/B сравниваются
здесь же; после перехода к платформе изменится Service, а не дашборд.

| Вопрос | График или счётчик |
| --- | --- |
| Почему ответа ещё нет? | Очередь и TTFT |
| Почему текст появляется медленно? | TPOT / ITL и выходные токены/с |
| Переиспользуется ли префикс? | Запросы и попадания prefix cache |
| KV действительно вернулся из RAM? | CPU→GPU bytes и external-prefix hits |
| Assistant приносит токены? | Предложенные и принятые draft-токены |
| Где кончаются ресурсы? | VRAM, GPU KV, RAM контейнера, ошибки и перезапуски |

Пустой график не означает нулевую нагрузку. Сначала проверьте scrape target,
временной интервал и выбранный сервис. Ручные A, Cache и Tune должны быть
в фильтрах вместе с платформенными сервисами. Для RTX нет NVLink-метрик.
Графики Simple backend не обязаны появиться у OffloadingConnector: проверяем
метрики активного backend. Настройка единиц и сбора уже проверена до занятия.

Теперь ненадолго приостановим свободные вопросы и выполним
одинаковую нагрузку: 2048 входных, 128 выходных
токенов, 8 запросов, параллельность 2. Это короткий измерительный опыт,
не лимит ответов для обычного разговора. Сохраним ошибки и фактические длины.
Сохраним исходный результат A. На этих графиках разберём, куда ушло время;
затем повторим тот же опыт с двумя конфигурациями B.

<details>
<summary>Одинаковая нагрузка для A, B Cache и B Tune</summary>

Команды выполняются в частном `k8s-config`; контексты и `NS=hardfest-rtx`
заданы при подготовке. Для каждой серии задайте новое имя файла:


Повтор seed прогревает prefix cache: первый проход и повтор сравниваем отдельно.
Клиент внутри Pod влияет на CPU; это короткий опыт, не независимый нагрузочный стенд.

<a id="latency"></a>
## 2. Разбираем время ответа

![Время ответа разделено на очередь, prefill, рассуждение и выдачу текста](assets/02-latency.svg)

`Tответа ≈ Tочереди + Tprefill + Tdecode + Tпрочее`.
Prefill обрабатывает входную историю; decode последовательно добавляет токены.
Reasoning и финальный текст — части генерируемого продолжения, не два разных
универсальных вычислительных режима. Первые слова ответа в UI могут появиться
позже первого токена движка. Сеть, шлюз и токенизация тоже добавляют время.

Длинный вход прежде всего влияет на TTFT, длинный выход — на полную длительность.
При нескольких пользователях появляется очередь. Посмотрим одновременно
waiting/running, TTFT и ITL, а не только GPU utilization. Prefill может быть
ограничен вычислениями, decode при малом batch — чтением памяти; это гипотезы,
которые проверяем нагрузкой, а не диагноз по одному проценту загрузки GPU.

Отправьте короткий запрос, затем запрос с длинным контекстом и коротким ответом.
Сопоставьте TTFT и TPOT. В дальнейших A/B-сериях длины входа, выхода,
параллельность и настройки reasoning должны совпадать.

<a id="memory"></a>
## 3. Считаем, что помещается в 16 GiB

Разделим память: веса модели, рабочие буферы и KV cache.
Веса одни на экземпляр, история у каждого запроса своя. После `t1, t2, t3`
модель выдаёт `t4`, затем продолжает уже четыре токена. На attention-слое
текущий query Q сравнивается с keys K; коэффициенты задают сумму values V.
Q нужен сейчас, K/V сохраняем для следующих шагов.

В GQA несколько query-голов используют общие K/V. Поэтому
в формуле нужно число KV-голов, а не число всех attention-голов.

### Считаем KV, а не угадываем по названию модели

Веса общие для запросов к одному экземпляру. KV — ключи и значения уже обработанных
токенов: новый query использует их при продолжении истории. Кеш позволяет не
вычислять прошлые K/V повторно; его размер зависит от истории, а не только от весов.

![От KV одного токена и слоя к формуле памяти нескольких независимых историй](assets/25-kv-derivation.svg)

Один токен одного слоя: два вектора на KV-голову, каждый из `D` элементов по `b`
байт. Для одинаковых full-attention слоёв умножаем на `S` токенов, `L` слоёв и
`B` независимых историй. `S` включает вход и ответ; `Hkv` — число KV-голов,
**не число query-голов**. BF16 KV занимает 2 байта на элемент, FP8 — 1.
Это настройка кеша, не квантование весов.

Для одинаковых full-слоёв: `KV = 2 × L × Hkv × D × b × (S₁ + … + Sₙ)`.
Восемь историй одинаковой длины дают `8 × KV(S)`, пока не разделяют префикс.
Но сначала узнаем, сколько слоёв действительно хранит независимый KV.

В [config.json Gemma E2B](https://huggingface.co/google/gemma-4-E2B-it/blob/3e22461f65e89153144f8adb70e3b8c2cc9845a7/config.json)
смотрим `text_config`. Из 35 слоёв последние 20 переиспользуют KV более ранних:
`num_kv_shared_layers=20`. Собственные K/V создают **15 слоёв: 3 full и 12 sliding**.
Это межслойное разделение внутри модели, не prefix cache между запросами.
[Как vLLM выбирает источник общего KV](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/gemma4.py#L473).

| Собственный KV | Слоёв | KV-голов | Размерность | Длина |
| --- | ---: | ---: | ---: | --- |
| Full attention | 3 | 1 | 512 | `S` |
| Sliding attention | 12 | 1 | 256 | `min(S, 512)` |

![Подстановка E2B: full 24 MiB плюс sliding 6 MiB дают 30 MiB BF16 на историю 4K](assets/26-rtx-kv.svg)

Один токен full-слоя: `2 × 1 × 512 × 2 = 2048 байт = 2 KiB`.
Три full-слоя дают **6 KiB на токен истории**.
Один sliding-слой: `2 × 1 × 256 × 2 = 1 KiB`; двенадцать — **12 KiB на токен
окна**, но только для последних 512 токенов.
Поэтому `KV(S) = 2 × b × [3 × 512 × S + 12 × 256 × min(S, 512)]` байт.

Для `S=4096`: full — `2 × 2 × 3 × 1 × 512 × 4096` = **24 MiB**;
sliding — `2 × 2 × 12 × 1 × 256 × 512` = **6 MiB**.
Итого **30 MiB** BF16 на историю; две независимые истории — **60 MiB**.
В FP8 получаем соответственно **15 и 30 MiB**.

```bash
awk -v S=4096 -v B=2 -v b=2 'BEGIN {
  W = S < 512 ? S : 512
  full = 2*b*3*1*512*S / 1048576
  local = 2*b*12*1*256*W / 1048576
  printf "Full %.0f + sliding %.0f = %.0f MiB/history; %d histories = %.0f MiB\n", full, local, full+local, B, B*(full+local)
}'
```

Поменяйте только `S` на 8192. Получится **54 MiB BF16**, не 60: full-слагаемое
выросло вдвое, sliding осталось 6 MiB. Это расчёт, **не смена окна A/B**.
Если умножить все 35 слоёв на всю историю или взять 8 query-голов вместо одной
KV-головы, получится неверная оценка.

Теперь окно 128K: `122880 входных + 8192 генерации = 131072 токена`.
Вход включает шаблон чата, генерация — reasoning и финальный текст.
Full занимает `6 KiB × 131072 = 768 MiB`, sliding — `12 KiB × 512 = 6 MiB`.
Получаем **774 MiB BF16**, или **387 MiB FP8** на историю.

| Независимые истории 128K | BF16 | FP8 |
| --- | ---: | ---: |
| 1 | 774 MiB | 387 MiB |
| 4 | 3096 MiB | 1548 MiB |
| 8 | 6192 MiB | 3096 MiB |

Это упражнение по памяти, не обещание восьми сессий для Gemma:
её профиль ограничен двумя. Восемь сессий проверим в финальном Qwen.

### Почему процесс занимает гораздо больше

KV хранится не сплошным массивом каждой истории, а блоками. Например,
при условных 16 токенах в блоке история из 35 токенов занимает три блока:
два полных и один частичный. Таблица истории указывает на физические блоки;
совпадающие полные блоки префикса можно переиспользовать. После завершения
запроса его активные ссылки освобождаются, кешированные блоки могут сохраняться
до вытеснения. Реальные block size и группы full/sliding берём из runtime;
16 — учебный пример. В RAM будем переносить именно KV-блоки.

![Бюджет памяти RTX: веса, служебная память и GPU KV; RAM хранит отдельную часть KV](assets/22-rtx-memory.svg)

30 MiB — полезные KV одной истории, не вся память GPU и не размер выделенного
пула. vLLM резервирует пул блоков для запросов, учитывает их округление и размещение
разных типов attention. Отдельно нужны веса, активации, буферы prefill, CUDA graphs
и память assistant. Поэтому формула не обещает, что произвольное окно запустится.

Бюджет: `Kpool ≈ G × u − W − R`. На RTX подставляем фактические `G`, память
весов `W` и прочие резервы `R` из запуска; `u` задаётся профилем.
Если после них осталось 1 GiB, одна история FP8 128K теоретически требует
387 MiB, две — 774 MiB, а три — 1161 MiB и уже не помещаются.
Это пример арифметики, не измеренный размер пула; блоки и рабочие буферы
могут уменьшить вместимость. Сверим расчёт с логами, а не с именем E2B.

После старта выпишите GPU KV capacity из логов. На дашборде сравните занятость
пула для одного и двух запросов; затем для повторённого и нового префикса.
Размер заранее выделенного пула при этом может не меняться, хотя доля занятых
блоков меняется. [Read-only команды и границы сравнения](docs/MEMORY_BUDGET.md#verify-kv).

| Параметр | Gemma A | Gemma B | Qwen TP2 |
| --- | --- | --- | --- |
| GPU | 1 | 1 | 2 |
| Точность весов | BF16 | BF16 | BF16 |
| Окно | 4096 для контроля | 4096 для A/B → 131 072 | 131 072 в заранее подготовленном рецепте |
| Максимум последовательностей | 2 | 2 | 8, отдельно проверяем исполняемые запросы |
| CPU KV | Нет | 4 GiB | 16 GiB в длинном рецепте |

E2B в названии Gemma не означает файл ровно из двух миллиардов параметров:
полный BF16 checkpoint занимает около 9,54 GiB. Языковые веса Qwen вместе с MTP —
примерно 17,13 GiB, больше доступных 15,93 GiB одной RTX. Поэтому финальный опыт
использует TP2 без квантования весов и без их выгрузки в RAM.

4K — контрольная точка сравнения, не конечная цель. Длинный контекст проверяем
после включения chunked prefill: сначала 64K, затем 128K. Короткий A/B отвечает
на вопрос о скорости при одинаковой нагрузке; длинный опыт — о новой вместимости.
Если длинный профиль не проходит приёмку, этот этап ещё не готов — нельзя
незаметно заменить его коротким чатом.

<a id="ram"></a>
## 4. Первая итерация: prefix cache и KV в RAM

![Общий префикс обрабатывается один раз и используется последующими запросами](assets/14-prefix.svg)

Prefix cache помогает, когда запросы имеют одинаковое начало: системный промпт,
документ, историю. Совпадения только по смыслу недостаточно — переиспользуются
совпадающие токены. Для независимых коротких запросов эффект может быть небольшим.

Но повтор полезен лишь пока сохранены вычисленные блоки. Если GPU-пул
понадобился другим документам, вернуться к старому префиксу можно через
его копию в RAM. Именно это добавляет KV-offload.

В [первом профиле B](values/rtx/gemma-cache.yaml) включены prefix cache,
FP8 KV и 4 GiB CPU KV. Chunked prefill, graphs и assistant ещё выключены.
Окно и параллельность пока те же, что у A. FP8 относится к KV, веса остаются BF16.

![KV-блоки уходят из GPU в RAM и возвращаются при повторном обращении](assets/05-kv-ram.svg)

Цена восстановления приближённо равна `объём / эффективная полоса`.
Даже теоретические 387 MiB FP8 для истории 128K нужно реально передать обратно
и синхронизировать. Выигрыш появится, если это дешевле повторного prefill.
Скорость PCIe не берём из спецификации вместо измерения.

Перейдём в Git и Argo. В частном `values/gemma-cache.yaml` включим одну реплику;
отдельный Application `rtx-gemma-cache` ссылается только на этот профиль.
После render, commit/push и адресного sync дождёмся ответа API новой B.
A остаётся работать на первой карте. В WebUI появляется `Gemma B — Cache`:
попробуем те же вопросы, затем повторим контрольную серию без фоновой нагрузки.

На дашборде выберем оба Service, а не только общие веса. Смотрим, изменилась ли
очередь и TTFT. Повтор одинакового префикса должен дать попадания в кеш;
это не означает, что он уже успел побывать в RAM. Для этого вытесняем его
другими префиксами и повторяем исходный запрос. CPU→GPU bytes вместе с
external-prefix hits подтверждают чтение из RAM. Только запись GPU→CPU этого не доказывает.

Если GPU-кеша хватает на всё, отдельный диагностический опыт уменьшает
его до 256 MiB. После проверки верните штатный размер; результаты диагностики
нельзя смешивать с A/B-замером. KV-offload не является выгрузкой весов модели.

<summary>Включить B Cache в Git и Argo</summary>

В `$RTX_DIR/values/gemma-cache.yaml` задайте `replicaCount: 1`.

<a id="speculation"></a>
## 5. Вторая итерация: chunked prefill и speculative decoding

![Планировщик чередует порции длинного prefill с генерацией текущих ответов](assets/06-scheduler.svg)

Пока один пользователь ждёт обработку большого документа, другой уже получает
ответ. **Chunked prefill** делит обработку входа на порции. Это позволяет обслуживать decode
уже начатых запросов, пока новый длинный вход ещё обрабатывается.
На RTX бюджет составляет 512 токенов, окно остаётся 4096.

Различаем длину истории (`max-model-len`), число обрабатываемых историй
(`max-num-seqs`) и токены одного шага (`max-num-batched-tokens`).
Например, в шаге на 512 токенов два обычных decode-запроса могут занять по
одному токену, а оставшийся бюджет — часть prefill. Это схема без деталей
speculation, не обещание фиксированного распределения каждого шага vLLM.

![Совместимый assistant предлагает токены, основная Gemma проверяет продолжение](assets/07-speculation.svg)

**Speculative decoding** работает иначе: draft предлагает продолжение,
target проверяет его. У этой Gemma совместимый assistant предлагает один токен
за цикл методом MTP; основная Gemma проверяет предложение.
Работа механизма видна по счётчикам предложенных и принятых токенов.
Его польза зависит от стоимости предложения, проверки и доли принятия.
Высокая доля принятия сама по себе не доказывает меньшую задержку.

Для нескольких реплик существуют cache-aware routing и prefill/decode
disaggregation: первая учитывает местонахождение KV при выборе реплики,
вторая разделяет стадии между исполнителями. Здесь их не разворачиваем;
[пояснения и источники](docs/SOURCES.md) позволяют отделить их от локальной настройки vLLM.

Сначала скроем `Gemma B — Cache` в WebUI и дождёмся завершения её текущих запросов.
Теперь вернёмся в Argo. Остановим `rtx-gemma-cache` через его values и адресный
sync, дождёмся освобождения claim. Затем включим отдельный `rtx-gemma-tune`
с [полным вторым профилем](values/rtx/gemma-spec.yaml). Он сохраняет первую
итерацию кешей и добавляет chunked prefill, assistant и CUDA graphs с capture size 4.
Два профиля B не работают одновременно. После ответа API откроем
`Gemma B — Tune` в WebUI; A остаётся прежней.

Попробуем чат, затем сравним A/B без посторонних запросов: один seed,
2048 входных, 128 выходных токенов, 8 запросов,
параллельность 2. Раздельно отмечайте холодный и прогретый кеш.
На графиках смотрим не только темп текста, но и TTFT, ITL, принятые draft-токены.
Весь выигрыш полного B нельзя приписать только speculative decoding.

При первом старте B компилируются основная модель и assistant, затем
захватываются CUDA graphs.
NodeCache хранит веса, а не результаты компиляции из временного каталога Pod.
Отсчитывайте готовность по Ready и успешному запросу, не по завершению чтения весов.

В `gemma-cache.yaml` задайте `replicaCount: 0`, отправьте изменение и
синхронизируйте `rtx-gemma-cache`. Только после освобождения claim задайте
`replicaCount: 1` в `gemma-spec.yaml`, проверьте render этого полного профиля,
отправьте commit и синхронизируйте `rtx-gemma-tune`.
Application Tune читает `../../values/gemma-spec.yaml`; Cache и Tune
имеют разные Service и не управляют одним workload.

### Длинный контекст: 64K, затем 128K

Теперь проверим, как обслужить историю, которую контрольный A с окном 4K
не принимает.
Отказ A здесь вызван настроенным лимитом 4K. Он не доказывает нехватку её VRAM
и сам по себе не доказывает необходимость KV-offload.

![Расчёт Gemma E2B для 4K, 64K и 128K и длины запросов для проверки](assets/27-rtx-long-context.svg)

В полном `values/gemma-spec.yaml` один раз расширим окно до 128K.
На этом запуске проверим сначала вход около 64K, затем около 128K;
отдельный перезапуск между запросами не нужен. Сохраним assistant, prefix cache,
FP8 KV, CPU KV 4 GiB, graphs и chunked prefill с бюджетом 512.
Бюджет шага не надо поднимать до размера окна.

```yaml
# Фрагмент существующего values; остальные поля сохраняются.
vllm:
  max-model-len: 131072
  gpu-memory-utilization: 0.95
  max-num-seqs: 2
  enable-chunked-prefill: true
  max-num-batched-tokens: 512
```

Проверьте render, отправьте diff и синхронизируйте `rtx-gemma-tune`.
После Ready проверьте фактическое окно, размер KV-пула и работу assistant.
`gpu-memory-utilization: 0.95` взято из успешного длинного прогона;
при 0.90 его первая проверка ёмкости KV не прошла.
В пресете **Gemma B — Tune** одновременно обновите описание окна на 128K
и `max_tokens` на 8192: увеличение серверного окна не снимает лимит ответа WebUI.

Длинный синтетический вход проверяет вместимость, не качество понимания.

<a id="platform"></a>
## 6. Gemma через AI Inference

Мы подобрали конфигурацию вручную. Для каждой новой модели повторять такой
подбор неудобно: передадим платформе заказ, а не всю командную строку движка.
Откроем Model в каталоге и [`rtx-gemma-platform`](platform/rtx-gemma.yaml)
в Git. Планировщик AI Inference сопоставляет модель, класс устройства,
стратегию и рецепты; затем Kubernetes и DRA выделяют конкретную GPU.

![Артефакты ai-models, заказ InferenceService, GPU-план и ответ в интерфейсе](assets/23-rtx-platform.svg)

В подготовку включена проверка доставки **обоих** артефактов — Gemma и assistant —
и рецепта с теми же параметрами, что у измеренной B. Теперь скроем Base в WebUI,
дождёмся завершения её запросов и остановим только ручную A через GitOps.
После освобождения claim включим заказ
`rtx-gemma-platform`. B остаётся на второй карте.

Параметры runtime берутся из рецепта AI Inference, не из произвольного поля
`InferenceService.spec`. Длинная Gemma использует профиль для
RTX 5060 Ti, vLLM 0.31 и Throughput: 128K, FP8 KV, RAM KV 4 GiB,
две последовательности и совместимый assistant. Он привязан к классу
GPU площадки; при переносе проверьте условия выбора. Общий рецепт
для другой карты или стратегии не получает 128K автоматически.

В Argo увидим применение заказа. В консоли **GPU-кластер → hardfest-rtx →
AI-модели** откроем InferenceService, рассчитанный план, claim и Pod.
Если Pod получил 4096 вместо 128K, длинный профиль не выбран — сравнение
ещё не началось. Во время опыта ревизии основной Model и assistant не меняем.

Теперь сопоставим ручной расчёт памяти, план платформы и реальный контейнер.
При одинаковых эффективных настройках зададим те же вопросы ручной B
и платформенной A. Автоматизация должна воспроизвести запуск, а не магически
ускорить тот же движок. Смотрим ответы, задержки и ошибки.

После Ready и ответа API вернёмся в чат: рядом с ручной B появилась
`Gemma A — DP`. Повторим короткие вопросы и длинный текст.
На дашборде сравним два Service на одном интервале, а по счётчикам проверим
работу assistant и кешей. Новый Pod использует те же подготовленные артефакты.

В `$RTX_DIR/platform/rtx-gemma.yaml` включите `order.enabled: true`.
Это Helm values, а не сырой InferenceService:

```bash
set -o pipefail
helm template rtx-gemma-platform "$RTX_DIR/charts/inference-service" -n "$NS" \
  -f "$RTX_DIR/platform/rtx-gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После успешной проверки — commit/push и Sync `rtx-gemma-platform`.
В консоли открываем заказ, затем claim и Pod. Включаем подготовленный маршрут
`rtx-gemma-platform` → `rtx-gemma-platform:80` с upstream-именем
`rtx-gemma-e2b` и показываем его в WebUI как `Gemma A — DP`.
Маршрут остановленной Base скрываем. Личные VK сохраняются: доступ к обоим
маршрутам входит в профиль участника, выдавать новый ключ не нужно.

<details>
<summary>Проверить API платформенной Gemma и Qwen</summary>

В отдельном терминале:

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" port-forward svc/rtx-gemma-platform 18005:80
```

При включённой аутентификации Token в основном терминале введите ключ сервиса

```bash

  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  http://127.0.0.1:18005/v1/models
curl --fail-with-body --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
```

Если подготовленный API не требует Token, уберите ввод ключа и обе строки
`--header`; не меняйте политику доступа ради проверки.
Для Qwen закройте этот port-forward и повторите с `svc/rtx-qwen35-tp2`,
его ключом и `"model":"rtx-qwen35-9b"`. Нужен текст ответа, не только HTTP 200.

</details>

Здесь сравниваем ответы и задержки на одинаковых вопросах. Строгий замер
производительности требует общего CPU-клиента с нужной авторизацией;
команда ручного A/B не переносится на платформенный StatefulSet буквально.

<a id="placement"></a>
## 7. Базы знаний и голос: три сервиса на A30

![На A30 две MIG-партиции: эмбеддер и реранкер через MPS, Whisper отдельно](assets/08-mig-mps.svg)

Теперь сменим кластер в консоли и datasource в графиках. Эта часть не переносится
на RTX: используем A30 соседнего кластера. Через три InferenceService разместим
Qwen3 Embedding 4B W4A16, Qwen3 Reranker 4B W4A16 и Whisper large-v3.
Модели для них заранее импортированы через ai-models в namespace
**кластера A30**, а не RTX.

Здесь решаем другую задачу: не уместить большую модель, а не отдавать целую
GPU каждому небольшому сервису. Device plugins публикуют ресурсы устройств;
DRA связывает ResourceClaim с подходящим устройством и подготовкой драйвера.
MIG аппаратно разделяет карту, MPS позволяет процессам совместно использовать
одну партицию, time-slicing чередует доступ без аппаратного раздела памяти.
[Термины, границы и сравнение с HAMi/Volcano](docs/SOURCES.md).

Снимем геометрию A30 до заказов, создадим три InferenceService и проверим её
снова через `nvidia-smi`. Для динамического создания нужны свободная геометрия,
поддержка драйвера и заранее включённый MIG mode. Выделение уже существующего
MIG не выдаём за создание нового. Эмбеддер и реранкер должны получить один
MIG UUID через MPS, Whisper — другой.

![Поиск документов через эмбеддер и реранкер передаёт контекст в модель чата](assets/16-rag.svg)

Добавьте документ в базу знаний и задайте вопрос, ответ на который есть в нём.
Проверьте источники, запросы к эмбеддеру/реранкеру и метрики сервиса чата.
Затем отправьте голосовое сообщение и проверьте транскрипцию Whisper.
Смена Gemma на Qwen не требует пересоздавать пользователя или базу знаний.

В подготовленных `platform/embedding.yaml`, `reranker.yaml`, `whisper.yaml`
включите `order.enabled: true`, проверьте render и отправьте commit.
Синхронизируйте `hardfest-embedding-platform`, `hardfest-reranker-platform`
и `hardfest-whisper-platform` с destination **кластера A30**.
В консоли этого кластера должны стать готовы все три InferenceService.

В терминале ноды A30 до и после заказов:

```bash
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

Эмбеддер и реранкер получают один MIG UUID, Whisper — другой.
Проверяем вопрос по документу с источником и узнаваемую транскрипцию
своей короткой записи. Ready без этих ответов недостаточно.

<a id="tp2"></a>
## 8. Qwen через AI Inference: TP2 и MTP

![Один Qwen разделён между двумя RTX 5060 Ti, в отличие от двух независимых реплик](assets/24-rtx-tp2.svg)

Сначала проверьте `rtx-qwen35-9b` в каталоге и готовность доставки на RTX.
Скройте обе Gemma в WebUI и дождитесь завершения текущих запросов.
Остановите обе Gemma через их GitOps-приложения, сохранив модели и хранилище.
Убедитесь, что старые DRA-заявки освобождены. Только после этого включайте
[`rtx-qwen35-tp2`](platform/rtx-qwen.yaml).

В рецепте Qwen — **acceleratorCount=2**, `tensor-parallel-size: 2`, BF16,
длинное окно и MTP. DeviceClass выбирает подходящий тип GPU; число карт задаёт
рецепт и подтверждает ResourceClaim. Две реплики по одной GPU — другой опыт.

В длинном Throughput-рецепте Qwen задаются окно 131 072, FP8 KV,
RAM KV-offload 16 GiB и до восьми активных последовательностей. Проверяем
сначала вход 57 344, затем 122 880 токенов; отдельно — восемь разных входов
по 32K. Восемь историй по полным 128K вместе с весами в VRAM этих карт не
помещаются: расчёт приведён ниже. Прежний рецепт 8192
не считается длинным запуском. Дочерний StatefulSet не патчим.

TP2 — **Tensor Parallelism** одной модели, не две реплики и не TensorRT.
Откроем заказ, его GPU claim, затем Pod: число карт должно совпадать на всех
трёх уровнях. После API вернёмся в привычный чат, не создавая новый аккаунт.

В [сохранённом запуске с окном 8K](results/rtx5060-qwen-nodecache-20261006.json)
от создания Pod до Ready прошло **6 минут 36 секунд**; это не время старта рецепта 128K.
Веса прочитаны примерно за 6 секунд; оставшееся время включает инициализацию,
компиляцию и прогрев. NodeCache не устраняет эти этапы.

![Встроенный MTP предлагает продолжение, основная модель проверяет токены](assets/18-qwen-mtp.svg)

В отличие от Gemma, Qwen использует MTP-веса внутри своего checkpoint.
Начните с одного speculative token. После запроса счётчик принятых токенов
должен увеличиться, но ускорение MTP on/off измеряется отдельно.
На RTX нет NVLink: обмен TP2 нельзя оценивать по цифрам H100.

После короткого ответа повторите длинную проверку на самом InferenceService:
входы 57 344 и 122 880 токенов, по 512 выходных. Окно сервиса уже 128K;
между этими запросами не меняем рецепт и не пересобираем модуль.
После API проверьте большой текст в WebUI: шлюз и настройки модели чата
не должны обрезать вход до прежних 8K.

Проверка завершения:

- В каталоге виден `Model rtx-qwen35-9b` с digest, а заказ ссылается на него через `ai-models`.
- `InferenceService Ready`; DRA выделил две разные RTX 5060 Ti, ошибок CUDA нет.
- API возвращает обычный и полный потоковый ответ; метрики MTP меняются.
- Длинные серии завершились без ошибок; сохранены фактические длины, память и TTFT для 64K/128K.
- Восемь сессий проверены с записью running, очереди и вытеснений; отдельно подтверждено чтение RAM-кеша обратно.
- В WebUI работает `Qwen 9B — TP2`, ответ сохраняется после обновления страницы.
- В ai-mcp-gateway запрос записан на личный VK; дашборд показывает Qwen.

<details>
<summary>Запустить Qwen через AI Inference</summary>

Ручную B остановите через `replicaCount: 0`. Для платформенной Gemma
задайте `order.enabled: false`, отправьте commit и в её Application выполните
адресный Prune только InferenceService. Обычный Sync без Prune его не удалит.
Дождитесь освобождения обеих GPU; Model и PVC не удаляйте.

В `$RTX_DIR/platform/rtx-qwen.yaml` задайте `order.enabled: true`:

```bash
set -o pipefail
helm template rtx-qwen35-tp2 "$RTX_DIR/charts/inference-service" -n "$NS" \
  -f "$RTX_DIR/platform/rtx-qwen.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После проверки — commit/push и Sync `rtx-qwen35-tp2`.
В консоли проверяем готовность заказа, два разных устройства в claim и TP2 в Pod.
Маршрут `Qwen 9B — TP2` ведёт на `rtx-qwen35-tp2:80`, имя модели upstream —
`rtx-qwen35-9b`. Проверяем содержательный ответ и его запись на личном VK.

</details>

<a id="qwen-long-context"></a>
### Длинный Qwen и восемь сессий

У Qwen3.5-9B 8 full-attention слоёв и 24 linear-attention слоя.
Full attention: 4 KV-головы по 256 элементов; при TP2 по две головы на GPU.
MTP добавляет ещё один full-attention слой. Для FP8 считаем:

`KV на GPU = 2 × 1 × 9 × (4 / 2) × 256 × S × B` байт.

| История | KV одной истории на GPU | Восемь историй на GPU |
| --- | ---: | ---: |
| 32K | 0,28125 GiB | 2,25 GiB |
| 64K | 0,5625 GiB | 4,5 GiB |
| 128K | 1,125 GiB | 9 GiB |

Ещё нужны веса, состояние linear attention, буферы и округление блоков.
Именно поэтому 8 × 128K не помещаются, хотя окно одного запроса — 128K.
RAM хранит KV вне GPU, но не расширяет рабочую память attention.
[Конфигурация Qwen](https://huggingface.co/Qwen/Qwen3.5-9B/blob/c202236235762e1c871ad0ccb60c8ee5ba337b9a/config.json),
[слой MTP](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/qwen3_5_mtp.py#L111).

<details>
<summary>Проверить длинный вход и восемь запросов</summary>

Сначала один длинный запрос. Укажите runtime-контейнер через `-c`, если их несколько.
При Token эта команда требует `OPENAI_API_KEY` в окружении клиента;
его готовят через Secret до занятия. Если его нет, используйте подготовленный
CPU-клиент с теми же параметрами; не отключайте аутентификацию.

```bash
export INPUT_TOKENS=57344 RUN_NAME=qwen-64k
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec rtx-qwen35-tp2-0 -- \
  vllm bench serve --backend vllm \
    --base-url "http://rtx-qwen35-tp2.$NS.svc.cluster.local" \
    --endpoint /v1/completions --model rtx-qwen35-9b \
    --tokenizer /data/modelcache/models/rtx-qwen35-9b \
    --dataset-name random --seed 73 \
    --random-input-len "$INPUT_TOKENS" --random-output-len 512 --random-range-ratio 0 \
    --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$RUN_NAME.txt"
```

Нужны completed=1, failed=0, заданный вход и 512 выходных токенов.
Повторите с `INPUT_TOKENS=122880 RUN_NAME=qwen-128k`, не меняя окно сервера.
Для восьми сессий в той же команде: вход 32768, seed 107,
`--num-prompts 8 --max-concurrency 8`, `RUN_NAME=qwen-8-sessions`.
Нужны completed=8, failed=0, 262144 входных и 4096 выходных токенов.
Одновременно смотрим running, waiting и preemptions: восемь клиентов
не доказывают восемь постоянно исполняемых историй.

Сначала определите backend по конфигурации и `/metrics`.
У OffloadingConnector возврат из RAM подтверждают CPU→GPU bytes и
external-prefix hits, у Simple CPU — `vllm:simple_kv_offload_load_blocks_total`.
Отсутствие метрик другого backend не означает отказ offload.

</details>

<a id="conclusion"></a>
## 9. Запрос участника, личный ключ и стоимость

Qwen и сервисы A30 ещё работают. Отправьте последний вопрос в чат
и найдите его в Bifrost: та же модель,
время запроса, входные и выходные токены, расчётная стоимость. Проверьте
личный VK пользователя, а не только ключ подключения к vLLM. У двух
одобренных аккаунтов должны быть разные VK; смена Gemma на Qwen не должна
создавать новый аккаунт или обнулять накопленный расход.

Теперь сопоставим три результата: сколько памяти потребовала история,
сколько запросов завершилось с приемлемой задержкой и сколько GPU заняли
сервисы. Кеш помог повторному входу, chunking изменил обслуживание запросов,
speculation — генерацию, а MIG/MPS позволили совместить небольшие сервисы.
TP2 решил другую задачу — разместил одну модель на двух картах. AI Inference
воспроизвёл выбранные параметры через заказ; ускорение одинакового движка
само по себе не является результатом автоматизации.

## Результаты измерений

<details>
<summary>Сохранённые серии: конфигурации, цифры и ограничения</summary>

[Измерения и исходные результаты](results/rtx5060-rehearsal-20261008.json)
получены на двух RTX 5060 Ti с vLLM 0.31 и доставкой из ai-models NodeCache.
В 19 сериях нагрузки завершились **110 запросов без ошибок**.
Это результаты при указанных условиях, а не обещание такой же скорости на другом стенде.

Сначала одинаковое окно 4K: по восемь запросов, 2048 входных и 128 выходных
токенов, параллельность 2. Профили испытывались последовательно.

| Профиль | Выходные токены/с, серии 0 / 1 | Средний TTFT, мс, серии 0 / 1 |
| --- | --- | --- |
| A — Base | 24,88 / 30,67 | 1345 / 337 |
| B — Cache | 23,74 / 30,90 | 1343 / 186 |
| B — Tune | 139,38 / 202,83 | 563 / 92 |

Серия 1 повторяет тот же seed без очистки кеша. Серия 0 не считается чистым
холодным стартом: до неё могли быть проверочные запросы. Клиент выполнялся
в runtime Pod и делил с ним CPU. Профили меняют несколько параметров сразу;
это не изолированный замер MTP, FP8 или CUDA graphs и не прогноз для H100.

При одинаковом окне 128K повторная короткая серия дала **201,05 токена/с**
у ручной Tune и **203,76 токена/с** у Gemma через AI Inference.
У ручной модели не установлен CPU limit, у платформенной он равен двум ядрам.
Ручная Tune, платформенная Gemma и Qwen TP2 также обработали по одному входу
57 344 и 122 880 токенов с выдачей 512 токенов, без ошибок.

**Qwen TP2, восемь клиентов:** 32K + 512 токенов на запрос,
262 144 входных и 4096 выходных токенов суммарно. Метрики зафиксировали
восемь running одновременно и отсутствие preemptions. Средний TTFT —
60,3 секунды: при длинных входах очередь и prefill по-прежнему заметны.
Это не проверка восьми историй по 128K.

Отдельно проверен возврат KV Qwen из RAM после заполнения GPU-кеша:
**1 239 220 224 CPU→GPU bytes и 64 416 external-prefix hits**.
Параметры сервера в этом опыте не менялись; это проверка механизма,
а не сравнение производительности. [Прежние серии Gemma](results/rtx5060-nodecache-20261006.json)
сохранены отдельно со своими условиями.

Для HA-шлюза отдельно проверяется общий лимит расходов: настройка бюджета
и корректная стоимость отдельного запроса ещё не доказывают его соблюдение.

</details>

<a id="cleanup"></a>
## Остановка после завершения работы

Останавливаем нагрузки только после финального вопроса, разбора личного VK
и сохранения результатов. Сначала скройте выключаемые маршруты в WebUI.
Для ручного профиля верните `replicaCount: 0` через GitOps.
Для платформенного — `order.enabled: false` и адресный prune только его
InferenceService по [процедуре остановки](docs/GITOPS.md#остановка).
Проверьте освобождение заявок. Не удаляйте namespace, Models, PVC,
пользователей и историю чатов.
Перед повтором показа верните выключенный Tune к окну 4096 и
`gpu-memory-utilization: 0.90`, а его пресет — к описанию 4K и ответу до 1024
токенов. Затем запустите только Base. Иначе следующий короткий A/B-замер
начнётся с разных профилей памяти.

<a id="setup"></a>
## Подготовка своего стенда

К началу основного маршрута запущена только ручная A; B и платформенные
Gemma/Qwen подготовлены, но не занимают RTX. Первая карта обслуживает A,
вторая свободна для первой B. Мониторинг уже собирает ручной runtime,
а новый одобренный пользователь получает личный VK и ответ A через WebUI.

В namespace `hardfest-rtx` заранее импортируются три артефакта:

| Объект Model | Репозиторий | Потребитель |
| --- | --- | --- |
| `rtx-gemma-e2b` | `google/gemma-4-E2B-it` | Все варианты Gemma |
| `rtx-gemma-e2b-assistant` | `google/gemma-4-E2B-it-assistant` | Speculative decoding Gemma |
| `rtx-qwen35-9b` | `Qwen/Qwen3.5-9B` | Финальный сервис TP2 |

Проверьте не только `Model Ready`, но и доставку на RTX-ноду, достаточную RAM
для двух настроенных Gemma и выбор длинных рецептов с assistant и offload.
`Pulling image` относится к OCI-образу runtime; NodeCache весов его не заменяет.
У Qwen MTP входит в основной checkpoint, отдельный Model для него не нужен.

[Подготовка стенда](docs/SETUP.md#rtx) содержит контексты, привязки площадки
и проверку стартового состояния. Сам показ проходит по этой странице.
Все публичные workload-профили по умолчанию выключены. Секреты и параметры
площадки задаются отдельно в частном окружении.
