# Инференс без простоя GPU: чиним LLM-сервис руками и делим карту на живом кластере

Александр Подмосковный, Флант / Deckhouse Platform

Вариант стенда: **две RTX 5060 Ti по 16 GiB и A30**.
[Вариант с двумя H100 и A30](README.md) — тот же доклад на других картах.

**Откройте [ai.ap4y.ru](https://ai.ap4y.ru), зарегистрируйтесь и дождитесь
одобрения.** Личный ключ и права выдаются автоматически; общий ключ вставлять
не нужно.

Первая модель, `Gemma A — Base`, уже работает. Начнём с вопроса в чате:
увидим задержку, найдём её причину на графиках и проверим, что изменилось
после настройки.

**LLM (Large Language Model)** — большая языковая модель.
**Инференс** — получение ответа от уже обученной модели, без нового обучения.

На двух GPU (Graphics Processing Unit — графический процессор) RTX 5060 Ti
по 16 GiB пройдём весь путь:

1. Посчитаем память KV-кеша (Key/Value — сохранённые ключи и значения токенов).
2. Включим две группы оптимизаций и расширим контекст до 128K.
3. Повторим запуск через AI Inference, подключим документы и голос на A30.
4. Отдадим обе RTX одной Qwen3.5-9B.

Все шаги этого варианта собраны на одной странице. Расчёты относятся
к Gemma E2B и Qwen3.5; цифры H100 на RTX не переносим.
**Участники работают в чате; изменения в Git
и запуск через Argo CD выполняет администратор стенда.**
На своей площадке их можно повторить самостоятельно.

![От уже работающей базовой Gemma через две итерации B к платформенной Gemma и Qwen TP2](assets/20-rtx-sequence.svg)

Веса уже доставлены, чат и графики подключены. По ходу работы будем менять
способ запуска, не аккаунты участников.

## Стенд и чат

![Два кластера: Open WebUI и A30, ai-mcp-gateway и две RTX 5060 Ti](assets/21-rtx-topology.svg)

| Компонент | Назначение |
| --- | --- |
| Две RTX 5060 Ti по 16 GiB на одной ноде | Две отдельные Gemma; в финале одна модель на обеих картах |
| ai-mcp-gateway | Маршруты моделей, личные Virtual Key, лимиты и учёт |
| Open WebUI | Один вход, история чатов, базы знаний и голос |
| A30 в соседнем кластере | Эмбеддер, реранкер и Whisper через AI Inference |
| ai-models | Каталог моделей и доставка весов на нужную ноду |
| AI Inference | Запуск модели из каталога по заказу InferenceService |
| Argo CD | Применение настроек из частного Git-репозитория k8s-config |

### Какие модели появятся в чате

| Этап | Первая RTX | Вторая RTX |
| --- | --- | --- |
| Начало | `Gemma A — Base` | Свободна |
| Первая настройка | Та же A | `Gemma B — Cache` |
| Вторая настройка | Та же A | `Gemma B — Tune` вместо Cache |
| Автоматический запуск | `Gemma A — DP` вместо Base | Та же Tune |
| Финал | `Qwen 9B — TP2` | Та же модель, вторая часть |

`DP` — подпись платформенного запуска, не Data Parallelism (параллельная
обработка разными копиями модели). `TP2` — Tensor Parallelism на двух GPU:
одна модель делится между картами. Подробно разберём это в финале.

Автоматическая подмена модели при ошибке (fallback) и кеш готовых ответов шлюза
для A/B отключены: иначе запрос может не попасть на сравниваемый экземпляр.

### Как устроен доступ

> **Virtual Key (VK)** — личный ключ шлюза. По нему проверяются разрешённые
> модели и лимиты, а запрос связывается с конкретным пользователем.

Участник после одобрения получает доступ к моделям, базам знаний и голосу.
Имена моделей меняются, пользователь и его накопленный расход — нет.

Административное подключение отдельно: вход по OIDC (OpenID Connect —
проверка личности через провайдера входа), инструменты по MCP (Model Context
Protocol — протокол подключения внешних инструментов к модели).
Обычному участнику инструменты управления Kubernetes не выдаются.

Сначала работаем с Base. Остальные модели появятся по мере запуска;
остановленные маршруты скрываются без удаления чатов и личных ключей.

## 1. Пробуем уже работающую Gemma A

### Первый вопрос и две задержки

1. Выберите `Gemma A — Base` в WebUI.
2. Спросите: «Почему длинная история чата занимает память GPU, если веса модели
   не меняются?» Затем задайте свой вопрос и попросите подробное объяснение.
3. Отметьте, когда начинается ответ и насколько быстро появляется текст.
4. Обновите страницу — ответ должен остаться в истории.

<details>
<summary>Что проверили, кроме готовности модели?</summary>

Вход → одобрение → личный VK → модель → сохранённый чат. Готовый Pod
не доказывает работу всей цепочки. К этому запросу вернёмся в журнале шлюза
в конце занятия; отдельный администраторский доступ участникам не нужен.

</details>

### Что запущено на первой карте

Пока модель отвечает, откроем `rtx-gemma-base` в Argo CD. Application уже
синхронизирован: видны применённый commit, [профиль A](values/rtx/gemma-base.yaml)
и заявка на одну RTX. Повторно запускать A не нужно.

Это ручной vLLM через Helm, ещё не InferenceService. **vLLM** — движок,
который обслуживает запросы к модели. Для программных запросов он предоставляет
**API (Application Programming Interface)** — интерфейс отправки запросов
и получения ответов. Helm собирает объекты Kubernetes из шаблонов и настроек `values`.

Такой порядок называют **GitOps**: настройки хранятся в Git, а Argo CD
применяет выбранную ревизию в кластере.

| Объект | Что означает в этом запуске |
| --- | --- |
| Pod | Контейнер с работающим vLLM |
| Deployment | Поддерживает нужное число Pod |
| ResourceClaim | Заявка на GPU |

| Параметр A | Значение |
| --- | --- |
| Движок | vLLM 0.31 |
| Окно | 4096 токенов |
| Активные последовательности | Не больше двух |
| Оптимизации | Prefix cache, chunked prefill, CUDA graphs, KV-offload и speculative decoding выключены |

**Токен** — единица текста модели: слово, часть слова или знак.
Сейчас сравниваем профили на одинаковой короткой нагрузке; длинное окно
проверим после настройки B. Искусственной задержки у A нет.

> [!IMPORTANT]
> Для этой архитектуры vLLM предупреждает, что отключение chunked prefill
> официально не поддерживается. A — контрольный опыт на 4K,
> а не рекомендуемая рабочая конфигурация. Длинное окно так не запускаем.

Каталог `hardfest-rtx` содержит Gemma, совместимый assistant и Qwen.
A использует только основную Gemma; assistant понадобится во второй настройке.

<a id="monitoring"></a>
### От ответа в чате к графикам

Перейдём в **AI Inference / Service performance**, выберем namespace
`hardfest-rtx` и Service `rtx-gemma-base`. На интервале только что заданных
вопросов должны быть новые запросы и токены. В дальнейшем A/B сравниваются
здесь же; после перехода к платформе изменится Service, а не дашборд.

| Вопрос | График или счётчик |
| --- | --- |
| Почему ответа ещё нет? | Очередь и TTFT |
| Почему текст появляется медленно? | TPOT / ITL и выходные токены/с |
| Переиспользуется ли префикс? | Запросы и попадания prefix cache |
| KV действительно вернулся из RAM? | CPU→GPU bytes и external-prefix hits |
| Assistant приносит токены? | Предложенные и принятые draft-токены |
| Где кончаются ресурсы? | VRAM, GPU KV, RAM контейнера, ошибки и перезапуски |

> **TTFT (Time to First Token)** — ожидание первого токена.
> **TPOT (Time per Output Token)** — среднее время на выходной токен после первого;
> **ITL (Inter-Token Latency)** — задержка между последовательными токенами.

VRAM (Video Random Access Memory) — память видеокарты.
RAM (Random Access Memory) — оперативная память сервера;
CPU (Central Processing Unit) — его центральный процессор.

Если график пуст, проверьте сервис, интервал и источник сбора метрик
(scrape target). Ручные A, Cache и Tune должны быть в фильтрах вместе
с платформенными сервисами. Для RTX нет NVLink-метрик.

Разные механизмы offload публикуют разные счётчики: у OffloadingConnector
не обязаны появляться графики Simple backend. Смотрим метрики того механизма,
который включён в профиле.

#### Контрольный замер без фоновых вопросов

Ненадолго приостановим свободные запросы. Одинаковую серию выполним сначала
на A, затем на двух конфигурациях B:

| Вход / выход на запрос | Запросов | Одновременно |
| --- | ---: | ---: |
| 2048 / 128 токенов | 8 | 2 |

128 выходных токенов — ограничение этого замера, не обычного разговора.
Сохраним ошибки и фактические длины; по графикам разберём, куда ушло время.

<details>
<summary>Одинаковая нагрузка для A, B Cache и B Tune</summary>

Команды выполняются в частном `k8s-config`; контексты и `NS=hardfest-rtx`
заданы при подготовке. Для каждой серии задайте новое имя файла:

```bash
export SERVICE=rtx-gemma-base SERIES=base-4k-1
# B1: export SERVICE=rtx-gemma-cache SERIES=cache-4k-1
# B2: export SERVICE=rtx-gemma-tune SERIES=tune-4k-1
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec "deployment/$SERVICE" -c vllm -- \
  vllm bench serve --backend vllm \
    --base-url "http://$SERVICE.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model "$SERVICE" \
    --tokenizer /data/modelcache/models/rtx-gemma-e2b \
    --dataset-name random --seed 42 \
    --random-input-len 2048 --random-output-len 128 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 2 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$SERIES.txt"
```

В JSON нужны completed=8, failed=0, total_input_tokens=16384,
total_output_tokens=1024. CLI может завершиться успешно и при ошибках запросов.

Повтор seed прогревает prefix cache: первый проход и повтор сравниваем отдельно.
Клиент внутри Pod влияет на CPU; это короткий опыт, не независимый нагрузочный стенд.

</details>

## 2. Разбираем время ответа

![Время ответа разделено на очередь, prefill, рассуждение и выдачу текста](assets/02-latency.svg)

```text
Tответа ≈ Tочереди + Tprefill + Tdecode + Tпрочее
```

| Этап | Что происходит | Что наблюдаем |
| --- | --- | --- |
| Очередь | Запрос ждёт возможности выполняться | Waiting / running и задержку |
| **Prefill** | Модель обрабатывает входную историю | Вклад в TTFT, особенно на длинном входе |
| **Decode** | Модель генерирует продолжение токен за токеном | TPOT / ITL и выходные токены/с |
| Прочее | Токенизация, сеть, шлюз | Разницу между замерами клиента и runtime |

**Reasoning** — генерируемое рассуждение, а не отдельный универсальный режим
вычислений. Оно занимает часть decode: первый видимый текст в UI может появиться
позже первого токена движка.

### Сначала прогноз, затем график

Что увеличит паузу перед первым словом: длинный вход или просьба дать длинный
ответ? Выберите вариант. Затем отправьте короткий запрос и запрос с длинным
входом, но тем же коротким ответом. Сравните TTFT и TPOT.

<details>
<summary>Разбор: почему одного GPU utilization недостаточно?</summary>

Длинный вход увеличивает работу prefill, длинный выход — число шагов decode.
Очередь, кеш и reasoning тоже влияют на задержку. Занятая память GPU не означает,
что вычислительные блоки непрерывно работают.

Prefill может упираться в вычисления, decode при малом batch — в чтение памяти.
Это гипотезы для проверки нагрузкой, не диагноз по одному проценту GPU utilization.
Для сравнения фиксируем длины входа и выхода, параллельность и reasoning.

</details>

<a id="memory"></a>
## 3. Считаем, что помещается в 16 GiB

| Часть памяти | Для чего нужна | Как меняется |
| --- | --- | --- |
| **Веса** | Выученные параметры модели | Общие для запросов одного экземпляра |
| **KV cache** | Сохранённые ключи и значения обработанных токенов | Растёт с историей и числом разных запросов |
| Рабочие буферы | Промежуточные вычисления, графы, служебные данные | Зависят от движка и профиля |

**Attention** связывает текущий токен с нужными частями контекста.
На таком слое текущий запрос **Q** сравнивается с ключами **K**;
полученные коэффициенты задают сумму значений **V**. Q нужен сейчас,
K/V сохраняем для следующих шагов.

**Головы** — несколько наборов attention-вычислений внутри слоя.
В **GQA (Grouped-Query Attention)** несколько query-голов используют общие K/V:
число KV-голов меньше числа query-голов.

### Считаем KV, а не угадываем по названию модели

После `t1, t2, t3` модель выдаёт `t4` и продолжает уже четыре токена.
KV-кеш избавляет её от повторного вычисления прошлых K/V, но требует места
для растущей истории. «Веса поместились» ещё не означает «поместились все запросы».

![От KV одного токена и слоя к формуле памяти нескольких независимых историй](assets/25-kv-derivation.svg)

Один токен одного слоя — два вектора на KV-голову, каждый по `D` элементов.
Для одинаковых full-attention слоёв и независимых историй одинаковой длины:

```text
KV = 2 × b × L × Hkv × D × S × N
```

| Символ | Что считаем |
| --- | --- |
| `2`, `b` | Ключи K и значения V; байт на элемент: BF16 — 2, FP8 — 1 |
| `L` | Число слоёв с собственным KV |
| `Hkv`, `D` | Число KV-голов и размерность головы |
| `S` | Токены входа **и** сгенерированного ответа |
| `N` | Число независимых историй — переменная, не цифра 8 |

BF16 (Brain Floating Point 16) и FP8 (Floating Point 8) — форматы чисел:
соответственно 2 и 1 байт на элемент KV в наших расчётах.

При разной длине вместо `S × N` подставляем `S₁ + … + Sₙ`.
**KV-головы — не query-головы; точность KV — не точность весов.**

### Подставляем архитектуру Gemma E2B

В [config.json Gemma E2B](https://huggingface.co/google/gemma-4-E2B-it/blob/3e22461f65e89153144f8adb70e3b8c2cc9845a7/config.json)
смотрим `text_config`. Из 35 слоёв последние 20 переиспользуют KV более ранних:
`num_kv_shared_layers=20`. Собственные K/V создают **15 слоёв: 3 full и 12 sliding**.

Это межслойное разделение внутри модели, не prefix cache между запросами.
[Как vLLM выбирает источник общего KV](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/gemma4.py#L473).

**Full attention** хранит всю историю; **sliding attention** в этом расчёте —
только последнее окно из 512 токенов. Для них нужны разные слагаемые.

| Собственный KV | Слоёв | KV-голов | Размерность | Длина |
| --- | ---: | ---: | ---: | --- |
| Full attention | 3 | 1 | 512 | `S` |
| Sliding attention | 12 | 1 | 256 | `min(S, 512)` |

![KV Gemma E2B на 128K: full 768 MiB плюс sliding 6 MiB; итого 774 MiB BF16 или 387 MiB FP8](assets/26-rtx-kv.svg)

#### От одного токена к длинной истории

Для BF16 промежуточный расчёт такой:

| Часть | Один токен одного слоя | Все слои этого типа |
| --- | --- | --- |
| Full | `2 × 1 × 512 × 2 = 2048 байт` | **6 KiB** на каждый токен истории |
| Sliding | `2 × 1 × 256 × 2 = 1024 байта` | **12 KiB** на токен последних 512 |

Отсюда формула основной Gemma на одну историю:

```text
KV(S) = 2 × b × [3 × 512 × S + 12 × 256 × min(S, 512)] байт
```

Берём **128K: 122 880 токенов входа + до 8192 токенов генерации = 131 072**.
Во вход входит шаблон чата, в генерацию — reasoning и финальный текст.

| Часть BF16 KV | Подстановка | Память |
| --- | --- | ---: |
| Full | `6 KiB × 131072` | 768 MiB |
| Sliding | `12 KiB × 512` | 6 MiB |
| Вся история | `768 + 6` | **774 MiB** |

Для FP8 элементов столько же, но каждый занимает вдвое меньше места:
**387 MiB на историю**.

```bash
awk -v S=131072 -v N=1 -v b=2 'BEGIN {
  W = S < 512 ? S : 512
  full = 2*b*3*1*512*S / 1048576
  local = 2*b*12*1*256*W / 1048576
  printf "Full %.0f + sliding %.0f = %.0f MiB/history; %d histories = %.0f MiB\n", full, local, full+local, N, N*(full+local)
}'
```

#### Одна и восемь независимых историй

| Независимые истории 128K | BF16 | FP8 |
| --- | ---: | ---: |
| 1 | 774 MiB | 387 MiB |
| 2 | 1548 MiB | 774 MiB |
| 4 | 3096 MiB | 1548 MiB |
| 8 | 6192 MiB | 3096 MiB |

Это полезный KV основной модели, ещё без assistant и резервов движка.
**Профиль Gemma допускает две последовательности, не восемь.** Последняя строка
показывает цену параллельности, а не обещает такой режим запуска.

У закреплённой Gemma E2B максимальный контекст — 131 072 токена.
Поэтому 256K для неё не задаём. У Qwen архитектура другая; её расчёт будет
[в разделе TP2](#qwen-long-context).

#### Проверка понимания: что именно растёт?

Вспомним контрольное окно: на 4K full занимает 24 MiB, sliding — 6 MiB.
Это **30 MiB BF16** на историю, **60 MiB** на две; в FP8 — 15 и 30 MiB.

Теперь сравним длинные истории: при переходе **64K → 128K**
получится 774 или 780 MiB BF16 на запрос?
Сначала назовите ответ, затем подставьте `S=65536` и `S=131072` в команду расчёта.
Окно работающей A пока не меняем.

<details>
<summary>Ответ и две типичные ошибки</summary>

**774 MiB BF16**: full вырос с 384 до 768 MiB, sliding осталось 6 MiB.
KV вырос с 390 до 774 MiB, не до 780: удваивается не вся память кеша.

Оценка будет неверной, если умножить все 35 слоёв на всю историю
или взять 8 query-голов вместо одной KV-головы.

</details>

### Почему процесс занимает гораздо больше

KV хранится блоками. Например, при условных 16 токенах в блоке история
из 35 токенов занимает три блока: два полных и один частичный.
Таблица истории указывает на эти физические блоки.

Совпавшие полные блоки префикса можно использовать повторно. После завершения
запроса его активные ссылки освобождаются, но кешированные блоки могут
сохраняться до вытеснения. В RAM будем переносить именно такие блоки.

16 — учебный пример; реальный размер блока и группы full/sliding смотрим
в запущенном движке.

![Бюджет памяти RTX: веса, служебная память и GPU KV; RAM хранит отдельную часть KV](assets/22-rtx-memory.svg)

774 MiB BF16 на 128K — полезные KV одной истории, не вся память GPU.
vLLM резервирует **пул** — набор блоков для обслуживания запросов.
Кроме него нужны веса, активации, буферы prefill, CUDA graphs и память assistant.

Бюджет пула: `Kpool ≈ G × u − W − R`.

| Символ | Что подставляем |
| --- | --- |
| `G` | Доступная память GPU |
| `u` | Доля памяти для движка из профиля |
| `W` | Память загруженных весов |
| `R` | Остальные резервы и рабочие буферы |

Если после них осталось 1 GiB, одна история FP8 128K требует 387 MiB,
две — 774 MiB, три — 1161 MiB и уже не помещаются. Это арифметический пример:
округление блоков и организация пула могут дополнительно уменьшить вместимость.

После старта выпишите GPU KV capacity из логов. На дашборде сравните занятость
пула для одного и двух запросов; затем для повторённого и нового префикса.

Размер заранее выделенного пула при этом может не меняться, хотя доля занятых
блоков меняется. [Read-only команды и границы сравнения](docs/MEMORY_BUDGET.md#verify-kv).

| Параметр | Gemma A | Gemma B | Qwen TP2 |
| --- | --- | --- | --- |
| GPU | 1 | 1 | 2 |
| Точность весов | BF16 | BF16 | BF16 |
| Окно | 4096 для контроля | 4096 для A/B → 131 072 | 131 072 в заранее подготовленном рецепте |
| Максимум последовательностей | 2 | 2 | 8, отдельно проверяем исполняемые запросы |
| CPU KV | Нет | 4 GiB | 16 GiB в длинном рецепте |

E2B в названии Gemma не означает файл ровно из двух миллиардов параметров:
полный BF16 checkpoint — набор файлов весов — занимает около 9,54 GiB.

Языковые веса Qwen вместе с MTP (Multi-Token Prediction — механизм
предсказания следующих токенов) занимают примерно 17,13 GiB:
больше доступных 15,93 GiB одной RTX. Поэтому в финале нужны обе карты —
без квантования весов и без их выгрузки в RAM. MTP разберём во второй настройке.

4K — контрольная точка сравнения, не конечная цель. Короткий A/B покажет
разницу скорости на одинаковой нагрузке; после настройки B проверим
вместимость сначала на 64K, затем на 128K.

<a id="ram"></a>
## 4. Первая итерация: prefix cache и KV в RAM

### Не считать общее начало заново

![Общий префикс обрабатывается один раз и используется последующими запросами](assets/14-prefix.svg)

> **Prefix caching** сохраняет результат обработки общего начала запросов.
> Модель использует готовые KV-блоки, вместо того чтобы повторять prefill.
> Это **не кеш готового ответа**.

Общее начало — системный промпт, документ, история. Совпадения по смыслу
недостаточно: нужны одинаковые токены. Для независимых коротких запросов
эффект может быть небольшим.

Но повтор полезен лишь пока сохранены вычисленные блоки. Если GPU-пул
понадобился другим документам, вернуться к старому префиксу можно через
его копию в RAM. Именно это добавляет KV-offload.

### Дать вытесненному кешу место в RAM

В [первом профиле B](values/rtx/gemma-cache.yaml) включены prefix cache,
FP8 KV и 4 GiB CPU KV. Chunked prefill, graphs и assistant ещё выключены.
Окно и параллельность пока те же, что у A. FP8 относится к KV, веса остаются BF16.

![KV-блоки уходят из GPU в RAM и возвращаются при повторном обращении](assets/05-kv-ram.svg)

**KV-offload** переносит блоки кеша между GPU и RAM сервера. Веса модели
остаются на GPU; физической VRAM больше не становится.

Цена восстановления приближённо равна `объём / эффективная полоса`.
Даже теоретические 387 MiB FP8 для истории 128K нужно реально передать обратно
и синхронизировать. Выигрыш появится, если это дешевле повторного prefill.

Скорость PCIe не берём из спецификации вместо измерения.

#### Запускаем B Cache рядом с A

1. В частном `values/gemma-cache.yaml` включим одну реплику.
   Отдельный Application `rtx-gemma-cache` ссылается только на этот профиль.
2. Проверим render, отправим commit и синхронизируем этот Application.
3. Дождёмся ответа API и откроем `Gemma B — Cache` в WebUI.
4. Зададим те же вопросы, затем повторим контрольную серию без фоновой нагрузки.

A всё это время остаётся на первой карте.

### Опыт: тот же документ, другой вопрос

1. В двух новых чатах B Cache отправьте **одинаковый документ примерно
   на 2000 токенов**, меняя вопрос в конце.
2. Сравните TTFT и prefix-cache hits первого и второго запросов.
   На дашборде выберите Service `rtx-gemma-cache`.
3. Измените начало документа. Сохранится ли выигрыш?

<details>
<summary>GPU-кеш или RAM: как различить?</summary>

Совпавшее начало позволяет повторно использовать KV. Изменение начала
уменьшает длину совпавшего префикса. Рост GPU cache hits ещё не доказывает
участие RAM.

Для проверки RAM вытесните исходный префикс другими запросами, затем повторите
его. **CPU→GPU bytes и external-prefix hits** подтверждают возврат KV.
Рост только GPU→CPU доказывает запись, но не чтение.

</details>

Если GPU-кеша хватает на всё, отдельный диагностический опыт уменьшает
его до 256 MiB. После проверки верните штатный размер; результаты диагностики
нельзя смешивать с A/B-замером.

### Работа в паре: сохраняем результат Cache

Пока Cache работает, один участник отправляет длинный вход, второй — короткий
запрос, пока первый ещё выполняется. Вход и ответ должны помещаться в окно 4K.
Сохраните оба текста, параметры генерации и интервал между отправками.

Отметьте на графиках задержку короткого запроса, очередь и ITL идущего ответа.
После следующей настройки повторим этот опыт на Tune.

<details>
<summary>Включить B Cache в Git и Argo</summary>

В `$RTX_DIR/values/gemma-cache.yaml` задайте `replicaCount: 1`.

```bash
set -o pipefail
helm template rtx-gemma-cache "$RTX_DIR/charts/vllm-runtime" -n "$NS" \
  -f "$RTX_DIR/values/gemma-cache.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

После успешной проверки:

```bash
git add -- "$RTX_DIR/values/gemma-cache.yaml"
git diff --cached --check
git diff --cached
git commit -S -s -m "Start RTX Gemma with prefix cache and RAM KV"
git push
git rev-parse HEAD
```

В Argo откройте `rtx-gemma-cache`, проверьте diff и выполните **Sync** этого
SHA без общего Prune. Дождитесь нового готового Pod, затем ответа API и чата.

Этот же порядок используем дальше для каждого изменённого профиля.
`helm upgrade` и `kubectl scale` поверх Argo не нужны.

</details>

Теперь мы умеем не пересчитывать знакомый вход. Но новый документ всё равно
нужно обработать, а каждый новый ответ — сгенерировать. Перейдём к вычислениям.

<a id="speculation"></a>
## 5. Вторая итерация: chunked prefill и speculative decoding

### Prefill: не задерживать все ответы одним длинным входом

![Планировщик чередует порции длинного prefill с генерацией текущих ответов](assets/06-scheduler.svg)

> **Chunked prefill** делит обработку длинного входа на порции.
> Между ними планировщик может продолжать decode уже начатых запросов.

В контрольном профиле RTX бюджет шага — 512 токенов, окно пока 4096.

| Параметр | Что ограничивает | Контрольная B |
| --- | --- | ---: |
| `max-model-len` | Вход и выход одной истории | 4096 токенов |
| `max-num-seqs` | Число одновременно обрабатываемых историй | 2 |
| `max-num-batched-tokens` | Объём работы одного шага | 512 токенов |

Например, в шаге на 512 токенов два обычных decode-запроса могут занять по
одному токену, а оставшийся бюджет — часть prefill. Это схема без деталей
speculation, не обещание фиксированного распределения каждого шага vLLM.

### Decode: предложить продолжение, затем проверить

![Совместимый assistant предлагает токены, основная Gemma проверяет продолжение](assets/07-speculation.svg)

> **Speculative decoding**: небольшая draft-модель предлагает продолжение,
> основная модель — target — его проверяет. **Assistant** — совместимая
> draft-модель Gemma, а не произвольная маленькая модель.

У этой Gemma assistant предлагает один токен за цикл методом MTP;
основная Gemma проверяет предложение.

Работа механизма видна по счётчикам предложенных и принятых токенов.
Его польза зависит от стоимости предложения, проверки и доли принятия.
Высокая доля принятия сама по себе не доказывает меньшую задержку.

Другие способы оптимизации требуют нескольких исполнителей и сегодня
остаются за рамками опыта:

| Технология | Идея |
| --- | --- |
| Cache-aware routing | Направить запрос в реплику, где уже есть нужный префикс |
| Prefill/decode disaggregation | Разделить обработку входа и генерацию между исполнителями |

[Пояснения и источники](docs/SOURCES.md).

### Меняем Cache на Tune

1. Скроем `Gemma B — Cache` в WebUI и дождёмся завершения её запросов.
2. Остановим `rtx-gemma-cache` через values и адресный Sync.
3. После освобождения claim включим отдельный `rtx-gemma-tune`
   с [полным вторым профилем](values/rtx/gemma-spec.yaml).
4. После ответа API откроем `Gemma B — Tune` в WebUI. A остаётся прежней.

Tune сохраняет все настройки Cache и добавляет chunked prefill, assistant
и CUDA graphs с capture size 4. **Два профиля B не работают одновременно.**

**CUDA graphs** переиспользуют подготовленную последовательность операций GPU,
уменьшая затраты на её повторный запуск. Они тоже требуют памяти.
CUDA (Compute Unified Device Architecture) — платформа вычислений NVIDIA.

### Повторяем опыт в паре: чей запрос ждёт?

На Tune отправьте те же два запроса с сохранёнными параметрами и интервалом:
сначала длинный, затем короткий, пока первый ещё выполняется. Окно остаётся 4K.
Сравните задержку короткого запроса, очередь и ITL с сохранённым результатом Cache.

<details>
<summary>Можно ли весь выигрыш приписать speculative decoding?</summary>

Нет. Chunked prefill меняет порядок обслуживания, assistant и CUDA graphs —
стоимость decode. Высокая доля принятых draft-токенов тоже не заменяет замер
задержки.

После свободных запросов повторяем контрольную нагрузку без помех: один seed,
2048 входных, 128 выходных токенов, 8 запросов, параллельность 2.
Холодный и прогретый кеш отмечаем отдельно. Это сравнение полных профилей,
не изолированный тест одной настройки.

</details>

При первом старте B компилируются основная модель и assistant, затем
захватываются CUDA graphs.
**NodeCache** хранит локальную копию весов, а не результаты компиляции
из временного каталога Pod.
Отсчитывайте готовность по Ready и успешному запросу, не по завершению чтения весов.

| Действие в частном Git | Application |
| --- | --- |
| `gemma-cache.yaml`: `replicaCount: 0`, commit/push и Sync | `rtx-gemma-cache` |
| После освобождения claim: `gemma-spec.yaml`, `replicaCount: 1`, render, commit/push и Sync | `rtx-gemma-tune` |

Application Tune читает `../../values/gemma-spec.yaml`; Cache и Tune
имеют разные Service и не управляют одним workload.

<a id="long-context"></a>
### Длинный контекст: 64K, затем 128K

Теперь проверим историю, которую контрольный A с окном 4K не принимает.
Этот отказ вызван **настроенным лимитом**. Он не доказывает нехватку VRAM
или необходимость KV-offload.

![Расчёт Gemma E2B для 4K, 64K и 128K и длины запросов для проверки](assets/27-rtx-long-context.svg)

В полном `values/gemma-spec.yaml` один раз расширим окно до 128K.
На этом запуске проверим сначала вход около 64K, затем около 128K;
отдельный перезапуск между запросами не нужен.

Assistant, prefix cache, FP8 KV, CPU KV 4 GiB и graphs сохраняем.
Бюджет chunked prefill остаётся 512: не нужно увеличивать один шаг
до размера всей истории.

```yaml
# Фрагмент существующего values; остальные поля сохраняются.
vllm:
  max-model-len: 131072
  gpu-memory-utilization: 0.95
  max-num-seqs: 2
  enable-chunked-prefill: true
  max-num-batched-tokens: 512
```

Проверьте render, отправьте diff и синхронизируйте `rtx-gemma-tune`.
После Ready проверьте фактическое окно, размер KV-пула и работу assistant.

`gpu-memory-utilization: 0.95` взято из успешного длинного прогона;
при 0.90 его первая проверка ёмкости KV не прошла.

В пресете **Gemma B — Tune** одновременно обновите описание окна на 128K
и `max_tokens` на 8192: увеличение серверного окна не снимает лимит ответа WebUI.

Длинный синтетический вход проверяет вместимость, не качество понимания.

<details>
<summary>Запросы около 64K и 128K</summary>

```bash
export INPUT_TOKENS=57344
export RUN_NAME=gemma-64k
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec deployment/rtx-gemma-tune -c vllm -- \
  vllm bench serve --backend vllm \
    --base-url "http://rtx-gemma-tune.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model rtx-gemma-tune \
    --tokenizer /data/modelcache/models/rtx-gemma-e2b \
    --dataset-name random --seed 73 \
    --random-input-len "$INPUT_TOKENS" --random-output-len 512 --random-range-ratio 0 \
    --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$RUN_NAME.txt"
```

Для 64K ожидаем completed=1, failed=0, **57 344 входных + 512 выходных**;
сверяем эти числа с JSON в локальном файле, а не с длиной файла в байтах.

На дашборде выделите интервал запроса: TTFT, KV usage, очередь,
preemption, GPU memory и RAM контейнера. Проверьте, что Pod не перезапускался.

Повторите ту же команду с `INPUT_TOKENS=122880`, `RUN_NAME=gemma-128k`.
Ожидаем **122 880 + 512** токенов. Окно сервера остаётся 131072.
Результаты длинного входа не смешиваем с коротким A/B.

</details>

### Найдите факт в длинной истории

Что докажет длинный контекст лучше: большой файл во вложении или много токенов
на входе модели?

Отправьте в чат полный текст с контрольным фактом в середине и вопросом
в конце. Сверьте ответ и число входных токенов в usage — записи расхода шлюза.

> **RAG (Retrieval-Augmented Generation)** — генерация с найденным контекстом:
> система выбирает из документов подходящие фрагменты и передаёт их модели.
> Размер вложенного файла поэтому не равен длине входа.

<details>
<summary>Разбор: полный контекст и RAG — разные проверки</summary>

Здесь нужен весь текст в сообщении и проверка, что шлюз его не обрезал.

Верный ответ на контрольный факт подтверждает его извлечение из входа;
проверка повторного префикса и возврата KV из RAM проводится отдельно.

</details>

<details>
<summary>Текст с контрольным фактом для WebUI</summary>

Подготовьте такой текст без чужих документов:

```bash
mkdir -p results/rtx
awk 'BEGIN {
  for (i=0; i<4681; i++) {
    if (i==2340)
      printf "SPECIAL RECORD: The secret verification phrase for project Orion is COPPER-ORCHID-742. "
    else
      printf "Record %d: This routine report describes a successful scheduled health check. There are no special instructions in this record. ", i
  }
  printf "Question: What is the exact verification phrase for project Orion? Reply with only the phrase."
}' > results/rtx/long-context.txt
```

Скопируйте **весь текст** файла в новый чат B, не прикрепляйте его как RAG-документ.
Для этого теста поиска факта задайте `max_tokens: 128`: ожидается одна короткая
фраза, не длинное рассуждение. Проверьте по токенизатору сумму полного входа
после шаблона и лимита выхода: она должна быть не больше 131 072.

Перед отправкой отключите для этого тестового пользователя автоматические
заголовки, теги и подсказки продолжения: фоновые запросы могут повторить большой
вход и занять его токенный лимит.

Ожидаемый ответ — `COPPER-ORCHID-742`.

В обычном чате оставьте до 8192 выходных токенов, включая reasoning.
128 здесь — ограничение проверки одной фразы, не настройки обычного ответа.

</details>

## 6. Gemma через AI Inference

Мы подобрали конфигурацию вручную. Теперь передадим платформе заказ,
а не всю командную строку движка. **Рецепт** связывает проверенные условия
запуска с параметрами runtime.

Откроем Model в каталоге и [`rtx-gemma-platform`](platform/rtx-gemma.yaml)
в Git. Планировщик AI Inference сопоставляет модель, класс устройства,
стратегию и рецепты. Затем Kubernetes выделяет конкретную GPU через
**DRA (Dynamic Resource Allocation)** — механизм заявок на устройства.

![Артефакты ai-models, заказ InferenceService, GPU-план и ответ в интерфейсе](assets/23-rtx-platform.svg)

### Заменяем A, оставляем B для сравнения

До переключения должны быть доставлены **оба** артефакта — Gemma и assistant —
и доступен рецепт с параметрами ручной B.

1. Скроем Base в WebUI и дождёмся завершения её запросов.
2. Остановим только ручную A через GitOps.
3. После освобождения claim включим заказ `rtx-gemma-platform`.

B остаётся на второй карте для сравнения.

| Параметр рецепта Gemma | Значение |
| --- | --- |
| Устройство и движок | RTX 5060 Ti, vLLM 0.31 |
| Стратегия | Throughput — приоритет пропускной способности |
| Окно / последовательности | 128K / 2 |
| KV | FP8; RAM-offload 4 GiB |
| Speculative decoding | Совместимый assistant |

Эти параметры приходят из выбранного рецепта, не из произвольных полей
`InferenceService.spec`. Для другого класса GPU или стратегии нужно проверить
выбор рецепта заново.

### Сверяем расчёт, план и работающую модель

В Argo увидим применение заказа. В консоли **GPU-кластер → hardfest-rtx →
AI-модели** откроем InferenceService, рассчитанный план, claim и Pod.

Если Pod получил 4096 вместо 128K, длинный профиль не выбран — сравнение
ещё не началось. Во время опыта ревизии основной Model и assistant не меняем.

Сопоставим ручной расчёт памяти, план платформы и фактические настройки
контейнера. При одинаковых настройках ожидаем сопоставимую работу:
платформа автоматизирует запуск того же движка.

После Ready и ответа API вернёмся в чат: рядом с ручной B появилась
`Gemma A — DP`. Повторим короткие вопросы и длинный текст.

На дашборде сравним два Service на одном интервале, а по счётчикам проверим
работу assistant и кешей.

#### Применить заказ из Git

В `$RTX_DIR/platform/rtx-gemma.yaml` включите `order.enabled: true`.
Это Helm values, а не сырой InferenceService:


| --- | --- | --- | --- |
| `rtx-gemma-platform` | `rtx-gemma-platform:80` | `rtx-gemma-e2b` | `Gemma A — DP` |

Включаем этот подготовленный маршрут.
Маршрут остановленной Base скрываем. Личные VK сохраняются: доступ к обоим

## 7. Базы знаний и голос: три сервиса на A30

### Несколько сервисов на одной карте

![На A30 две MIG-партиции: эмбеддер и реранкер через MPS, Whisper отдельно](assets/08-mig-mps.svg)

Теперь решим другую задачу: не отдавать целую GPU каждому небольшому сервису.
Сменим кластер в консоли и источник данных (datasource) в графиках на A30.
У RTX нет нужного аппаратного разделения.

Три модели заранее импортированы через ai-models в namespace **кластера A30**.
Создадим для них три InferenceService: эмбеддер, реранкер и Whisper.

| Механизм | Что делает | Важно не перепутать |
| --- | --- | --- |
| Device Plugin | Публикует устройства как ресурсы Kubernetes | Один из способов выдачи GPU |
| **DRA** | Выделяет устройства через классы и заявки ResourceClaim | В стенде используем этот механизм |
| **MIG (Multi-Instance GPU)** | Делит поддерживаемую карту на аппаратные части | Разделяет ресурсы самой GPU |
| **MPS (Multi-Process Service)** | Позволяет процессам совместно использовать вычисления | В стенде — внутри одной MIG-части |
| Time-slicing | Чередует доступ процессов к GPU | Не даёт аппаратного раздела памяти |

MIG и MPS не заменяют DRA: первые определяют использование карты,
а DRA — как Kubernetes запрашивает и выделяет ресурс.
[Термины, границы и сравнение с HAMi/Volcano](docs/SOURCES.md).

Сравним геометрию — набор аппаратных частей A30 — до и после заказов.
Динамическое создание требует свободных ресурсов, поддержки драйвера
и заранее включённого MIG mode.

Если части уже созданы, увидим выдачу готовых, а не изменение геометрии.
Эмбеддер и реранкер должны получить один идентификатор MIG (UUID), Whisper — другой.
**Работающие чужие партиции не переразмечаем.**

### Зачем нужны эмбеддер, реранкер и Whisper

| Сервис | Простое объяснение | Размещение |
| --- | --- | --- |
| Qwen3 Embedding 4B W4A16 | Превращает текст в числовой вектор для поиска по смыслу | Первая MIG-часть, MPS |
| Qwen3 Reranker 4B W4A16 | Пересортировывает найденные фрагменты по полезности для вопроса | Та же MIG-часть |
| Whisper large-v3 | Преобразует речь в текст | Вторая MIG-часть |

**W4A16** — 4-битные веса и 16-битные активации, то есть промежуточные
значения вычислений. Это не настройка KV-кеша.

### Создание сервисов и проверка геометрии

Сначала в терминале ноды A30 сохраните исходную геометрию:

```bash

nvidia-smi mig -lci
```

1. В `platform/embedding.yaml`, `reranker.yaml`, `whisper.yaml`

2. Синхронизируйте `hardfest-embedding-platform`, `hardfest-reranker-platform`
   и `hardfest-whisper-platform` с destination **кластера A30**.
3. Дождитесь готовности трёх InferenceService в консоли этого кластера.
4. Повторите команды на той же ноде и сравните геометрию.

Эмбеддер и реранкер должны получить один MIG UUID, Whisper — другой.
Теперь проверим не только размещение, но и ответы сервисов.

## 8. Qwen через AI Inference: TP2 и MTP

**Tensor Parallelism, TP2** — одна модель распределена по двум GPU;
карты совместно выполняют её вычисления. Это не две реплики и не TensorRT.

![Один Qwen разделён между двумя RTX 5060 Ti, в отличие от двух независимых реплик](assets/24-rtx-tp2.svg)

### Освобождаем обе карты и создаём заказ

1. Проверьте `rtx-qwen35-9b` в каталоге, готовность доставки на RTX
   и длинный Throughput-рецепт из таблицы ниже.
2. Скройте обе Gemma в WebUI и дождитесь завершения текущих запросов.
3. В ручной Tune задайте `replicaCount: 0`, в платформенной Gemma —
   `order.enabled: false`; сохраните изменения и примените их через GitOps.
4. После освобождения обеих DRA-заявок включите
   [`rtx-qwen35-tp2`](platform/rtx-qwen.yaml).

**Обычный Sync без Prune не удалит платформенную Gemma.**
Просмотрите diff и выполните адресный Prune только её InferenceService.
Модели и хранилище — Model и PVC — сохраняем.

В рецепте Qwen — **acceleratorCount=2**, `tensor-parallel-size: 2`, BF16,
длинное окно и MTP. DeviceClass выбирает подходящий тип GPU; число карт задаёт
рецепт и подтверждает ResourceClaim. Две реплики по одной GPU — другой опыт.

| Параметр Throughput-рецепта Qwen | Значение |
| --- | --- |
| Окно | 131 072 токена |
| Активные последовательности | До 8 |
| KV | FP8; RAM-offload 16 GiB |
| Speculative decoding | MTP, одно предложение за цикл |

Проверяем сначала один вход 57 344, затем 122 880 токенов; отдельно —
восемь разных входов по 32K. **Восемь полных историй по 128K вместе с весами
в VRAM этих карт не помещаются** — ниже посчитаем почему.

Настройки приходят из рецепта: дочерний StatefulSet не патчим.
Если он получил прежнее окно 8192, сначала исправляем выбор рецепта.

Откроем заказ, его GPU claim, затем Pod: число карт должно совпадать на всех
трёх уровнях. После API вернёмся в привычный чат, не создавая новый аккаунт.

В [сохранённом запуске с окном 8K](results/rtx5060-qwen-nodecache-20261006.json)
от создания Pod до Ready прошло **6 минут 36 секунд**; это не время старта рецепта 128K.
Веса прочитаны примерно за 6 секунд; оставшееся время включает инициализацию,
компиляцию и прогрев. NodeCache не устраняет эти этапы.

### MTP: draft внутри checkpoint

![Встроенный MTP предлагает продолжение, основная модель проверяет токены](assets/18-qwen-mtp.svg)

В отличие от Gemma, Qwen использует MTP-веса внутри своего checkpoint —
набора весов модели. Отдельный assistant не нужен.

Начните с одного speculative token. После запроса счётчик принятых токенов
должен увеличиться, но ускорение MTP on/off измеряется отдельно.

На RTX нет NVLink: обмен TP2 нельзя оценивать по цифрам H100.

После короткого ответа повторите длинную проверку на самом InferenceService:
входы 57 344 и 122 880 токенов, по 512 выходных. Окно сервиса уже 128K;
между этими запросами не меняем рецепт и не пересобираем модуль.

После API проверьте большой текст в WebUI: шлюз и настройки модели чата
не должны обрезать вход до прежних 8K.

Проверка завершения:

- В каталоге виден `Model rtx-qwen35-9b` с digest, а заказ ссылается на него через `ai-models`.
- `InferenceService Ready`; DRA выделил две разные RTX 5060 Ti, ошибок CUDA нет.
- API возвращает обычный и полный потоковый ответ; метрики MTP меняются.
- Длинные серии завершились без ошибок; сохранены фактические длины, память и TTFT для 64K/128K.
- Восемь сессий проверены с записью running, очереди и вытеснений; отдельно подтверждено чтение RAM-кеша обратно.
- В WebUI работает `Qwen 9B — TP2`, ответ сохраняется после обновления страницы.
- В ai-mcp-gateway запрос записан на личный VK; дашборд показывает Qwen.

### Длинный Qwen и восемь сессий

У Qwen3.5-9B 8 full-attention слоёв и 24 linear-attention слоя.
Full attention: 4 KV-головы по 256 элементов; при TP2 по две головы на GPU.
MTP добавляет ещё один full-attention слой. Для FP8 считаем:

```text
KV на GPU = 2 × 1 × 9 × (4 / 2) × 256 × S × N байт
```

`S` — вся история, включая ответ; `N` — число независимых историй.
Один токен всех девяти full-слоёв занимает на каждой GPU
`2 × 1 × 9 × 2 × 256 = 9216 байт = 9 KiB`.

Для одной истории 128K: `9 KiB × 131072 = 1,125 GiB` на GPU.
При восьми независимых историях: `1,125 × 8 = 9 GiB` **на каждой карте**.

| История | KV одной истории на GPU | Восемь историй на GPU |
| --- | ---: | ---: |
| 32K | 0,28125 GiB | 2,25 GiB |
| 64K | 0,5625 GiB | 4,5 GiB |
| **128K — окно нашего сервиса** | **1,125 GiB** | **9 GiB** |
| 256K — расчёт, не режим этого сервиса | 2,25 GiB | 18 GiB |

В [конфигурации Qwen](https://huggingface.co/Qwen/Qwen3.5-9B/blob/c202236235762e1c871ad0ccb60c8ee5ba337b9a/config.json)
допускается 262 144 позиции. Строка 256K показывает цену такого контекста;
наш рецепт и проверка остаются на 128K. Восемь историй 256K не помещаются
даже без весов: один их KV требует 18 GiB на карту.

Ещё нужны веса, состояние linear attention, буферы и округление блоков.
**Linear attention** хранит состояние иначе, чем K/V всей истории;
его нельзя просто умножить на длину входа той же формулой.

> [!IMPORTANT]
> Окно 128K не обещает восемь полных историй по 128K одновременно:
> их KV вместе с весами превышает память этих карт. RAM хранит кеш вне GPU,
> но не расширяет рабочую память attention. Проверяем отдельно один длинный
> вход, восемь входов по 32K и возврат вытесненного префикса из RAM.

Дополнительный full-attention слой виден в
[реализации MTP](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/qwen3_5_mtp.py#L111).

### Восемь запросов: исполняются или ждут?

До серии предположите: восемь клиентов получили ответ — значит ли это,
что все восемь выполнялись одновременно? Во время опыта смотрите
активные запросы, очередь и вытеснения, а не только число завершений.

<details>
<summary>Разбор и ориентир из записанного прогона</summary>

Нет: клиентская параллельность не равна числу исполняемых историй. Часть запросов
может ждать. Запишите максимум running, waiting, TTFT и preemptions — вытеснения
при нехватке ресурсов.

В [записанном опыте](results/rtx5060-rehearsal-20261008.json) восемь историй
по 32K действительно встретились в running одновременно; вытеснений не было.
Но средний TTFT составил **60,3 секунды**: очередь и prefill никуда не исчезли.

По 512 токенов ответа тоже занимают KV — строка 32K в таблице ещё не весь
бюджет такого запроса. Это не опыт с 8 × 128K.

</details>

<details>
<summary>Проверить длинный вход и восемь запросов</summary>

Сначала один длинный запрос. Укажите runtime-контейнер через `-c`, если их несколько.

При Token эта команда требует `OPENAI_API_KEY` в окружении клиента;
его готовят через Secret до занятия. Если его нет, используйте подготовленный
CPU-клиент с теми же параметрами; не отключайте аутентификацию.

```bash
export INPUT_TOKENS=57344 RUN_NAME=qwen-64k
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec rtx-qwen35-tp2-0 -- \
  vllm bench serve --backend vllm \
    --base-url "http://rtx-qwen35-tp2.$NS.svc.cluster.local" \
    --endpoint /v1/completions --model rtx-qwen35-9b \
    --tokenizer /data/modelcache/models/rtx-qwen35-9b \
    --dataset-name random --seed 73 \
    --random-input-len "$INPUT_TOKENS" --random-output-len 512 --random-range-ratio 0 \
    --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$RUN_NAME.txt"
```

Нужны completed=1, failed=0, заданный вход и 512 выходных токенов.
Повторите с `INPUT_TOKENS=122880 RUN_NAME=qwen-128k`, не меняя окно сервера.

Для восьми сессий в той же команде: вход 32768, seed 107,
`--num-prompts 8 --max-concurrency 8`, `RUN_NAME=qwen-8-sessions`.
Нужны completed=8, failed=0, 262144 входных и 4096 выходных токенов.

Одновременно смотрим running, waiting и preemptions: восемь клиентов
не доказывают восемь постоянно исполняемых историй.

Возврат из RAM проверяется по счётчикам выбранного backend:

| Backend в конфигурации и `/metrics` | Что должно увеличиться |
| --- | --- |
| OffloadingConnector | CPU→GPU bytes и external-prefix hits |
| Simple CPU | `vllm:simple_kv_offload_load_blocks_total` |

Отсутствие метрик другого backend не означает отказ offload.

<a id="conclusion"></a>
## 9. Запрос участника, личный ключ и стоимость

### Найдите свой запрос в шлюзе

Qwen и сервисы A30 ещё работают. Отправьте последний вопрос в чат,
затем найдите его в журнале Bifrost по времени и модели.

Проверьте четыре поля:

- Личный **VK пользователя**, не ключ подключения к vLLM.
- Число входных и выходных токенов.
- Расчётную стоимость запроса.
- Накопленный расход того же пользователя после перехода с Gemma на Qwen.

Сравните два одобренных аккаунта: у них должны быть разные VK.
Новый ключ при каждой смене модели не нужен.

### Из токенов в условную стоимость

Для демонстрационного учёта используем тарифы из
[примера политики](examples/webui-access.yaml):

| Параметр | Значение |
| --- | --- |
| Выдача ключа | Автоматически после одобрения аккаунта |
| Права | Разрешённые модели чата; без инструментов управления Kubernetes |
| Входные токены | $10 за миллион |
| Выходные токены | $20 за миллион |
| Бюджет VK | $500 с периодом сброса 24 часа |

**Деньги не списываются.** Это условные единицы для сравнения запросов,
не цена эксплуатации GPU и не счёт участнику.

Например, запрос с 122 880 входными и 8192 выходными токенами даёт:

```text
122880 × 10 / 1000000 + 8192 × 20 / 1000000 = $1,39264
```

Сумма считается по фактическим токенам, а не по настроенному максимальному
окну. Генерация заголовков и другие фоновые чат-запросы WebUI тоже попадают
в расход пользователя.

Индексация документов, reranking и голос используют
отдельные служебные подключения — личный VK чата не персонализирует их автоматически.

На HA-шлюзе (High Availability — несколько реплик для отказоустойчивости)
есть [известное ограничение общего счётчика бюджета](docs/CHAT_AND_ACCESS.md#проверить-выдачу-и-отзыв).
Стоимость записи можно проверять, но строгий общий лимит расходов $500
этим опытом не подтверждён.

### Что изменилось от первого вопроса до последнего

| Задача | Что использовали | Что проверили |
| --- | --- | --- |
| Не пересчитывать знакомый вход | Prefix cache и RAM-offload | Попадания кеша и возврат блоков из RAM |
| Обслуживать длинные входы и выдавать текст | Chunked prefill, assistant, CUDA graphs | TTFT, ITL, принятые draft-токены |
| Повторить подобранный запуск | AI Inference | Совпадение рецепта, плана и работающего сервиса |
| Совместить небольшие сервисы | MIG и MPS на A30 | Геометрия карты, ответы по документу и голос |
| Разместить модель больше одной карты | TP2 | Две GPU в одном заказе и ответы Qwen |

Высокий процент занятости GPU сам по себе не цель. Важно, сколько запросов
получили полный ответ с нужным контекстом и приемлемой задержкой —
и сколько ресурсов для этого понадобилось.

<a id="cleanup"></a>
## Остановка после завершения работы

Останавливаем нагрузки только после финального вопроса, разбора личного VK
и сохранения результатов.

1. Скройте выключаемые маршруты в WebUI.
2. Для ручного профиля верните `replicaCount: 0` через GitOps.
3. Для платформенного задайте `order.enabled: false` и выполните адресный
   Prune только его InferenceService по [процедуре остановки](docs/GITOPS.md#остановка).
4. Проверьте освобождение заявок.

**Namespace, Models, PVC, пользователей и историю чатов сохраняем.**

### Вернуться к началу сценария

У выключенного Tune восстановите:

- Окно `4096`, `gpu-memory-utilization: 0.90` в профиле.
- Описание 4K и ответ до 1024 токенов в пресете WebUI.

Затем запустите только Base. Это вернёт одинаковые условия короткого A/B.

## Подготовка своего стенда

К началу маршрута:

- Ручная A работает на первой RTX, вторая свободна для B.
- Профили B, платформенной Gemma и Qwen подготовлены, но выключены.
- Мониторинг собирает метрики ручного runtime.
- Новый одобренный пользователь получает личный VK и ответ A через WebUI.

В namespace `hardfest-rtx` заранее импортируются три артефакта:

| Объект Model | Репозиторий | Потребитель |
| --- | --- | --- |
| `rtx-gemma-e2b` | `google/gemma-4-E2B-it` | Все варианты Gemma |
| `rtx-gemma-e2b-assistant` | `google/gemma-4-E2B-it-assistant` | Speculative decoding Gemma |
| `rtx-qwen35-9b` | `Qwen/Qwen3.5-9B` | Финальный сервис TP2 |

Проверьте не только `Model Ready`, но и доставку на RTX-ноду, достаточную RAM
для двух настроенных Gemma и выбор длинных рецептов с assistant и offload.

`Pulling image` относится к контейнерному образу runtime; NodeCache весов его не заменяет.
У Qwen MTP входит в основной checkpoint, отдельный Model для него не нужен.

[Подготовка стенда](docs/SETUP.md#rtx) содержит контексты, привязки площадки
и проверку стартового состояния. Сам показ проходит по этой странице.

Все публичные workload-профили по умолчанию выключены. Секреты и параметры
площадки задаются отдельно в частном окружении.
