# Инференс без простоя GPU: чиним LLM-сервис руками и делим карту на живом кластере

Александр Подмосковный, Флант / Deckhouse Platform

Вариант стенда: **две RTX 5060 Ti по 16 GiB и A30**.
[Вариант с двумя H100 и A30](README.md) — аналогичная конфигурация на других картах.

Исходное состояние: `Gemma A — Base` работает на первой RTX, вторая свободна.
После регистрации и одобрения в [ai.ap4y.ru](https://ai.ap4y.ru) модель доступна
в чате; личный ключ подставляется автоматически.

<a id="ab"></a>
## 1. Базовая модель под нагрузкой

**Инференс** — получение ответа от обученной LLM (Large Language Model,
большой языковой модели). GPU (Graphics Processing Unit, графический
процессор) выполняет её вычисления. Ответ появляется **токенами**:
словами, частями слов или знаками в представлении модели.

Первый ответ подтверждает, что Base доступна. Затем серия запросов показывает
ожидание и темп продолжения. У этого экземпляра разрешены две активные
последовательности: дополнительные клиенты могут ждать даже у исправного сервиса.

<a id="monitoring"></a>
### Что ограничивает ответ

На дашборде **AI Inference / Service performance** выбираются namespace
`hardfest-rtx`, Service `rtx-gemma-base` и время нагрузки.
**Running / Waiting** показывают выполнение и очередь. Отдельно оцениваются
вычислительная утилизация GPU и занятость её памяти: это разные величины.

| Группа ограничений | Что требуется выяснить |
| --- | --- |
| Память | Помещаются ли веса и истории запросов; что можно переиспользовать |
| Вычисления | Почему долго обрабатывается вход или медленно идёт продолжение |
| Размещение | Нужна ли сервису целая GPU, её часть или несколько карт |

CPU, сеть и шлюз тоже могут создавать задержки. Поэтому высокая утилизация,
заполненная память или очередь по отдельности ещё не указывают причину.
Очередь вместе с вытеснениями из KV-пула ведёт к проверке памяти;
медленная генерация без вытеснений — к проверке времени вычислений.

### Одинаковая нагрузка для сравнения

Контрольная серия без фоновых запросов: **8 запросов × 2048 входных
и 128 выходных токенов, параллельность 2**. Она повторяется на Base,
Cache и Tune. Лимит 128 относится к замеру, не к обычному чату.

Base развёрнута через Helm: чарт формирует объекты Kubernetes
из [ручного профиля](values/rtx/gemma-base.yaml).
Профиль задаёт vLLM 0.31, окно 4K, без prefix cache, RAM-offload, CUDA graphs,
chunked prefill и speculative decoding.

> [!IMPORTANT]
> Отключение chunked prefill у Gemma E2B официально не поддерживается.
> Base — ограниченный контрольный профиль 4K, не конфигурация для длинного контекста.

<details>
<summary>Команда и критерии контрольной серии</summary>

`GPU_CONTEXT`, `RTX_DIR` и `NS=hardfest-rtx` заданы при
[подготовке](docs/SETUP.md#rtx). Каждой серии соответствует отдельный файл.

```bash
export SERVICE=rtx-gemma-base SERIES=base-4k-1
# B1: export SERVICE=rtx-gemma-cache SERIES=cache-4k-1
# B2: export SERVICE=rtx-gemma-tune SERIES=tune-4k-1
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec "deployment/$SERVICE" -c vllm -- \
  vllm bench serve --backend vllm \
    --base-url "http://$SERVICE.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model "$SERVICE" \
    --tokenizer /data/modelcache/models/rtx-gemma-e2b \
    --dataset-name random --seed 42 \
    --random-input-len 2048 --random-output-len 128 --random-range-ratio 0 \
    --num-prompts 8 --max-concurrency 2 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$SERIES.txt"
```

Критерии JSON: completed=8, failed=0, total_input_tokens=16384,
total_output_tokens=1024.
Первый проход и повтор с тем же seed учитываются отдельно: повтор прогревает кеш.

Для отдельного опыта с очередью та же команда запускается с
`--max-concurrency 8`, `SERIES=base-queue-8`. Это восемь одновременных клиентов
при лимите двух активных последовательностей, а не контрольное A/B.
Перед сравнением возвращается параллельность 2.

**TTFT (Time to First Token)** — время до первого токена;
**ITL (Inter-Token Latency)** — интервалы между токенами;
**TPOT (Time per Output Token)** — среднее время выходного токена после первого.
Клиент внутри Pod (группы контейнеров) делит CPU — центральный процессор —
с движком; это ограничение данного замера.

</details>

<a id="memory"></a>
## 2. Память: веса и KV-кеш

Веса — постоянные параметры модели, общие для запросов экземпляра.
Их грубая оценка: `число параметров × байт на параметр`.
Истории чатов растут, поэтому дополнительная память зависит от нагрузки.

**KV cache (Key/Value cache)** хранит ключи и значения обработанных токенов.
Модель использует их при продолжении истории, не вычисляя прошлые K/V заново.
Кроме весов и KV нужны рабочие буферы. VRAM (Video Random Access Memory) — память видеокарты,
RAM (Random Access Memory) — оперативная память сервера.

### Почему важна архитектура модели

**Attention** связывает текущий токен с контекстом. Слой с **full attention**
хранит KV всей истории; со **sliding-window attention** — только последнего
окна. Некоторые слои E2B переиспользуют чужой KV вместо собственной копии.
Поэтому расчёт «байты на токен» нельзя перенести с большой Gemma без изменений.

### Расчёт длинной истории Gemma E2B

У E2B собственный KV создают три слоя полной истории и двенадцать слоёв
последних 512 токенов. Остальные переиспользуют KV ранних слоёв.
Поэтому для `S ≥ 512` полезный кеш основной модели равен **`6 KiB × S + 6 MiB` в BF16**.

`S` включает вход и ответ. BF16 (Brain Floating Point 16) занимает
2 байта на элемент, FP8 (Floating Point 8) — 1; FP8 KV вдвое меньше.
Формат кеша не обязан совпадать с форматом весов.

| Длина всей истории | Одна история, BF16 / FP8 | Восемь независимых, BF16 / FP8 |
| --- | ---: | ---: |
| 64K | 390 / 195 MiB | 3120 / 1560 MiB |
| 128K | 774 / 387 MiB | 6192 / 3096 MiB |

128K — это, например, `122880 входных + 8192 ответа`.
Шаблон входит во вход, рассуждение модели — в выход.
**Максимум закреплённой E2B — 128K; профиль запускает две последовательности,
а восемь в таблице — расчёт, не обещание вместимости.**

<details>
<summary>Архитектура, полная формула и сверка с памятью runtime</summary>

Attention связывает текущий токен с контекстом: запрос Q сравнивается с K,
по результату смешиваются V. Сохраняются K/V, не Q.
Attention-головы — параллельные части этого механизма. В GQA (Grouped-Query
Attention) несколько query-голов используют общие KV-головы.

Для одинаковых слоёв:

```text
KV = 2 × b × L × Hkv × D × S × N
```

`2` — K и V; `b` — байт на элемент; `L` — слои с собственным KV;
`Hkv` — KV-головы; `D` — их размерность; `S` — длина;
`N` — независимые истории. При разных длинах вместо `S × N` используется их сумма.

В [закреплённой E2B](https://huggingface.co/google/gemma-4-E2B-it/blob/3e22461f65e89153144f8adb70e3b8c2cc9845a7/config.json)
35 слоёв, последние 20 переиспользуют KV. Оставшиеся слои имеют одну KV-голову:

| Тип | Слоёв | Размерность | Сохраняемая длина |
| --- | ---: | ---: | --- |
| Full attention | 3 | 512 | `S` |
| Sliding attention | 12 | 256 | `min(S,512)` |

```text
KV(S) = 2 × b × [3 × 512 × S + 12 × 256 × min(S, 512)] байт
```

При 128K и BF16 полная часть: `2 × 2 × 3 × 512 × 131072 = 768 MiB`.
Локальная: `2 × 2 × 12 × 256 × 512 = 6 MiB`. Итого 774 MiB,
FP8 — 387 MiB; для восьми независимых историй — 6192 / 3096 MiB.

```bash
awk -v S=131072 -v N=1 -v b=2 'BEGIN {
  W = S < 512 ? S : 512
  full = 2*b*3*1*512*S / 1048576
  local = 2*b*12*1*256*W / 1048576
  printf "Full %.0f + sliding %.0f = %.0f MiB/history; %d histories = %.0f MiB\n", full, local, full+local, N, N*(full+local)
}'
```

Общий prefix cache считается по уникальным блокам, а не автоматически
умножается на восемь. Межслойный sharing — другой механизм.

GPU-пул для KV приблизительно равен `Kpool ≈ G × u − W − R`: объём GPU,
доля использования, веса и прочие резервы. Формула KV не включает assistant,
рабочие буферы и округление блоков. Размер пула берётся из логов;
занятость — из метрик. [Подробная сверка](docs/MEMORY_BUDGET.md#verify-kv).

</details>

<a id="ram"></a>
### B Cache: повторное использование и вынос в RAM

**Prefix caching** переиспользует KV одинаковых начальных токенов.
Это кеш вычислений, не готового ответа. **KV-offload** сохраняет блоки
в RAM и возвращает на GPU при повторе. Веса остаются на GPU;
RAM не превращается в дополнительную VRAM для attention.

[Cache](values/rtx/gemma-cache.yaml) включается на второй карте:
4K, две последовательности, prefix cache, FP8 KV и 4 GiB RAM KV.
Остальные оптимизации выключены. **Для сохранения работающей A узлу
должно хватать RAM на оба экземпляра.**

<details>
<summary>Запуск отдельного приложения Cache</summary>

В `$RTX_DIR/values/gemma-cache.yaml` задаётся `replicaCount: 1`.
Проверка и отправка изменения:

```bash
set -o pipefail
helm template rtx-gemma-cache "$RTX_DIR/charts/vllm-runtime" -n "$NS" \
  -f "$RTX_DIR/values/gemma-cache.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

```bash
git add -- "$RTX_DIR/values/gemma-cache.yaml"
git diff --cached --check
git diff --cached
git commit -S -s -m "Start RTX Gemma with prefix cache and RAM KV"
git push
git rev-parse HEAD
```

В Argo CD приложение `rtx-gemma-cache` синхронизируется с этим SHA,
без общего Prune. После Ready и успешного ответа включается маршрут
`Gemma B — Cache` в WebUI. Дальнейшие изменения проходят тот же путь:
render → commit/push → адресный Sync, без прямого scale поверх GitOps.

</details>

Проверка использует два новых чата: одинаковый текст около 2000 токенов
**в начале сообщения**, разные вопросы в конце. Текст передаётся целиком,
не вложением и не через базу знаний. Сравниваются TTFT — время до первого
токена — и prefix-cache hits. Изменение начала текста убирает соответствующее
совпадение.

Возврат RAM подтверждается **CPU→GPU bytes и external-prefix hits**
после вытеснения исходного префикса другими запросами. Один GPU→CPU
доказывает только запись. Затем повторяется контрольная серия:
TTFT и очередь сравниваются при прежней нагрузке.

<details>
<summary>Если возврат RAM не виден</summary>

Backend определяется по конфигурации и `/metrics`. У OffloadingConnector
нужны CPU→GPU bytes и external-prefix hits; у Simple CPU —
`vllm:simple_kv_offload_load_blocks_total`.
Отсутствующий счётчик другого backend не означает отказ.

[Опыт вытеснения и повтора](docs/MEASUREMENTS.md#offload-replay) использует
`vllm.kv-cache-memory-bytes: 268435456` (256 MiB), один исходный вход на 3072
токена, 32 новых префикса и повтор исходного. До повтора фиксируются метрики,
после него — приращения. Затем ограничение GPU-пула снимается через Git/Argo.

Это диагностика механизма, не A/B рабочего профиля. Цена возврата — объём
и синхронизация при фактической полосе PCIe; offload не гарантирует ускорения.

</details>

Кеш уменьшает повторную работу. Новый вход и генерация ответа остаются
вычислительной задачей.

<a id="speculation"></a>
## 3. Вычисления: prefill и decode

<a id="latency"></a>
### Две фазы ответа

**Prefill** обрабатывает вход и строит его KV.
**Decode** последовательно генерирует продолжение.
Рассуждение (**reasoning**), если модель его выдаёт, тоже относится к decode;
оно может предшествовать видимому тексту.

![Очередь, prefill и decode в полном времени ответа](assets/02-latency.svg)

```text
Tответа ≈ Tочереди + Tprefill + Tdecode + Tпрочее
```

Prefill обрабатывает много токенов параллельно. При decode следующий токен
зависит от предыдущих. Длинный prefill может задерживать уже начатые ответы;
медленный decode — давать большие интервалы между токенами.

### Chunked prefill: длинный вход по частям

До остановки Cache выполняется смешанный тест: вход **3072 токена**, через
**50 мс** — вход **128 токенов**, у обоих выход 128. Пара помещается в окно 4K
и повторяется на Tune с теми же входами.
[Клиент с фиксированным расписанием](docs/MEASUREMENTS.md#mixed-prefill)
сохраняет реальные времена; заданная задержка сама по себе не доказывает перекрытия.

**Chunked prefill** делит вход на порции. В один шаг планировщик может
включить и порцию нового входа, и decode уже начатых ответов.
Длинный запрос перестаёт занимать весь шаг обработки входа.
Размер порции задаёт `max-num-batched-tokens`, а не длина всего контекста.

![Обработка длинного входа порциями оставляет место шагам decode](assets/06-scheduler.svg)

Меньшая порция может сократить паузы в соседнем ответе, но требует больше
шагов для самого входа. Поэтому сравниваются оба запроса, не только короткий.

### Speculative decoding: черновик и проверка

Маленькая **draft-модель** предлагает продолжение, основная **target-модель**
проверяет несколько предложенных токенов за проход. Принятый префикс остаётся
в ответе; после первого отказа хвост отбрасывается и продолжение исправляется.

![Основная модель принимает начало черновика, но отбрасывает неверный хвост](assets/07-speculation.svg)

У Gemma draft — совместимый **assistant**, не произвольная маленькая модель.
Профиль использует **MTP (Multi-Token Prediction)** с одним предлагаемым токеном.
Стоимость черновика тоже входит во время ответа. Даже высокая доля принятых
токенов не гарантирует ускорения: оно проверяется по времени генерации.

### B Tune: второй шаг настройки

Tune сохраняет кеши и добавляет эти механизмы вместе с **CUDA graphs** —
переиспользуемой последовательностью операций GPU, уменьшающей расходы на их запуск.

Маршрут `Gemma B — Cache` скрывается от новых запросов. После завершения
текущих Cache останавливается, и только после освобождения карты запускается
**отдельное приложение Tune**. A не меняется; два профиля B одновременно не работают.

<details>
<summary>Параметры и переключение Cache → Tune</summary>

| Приложение | Файл | Значение |
| --- | --- | --- |
| `rtx-gemma-cache` | `values/gemma-cache.yaml` | `replicaCount: 0` |
| После освобождения GPU: `rtx-gemma-tune` | `values/gemma-spec.yaml` | `replicaCount: 1` |

Каждый шаг проходит render, commit/push и Sync своего приложения.
Tune использует полный профиль, не наложение поверх Cache:
окно 4096, `max-num-seqs: 2`, `max-num-batched-tokens: 512`,
CUDA graphs capture size 4, FP8 KV и 4 GiB RAM KV.

Первый запуск включает компиляцию и прогрев. NodeCache хранит локальные
веса, не результаты компиляции из временного каталога Pod.
Готовность подтверждается ответом после Ready.
Только затем в WebUI включается маршрут `Gemma B — Tune` на
`rtx-gemma-tune:8000`, served model `rtx-gemma-tune`. Маршрут Cache остаётся
скрытым; личный ключ пользователя и его лимиты не заменяются.

</details>

Смешанная нагрузка и короткая контрольная серия повторяются на Tune.
Сравниваются очередь, TTFT и **ITL (Inter-Token Latency)** — интервалы
между выходными токенами. Это сравнение **наборов настроек**,
не изолированное ускорение от assistant.

<a id="long-context"></a>
### Длинный контекст отдельно от короткого A/B

После сравнения окно Tune расширяется до **131072**, параллельность остаётся 2,
бюджет шага — 512. В WebUI лимит ответа становится **8192**.
Вход, шаблон и допустимый выход вместе должны помещаться в окно.

Проверка использует входы **57344**, затем **122880** токенов с выходом 512
на одном запуске 128K. Отказ Base принять их означает её лимит 4K,
а не доказанную нехватку VRAM.

<details>
<summary>Параметры 128K и команды длинных запросов</summary>

В полном `values/gemma-spec.yaml` меняются эти поля:

```yaml
# Фрагмент существующего values; остальные поля сохраняются.
vllm:
  max-model-len: 131072
  gpu-memory-utilization: 0.95
  max-num-seqs: 2
  enable-chunked-prefill: true
  max-num-batched-tokens: 512
```

После render, commit/push и Sync `rtx-gemma-tune` сверяются фактическое окно,
пул KV и assistant. `0.95` использовано в успешном прогоне;
при `0.90` первая проверка ёмкости KV не прошла.

```bash
export INPUT_TOKENS=57344
export RUN_NAME=gemma-64k
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec deployment/rtx-gemma-tune -c vllm -- \
  vllm bench serve --backend vllm \
    --base-url "http://rtx-gemma-tune.$NS.svc.cluster.local:8000" \
    --endpoint /v1/completions --model rtx-gemma-tune \
    --tokenizer /data/modelcache/models/rtx-gemma-e2b \
    --dataset-name random --seed 73 \
    --random-input-len "$INPUT_TOKENS" --random-output-len 512 --random-range-ratio 0 \
    --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$RUN_NAME.txt"
```

Первая серия: completed=1, failed=0, 57344 + 512 токенов.
Для второй: `INPUT_TOKENS=122880`, `RUN_NAME=gemma-128k`;
критерий — 122880 + 512. Результат включает память, ошибки и перезапуски.

</details>

Длина входа ещё не доказывает извлечение информации. Дополнительный тест
передаёт полный текст с контрольным фактом в середине и вопросом в конце;
проверяются точный ответ и число входных токенов в журнале.

<details>
<summary>Текст для проверки длинного контекста в WebUI</summary>

```bash
mkdir -p results/rtx
awk 'BEGIN {
  for (i=0; i<4681; i++) {
    if (i==2340)
      printf "SPECIAL RECORD: The secret verification phrase for project Orion is COPPER-ORCHID-742. "
    else
      printf "Record %d: This routine report describes a successful scheduled health check. There are no special instructions in this record. ", i
  }
  printf "Question: What is the exact verification phrase for project Orion? Reply with only the phrase."
}' > results/rtx/long-context.txt
```

В чат передаётся всё содержимое файла, не вложение для поиска фрагментов.
После шаблона вход плюс лимит выхода не превышают 131072.
Для единственной фразы достаточно `max_tokens: 128`;
ожидается `COPPER-ORCHID-742`. Обычный чат сохраняет лимит 8192.

Фоновые заголовки, теги и подсказки у тестового пользователя временно
выключены: они могут повторно отправлять длинный вход.

</details>

За пределами этой конфигурации остаются
[prefill/decode disaggregation](https://docs.vllm.ai/en/v0.31.0/features/disagg_prefill/) —
разные исполнители стадий с передачей KV — и
[cache-aware routing](https://docs.dynamo.nvidia.com/dynamo/knowledge-base/concepts/system-architecture/kv-aware-routing) —
выбор реплики с нужным кешем и доступной ёмкостью.

Даже настроенному движку нужно подходящее размещение: маленькому сервису
может быть достаточно части GPU, большой модели — недостаточно целой.

<a id="placement"></a>
## 4. Размещение моделей на GPU

Целая карта под небольшой сервис может оставаться почти пустой, но быть
недоступной другим Pod. Эта проблема решается не настройкой генерации,
а способом выделения устройств.

### От Device Plugin к DRA

**Device Plugin** публикует целочисленные extended resources:
например, `nvidia.com/gpu: 1`. Стандартный запрос выражает количество,
но не выбор по произвольным атрибутам GPU. Реализации могут дополнительно
предлагать MIG и sharing.
[Device plugins в Kubernetes](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/).

**DRA (Dynamic Resource Allocation)** использует отдельную заявку
**ResourceClaim** и класс **DeviceClass**. Это позволяет выбирать устройство
по атрибутам и передавать настройки драйверу для workload.
DRA не гарантирует нарезку любой карты: нужны поддержка железа и драйвера.
[Авторский разбор](https://habr.com/ru/companies/flant/articles/1020276/),
[документация Kubernetes](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/).

### Три сервиса на A30

**MIG (Multi-Instance GPU)** создаёт аппаратные части с собственной долей
памяти и вычислений. **MPS (Multi-Process Service)** позволяет процессам
совместно использовать вычисления внутри выбранной части; новой аппаратной
границы памяти он не создаёт.

![Два процесса в первой MIG-части, Whisper во второй](assets/08-mig-mps.svg)

В соседнем кластере A30 заранее подготовлены:

| Сервис | Назначение | Размещение |
| --- | --- | --- |
| Qwen3 Embedding 4B W4A16 | Векторы для поиска текста | Общая MIG-часть через MPS |
| Qwen3 Reranker 4B W4A16 | Пересортировка найденного | Та же MIG-часть через MPS |
| Whisper large-v3 | STT (Speech-to-Text), речь в текст | Отдельная MIG-часть |

W4A16 — 4-битные веса и 16-битные активации, промежуточные значения модели.
У эмбеддера и реранкера ожидается один MIG UUID — идентификатор части,
у Whisper — другой.
Консоль и источник метрик здесь относятся к A30, не к RTX.

```bash
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

<details>
<summary>Связь Pod → заявка → MIG и проверка MPS-клиентов</summary>

Для эмбеддера, реранкера и Whisper проверяется не только список частей,
но и фактически выделенное устройство:

```bash
kubectl --context "$MIG_CONTEXT" -n hardfest-demo get pods -o wide
export A30_POD=REPLACE_EMBEDDING_POD
kubectl --context "$MIG_CONTEXT" -n hardfest-demo get pod "$A30_POD" \
  -o jsonpath='{.spec.resourceClaims}{"\n"}{.status.resourceClaimStatuses}{"\n"}'
export A30_CLAIM=REPLACE_ALLOCATED_CLAIM
kubectl --context "$MIG_CONTEXT" -n hardfest-demo get resourceclaim "$A30_CLAIM" \
  -o jsonpath='{.status.allocation.devices}{"\n"}'
kubectl --context "$MIG_CONTEXT" -n hardfest-demo exec "$A30_POD" \
  -c REPLACE_RUNTIME_CONTAINER -- nvidia-smi -L
```

Имя заявки берётся из Pod; идентификатор выделенного устройства сопоставляется
с MIG UUID по данным драйвера и `nvidia-smi`. Так проверяется общая часть у двух
моделей, а не просто наличие двух разделов на карте.

Конфигурация MPS в заявке — ещё не список подключённых процессов.
В контейнере управляющего процесса MPS на A30, с его
`CUDA_MPS_PIPE_DIRECTORY`, [интерфейс MPS v2](https://docs.nvidia.com/deploy/mps/mpsv2-interface.html)
позволяет прочитать:

```bash
printf 'get_server_list\n' | nvidia-cuda-mps-control
export MPS_SERVER_PID=REPLACE_SERVER_PID
printf 'get_client_list %s\n' "$MPS_SERVER_PID" | nvidia-cuda-mps-control
```

PID сервера берётся из первого ответа. Клиенты сопоставляются с процессами
эмбеддера и реранкера по логам драйвера. Без этой сверки фактическое использование
MPS не подтверждено. Команды только читают состояние; новый MPS-сервер не запускается.

</details>

**MIG mode включён заранее; чужие workloads и режим карты не меняются.**
Готовые части не доказывают динамическую нарезку.
Для этого сравниваются состояния до и после
[создания заказов](#a30-orders) при свободных ресурсах.

### Проверка поиска и голоса

**RAG (Retrieval-Augmented Generation)** дополняет вопрос найденными
фрагментами документа. Эмбеддер переводит текст в векторы; поиск в индексе
находит похожие фрагменты, реранкер уточняет их порядок, модель чата отвечает.

Контрольный документ: «В проекте “Липа” окно обслуживания начинается
во вторник в 16:40». Он добавляется в базу знаний WebUI, индексируется,
затем база подключается к чату. Один вопрос проверяется без базы и с ней.
Критерии — точный факт, ссылка на источник и запросы к обоим сервисам в метриках.
Голосовая версия дополнительно проверяет распознанный текст Whisper.

Теперь известны и параметры движка, и требования к размещению.
Собирать их вручную для каждой модели неудобно; следующая часть
автоматизирует именно эту работу.

<a id="platform"></a>
## 5. Автоматический запуск через AI Inference

**ai-models** хранит каталог и доставляет закреплённые веса.
**InferenceService** — заказ на запуск модели.
Планировщик AI Inference сопоставляет четыре входа:

| Вход | Решение |
| --- | --- |
| Архитектура модели | Совместимость и потребность в памяти |
| Требования заказа | Стратегия, контекст и ограничения |
| Класс оборудования | Объём VRAM, число GPU, возможности |
| Рецепты | Конкретные параметры движка |

План описывает запуск, Kubernetes выделяет устройство через DRA.
Успешный расчёт ещё не означает готового ответа.

![От модели и требований к плану и работающему сервису](assets/23-rtx-platform.svg)

### Платформенная Gemma вместо Base

В каталоге проекта `hardfest-rtx` Gemma должна иметь статус «Скачана»,
assistant также доставлен. **«Запустить инференс»** ведёт к заказу.
Нужны класс RTX 5060 Ti и рецепт Throughput: vLLM 0.31, **128K,
две последовательности, FP8 KV, 4 GiB RAM KV и assistant**.

В этом руководстве тот же заказ хранится в Git и применяется Argo CD,
без второго создания через UI. В «Сервисах инференса» видны план,
подготовка и готовность экземпляра.

**Узлу требуется RAM на обе Gemma.** После завершения запросов Base
останавливается. Платформенная A занимает освободившуюся GPU;
ручная Tune остаётся для сравнения.

<details>
<summary>Заказ Gemma и проверка API</summary>

После остановки Base через GitOps и освобождения её GPU в
`$RTX_DIR/platform/rtx-gemma.yaml` задаётся `order.enabled: true`.

```bash
set -o pipefail
helm template rtx-gemma-platform "$RTX_DIR/charts/inference-service" -n "$NS" \
  -f "$RTX_DIR/platform/rtx-gemma.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

Далее commit/push и Sync `rtx-gemma-platform`.
При Ready и ответе API маршрут `Gemma A — DP` заменяет Base в WebUI.
DP — имя платформенного варианта, не Data Parallelism.
Service — `rtx-gemma-platform:80`, модель — `rtx-gemma-e2b`.

Для проверки API (Application Programming Interface — программного интерфейса)
в отдельном терминале запускается port-forward:

```bash
kubectl --context "$GPU_CONTEXT" -n "$NS" port-forward svc/rtx-gemma-platform 18005:80
```

Следующие запросы выполняются в основном терминале.
При Token ключ вводится из менеджера секретов, не помещается в Git
или аргументы командной строки:

```bash
set +x
IFS= read -r -s MODEL_API_KEY
curl --fail --max-time 30 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  http://127.0.0.1:18005/v1/models
curl --fail-with-body --max-time 180 \
  --header @<(printf 'Authorization: Bearer %s\n' "$MODEL_API_KEY") \
  -H 'Content-Type: application/json' http://127.0.0.1:18005/v1/chat/completions \
  -d '{"model":"rtx-gemma-e2b","max_tokens":512,"temperature":0,"messages":[{"role":"user","content":"Зачем нужен KV-кеш?"}]}'
unset MODEL_API_KEY
```

После проверки терминал с port-forward закрывается.
Для API без Token отсутствуют ввод ключа и оба заголовка авторизации;
политика ради теста не меняется. Позже Qwen проверяется аналогично:
`svc/rtx-qwen35-tp2`, его ключ и модель `rtx-qwen35-9b`.

</details>

План и фактические параметры должны совпасть с Tune: окно 4096 вместо
131072 означает неверный рецепт. Одинаковые короткие и длинные запросы
проверяют задержки, ошибки, assistant и кеш. Обе модели должны
присутствовать в фильтре дашборда.

<details>
<summary>Числовое сравнение Tune и автоматического запуска одним CPU-клиентом</summary>

[Общий Job](examples/gemma-benchmark-job.yaml) проверяет ручную Tune, затем
автоматическую Gemma. Для каждой делает первый проход и повтор и выгружает
четыре отдельных JSON. Копия готовится из корня частного `k8s-config`:

```bash
export BENCH_DIR="$(mktemp -d)"
cp ../hardfest-gpu-workshop/examples/gemma-benchmark-job.yaml "$BENCH_DIR/job.yaml"
```

В редакторе задаются параметры RTX:

| Поле | Значение |
| --- | --- |
| `metadata.namespace` | `hardfest-rtx` |
| `MANUAL_BASE_URL` / `MANUAL_MODEL` | `http://rtx-gemma-tune.hardfest-rtx.svc.cluster.local:8000` / `rtx-gemma-tune` |
| `PLATFORM_BASE_URL` / `PLATFORM_MODEL` | `http://rtx-gemma-platform.hardfest-rtx.svc.cluster.local:80` / `rtx-gemma-e2b` |
| `TOKENIZER_ID` | `google/gemma-4-E2B-it` |
| `TOKENIZER_REVISION` | `3e22461f65e89153144f8adb70e3b8c2cc9845a7` |
| `INPUT_TOKENS` / `OUTPUT_TOKENS` / `CONCURRENCY` | `2048` / `128` / `2` |

`NUM_PROMPTS=8` и `BENCH_TARGET=both` сохраняются. Задаются CPU-нода и ссылки
на Secrets в `hardfest-rtx`. `HF_TOKEN` позволяет скачать только токенизатор;
ключ платформенного API хранится в отдельном Secret. Для ручной модели без
авторизации допустима optional-ссылка на отсутствующий `replace-manual-runtime-api-secret`.
Значения ключей в файл не попадают; авторизация платформы не отключается.

У обеих Gemma — одинаковые 128K и полный профиль Tune. CPU-нода должна
достигать обоих Service. Копия получает уникальное имя Job и `spec.suspend: false`:

```bash
kubectl --context "$GPU_CONTEXT" create --dry-run=server -f "$BENCH_DIR/job.yaml"
kubectl --context "$GPU_CONTEXT" create -f "$BENCH_DIR/job.yaml"
export BENCH_JOB=gemma-benchmark
kubectl --context "$GPU_CONTEXT" -n hardfest-rtx logs -f "job/$BENCH_JOB" \
  --pod-running-timeout=5m | tee "$BENCH_DIR/benchmark.log"
kubectl --context "$GPU_CONTEXT" -n hardfest-rtx get job "$BENCH_JOB"
```

`BENCH_JOB` — выбранное имя. Этот временный Job не меняет настройки моделей.
В четырёх блоках `RESULT_JSON_BEGIN` / `RESULT_JSON_END` ожидаются
`completed=8`, `failed=0`, 16 384 входных и 1024 выходных токена на серию.
Неполная серия завершает Job ошибкой. Логи сохраняются до его удаления через сутки.

Сопоставляются первые проходы между собой и повторы между собой.
«Первый» не означает пустой серверный кеш. Три запуска с новыми именами Job
показывают разброс; короткая серия не заменяет проверку длинного входа.

</details>

Автоматизация сокращает ручной подбор. Время до Ready и скорость ответа
измеряются отдельно — сам заказ не делает движок быстрее.

<summary>Первоначальное создание сервисов A30</summary>

<a id="conclusion"></a>
## 6. Шлюз и модель на двух GPU

<a id="topology"></a>
### Пользовательский запрос через шлюз

**ai-mcp-gateway** с Bifrost связывает WebUI с маршрутами моделей.
**VK (Virtual Key)** закрепляет доступ, лимиты и учёт за пользователем.
После одобрения аккаунта личный VK должен создаваться автоматически;
у двух пользователей — разные ключи. Это не ключ подключения к vLLM.

В журнале запроса проверяются владелец, выбранная модель, входные и выходные
токены и расчётная стоимость. Тарифы стенда условные, деньги не списываются.
Подробности политики и ограничений учёта — в
[описании доступа](docs/CHAT_AND_ACCESS.md).

Смена модели не должна менять пользователя, терять историю или базу знаний.
Теперь через тот же маршрут запускается модель, которой действительно
нужны обе RTX.

<a id="tp2"></a>
### Qwen: одна модель на двух GPU

Языковые веса Qwen3.5-9B вместе с MTP занимают около **17,13 GiB**,
доступная память одной RTX — около **15,93 GiB**.
**TP2 (Tensor Parallelism)** распределяет одну модель между двумя GPU;
это не две реплики и не TensorRT.

![Qwen распределена между двумя RTX](assets/24-rtx-tp2.svg)

MTP Qwen находится в основном checkpoint, отдельный assistant не нужен.
Рецепт задаёт один предлагаемый токен, окно **128K**, до **8 активных
последовательностей**, FP8 KV и **16 GiB RAM-offload**.

До остановки Gemma должны быть готовы Model `rtx-qwen35-9b`,
доставка и длинный рецепт TP2/MTP. Затем обе Gemma завершают запросы
и освобождают карты. **Models, PVC и данные не удаляются.**

<details>
<summary>Остановка Gemma и заказ Qwen</summary>

Ручная Tune получает `replicaCount: 0` через GitOps.
Платформенная Gemma — `order.enabled: false` и адресный
**Prune только её InferenceService**; обычного Sync для удаления недостаточно.

После освобождения обеих GPU в `$RTX_DIR/platform/rtx-qwen.yaml`
задаётся `order.enabled: true`:

```bash
set -o pipefail
helm template rtx-qwen35-tp2 "$RTX_DIR/charts/inference-service" -n "$NS" \
  -f "$RTX_DIR/platform/rtx-qwen.yaml" |
  kubectl --context "$GPU_CONTEXT" apply --dry-run=server -f -
```

Commit/push и Sync `rtx-qwen35-tp2`. В плане, ResourceClaim и Pod —
две GPU, `tensor-parallel-size: 2`, окно 131072.
Параметры приходят из рецепта, дочерний StatefulSet вручную не меняется.

После ответа API включается `Qwen 9B — TP2`:
Service `rtx-qwen35-tp2:80`, модель `rtx-qwen35-9b`.
Прежнее окно 8192 требует исправления выбора рецепта.

</details>

<a id="qwen-long-context"></a>
### Длинный контекст и восемь сессий

Full-attention KV Qwen с MTP занимает **9 KiB на токен на каждой GPU**.
Для восьми независимых историй объём умножается на восемь:

| Вся история | Одна на GPU | Восемь на GPU |
| --- | ---: | ---: |
| 32K | 0,28125 GiB | 2,25 GiB |
| 128K | 1,125 GiB | 9 GiB |
| 256K, только расчёт | 2,25 GiB | 18 GiB |

**Восемь полных историй 128K с весами не помещаются в этих RTX.**
RAM-offload не расширяет рабочую память attention.
Поэтому отдельно проверяются один длинный вход и восемь входов по 32K;
окно сервиса остаётся 128K.

<details>
<summary>Вывод KV Qwen и команды проверок</summary>

В [закреплённой Qwen](https://huggingface.co/Qwen/Qwen3.5-9B/blob/c202236235762e1c871ad0ccb60c8ee5ba337b9a/config.json)
8 full-attention и 24 linear-attention слоя. У full — 4 KV-головы
размерности 256. [MTP добавляет один full-слой](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/model_executor/models/qwen3_5_mtp.py#L111);
TP2 оставляет две головы на GPU.

```text
KV на GPU = 2 × 1 × 9 × (4 / 2) × 256 × S × N байт
```

`S` — вся история, `N` — независимые истории.
`2 × 1 × 9 × 2 × 256 = 9216 байт`, то есть 9 KiB на токен.
Состояние linear attention, веса, буферы и округление добавляются отдельно.
Конфигурация модели допускает 262144 позиции, но рецепт здесь — 128K.

При Token клиенту нужен `OPENAI_API_KEY` из Secret; при его отсутствии
используется подготовленный CPU-клиент с авторизацией.
Проверка доступа не отключается. Если контейнеров несколько, runtime
указывается через `-c`.

```bash
export INPUT_TOKENS=57344 RUN_NAME=qwen-64k
mkdir -p results/rtx
set -o pipefail
kubectl --context "$GPU_CONTEXT" -n "$NS" exec rtx-qwen35-tp2-0 -- \
  vllm bench serve --backend vllm \
    --base-url "http://rtx-qwen35-tp2.$NS.svc.cluster.local" \
    --endpoint /v1/completions --model rtx-qwen35-9b \
    --tokenizer /data/modelcache/models/rtx-qwen35-9b \
    --dataset-name random --seed 73 \
    --random-input-len "$INPUT_TOKENS" --random-output-len 512 --random-range-ratio 0 \
    --num-prompts 1 --max-concurrency 1 --ignore-eos --temperature 0 \
    --ready-check-timeout-sec 0 --num-warmups 0 \
    --save-result --result-dir /dev --result-filename stdout \
  | tee "results/rtx/$RUN_NAME.txt"
```

Длинные серии: 57344 + 512, затем `INPUT_TOKENS=122880 RUN_NAME=qwen-128k`.
Ожидаются completed=1, failed=0 и фактические заданные токены.

Восемь запросов: `INPUT_TOKENS=32768`, seed 107,
`--num-prompts 8 --max-concurrency 8`, `RUN_NAME=qwen-8-sessions`.
Критерии: completed=8, failed=0, 262144 входных и 4096 выходных токенов.
Для подтверждения одновременности нужны running/waiting, а не только число
успешных клиентов; также сохраняются preemptions и рестарты.

</details>

Финальная проверка через WebUI — полный длинный вход, законченный ответ,
сохранённая история и запись под личным VK. Использование RAM подтверждается
возвратом вытесненного префикса; работа MTP — предложенными и принятыми
токенами.

<a id="cleanup"></a>
### Остановка

Маршруты скрываются до завершения текущих запросов.
Ручные профили получают `replicaCount: 0`; заказы — `order.enabled: false`
и адресный Prune только нужных InferenceService по
[процедуре GitOps](docs/GITOPS.md#остановка).
**Namespace, Models, PVC, пользователи и чаты сохраняются.**

Для повторного A/B выключенный Tune возвращается к 4K и
`gpu-memory-utilization: 0.90`, WebUI — к 4K и ответу до 1024.
Запускается только Base; Cache и Tune остаются отдельными приложениями.

<a id="setup"></a>
### Подготовка и привязки площадки

[Подготовка RTX](docs/SETUP.md#rtx) задаёт контексты и каталоги частного Git.
Веса `rtx-gemma-e2b`, assistant и `rtx-qwen35-9b` доставлены;
RAM рассчитана на две Gemma. A30 подготовлена по [заказам](#a30-orders).
Base отвечает новому одобренному пользователю, её метрики собираются;
B, автоматическая Gemma и Qwen выключены.

NodeCache хранит веса; загрузку образа runtime он не заменяет.
Публичные профили по умолчанию выключены, секреты в Git не попадают.
