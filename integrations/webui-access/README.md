# Персональные ключи Bifrost для Open WebUI

Адаптер автоматически создаёт Bifrost Virtual Key для одобренного пользователя
Open WebUI и подставляет его в запросы к моделям. Ключ остаётся на сервере:
пользователю не нужно копировать его в настройки или выпускать API-ключ WebUI.

Модели, провайдеры, квоты и тарифы задаются в Helm values. Зависимости от Gemma,
названия мероприятия или фиксированного числа моделей в коде нет.
[Пример для двух Gemma](../../examples/webui-access.yaml) — отдельный overlay.

## Выдача и отзыв

1. Пользователь регистрируется с ролью `pending`; доступа к чату ещё нет.
2. Администратор меняет роль на `user`. Сверка создаёт персональный VK,
   проверяет права и тариф, затем разрешает использовать его через адаптер.
   В native-режиме Bifrost сразу создаёт активный ключ с владельцем;
   в прежнем core-режиме ключ создаётся выключенным и затем активируется.
3. Open WebUI передаёт подписанный `X-OpenWebUI-User-Jwt`. Адаптер проверяет
   подпись, срок действия и актуальную роль через API WebUI, затем отправляет
   запрос в Bifrost с личным VK.
4. Возврат в `pending` или удаление аккаунта запрещает новые запросы.
   Сверка пытается выключить VK через core API; уже начатый ответ может завершиться.
   Если этот API не видит новый native VK, отзыв на самом шлюзе не подтверждён:
   ошибка отражается в логах. Запрет в адаптере продолжает действовать.

Сверка выполняется раз в 15 секунд после окончания предыдущей; интервал
настраивается. Первый запрос также проверяет наличие ключа. Обрабатываются все
аккаунты с ролью `user` или `admin`, кроме указанной служебной учётки.
Групповые политики и разные квоты по ролям здесь не реализованы.

Идентификатор связи — неизменяемый UUID WebUI, а не email или имя.
Имя нового VK: `<managed_by>:<user-id>`; описание содержит имя пользователя.
Повторный вход и рестарт используют тот же VK и расход. Повторное одобрение
выключенного ключа требует доступного штатного API его активации.
Чужие ключи адаптер не принимает, не удаляет и не перенастраивает.

При задержке активации на реплике Bifrost адаптер повторяет только точный
отказ `Virtual key is inactive`: не более четырёх повторов с паузами
250, 500, 1000 и 2000 мс. Перед повтором он заново проверяет роль пользователя,
активность VK и его политику через API управления. Ключ при этом не активируется
повторно. Отказы по бюджету, ошибки модели, сетевые сбои и начатый поток
не повторяются автоматически.

Если POST завершился ошибкой, объект мог сохраниться. Адаптер ищет его через GET;
при неопределённом результате отказывает, не повторяя POST в текущем процессе.
Уникальное имя VK в целевом Bifrost дополнительно защищает от дубликата после
рестарта. В native-режиме восстановление использует список ключей владельца,
а не снимок видимости core API. Ни ошибка тарифа, ни повторный вход
не являются поводом выпускать ещё один ключ.

## Конфигурация

[Чарт](../../charts/webui-access/values.yaml) по умолчанию остановлен.
Минимальный `access-site.yaml` для одной модели:

```yaml
replicaCount: 0
existingSecret: webui-access
config:
  webui_url: http://open-webui:8080
  gateway_url: https://gateway.example.com
  service_user_id: REPLACE_WITH_WEBUI_SERVICE_USER_UUID
  managed_by: team-webui
  key_name_prefix: Team WebUI
  provisioning_mode: create
  chat_models:
    - vllm/assistant
  providers:
    - provider: vllm
      allowed_models: [assistant]
      key_ids: [REPLACE_WITH_BIFROST_PROVIDER_KEY_ID]
  budget_usd: 10
  budget_reset: 24h
  requests_per_minute: 10
  tokens_per_minute: 200000
  max_concurrent_total: 8
  max_concurrent_per_user: 3
  reconcile_interval_seconds: 15
  pricing: []
```

`chat_models` содержит внешние ID вида `provider/model`. В `providers`
перечисляются разрешённые модели и точные ID ключей провайдера из Bifrost.
Можно задать несколько провайдеров и любое непустое число моделей.
При маршрутизации через alias внесите в политику необходимые alias и конечные
имена моделей. Wildcard-доступ и все ключи провайдера не разрешаются.

Open WebUI может одновременно отправлять запрос чата и фоновые запросы
названия или продолжения диалога. Поэтому пример разрешает до трёх запросов
одного пользователя при общем пределе восемь. При пределе один фоновый запрос
может занять слот раньше чата: пользователь получит `concurrency limit reached`,
хотя прямой одиночный запрос к API модели проходит. Проверяйте отправку из UI
с включёнными фоновыми задачами. Это ограничение адаптера по UUID WebUI,
оно одинаково применяется к новым и существующим VK; не меняет RPM/TPM,
бюджет или накопленный расход Bifrost и не требует перевыпуска ключей.

В `chat_models` оставляйте только модели работающих backend-сервисов.
При переключении отдельно отключайте соответствующие сохранённые presets
в Open WebUI и меняйте модель по умолчанию. Удалять чаты, ключи и настройки
остановленных моделей для этого не нужно.

`managed_by` должен быть уникальным для установки и постоянным при обновлениях.
Его изменение создаёт другую область владения; это не способ ротации ключей.
`key_name_prefix` задаёт имена тарифных правил;
для новых ключей в режиме `create` используется стабильное имя выше.

В прежнем core-режиме, если management-учётка ограничена командой Bifrost (`team-data`), задайте
`config.team_id` — UUID этой команды. Новый VK создаётся сразу в ней, чтобы
служебная учётка могла его прочитать и активировать. Для существующих ключей
адаптер проверяет совпадение команды, но не переносит их и не расширяет права
management-учётки. Без `team_id` используется область доступа, настроенная в Bifrost.

### Native-выдача с владельцем

Включается только явной парой параметров, не автоматически:

```yaml
config:
  provisioning_mode: create
  issuer_user_id: REPLACE_WITH_BIFROST_OWNER_UUID
  issuer_user_access_profile_id: 7 # ID профиля у владельца, не родительского шаблона
```

`service_user_id` остаётся UUID служебного аккаунта **WebUI**;
`issuer_user_id` — владелец management-credential в **Bifrost**.
До включения проверьте `GET /api/users/{owner}/access-profiles`: профиль должен
быть активен, принадлежать владельцу и точно соответствовать values по моделям,
provider key IDs, бюджету и rate limits, без MCP grants и wildcard.
Не меняйте и не распространяйте политику старого общего профиля ради миграции.

Адаптер выпускает ключ через
`POST /api/users/{owner}/access-profiles/{userProfileID}/virtual-keys`,
сохраняет полный успешный ответ в памяти до проверки тарифа и восстанавливает
ключ через `GET /api/users/{owner}/virtual-keys`. Права и лимиты наследуются
из профиля; адаптер не изменяет профиль, пользователей Bifrost или роли.
Сразу после `201` не требуется management GET или активация через core API.
Если owner-list временно недоступен, успешный ответ POST можно использовать
для восстановления не более двух минут: актуальная роль, профиль, квоты и тариф
всё равно проверяются перед чатом.
На рестарте источником восстановления остаётся owner-list, не локальный диск.

Owner API может возвращать `budgets: []` и `rate_limit: null` у существующих
ключей: их лимиты хранятся в VK-scoped model configs и не подставляются в этот
DTO. Поэтому адаптер отдельно читает
`GET /api/governance/virtual-keys/quota` с **тем же личным VK** в `x-bf-vk`,
без management-credential. Имя и состояние должны совпасть с owner-ответом;
бюджет, окна и rate limits — с values. Provider/model allowlists сверяются
по обоим ответам; provider key IDs и MCP — по owner API. Дополнительные
provider/model лимиты, `allow_all_keys: true`, несовпадение или недоступность
quota API закрывают доступ. Лимиты профиля не подставляются вместо доказательства
политики конкретного VK. Если owner API прислал непустые лимиты, они тоже
обязаны соответствовать values. Эти проверки ничего не перезаписывают
и не сбрасывают расход.

Relational native API не сохраняет team/customer-привязку профиля. Поэтому
отсутствие этих полей у native-профиля и VK допустимо: проверяются владелец,
точный активный профиль и вся политика моделей, ключей провайдера и лимитов.
`team_id` здесь не обеспечивает группировку новых ключей по команде.
Персональный учёт остаётся по ID VK и UUID WebUI в запросе.
Непустая команда профиля или ключа должна совпадать с `config.team_id`;
непустой customer отвергается, так как адаптер не поддерживает customer scope.
В core-режиме обязательное совпадение заданного `team_id` сохраняется.
Существующие ключи с правильным marker и политикой сохраняются независимо
от того, через какой профиль их создали; имя, ID, значение и расход не меняются.
Перед переключением проверьте, что owner-list содержит все используемые
личные ключи. Чужие и неоднозначные записи не принимаются.
Native owner DTO не показывает внутренний core-флаг `allow_all_keys`;
его явное значение `false` проверяется в ответе quota API. Поле `keys` там
может быть пустым, поэтому точные provider key IDs проверяются по owner-list.

Native `DELETE` дочернего ключа лишь отвязывает владельца и **не используется
как отзыв доступа**. Пока выключение через core API не подтверждено,
нельзя обещать отзыв самого VK. Ключ не выдаётся клиенту: каждый запрос через
адаптер заново проверяет актуальную роль WebUI. Отзыв одного ключа с ошибкой
не блокирует выдачу другим одобренным пользователям.

Пустой `pricing` оставляет тарифы шлюза. Для персонального тарифа добавьте правило
с точным именем модели:

```yaml
config:
  pricing:
    - model: assistant
      input_usd_per_million_tokens: 10
      output_usd_per_million_tokens: 20
```

Это учёт стоимости, не платёжная система. Квоты и расход применяются в Bifrost;
локальное ограничение параллельных запросов защищает адаптер.
Служебные запросы WebUI, например заголовки чатов, используют тот же VK.

При несовпадении политики существующего VK с values адаптер отказывает.
Он не переписывает бюджет и не обнуляет расход. Меняйте действующие политики
через API управления Bifrost с сохранением usage, затем согласуйте values.

## Сборка и развёртывание

```bash
export ACCESS_IMAGE=registry.example.com/integrations/webui-access:0.3.0
docker build --platform linux/amd64 \
  -t "$ACCESS_IMAGE" integrations/webui-access/bridge
docker push "$ACCESS_IMAGE"

helm lint charts/webui-access --strict
helm template webui-access charts/webui-access \
  --namespace workshop-ui -f access-site.yaml
```

Получите digest опубликованного образа и задайте `image: registry/...@sha256:...`.
Перед запуском замените placeholders, настройте `webuiSelector` и создайте Secret
вне Git. Чарт размещается в namespace WebUI; сетевые правила по умолчанию
рассчитаны на WebUI:8080, DNS и HTTPS-шлюз:443. Для своего окружения проверьте порты.

| Поле Secret | Назначение |
| --- | --- |
| `WEBUI_ADMIN_API_KEY` | Чтение списка и актуальной роли пользователей WebUI |
| `BIFROST_MANAGEMENT_KEY` | Создание, чтение и изменение собственных VK; при `pricing` также тарифов |
| `WEBUI_TRANSPORT_KEY` | Авторизация подключения WebUI к адаптеру |
| `FORWARD_USER_INFO_HEADER_JWT_SECRET` | Проверка подписанной личности WebUI |

Используйте отдельные служебные учётки. Все четыре значения должны быть не короче
32 символов; транспортный и подписывающий секреты — разные случайные значения.
Храните их в менеджере секретов или защищённых файлах для
`kubectl create secret generic --from-file`, не в values и не в истории shell.
Для внутреннего CA используйте `caConfigMap`; проверку TLS не отключайте.

После подготовки измените `replicaCount` на 1 и доставьте чарт и values через
[Git/Argo CD](../../docs/GITOPS.md). Чарт не создаёт Secret, Namespace и учётные записи.

## Подключение WebUI

В используемой версии WebUI должна поддерживаться передача подписанного JWT:

```yaml
ENABLE_FORWARD_USER_INFO_HEADERS: "True"
FORWARD_USER_INFO_HEADER_JWT_EXPIRES_SECONDS: "60"
# FORWARD_USER_INFO_HEADER_JWT_SECRET — ссылка на тот же Secret.
```

Сохраните существующие Secret-ссылки WebUI при изменении env: Helm заменяет списки
целиком. Добавьте OpenAI-подключение к `http://webui-access:8080/v1` с
`WEBUI_TRANSPORT_KEY`. Разрешите нужные модели группе пользователей в WebUI.
Адаптер не управляет модельными ACL, регистрацией и базами знаний.

Участники не получают MCP через этот путь: непустые tools/functions, автоматический
выбор инструмента и MCP-поля отклоняются. Пустые массивы и `null` для
`tools/functions`, а также `"none"` и `null` для `tool_choice/function_call`
удаляются как отсутствие запроса на инструменты. Остальные значения запрещены.
VK создаются без MCP grants; в Bifrost должны оставаться включены mandatory VK
и enforce-auth, чтобы глобальный MCP fallback не расширял доступ.
OIDC и административный MCP оставьте
в отдельном подключении с собственными OAuth/RBAC-правами.

### Настройки моделей для участников

В редакторе каждой модели, подключённой через адаптер, задайте:

| Раздел модели в WebUI | Значение |
| --- | --- |
| Advanced Params → Function Calling | `Legacy` |
| Capabilities → Builtin Tools | Выключено |
| File Context, File Upload | Включено для работы с документами |
| Web Search, Image Generation, Code Interpreter, Terminal, Memory | Выключено |

Настройки применяются только к моделям участников. Административные модели
с MCP остаются на своём подключении; их Function Calling менять не нужно.
Режим Legacy передаёт найденный RAG-контекст в сообщениях, без вызова инструментов
моделью. Само распознавание голоса настраивается отдельным подключением Whisper.

В актуальном WebUI режим Native может добавлять встроенные инструменты даже
к обычному сообщению из браузера. Для этого достаточно `session_id`; прямой
API-запрос без него может успешно пройти, хотя чат в UI получает
`request capability not allowed`. Это отказ адаптера до обращения к Bifrost,
а не исчерпание бюджета. Не устраняйте его выдачей MCP-прав участникам.
Поведение описано в [документации WebUI](https://docs.openwebui.com/reference/server-side-tool-calling/).

## Проверка

С тестовым аккаунтом проверьте `pending → user → pending → user`:
до одобрения — отказ, после — ответ, после отзыва — отказ; повторное одобрение
не меняет ID VK и расход. Проверьте два разных аккаунта, SSE, бюджет и лимиты.
В логах Bifrost выбирайте **«Виртуальные ключи»**, а не «Ключи провайдера».
На HA-шлюзе проверьте доступ и стоимость через каждую реплику.

Отдельно отправьте обычное сообщение **из браузера**, затем проверьте потоковый
ответ и запись с ID личного VK в Bifrost. Для API-проверки этой ветки добавляйте
непустой `session_id`, не передавайте `tools: []` и не задавайте Function Calling
в самом запросе: иначе тест обойдёт настройки, которыми пользуется UI.
Стоимость контрольного ответа должна равняться
`input_tokens × input_price / 1 000 000 + output_tokens × output_price / 1 000 000`.
Ошибку недоступного backend проверяйте отдельно от отказа по правам или бюджету.

```bash
(cd integrations/webui-access/bridge && go vet ./... && go test -race ./...)
python3 -m unittest discover -s tests -p 'test_webui_access_chart.py' -v
```

Тесты проверяют контракт API на локальных HTTP-серверах, без обращения к кластеру.
Core-совместимость использует `/api/governance/virtual-keys`;
native-выдача — owner-linked POST и owner-list, описанные выше. Native DTO
провайдера использует `provider_name`, `all_models_allowed` и `key_ids`,
а не core `keys[].key_id`. Тесты моделируют успешный native POST при постоянно
недоступном core GET, перезапуск, неоднозначный POST и отказ тарифа. Отдельные
owner/quota fixtures воспроизводят пустые legacy-лимиты, проверку фактических
квот и отказ при их недоступности или изменении. Тарифы —
`/api/governance/pricing-overrides`. Совместимость другого релиза проверяется
перед переключением рабочего подключения.

## Обновление с 0.1

Сохраните прежние `name`, `existingSecret`, `managed_by` и `key_name_prefix`.
Для старой установки это могло быть `hardfest-webui-access`,
`hardfest-webui-access`, `hardfest-webui-access` и `HardFest` соответственно.
Описание без имени пользователя, заканчивающееся на `user-id=<UUID>`, распознаётся.

Перенесите `allowed_models` и `provider_key_ids` внутрь `providers[]`;
`price_models` и общие цены — в `pricing[]`. Старые поля отвергаются схемой.
Сначала проверьте рендер и доступ management-ключа к уже выданным VK.

Историческое значение `provisioning_mode: reserve` распознаётся только для
обратной совместимости; с native issuer оно отвергается. Новые установки
используют `create`, резервный пул не нужен и автоматически не подключается.

## Ограничения

Одна реплика адаптера; это не HA-сервис. `/healthz` проверяет только процесс,
ошибки сверки нужно отслеживать в логах. Поддерживаются чат и SSE, не Responses API,
Whisper, embeddings или reranking. Их отдельные подключения и учёт не меняются.
RAG-контекст в сообщении учитывается как входные токены чата.
