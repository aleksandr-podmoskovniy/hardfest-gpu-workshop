# Личный ключ участника в Bifrost

После одобрения аккаунта в Open WebUI участник получает отдельный Virtual Key
Bifrost. Обе Gemma используют этот ключ. Пользователь ничего не копирует
в настройки и не получает management-ключ шлюза.

Адаптер разворачивается рядом с Open WebUI. Он проверяет подписанный
`X-OpenWebUI-User-Jwt`, запрашивает актуальную роль пользователя в WebUI
и подставляет его VK при обращении к Bifrost в другом кластере.
Обычные заголовки с именем или email не являются доказательством личности.

| Политика | Значение |
| --- | --- |
| Модели чата | Gemma A — Base, Gemma B — Tune |
| Вход / выход | $10 / $20 за миллион токенов |
| Бюджет | $500 за 24 часа |
| Частота | 10 запросов и 200 000 токенов в минуту |
| Одновременные запросы | 1 на пользователя, 8 на адаптер |
| MCP, другие модели, API управления | Недоступны через это подключение |

Это демонстрационный учёт, без списания денег. В стоимость входят также
служебные запросы WebUI, например генерация заголовка чата. Они расходуют
тот же бюджет и лимит запросов.

## Как выдаются ключи

Сверка одобренных аккаунтов запускается каждые 15 секунд после завершения
предыдущей сверки. Первый запрос также проверяет выдачу. Связь с VK хранится
в его описании: `managed-by=hardfest-webui-access; user-id=<UUID>`.
Повторный вход, переименование и рестарт не выпускают новый ключ
и не сбрасывают накопленный расход.

В проверенной `d8-edition 2.0.38` сервисный management-ключ имеет проблему
видимости только что созданных объектов. Поэтому для этого стенда используется
**предварительно созданный резерв отключённых VK**. Адаптер назначает один
резервный ключ пользователю и активирует после проверки политики и тарифа.
На стенде подготовлено 32 ключа. Это не безлимитный выпуск: исчерпание резерва
даёт отказ, а не переход на общий ключ.

Активация распространяется между репликами Bifrost не мгновенно. Если первый
запрос сразу после одобрения получил 403, дождитесь очередной сверки и повторите.
Постоянный отказ требует проверки ключа и реплик, а не выдачи общего VK.

Администратор готовит резерв через штатное API или интерфейс Bifrost:

- отдельный сервисный владелец с `own-data`, без доступа к чужим VK;
- отключённые ключи с описанием `managed-by=hardfest-webui-access; reserve`;
- только две нужные записи ключей провайдера `vllm`, `allow_all_keys=false`;
- разрешённые модели, бюджет и лимиты из values, пустой список MCP;
- привязка ключей к сервисному владельцу без сброса usage;
- проверка, что каждый ключ читается management-ключом этого владельца.

Если создание вернуло 500, сначала проверьте наличие объекта администратором:
запись могла сохраниться. Не повторяйте POST вслепую. Подробности проверки
ограничений версии находятся в [журнале интеграции](tasks.md).

## Сборка и GitOps

Исходники адаптера — небольшой Go-сервис без внешних зависимостей.
Образ собирается из отдельного каталога, без kubeconfig и операторских файлов:

```bash
export ACCESS_IMAGE=registry.example.com/workshop/webui-access:0.1.0
docker build --platform linux/amd64 \
  -t "$ACCESS_IMAGE" integrations/webui-access/bridge
docker push "$ACCESS_IMAGE"

helm lint charts/webui-access --strict
helm template hardfest-webui-access charts/webui-access \
  --namespace workshop-ui -f access-site.yaml
```

В частном `access-site.yaml` задайте закреплённый digest образа, адрес WebUI,
HTTPS-адрес Bifrost, UUID служебной учётки WebUI и ID двух ключей провайдера.
Для внутреннего CA укажите `caConfigMap`; проверку TLS не отключайте.
По умолчанию `replicaCount: 0`. После подготовки Secret и резерва установите
`replicaCount: 1`, закоммитьте values в GitOps-репозиторий и синхронизируйте
Application Argo CD. Namespace должен совпадать с namespace WebUI.

Secret, указанный в `existingSecret`, создаётся вне Git и содержит:

| Поле | Назначение |
| --- | --- |
| `WEBUI_ADMIN_API_KEY` | Ключ отдельной служебной учётки для чтения пользователей WebUI |
| `BIFROST_MANAGEMENT_KEY` | Управление только подготовленными VK и их тарифами |
| `WEBUI_TRANSPORT_KEY` | Авторизация подключения WebUI к адаптеру |
| `FORWARD_USER_INFO_HEADER_JWT_SECRET` | Проверка подписи пользователя |

Последние два значения должны быть разными случайными секретами, не короче
32 символов. Их можно сгенерировать командой `openssl rand -hex 32`
непосредственно в защищённый файл и загрузить Secret через `kubectl create
secret generic --from-file`, либо использовать менеджер секретов.
Не помещайте значения в values, команды с `--from-literal` или историю shell.

## Подключение Open WebUI

В WebUI включите передачу подписанной личности:

```yaml
ENABLE_FORWARD_USER_INFO_HEADERS: "True"
FORWARD_USER_INFO_HEADER_JWT_EXPIRES_SECONDS: "60"
# FORWARD_USER_INFO_HEADER_JWT_SECRET берётся из Secret, как и у адаптера.
```

При добавлении `extraEnvFrom` сохраните **все прежние ссылки на Secret**:
Helm заменяет список целиком, а не дополняет его. В частности, нельзя потерять
`DATABASE_URL`, `WEBUI_SECRET_KEY` и OAuth-настройки существующего WebUI.

В административных настройках OpenAI-подключений замените только подключение
участников:

- URL: `http://hardfest-webui-access:8080/v1`;
- ключ: `WEBUI_TRANSPORT_KEY` из Secret;
- модели: `vllm/hardfest-gemma-a` и `vllm/hardfest-gemma-b`.

Отдельное OIDC-подключение администратора, его MCP и OAuth credentials
не изменяются. Личный VK хранится на серверной стороне; раздел API-ключей
пользователя в Open WebUI для него не используется.

## Проверка учёта

В Bifrost откройте логи и фильтр **«Виртуальные ключи»**, выберите
`HardFest: <имя> (<UUID>)`. Фильтр «Ключи провайдера» выбирает маршрут A/B,
а не пользователя. Отправьте короткий запрос в каждую Gemma и проверьте
VK, входные и выходные токены, стоимость и расход бюджета.

Например, 21 входной и 5 выходных токенов стоят
`21 × 10 / 1 000 000 + 5 × 20 / 1 000 000 = $0,00031`.

Для HA проверка обязательна на каждой реплике шлюза. В проверенной версии
новый pricing override не всегда попадал в память остальных реплик.
Одинаковый тариф закреплён также за двумя ключами провайдера Gemma
и загружен через штатное API на каждой реплике. Он служит общим тарифом
этих двух маршрутов; бюджеты и расход остаются персональными. Перед сменой
тарифа повторите проверку всех реплик, а не только успешного POST.

Затем переведите отдельного тестового пользователя в `pending`: следующий
запрос должен получить отказ, а сверка — выключить его VK. Верните `user`
и убедитесь, что ID ключа и накопленный расход не изменились.
Не проводите проверку отзыва на реальных участниках.

## Границы этой реализации

Адаптер имеет одну реплику и не является HA-компонентом. Несколько реплик
потребуют распределённой блокировки назначения резервных ключей.
`/healthz` проверяет HTTP-процесс, а не готовность всех внешних API;
ошибки сверки нужно контролировать в логах.

Этот путь обслуживает чат и SSE. Whisper, embeddings и reranking сохраняют
существующие отдельные подключения; их персональный биллинг этим адаптером
не реализован. RAG-контекст, включённый в запрос к Gemma, учитывается как
входные токены пользователя. Начатый ответ может завершиться после отзыва
аккаунта; новые запросы проверяют актуальную роль.
